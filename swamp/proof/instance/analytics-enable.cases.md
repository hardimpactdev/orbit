# instance:analytics:enable verification cases

`instance:analytics:enable` publishes the tracking hosts of an Instance, following [its chart](../../../docs/cli/instance/analytics-enable.mmd). The proof runs the built CLI against a fresh nested topology with the analytics role and a real Plausible, a Node-scoped Instance, a Cluster-scoped private Instance with a Router, a Cluster-scoped public Instance with an Ingress, and an Instance without a domain. It compares the output with the Gateway records, the Caddy sites, the private DNS records and Plausible's site list. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Default host | Enable the Node-scoped Instance with the Instance ID only. | The tracking Route `analytics.<domain>` is active and the Plausible site exists with the Instance's domain. Over TLS the host serves `/js/script.js` and accepts `/api/event`, and every other path, the dashboard included, answers 404. The output shows the DNS record to create and the script tag. |
| Serving Node | Enable a Node-scoped Instance, a Cluster-scoped private Instance and a Cluster-scoped public Instance. | The Instance's Node, the Router, and the Router behind the Ingress serve the host. Only the Router case requests and signs a certificate (`Request the certificate`, `Sign the CSR`), and the private key never leaves the Node. |
| Private DNS | Enable a host outside the TLD and one inside it. | The outside host gets a private DNS record. The inside host gets none. |
| Repeat | Run the same command again. | The task succeeds. There is still one Plausible site and one tracking Route per host, and the sites are unchanged. |
| Exact host set | Enable with `--host=a.example.com`, then with `--host=b.example.com`, then with both. Then name eleven hosts. | `a` is removed (its Caddy site, certificate and Route) when only `b` is named, and `b` is published. Naming both keeps both. The eleventh host gives `validation.failed` and nothing changes. |
| Invalid host | A host with a scheme, with a path, an IP address, without a dot, one under the private `orbit` names, and a host named twice. Then an Instance whose domain is under the private `orbit` names, with no `--host`. | `validation.failed` for each named host, with no task and nothing changed. `analytics.host_invalid` for the default host of the last Instance. |
| Host taken | Name a host that another Route already uses. | `analytics.host_taken`, with no task and nothing changed. |
| No role or domain | Enable with no active analytics role, and for an Instance without a domain. | `analytics.role_missing` and `analytics.domain_required`, with no task and nothing changed. |
| Credentials missing | Remove the protected Plausible credentials, then enable. | `analytics.credentials_missing`, with no task and no tracking Route left `pending`. |
| Competing change | Enable while another analytics or Route change runs for the Instance. | `operation.target_busy`. Nothing changes. |
| Placement change | Move the Instance to another Cluster between admission and the end of the run. | `analytics.tracking_changed`, and a rerun uses the new placement. Fails today: the check runs after the run succeeds, so Caddy and DNS are already changed. |
| Failure after a partial change | Make Plausible unreachable, the certificate request fail, a certificate signature fail, Caddy refuse the config, the probe fail and private DNS fail, one at a time, and a failure outside any named step. | `analytics.site_failed`, `app-dev.certificate_request_failed`, `app-dev.certificate_sign_failed`, `route.publish_failed`, `route.probe_failed`, `private_dns.publication_failed` and `analytics.enable_failed`. The tracking Routes stay unpublished, and `operation:show` shows the failed step and its error code. Steps that finished stay, and a Plausible site already created stays. After the fix the same command succeeds and reuses the site. Fails today: the Routes stay `pending` with no failed step or error code. |
| Output forms | A wide and a narrow terminal, output piped to a file, and `--json`. | A detail, a host table, the DNS records and the script tag at the wide width, and labeled records at the narrow one. The piped output has no animation or escape codes. With `--json`, stdout holds the tracking record with `instance_id`, `enabled`, `domain`, `dashboard_url`, `hosts`, `snippet` and `request_id`. Fails today: with `--json` the command prints the task result and not the tracking record, and the detail shows the Instance as `#<id>`. |
| Missing input | In a terminal, run the command with no argument and cancel the list. Then run it noninteractively and with `--json`. Then use `0`, `-1` after `--`, `abc` and a name. | The terminal lists Instances, and cancel ends with `input.cancelled` and no request. The other calls give `instance.id_invalid`, with no request. Fails today: the Instance is a required argument, so a call without it is refused by the parser, and `-1` without `--` is read as an option. |
| Unknown and access | An Instance that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing changes. |
| Activity and output | After a successful run and a failed one, read the task, Activity, the run output and every command output. | No Plausible password, session cookie or token appears. The task holds only the vault key name. |
