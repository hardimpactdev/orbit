---

```bash
orbit instance:auto-deploy:enable <instance> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `instance` | yes | Numeric Instance ID of a production Instance or a ready development container default. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--json` | off | Print the Instance as JSON. |

```bash
orbit instance:auto-deploy:enable 71
```

In a terminal, an omitted Instance is chosen from an interactive list. A noninteractive or `--json` call without it is refused with `instance.id_invalid` and sends no request, and so is a value that is not a positive integer.

The command turns automatic deployment on. For production it also resumes a pause caused by manual deployment or rollback. It deploys nothing now and changes nothing on a Node. The branch is checked each minute. Production can select the newest green ancestor; development deploys only the current default-branch head once green. Both read the commit's GitHub Actions runs named by the Project's `merge_check`, such as `Required checks`. A red or running check never permits deployment. Without a configured check, both permit a moved head without checking.

The deployment uses the same steps as [`instance:deploy`](/cli/instance/deploy). Automatic deployment keeps acting after the command returns, so it is an `enable` and `disable` pair, not an `instance:update` option. See [Automatic deployments](/reference/deployments#automatic-deployments) for retry rules and status.

Automatic deployment needs a production Instance or an active development container default with a seed snapshot. Before a production Instance's first succeeded deployment the check reports `not_deployed`. A new container default starts with automatic deployment on; use [`instance:auto-deploy:disable`](/cli/instance/auto-deploy-disable) to turn it off for that Instance. Enabling sets the same `auto_deploy` flag back on. Checkout Instances refuse with `instance.auto_deploy_container_default_required`: they are user working trees, never automatic deployment targets.

When the Project has a `merge_check`, the GitHub App must be able to read it. Without one, enabling succeeds and warns that every commit deploys without a check. Enabling an Instance that already has automatic deployment on succeeds and moves the resume point to the newest deployment, so it also clears a pause.

For production, a manual `instance:deploy` or `instance:rollback` pauses automatic deployment again, whether it succeeds or fails, and a rollback blocks the commit it moved away from. Enabling resumes from the commit that is live. The command starts no task.

The command prints a detail titled `Instance: <name>` with ID and the `Auto deploy` fields (`on, without a merge check` or `on, after <merge check> passes`, and the state, pause and error lines when there are any), the warning when there is one, and the request ID. With `--json`, stdout holds the Instance with `auto_deploy`. Use [`instance:show`](/cli/instance/show) to see the last automatic deployment.

## Errors

| Code | Meaning |
| --- | --- |
| `instance.id_invalid` | The Instance is missing in a call that cannot prompt, or is not a positive integer. |
| `input.cancelled` | You cancelled the Instance list. |
| `deployment_config.unavailable` | Production deployment configuration is unavailable. |
| `instance.auto_deploy_container_default_required` | Development automatic deployment requires an active container default with a seed snapshot, never a checkout working tree. |
| `instance.auto_deploy_role_inactive` | The development Node or its app-dev role is inactive. |
| `instance.auto_deploy_gate_unreadable` | The Project has a `merge_check` that the Gateway GitHub App cannot read: the Project reads through the GitHub CLI or is not on `github.com`. |
| `http.404` | The Instance is unknown. |
| `node_access.required` | The caller has no access grant to the Instance's Node. |
