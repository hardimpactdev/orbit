title: "orbit task:cancel"
sidebarTitle: "task:cancel"
description: "Cancel the selected task or subtask. The Gateway removes the task's workspace and task VM when it has them and marks the task `cancelled`. Subtasks, comments, and agent thread records stay as history. Cancellation does not stop the external agent conversation."
---

```bash
orbit task:cancel [task] [--yes] [--idempotency-key=KEY] [--json]
```

| Option | Meaning |
| --- | --- |
| `--yes` | Confirm without a prompt. Required for `--json` and `-n` calls. |
| `--idempotency-key=KEY` | Reuse a key to retry this operation start. |

In a terminal, the task list leaves out `settling`, `waiting_for_review`, and `completed` tasks. Before it asks, the CLI reads the task and names it and its Instance in the question. The question defaults to No. A `--json` or `-n` call without `--yes` fails with `input.confirmation_required`. Declining fails with `input.cancelled`. Neither changes the task. A `completed` task, or a `settling` task with a pull request, fails with `tasks.not_cancellable`; complete a settling task instead. Pass the task ID to cancel a `settling` task without a pull request. When the task holds a workspace or a task VM, origin's task branch must already reach its latest approved commit. Otherwise the call fails with `tasks.approved_work_unpublished`, names the commit, and changes nothing; run [`task:publish`](/cli/task/publish) first, which resumes a parked VM. A failed GitHub read fails the same way. The [tasks reference](/reference/tasks#cancel-a-stuck-task) describes the rule.

When the task has a running Operation, such as its task start, the cancel asks it to stop and answers `operation.target_busy` with its id if it is still running. Run the cancel again once that Operation has ended.

When the task owns a task copy (see [`task:start`](/cli/task/start#a-task-copy)), the cancel first reads the copy's workspace. It then admits `instance:destroy` of the copy with force and records the cancel at once. Its result names the destroy Operation as `destroy_operation_id` and holds the read as `workspace`. The read gives `unpushed` commits, `uncommitted`, `modified`, `untracked` and `stashes` counts and the `head`. A stopped or unreachable copy reads `state: unknown` with its `reason`. The cancel does not wait for that work: nothing is pushed first. The task becomes `cancelled` when the destroy succeeds. While the copy's create or an earlier destroy still runs, the cancel answers `operation.target_busy` with that Operation's id. When the destroy fails, the task keeps the copy and runs on; cancel again.

A child ID cancels only that child’s turn/check and keeps its parent workspace. The Gateway derives ownership from the selected row.
