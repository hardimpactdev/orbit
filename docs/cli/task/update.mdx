title: "orbit task:update"
sidebarTitle: "task:update"
---

Change a task's title, brief, status, copy turn agent, or pull request mode. For a task group or started subtask, title and brief change only while the group is in `backlog`. For a `todo` subtask in a `todo`, `running`, `reviewing`, `settling`, or `waiting_for_review` group, you can still update its title, brief, and non-empty deliverables and reorder it within the remaining `todo` tail.

The status moves between `backlog` and `todo`, leaving a parent ready for `task:start`. Groups also move among `running`, `reviewing`, `settling`, and `waiting_for_review`, without running work. In a task copy, `--status=running` reopens the last completed subtask while the group is open ([reopen the last subtask](/reference/tasks#reopen-the-last-subtask), [external status rules](/reference/tasks#tasks-and-subtasks)).

```bash
orbit task:update [task] [--title=TEXT] [--brief=TEXT] [--status=STATUS] [--preview | --no-preview] [--position=N] [--deliverables=FILE] [--reason=TEXT] [--work-status=STATUS] [--implementer-provider=NAME] [--implementer-model=MODEL] [--implementer-effort=LEVEL] [--reviewer-provider=NAME] [--reviewer-model=MODEL] [--reviewer-effort=LEVEL] [--clear-implementer-agent] [--clear-reviewer-agent] [--pr-mode=MODE] [--json]
```

| Option | Meaning |
| --- | --- |
| `--title=TEXT` | New title. |
| `--brief=TEXT` | New brief. |
| `--status=STATUS` | `backlog` or `todo`; an external group also accepts its current status or an allowed active status move. |
| `--preview` | Keep the sandbox running during review. It can change while the task is in `backlog`, waiting, or active. |
| `--no-preview` | Let the sandbox park during review. Do not combine it with `--preview`. |
| `--position=N` | A subtask's new position, starting at 1. |
| `--deliverables=FILE` | A JSON file whose list replaces the deliverables of a subtask, or of a [task with no subtask](/reference/tasks#a-task-with-no-subtask). |
| `--work-status=STATUS` | The status of the work of a task with no subtask, by the moves of a subtask's status: `todo`, `reserved`, `running`, `reviewing`, `completed`, `failed` or `cancelled`. `completed` approves the work; `running` reopens it. `--status` stays the task's own. Send it alone. Another value returns `task.work_status_invalid` and sends nothing. |
| `--reason=TEXT` | Why a [correction after a failed check](/reference/tasks#correct-the-deliverables-of-a-started-subtask) replaces a started subtask's deliverables in a task copy, 1 to 500 characters. Only that correction takes it, and it needs it. |
| `--implementer-provider=NAME` | The implementer's provider in a [task copy](/reference/tasks#copy-turn-agents): `claude`, `codex` or `antigravity`. Antigravity needs a copy on the Conn Server. When the update sets any of a role's three values, the Gateway [checks that whole role](/reference/tasks#copy-turn-agents) as it resolves from the task, the Project and the Gateway, and refuses one whose provider cannot honour its model and effort. |
| `--implementer-model=MODEL` | The implementer's model in a task copy, such as `claude-opus-5-5`. Antigravity takes its own [models](/reference/tasks#copy-turn-agents) only, such as `gemini-4-neon`: set the model with the provider. |
| `--implementer-effort=LEVEL` | The implementer's effort in a task copy: `low`, `medium`, `high`, `xhigh` or `max`. Codex adds `ultra`. Each Antigravity model takes [its own efforts](/reference/tasks#copy-turn-agents). |
| `--reviewer-provider=NAME` | The reviewer's provider in a task copy. |
| `--reviewer-model=MODEL` | The reviewer's model in a task copy. |
| `--reviewer-effort=LEVEL` | The reviewer's effort in a task copy. |
| `--clear-implementer-agent` | Clear the implementer's three values, so the Project's default, then the Gateway's, apply. Do not combine it with an implementer value. |
| `--clear-reviewer-agent` | The same for the reviewer. |
| `--pr-mode=MODE` | `review_before_pr` or `pr_when_done`: what Orbit does once the work is done. It changes only until the group has a pull request. See [Task group modes](/reference/tasks#task-group-modes). |

```bash
orbit task:update 13 --status=todo
orbit task:update 13 --reviewer-model=claude-sonnet-5-5 --clear-implementer-agent
orbit task:update 5354 --deliverables=deliverables.json --reason="The tools tests need discover -s tools."
```

In a task copy, the current subtask's deliverables change once after each failed handoff check, with `--reason`. Task activity records the old list, the new list, the reason and the check. The next handoff check runs the new list.

A role's agent values change until the role has its first thread in the task copy; after that, its thread keeps the values it started with.

In a terminal, the task list includes active tasks for a status update. Title and brief selection still uses `backlog` and `todo`. Without a change option, the CLI prompts for a new title. A `--json` or `-n` call without a change option fails with `tasks.update_required`.

## Errors

| Error code | Meaning |
| --- | --- |
| `tasks.not_in_backlog` | A title, brief, or position change outside `backlog` for a group or a started subtask (deliverables changes on a started subtask return `tasks.deliverables_locked`). |
| `tasks.no_subtasks` | A move to `todo` for a task without subtasks or deliverables of its own. Add at least two subtasks with deliverables. Or give a task with no subtask its own `--deliverables`, as [a task that leaves backlog](/reference/tasks#tasks-and-subtasks) says. |
| `tasks.one_subtask` | A move to `todo` for a task with exactly one subtask, before its deliverables are checked. Add a second subtask, or fold the one into the task: destroy it and give the task its `--deliverables`, as [a task that leaves backlog](/reference/tasks#tasks-and-subtasks) says. |
| `tasks.subtask_deliverables_missing` | A move to `todo` while one of two or more subtasks has no deliverables, and then the error details name them, or for a task whose own deliverables are empty. |
| `task.pr_mode_invalid` | `--pr-mode` is not `review_before_pr` or `pr_when_done`. The API answers `validation.failed` on `pr_mode`. |
| `tasks.pr_mode_locked` | The group has a pull request, a publish of it runs, or it has ended. |
| `tasks.already_claimed` | The scheduler claimed the task before the status change. |
| `tasks.deliverables_locked` (409) | A `--deliverables` change of a subtask that has started, when no correction applies: before any check, after a passed newest check, a second correction before a new check, a subtask that is not current, or a group without a task copy. |
| `task.reason_invalid` | `--reason` is blank or longer than 500 characters. Nothing is sent. |
| `tasks.reason_unexpected` (422) | `--reason` on any update other than a correction after a failed check. |
| `tasks.status_move_refused` (422) | The status move is not allowed. A `completed` subtask reopens only when it is the last subtask of an open group with a task copy and every other subtask has ended. |
| `tasks.copy_turn_unended` | A move of a task copy's subtask to `completed`, or a reopen, while a turn of its group still runs. Repeat it once the turn has ended. |
| `tasks.handoff_required` (409) | A move of a gated group's subtask to `completed` while its latest review is not an accepted `approve` of its latest delivery ([The review gate](/reference/tasks#the-review-gate)). |
| `tasks.agent_settings_locked` (409) | An agent value of a role that already has a thread. `details.role` names the role. Nothing changes. |
| `task.agent_conflict` | A role's clear option together with one of its values. |
| `task.agent_invalid` | An agent option is empty. |
| `validation.failed` | A provider or effort the task copy does not offer, or a model that is no model name. Also a correction after a failed check without a reason, or a reason over 500 characters. |

The Task ID may select a parent or child. Children also accept `--position`, `--deliverables` and `--reason`; parents accept preview intent and `--pr-mode`. A [task with no subtask](/reference/tasks#a-task-with-no-subtask) also accepts `--deliverables` with `--reason`, or `--work-status`, each in an update of its own. Each level keeps its existing status rules. Updating a parent to Todo does not start work.
