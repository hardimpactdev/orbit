```bash
orbit node:role:list <node> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | See the [Node family selector rule](/cli/node) and [input modes](/reference/cli-ux#input-and-output-modes). |

| Option | Default | Meaning |
| --- | --- | --- |
| `--json` | off | Use the [standard machine-output mode](/reference/cli-ux#input-and-output-modes). |

```bash
orbit node:role:list 7
```

The list has one row per role assignment, sorted by role name, with the columns ID, ROLE, STATUS, FAILED STEP and ERROR CODE. A Node without roles says `No roles.`. The JSON result contains `assignments` and `request_id`; each assignment has `id`, `role`, `status`, `failed_step` and `error_code`. Unset failure fields are null.

A role's status is `provisioning`, `active`, `failed`, or `removing`. Failed assignments retain their failed step and error code; listing them still succeeds. For recovery, see [`node:role:add`](/cli/node/role-add) and [`node:role:remove`](/cli/node/role-remove).

## How it works

Orbit reads its recorded assignments without contacting the Node, so the command works while the Node is unreachable. It starts no Operation and changes no state, even if a role is in progress or failed. Repeating it reads the current records again; this is not a skipped action and has no skip reason code. A failed read leaves nothing to undo.

## Errors

| Code | Meaning |
| --- | --- |
| `node.id_invalid` | The supplied Node selector is not a positive integer. The CLI sends no role-list request. |
| `node_access.required` | The caller has no access grant to the Node. |
| `http.404` | The Node is unknown. |
