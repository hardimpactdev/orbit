Create a development Instance on a Node with the active `app-dev` role. A Node with the active `app-prod` role returns `instance.candidate_required`, including a repeat for an existing production Instance. Create a production Instance with [`instance:clone`](/cli/instance/clone).

```bash
orbit instance:create <project> <node> <name> [--idempotency-key=KEY] [options]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `project` | yes | Numeric Project ID. |
| `node` | yes | Numeric Node ID. |
| `name` | yes | Instance name. `default` is reserved for the Project's default development source. A name that equals the Project `default_branch`, such as `main`, creates the `default` Instance. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--root=PATH` | the Project root | Relative web-root override for this Instance. |
| `--domain=HOST` | generated | Explicit Route domain for the development source. Without it, Orbit generates a domain from the active Cluster TLD, then the Node TLD. A Project that serves no web pages takes no domain and returns `instance.route_unserved`. A domain that another Route owns, or a reserved name such as `gateway.orbit`, returns `route.domain_conflict`. |
| `--branch=BRANCH` | see [branch selection](/domains/applications#create-a-development-instance) | Explicit source branch. |
| `--database-server=SLUG` | none | Create the Instance's database on this [Database server](/reference/database-servers) before the setup steps run. Only for an Instance that this create makes; an Instance that finished setup returns `instance.database_server_existing`. See [database on a server](/domains/applications#database-on-a-server). Needs access to the Gateway too. |

Create runs these steps on the Node, in order:

1. Clone the repository and check out the branch. The Gateway mints a read token for this one repository, valid one hour.
2. Write `.env`. The Gateway renders it from the Project's env template with `APP_URL`, a new `APP_KEY`, and the database keys. The file has mode 0640 and group `orbit-env`, so the Node agent can report its key names.
3. When the Project's `default` Instance has a SQLite database under `DB`, copy it to the same path in the new checkout. The copy is the Instance's own `<project>-<instance>` connection, and `.env` already names it.
4. With `--database-server`, create the database owner, the database, and the test database. An owned MySQL or PostgreSQL database also gets `.env.testing`. Native create does not run this step yet: `--database-server` returns `operation.kind_unavailable` before a run starts.
5. Run the Project setup steps, such as `composer install`, `vp install`, and `php artisan migrate`.
6. Create and start the Processes from the Project's development Process definitions.
7. For a web-serving Project, create its Route the way [`route:create`](/cli/route/create) does, and probe the site over TLS. When this run starts every Process of the Instance, including those a failed earlier run started, it also marks the Instance awake, so the first request reaches the application instead of the wake page. A standalone `route:create` does not set the marker.

The run has 60 seconds, plus the setup step timeouts, 30 seconds for the Processes, 180 seconds for the Route, and 180 seconds for a database copy.

A task VM Node returns `instance.task_vm_node`: a task VM gets its workspace from [`tasks:provision`](/reference/tasks#provision-an-external-group).

Development placement and branch selection follow the requested name.

| Creation input | Managed placement | Selected branch |
| --- | --- | --- |
| `default` or the default branch name, without `--branch` | `<node-apps-root>/<project-slug>/default` | The Project `default_branch`. |
| Another name without `--branch` | `<node-apps-root>/<project-slug>/<name>` | The matching origin branch, otherwise the existing local branch, otherwise a new branch from the fetched `default_branch` commit. |
| Any name with `--branch` | The placement for the requested name | The requested origin branch, otherwise the existing local branch, otherwise a new branch from the fetched `default_branch` commit. It need not match the Instance name. |

```bash
orbit instance:create 4 7 default
orbit instance:create 4 7 feature-one --branch=release --domain=feature.example.test
orbit instance:create 4 7 t3-1a2b3c4d --branch=t3code/1a2b3c4d
```

When the name equals the Project default branch, Orbit creates the `default` Instance, and `--branch` keeps its meaning as the `branch_override`. The final Operation result carries `name_converted_from` with the requested name, or null when no conversion was needed. See [A default-branch name means default](/domains/applications#a-default-branch-name-means-default).

A requested origin branch keeps its existing selection behavior. Orbit does not reset an existing local branch to the default commit. A missing fetched `default_branch` when required returns `instance.branch_resolution_failed`, not a different fallback branch. An invalid Git branch name returns `validation.failed` before source changes.

A create that fails before activation removes its owned resources and Instance row without teardown. The response keeps the original error code. Once cleanup completes, a new create can select a different branch. If an interruption or incomplete cleanup leaves a pre-activation Instance, an identical retry resumes it; a retry that changes the root or `--branch` returns `instance.placement_conflict`. Incomplete cleanup reports `details.cleanup = "incomplete"` and a recovery command. An identical retry finishes a started cleanup first, without `--force`, and then creates the Instance. [`instance:destroy`](/cli/instance/destroy) accepts `reserved`, `checkout_prepared`, and `source_resolved` for [pre-activation removal](/reference/instance-removal#pre-activation-removal).

<Note>
The Instance and its Route become active only after every step succeeds. A successful create means every setup step succeeded; an empty list counts as success. The application can still fail for other reasons.
</Note>

A failed setup step removes the new Instance after the teardown steps run. A missing or non-executable setup command returns `instance.setup_step_unavailable` with `outcome: missing`, naming the step, Node, and exit 127 or 126. That classification and diagnostic survive rollback, including an incomplete or unconfirmed cleanup annotation. Other command failures return `instance.setup_step_failed`. See [Instance setup and teardown](/reference/instance-setup#run-setup).
