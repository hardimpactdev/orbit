# Verification cases

**Design draft.** The case format, the runner and the steps that the cases of `firewall:allow` use are built. `bin/check-cases` is not built.

A verification case proves one behavior of one command on the nested test fleet of [stage 3](/reference/command-development-pipeline#3-proof). A case is a specification, not code: a short YAML block built from a fixed set of steps. One shared runner executes every case. Code is written only for a new kind of check, and then once, as a new step.

The design has four aims:

- Writing a case is quick. An agent turns the command page and chart into cases, and another agent reviews them. Different commands are written in parallel.
- Every part of a command's flow has a case. A check lists what no case covers.
- Cases run in batches. The fleet restores its base snapshot once per batch, and a case undoes nothing.
- The same cases run on a developer's fleet and in CI.

## The case file

Each command has one file, `swamp/proof/<family>/<command>.cases.yaml`. The cases come from the command's chart and page, never from the code. The draft for `firewall:allow` is [`allow.cases.yaml`](https://github.com/hardimpactdev/orbit/blob/main/swamp/proof/firewall/allow.cases.yaml). `orbit proof:run` selects a command with the [selection list](/reference/feature-flow#choose-the-cases) and runs this file; a selected command without it is uncovered (`no cases file for COMMAND`).

YAML, because:

- A tool reads it, so it can reject an unknown step, an unknown chart path or a missing batch. A Markdown table cannot be checked.
- It allows comments, which JSON does not, and nested lists, which TOML writes badly.
- Swamp workflows are YAML, so authors and reviewers already know it.

One file per command, because the reviewer reads the whole contract of a command beside its chart and page, and the coverage check works on one chart. Agents that write at the same time work on different commands, so their files do not collide. If two agents must write one command, each writes its cases to a scratch file and the author joins them. Cases are independent list items, so joining is concatenation.

| Key | Meaning |
| --- | --- |
| `command` | The command, such as `firewall:allow`. |
| `chart` | The chart under `docs/cli`, such as `firewall/allow`. |
| `target` | The Node the command acts on. |
| `sources` | The Nodes that probe the target. |
| `baseline` | The state that `unchanged` compares: the runner records it at the start of `act`. |
| `batch` (on each case) | The name of a batch in `swamp/proof/batches.yaml`, which defines every batch, its start state and the run order. |
| `vars` | Named lists that a command line splices with `"@name"`. |
| `fixtures` | Named lists of steps that cases reuse. |
| `uncovered` | Chart paths, options or codes that have no case yet, each with a reason. |
| `cases` | The cases. |

A case from the draft (its `negative` key is shown [below](#prove-a-case-can-fail)):

```yaml
- id: new-restricted-allow
  batch: fresh-fleet
  covers: [main, changes-needed, succeeded]
  summary: A new allow for one source opens the port for that source only, in the right order.
  setup:
    - use: blocked-port
  act:
    - cli:
        run: [firewall:allow, "@tcp_rule"]
        expect: {exit: 0, status: succeeded}
  expect:
    - probe: {id: gateway-connects, from: gateway, to: app-dev, port: "${port}", expect: connect}
    - probe: {from: app-prod, to: app-dev, port: "${port}", expect: blocked}
    - probe: {from: "${sources}", to: app-dev, port: "${control}", expect: connect}
    - record: {list: firewall:list, node: app-dev, where: {port: "${port}", action: allow, protocol: tcp, source: "${gateway.src}", status: active}, count: 1}
    - ufw: {on: app-dev, family: 4, rows: [{to: "${port}/tcp", action: ALLOW, from: "${gateway.src}"}, {ref: deny}]}
    - unchanged: {since: act, except: {port: "${port}"}}
    - doctor: {node: app-dev, drift: 0}
```

| Case key | Required | Meaning |
| --- | --- | --- |
| `id` | yes | Short name, unique in the file. The verdict carries it. |
| `batch` | yes | The starting state the case needs. |
| `covers` | yes | The chart path ids the case exercises. Use `[]` for a case that covers no drawn path, such as a refusal. |
| `summary` | yes | One sentence: the behavior the case proves, taken from the page. |
| `setup` | no | Steps that build the starting state. A failed step makes the case `unrun`. |
| `act` | yes | The command under test, called through the real CLI. |
| `expect` | yes | What must be true afterwards. Every step runs, so one verdict lists all failures. |
| `stages` | no | Replaces `act` and `expect` when a case needs more than one round. A list of `act` and `expect` pairs, run in order. |
| `variants` | no | A list of variable sets. The case runs once per set, and each run has its own verdict, such as `protocols[both]`. |
| `fails_today` | no | One line saying why the case fails on the current code. The build removes it. |
| `negative` | no | How to prove that the case can fail. See [Prove a case can fail](#prove-a-case-can-fail). |
| `timeout` | no | Seconds for the case. Default 180. |

A case writes no cleanup. Each batch starts from a restore of the task's `base` snapshot, and each case creates what it needs on its own resources: free ports, its own listeners, a new Instance. So cases in a batch do not touch each other. A case that did not pass triggers a restore before the next case.

## Steps

The vocabulary is fixed. The first set is small and covers the `firewall` commands.

| Step | Where | What it does |
| --- | --- | --- |
| `use` | any | Insert a [fixture](#fixtures), with parameters. |
| `listener` | setup | Start TCP or UDP listeners on a Node, on free ports, and bind each port to a name. `block` starts a run of consecutive ports. |
| `ufw_rule` | setup | Add a rule that the test owns, straight on the Node, above or below another row. The row's comment is `proof:<as>`, or the text of `comment`. |
| `fault` | setup, act | Make `ufw` on the Node fail after the n-th call that contains a word. `clear` removes it. The runner also removes it when the case ends. |
| `busy_node` | setup | Keep one firewall write running on the Node, so its lock is held. The runner releases it when the case ends. |
| `agent_report` | setup | Wait until the agent of each listed Node has reported again, so the Gateway holds the state the case built. |
| `node_down` | setup | Stop the agent and the SSH of a Node, then wait 20 seconds until the Gateway counts the agent as offline. A case that stops a Node needs its own batch. |
| `node_access_remove` | batch setup | Remove the access grant of one Node to another. |
| `ipv6_addresses` | batch setup | Give Nodes an IPv6 address on the proof bridge. |
| `cli` | setup, act | Run `orbit` built from the tested commit. Keys: `run`, `forms`, `tty`, `expect`, and `as` (the Node that runs the CLI; default `gateway`). |
| `probe` | any | Open a connection from a Node to a port and expect `connect` or `blocked`. |
| `ufw` | expect | Read `ufw status numbered` on a Node and check rows. |
| `record` | expect | Run a read command and count the rows that match. |
| `doctor` | expect | Run Doctor for a Node and check its drift count. |
| `unchanged` | expect | Compare the baseline with the state at the start of `act`. |
| `ufw_delete` | setup, negative | Delete a row by hand, to build drift or to prove that a case can fail. |

Details that a case author needs:

- **`listener`** starts listeners on free ports and binds each name in `ports`. `proto` is `tcp`, `udp` or a list of both: a list uses the same port for each protocol. `family` is 4 or 6; an IPv6 listener takes IPv6 only. `block: {as: range, size: 5}` starts `size` consecutive ports (2 to 50) and binds `${range.lo}`, `${range.mid}`, `${range.hi}` and `${range.spec}`. The step fails if a port does not answer on the Node itself.
- **`cli`** appends `--json`. `forms: [json, human]` runs the call in each form, `human` without `--json`; use it only on calls that are safe to repeat, such as a refusal or a skip. `tty` runs the call in a terminal and answers prompts, in the human form only (see below). `expect` takes:
  - `exit`: the exit code.
  - `status`: the status of the Operation. In the JSON form it is the `status` of the document; in a human run it is read from the Operation named on the `Operation:` line.
  - `code`: an error code, read from the JSON form. A human run that has no JSON form takes the text instead: the output must contain the code.
  - `skipped`: a reason code that the JSON document gives under a key named `skipped` (or any key with `skip` in its name). It needs the JSON form.
  - `request: none`: the call created no Operation. The runner lists the Operations before and after the call.
  - `human`: a text, or a list of texts, that the output must contain. Escape codes are removed first.
- **`tty`** is a list of steps. `see` waits for text in the output that came after the previous step; `send` types a text and Enter, and `^C` sends Ctrl-C; `choose` moves a list prompt (Laravel Prompts) to the item with that label and presses Enter. A command that never shows the text, or ends before it, fails the case with the end of its output: that is a finding about the command, not about the runner. The driver is `swamp/proof/runner/terminal.py`, built on the standard `pty` module.
- **`probe`** in `setup` is a precondition: a mismatch makes the case `unrun`. In `expect` it is an assertion: a mismatch fails the case. A list in `from`, `proto` or `port` runs one probe for each combination. `family` is 4 or 6, and `proto` is `tcp` or `udp`. A TCP probe connects. A UDP probe sends one datagram and waits for the listener's answer, so `connect` means the answer came and `blocked` means nothing came in 3 seconds. A refusal (an ICMP error, or a closed TCP port) is neither: it is reported as `refused`. An IPv6 probe needs `ipv6_addresses` in the batch.
- **`ufw`** checks that each row appears exactly once, in the order listed, top to bottom. `absent` rows must not appear. A row is `to`, `action`, `from` and an optional `comment`, or `ref` to a rule that `ufw_rule` bound with `as`.
- **`record`** runs `list`, for one `node` or for every Node when `node` is left out, then matches `where` against each row. Each row carries the name of its Node under `node`. A list as a value matches any of its items, and the word `present` matches any value that is not null. A `record` needs `count`, `min` or `order`. `count` is exact; `min` is a lower bound. `args` adds options to the list call. `section` names the part of the JSON to read: `rules` (default), `managed`, `unmatched` or `live`. `order` lists rows that must appear in that sequence, not necessarily next to each other.
- **`doctor`** waits until 65 seconds after `act` ended, so that a report of the Node agent follows the change, then runs Doctor for the Node. The agent's tick has no fixed phase after a restore of `base`, so the wait does not use it. Use it in the main success case, not in every case.
- **`unchanged`** compares the providers named in `what`, or all of `baseline` except `operations`. `operations` runs only when `what` names it, because the command under test creates an Operation. `except` leaves out rows for one port. `request: none` uses the `operations` provider.
- **`fault`** puts a shim in place of `/usr/sbin/ufw` on the Node (the real program stays as `ufw.real`; a shell script of 20 lines, `tools/swamp-proof-guest/ufw-shim.sh`). `fail_after: {match: delete, count: 1}` lets the calls through until the 1st call whose arguments contain the word has run; every later call that writes then exits 1 with `ufw: injected fault`. Calls that read (`status`, `show`, `version`, `help`) always pass, so the runner's own reads and the Node's reports keep working. `fault: {clear: true}` removes the fault on every Node where the case set one. Only `command: ufw` exists.
- **`busy_node`** holds a firewall write on the Node. It puts the same shim in place, holds a lock that the shim's writes wait on (`flock`), and starts a real `firewall:allow` of a spare port in the background. The step ends when the CLI prints its first line, which it does after the Gateway admitted the request, so the Gateway holds the Node's firewall for that Operation. `seconds` (default 120) bounds the lock. When the case ends, the runner releases the lock, waits for the held write to finish, and puts the real `ufw` back, so the next case does not meet an Operation that still runs. `command` is `firewall:allow` (the default) or `firewall:deny`.
- **`ipv6_addresses`** gives each listed Node an address `fd42:232:2::<last octet of its IPv4 address>/64` on the interface of its bridge address, then pings every Node from every other over IPv6; a failed ping makes the case `unrun`. It binds `${<node>.src6}` and the IPv6 address that `probe` uses. It stands in the `setup` of a batch.

A fault, a held write and the Node's IPv6 addresses live on the Node. The runner ends the fault and the held write when the case ends, so a later case in the batch does not see them. A restore of `base` removes everything else.

Placeholders:

| Placeholder | Value |
| --- | --- |
| `${app-dev.id}` | The Node ID in the nested Gateway. The Nodes are `gateway`, `app-dev` and `app-prod`. |
| `${gateway.src}`, `${gateway.src6}` | The IPv4 or IPv6 address that the Node uses to reach the target. |
| `${port}`, `${control}` | Names that `listener` bound. A `block` binds `${range.lo}`, `${range.mid}`, `${range.hi}` and `${range.spec}` (`lo:hi`). |
| `${sources}` | The `sources` list of the file. |
| `${proto}` | A fixture parameter or a variant variable. |

A placeholder that holds a list expands the step or row that uses it, once per item. `"@name"` in a command line splices a `vars` list.

## Fixtures

A fixture is a named list of steps with parameters. It keeps the starting state out of every case. `use: blocked-port` inserts it; `use: {fixture: blocked-port, proto: [tcp, udp]}` sets its parameters.

```yaml
fixtures:
  blocked-port:
    params: {proto: [tcp], family: 4}
    steps:
      - listener: {on: app-dev, proto: "${proto}", family: "${family}", ports: [port, control]}
      - ufw_rule: {as: deny, on: app-dev, action: deny, proto: "${proto}", port: "${port}", above: proof-network}
      - probe: {from: "${sources}", to: app-dev, family: "${family}", proto: "${proto}", port: "${control}", expect: connect}
      - probe: {from: "${sources}", to: app-dev, family: "${family}", proto: "${proto}", port: "${port}", expect: blocked}
```

This is the setup that [verifying-commands](https://github.com/hardimpactdev/orbit/blob/main/.agents/skills/verifying-commands/SKILL.md) asks for: a healthy listener, a control probe that connects, and a test port that is blocked over the test path before the command runs, with the broad `proof-network` allowance out of the way. A fixture that several commands share moves to `swamp/proof/<family>/fixtures.yaml`.

## Chart paths and coverage

Every `alt` branch, `else` branch and `opt` block of a command chart carries an id, on a comment line directly below it:

```text
alt changes needed
  %% path: changes-needed
```

`main` is the path with the required arguments only; it needs no marker. A case lists the ids it exercises in `covers`.

Ids, because the alternatives break. A branch label is also a progress name and changes when someone improves the wording. A line number moves with every edit. An id changes only when someone rewrites the branch on purpose, and then the check fails until the case follows. Name an id for what happens (`already-applied`), unique in its chart. Markers are comments, so the chart renderer ignores them. `bin/check-flows` also fails a branch without an id, for charts that have a cases file.

`bin/check-cases` (new) reads the cases file, the chart and the command page. It lists three kinds of item that no case covers:

| Item | Where it comes from | Covered when |
| --- | --- | --- |
| Chart path | `main` and every `%% path:` id | a case names it in `covers` |
| Option | the option table of the page | a `cli` step passes it (`--json` counts through `forms`) |
| Code | every `family.code` token on the page or in the chart, such as `firewall.rule_exists` | a `cli` step expects it as `code` or `skipped` |

An item that no case covers fails the check unless `uncovered` lists it with a reason. The check also fails on an unknown step, chart path, fixture, variable or batch, and on a case without `batch`, `covers` or `summary`. A code that a case expects but the page and chart do not name is reported as a page gap.

For the drafted `firewall:allow` file it reports:

```text
firewall:allow  14 cases, 16 verdicts
  chart paths  5 of 5
  options      3 of 4   no case: --label
  codes        3 of 4   no case: firewall.backend_inactive
  page gap     firewall.node_id_invalid, input.cancelled: expected by cases, named by neither page nor chart
```

The check cannot read prose. The reviewer walks the `Requirements` of each chart step against the cases. For `firewall:allow` that finds three more gaps: the access grant, a target that is not an active Linux Node, and an invalid port or source.

## Batches and restores

A batch is a group of cases that run one after another after one restore. Every case names its batch. `swamp/proof/batches.yaml` defines each batch: a name, a summary, optional setup steps, and the order in which batches run. A run proves one command, so cases of different commands never share a batch; batch definitions such as `dual-stack` are shared.

- The run starts on the task's `base` snapshot. The first batch needs no restore.
- A later batch starts with a restore of `base`, about 16 seconds, then its setup steps. The workflow runs it with `runner setup BATCH`; a later `runner case` finds the result on the fleet (for IPv6, the addresses that Incus reports for the guests).
- Inside a batch, cases run one after another and undo nothing. Each uses its own resources, so it does not see the others.
- A case that changes state all cases share gets its own batch: UFW turned off, an injected `fault`, a held lock (`busy_node`), network setup, or a check of the complete list.
- A case that does not pass triggers a restore of `base` and the batch setup before the next case.
- A restore that fails or is not healthy within 45 seconds stops the run. The cases that did not run become `unrun` with cause `infrastructure`; the verdicts already reached stay.
- A case that needs a state that no batch offers gets a new batch. Do not build a different world inside one case.

A batch costs a restore, so keep few. `firewall:allow` needs two:

| Batch | Starting state | Cases |
| --- | --- | --- |
| `fresh-fleet` | The healthy fleet. Only Orbit's own rules and the `proof-network` allowance exist. | 13 |
| `dual-stack` | As above, and every Node has an IPv6 address on the proof bridge. | 1 |

## The run

<div className="flow-at" data-chart="reference/pipeline/3-proof-runner"></div>

The flow of a proof is [stage 3](/reference/command-development-pipeline#3-proof); in CI, [`proof:run`](/cli/proof/run#how-it-works) starts it. This page does not restate them. The shared runner is `swamp/proof/runner/`.

Each case ends with one JSON line of at most 1 KB, because Swamp cuts step output at 4096 bytes:

```json
{"id": "protocols[both]", "verdict": "failed", "cause": "assertion", "secs": 41.2, "failed": ["expect[2] probe: app-prod to 47212/udp connected, expected blocked"]}
```

| Verdict | Cause | Meaning |
| --- | --- | --- |
| `passed` | | Every step passed. |
| `failed` | `assertion` | An `act` or `expect` step failed. |
| `failed` | `infrastructure` | A step could not run, for example the fleet is unreachable. |
| `unrun` | `precondition` | A `setup` step failed, such as a port that was not blocked before the command. |
| `unrun` | `infrastructure` | A failed restore stopped the run before the case. |

Neither `failed` nor `unrun` is a pass. The full receipt of a case, with every step, command output, the firewall before and after and the timings, stays in the evidence directory of the task VM. There is no receipt store. In CI the proof VM is destroyed, so only the verdict lines stay; the author reruns the proof in their own task VM for the full receipt.

A case marked `fails_today` runs like any other and reports its real verdict. The build PR removes the mark when the command passes.

## Write and review

The cases are written last, after the chart and the page, from those two and never from the code.

1. List the chart paths, options and codes. For each, decide which case covers it.
2. Write each case from the fixture and step tables. A case needs no code. A check that the steps cannot say is a request for a new step.
3. Run `bin/check-cases` and `runner plan --dry-run` (both new). The dry run prints every case with fixtures and placeholders resolved, and the batch order, without a fleet.
4. A second agent reviews, read-only, with the chart, the page and the file.

A new step is a function in the runner, an entry in its argument schema, a row in the table above and a test. It lands in the PR of the first case that needs it, and every later case can use it.

Cases of different commands are written by different agents at the same time. They share only the vocabulary, the fixtures and the batch list, which change rarely and in their own PRs.

The reviewer checks:

| Check | Question |
| --- | --- |
| Source | Does each expectation follow from the page and the chart, not from the code? |
| Precondition | Does each effect case first show, in `setup`, that the port is blocked and a control port works over the test path? |
| Real effect | Does a case that promises traffic check traffic, and not only the record? |
| Refusal | Does each refusal expect `request: none` and `unchanged`, with one case for each way past a guard? |
| Repeat and failure | Does a repeat case exist, and a failure after a partial change that a retry settles without duplicates? |
| Coverage | Does `bin/check-cases` print nothing unexplained, and does each `uncovered` entry hold a real reason? |
| Size | Is any case longer than about 30 lines? Split it or move steps to a fixture. |
| Names | Are there only placeholders, no concrete IDs, hosts or addresses? |

## Prove a case can fail

A new case must show that it can fail. The `negative` key says how:

```yaml
negative:
  after: act
  do:
    - ufw_delete: {on: app-dev, to: "${port}/tcp", from: "${gateway.src}"}
  must_fail: [gateway-connects]
```

The Swamp workflow restores `base` and runs `runner case ID --negative`, which runs the case a second time. After `act` it runs the `do` steps, which break the effect. The expectations in `must_fail`, named by their `id`, must fail, and the rest still run and are listed in the receipt. A case where they pass is not a test. The proof CI also proves that a new case needs the new code, by running it on the merge base; see the [stage 3 chart](/reference/command-development-pipeline#3-proof). The two checks differ: `negative` breaks the effect, the merge-base run removes the code. The verdict is `passed` with `"negative": true` when every one of them failed. The run happens when the case is new or changed, with `runner case ID --negative`, and not in every proof run.

## Where the code is

The runner is `swamp/proof/runner/`: `runner.py plan|case|restore|setup`, the loader `spec.py`, the steps `steps.py`, the fleet access `fleet.py`, the programs that run on a Node (`listener.py`, `probe.py`) and the tests. The terminal driver and the `ufw` shim are in `tools/swamp-proof-guest/`. A step that is not built fails the case with cause `infrastructure` and the message `... is not built`. `bin/check-cases` (about 150 lines) is not built. After it, a case costs 15 to 40 lines of YAML and no code, and a new kind of check costs one step.
