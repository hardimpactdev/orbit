### DEFECT 2 — stale-main guard misdiagnoses the normal post-LAND state

- Severity: blocking (operator UX; misdirection toward a destructive command).
- Evidence: `bin/orbit-prepare-worktree:76`; `HARNESS.md:255-300`; `bin/orbit-feature-land` (no `git push`); `AGENTS.md:65-70`.
- The documented LAND flow merges into local `main` and ends with "Leave the primary checkout on updated `main`". Neither HARNESS.md nor `bin/orbit-feature-land` pushes; `git push origin main` appears only in `.agents/skills/release/SKILL.md:151`. So immediately after every landed feature, local `main` is **ahead** of `origin/main`.
- In that state the guard fires and prints `local main (X) differs from origin/main (Y); local main must be updated before preparing a worktree from --base=main`. Local main is the newer side, not the stale one. An operator following "must be updated" literally (`git reset --hard origin/main` / `git pull`) discards or rewinds just-landed work — exactly the mutation the invariant forbids the script from performing.
- The Scope constraint says "differs", so failing in both directions is authorized; the wrong part is the diagnosis, not the block.
- Smallest correction: in `reject_stale_local_main`, branch the message on `git merge-base --is-ancestor origin/main main`. When `origin/main` is an ancestor of local `main`, say local `main` is ahead of `origin/main` and must be pushed; otherwise keep the current stale wording. Keep both SHAs in both messages, and add one fixture case asserting the ahead-direction message. Whether the ahead case should block at all is an owner decision against the Scope wording, not a reviewer change.
