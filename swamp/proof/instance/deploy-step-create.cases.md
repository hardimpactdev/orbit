# instance:deploy-step:create verification cases

`instance:deploy-step:create` records a step on a production Instance and has no chart. The proof runs the built CLI against a fresh nested topology with production Instances that have step lists of different sizes and a development Instance, and compares the output with the Gateway records. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Add at the end | Create a step with only the Instance, the name and `--command`. | The step is the last `before_activation` step in `deploy-step:list`, with the timeout 300. The result is at once, with no task and no file written on any Node. |
| Phase | Create steps in `after_activation`, and with an invalid phase. | The after-activation step lists after all before-activation steps. The invalid phase gives `validation.failed`. |
| Placement | Create steps with `--before=NAME` and `--after=NAME` for a step of the same phase, of the other phase, and one naming no step. | The same-phase ones land at the named place and the others keep their order. The other-phase and unknown ones give `validation.failed`. |
| Timeout | `--timeout=1`, `--timeout=900`, `--timeout=0`, `--timeout=901`, `--timeout=abc` and an empty `--timeout=`. | The first two are stored. `0` and `901` give `validation.failed`. `abc` and the empty value give `deploy_step.timeout_invalid` before any request. |
| Name | `a`, a name of 63 characters, a name of 64, one with an upper-case letter, a leading hyphen, and a duplicate, then the identical create repeated. | The first two are stored. The others give `validation.failed`, and the repeat gives the same refusal: there is no skip. |
| Command | A 16 KiB command, a multiline one, one whose multibyte characters reach exactly and then pass 16 KiB, an empty `--command=`, a blank one made of spaces, one with a NUL byte, and one over 16 KiB. | The first three that fit are stored whole. The empty one gives `deploy_step.command_required` before any request, in a noninteractive call. The others give `validation.failed`. Fails today: a blank command passes the Gateway and is stored. |
| Before and after | `--before` with `--after`, and an empty `--before=`. | `validation.failed` for the first, and nothing is stored. The empty one is read as omitted. |
| Instance limits | Create the 33rd step, and a step that makes the timeouts total 3,601 seconds. | `validation.failed`, and nothing is stored. Fails today: every refusal says only `The request data is invalid.` with the reason under `body`, and these two give the generic reason `The deployment configuration is invalid.`. |
| Not available | A development Instance, and a production Instance that is neither source-resolved nor active. | `deployment_config.unavailable`. Nothing is stored. |
| Competing creates | Two creates of the same name at once, and a create while a deploy is admitted. | One of the two is stored and the other gets `validation.failed`. A deploy that was admitted before the create refuses to start when the step's command differs from the admitted one. |
| Used by the next deploy | After a create, run `instance:deploy`. | The step runs in its phase and order. The create itself ran nothing. |
| Output forms | A wide and a narrow terminal, a 16 KiB multiline command, output piped to a file, and `--json`. | A detail `Deploy step: <name>` with Phase, Command, Timeout (seconds) and the request ID at the wide width, and labeled records at the narrow one, with the command wrapped and never cut. The piped output has no animation or escape codes. With `--json`, stdout holds the step with `request_id`. |
| Activity | After a successful create and a failed one. | Activity and the error hold no command text. |
| Missing input | In a terminal, run the command with no arguments, cancel the list, and leave the name and the command empty. Then run it noninteractively and with `--json`. | The terminal lists Instances by name and asks for the name and the command. Cancel ends with `input.cancelled` and no request. The noninteractive calls are refused with `instance.id_invalid`, `deploy_step.name_required` or `deploy_step.command_required`, with no request. Fails today: the Instance and name are required arguments, and the command is refused even in a terminal. |
| IDs only | An Instance by name, the ID `0`, the ID `-1` passed after `--`, and `abc`. | `instance.id_invalid`, with no request. Fails today: `-1` without `--` is read as an option and gives a parser error. |
| Unknown and access | An ID that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing is stored. |
