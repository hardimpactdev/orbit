# Human Renderer: `orbit update`

[Back to `update` technical contract.](1_update.md)

This page describes the human-rendered terminal output for `update`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

`update` may perform network, dependency installation, and migration work, so
the human renderer must show an in-progress tree after prerequisite validation
and before side effects begin.

```text
┌ Updating Orbit
○ Pull source
○ Verify entry point
○ Install gateway dependencies
○ Run gateway migrations
└ Working...
```

Each step is updated in place as it starts, succeeds, or fails. The final tree
must make the failed step visible when the command exits with failure.

## Success Output

On success:

```text
Updated local Orbit checkout.
```

The success message may appear after the completed progress tree. It must not
suggest that fleet drift or runtime readiness has been verified.

## Related Multi-Node Renderer

`update` only renders the local checkout update sequence. Multi-node progress
for `update:all` is specified separately in the
[`update:all` human renderer contract](../../2_update-all/technical/6.1_update-all_output-render_human.md).
That renderer shows one row per Orbit node and changes each row through
`Pulling source`, `Installing gateway dependencies`, `Running gateway migrations`,
and `Done`.

## Failure Output

Human-rendered failures must show:

- the failed update step;
- a clear prose error;
- captured command output from Git, `orbit-runtime` dependency installation, or
  migrations when available;
- no JSON envelope.

Example:

```text
Failed to update local Orbit checkout.
orbit-runtime container unavailable
```

For source-mounted Docker/Incus development and E2E targets, the renderer may
complete after `Pull source` and `Verify entry point` because those targets keep
`/usr/local/bin/orbit` pointed at `<source>/apps/cli/orbit`. `Install gateway
dependencies` and `Run gateway migrations` are gateway-context stages only.
