# instance:setup verification cases

The proof runs the built CLI against a fresh nested topology with a Gateway and an `app-dev` Node with an active development Instance of a Project with setup steps. It checks the Gateway records and the effects of the steps on the Node. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Run the list | A Project with three setup steps that each leave a marker file. | The task succeeds. The steps ran in list order as the Instance's account in the repository root, each with its own timeout, and the markers show the order. They received `ORBIT_INSTANCE_ID`, `ORBIT_INSTANCE_NAME`, `ORBIT_SEED_PATH` and `ORBIT_SEED_COMMIT` (empty seed values for a `default`) and the Node's Vite+ store as `VP_HOME`. The Instance record has no failed step or error code, and `first_setup_pending` is false. Fails today: the workflow does not set `VP_HOME`. |
| Nested root | A Laravel Project whose application directory is nested, with a step `cd apps/site && composer install`. | The step runs at the repository root and installs the application. |
| From the start | Run setup twice. | The second run starts from the first step again. |
| Empty list | A Project with no setup steps. | The task succeeds with a no-op receipt and nothing on the Node changes. |
| Failed step | Make the second step exit nonzero. | The task fails with `instance.setup_step_failed` and the step name. The first step's effects stay, the third step did not run, and the Instance and checkout stay with the failed step and the error code recorded. A rerun after the fix starts from the first step, succeeds, and clears both. Fails today: the Instance records the literal `setup` instead of the step name. |
| Missing command | A step whose command is not found, and one that is not executable. | `instance.setup_step_unavailable` for the first, naming the step. The second gives the same code. Fails today: exit 126 gives `instance.setup_step_failed`. |
| Deadline | A step that outlasts its timeout, and a list stored before the 540-second cap that adds up to more. | Both end with `command.deadline_exceeded`, `outcome: deadline` and the step name, and no command keeps running after its timeout. The Instance stays. |
| List changed | Change the list after the task was admitted and before it runs. | The run refuses the admitted list with `instance.step_not_admitted`. A new run uses the new list. |
| Not eligible | A production Instance, a development Instance that is not active, one not placed on an `app-dev` Node, one with a `root` account, and one with an invalid checkout path. | `instance.setup_unavailable` for the first two and `instance.step_not_admitted` for the rest. No task. |
| Busy | Start setup while another operation holds the Instance, and while a development `default` deploy holds the checkout. | `operation.target_busy` for the first and `instance.lifecycle_busy` for the second. The running operation is unaffected. Fails today: setup takes no hold, so the first starts a second task. |
| No output kept | Run a step that prints to both streams and one that prints a secret. | Neither the task, the Activity nor the history holds the command text or output. A failure shows only the step name and its code. |
| Interrupt | Cancel a run, let one time out, and stop the executor mid-run, and lose the SSH connection. | Cancel and timeout end like a failed step. A lost connection or stopped executor with no proven failed step ends with `instance.step_execution_unconfirmed`. A rerun finishes. |
| Progress and output | Follow a setup in a terminal, a narrow terminal and a pipe, and press Ctrl-C. | A tree of the steps. Ctrl-C stops following, exits 130 and leaves the setup running. The piped output has no animation or escape codes. With `--json`, nothing prints while it follows, then stdout holds only the final task. A success, a failure and a refusal exit `0`, nonzero naming the failed step, and nonzero with the one-line error. Fails today: one `native` row replaces the tree. |
| Missing input | In a terminal, run the command with no argument and cancel the list. Then run it noninteractively and with `--json`. | The terminal lists Instances by name. Cancel ends with `input.cancelled` and no request. The noninteractive calls are refused with `instance.id_invalid`, with no request. Fails today: the Instance is a required argument, so every call without it is refused by the parser. |
| IDs only | An Instance by name, the ID `0`, the ID `-1` passed after `--`, and `abc`. | `instance.id_invalid`, with no request. Fails today: `-1` without `--` is read as an option and gives a parser error. |
| Idempotency option | Run with `--idempotency-key`. | The option is refused as unknown. Fails today: the CLI offers it. |
| Lost response | Lose the response to the start and repeat the command. | While the first run is live the repeat is refused with `operation.target_busy`, and exactly one task exists. Fails today: no hold, so a second task starts. |
| Unknown and access | An ID that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing starts. |
