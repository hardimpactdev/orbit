---
title: "orbit node:role:relocate"
sidebarTitle: "node:role:relocate"
description: "Move `gateway`, `websocket`, or `metrics` from its current Node to another Node. One assignment stays active for the whole request."
---

```bash
orbit node:role:relocate <node> <role> [--from=NODE] [--force] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Numeric ID of the target Node. It must be active and hold no conflicting role. |
| `role` | yes | `gateway`, `websocket`, or `metrics`. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--from=NODE` | the current holder | Numeric ID of the source Node. After an earlier relocation of this role from that Node, the target already holds the role and `--from` names the Node whose leftovers to remove. |
| `--force` | prompt | Confirm the move without prompting. Required without a terminal and with `--json`. |
| `--idempotency-key=KEY` | generated | Reuse a key to retry the same [Operation start](/reference/operations#start-an-operation). |
| `--json` | off | Print the final Operation as JSON. |

```bash
orbit node:role:relocate 7 gateway --force
orbit node:role:relocate 9 websocket --from=7 --force
```

In a terminal, an omitted Node is chosen from an interactive list and an omitted role from the roles that can move. The CLI asks to confirm the move with the Node names and the role, with No selected. Declining, Ctrl-C or end of input exits 1 with `input.cancelled`. The prompt appears only after the checks that can refuse the move have passed. A noninteractive or `--json` call without `--force` or without the role is refused with `validation.failed`, and one without the Node with `node.id_invalid`; neither starts an Operation.

For `gateway`, the Gateway opens the `orbit:gateway-https` firewall rule on the target and moves the assignment. It grants the new Gateway Node access to the `vpn` and `metrics` Nodes, publishes private DNS on the `vpn` Node, and adds the [private DNS route](/reference/private-dns#the-gateway-machine) on the target. It then removes that route and the firewall rule from the source. A failed route on the target reports `follow_up` and does not stop the move.

Relocating `gateway` does not move `vpn`, the Gateway checkout, its SQLite database, the Orbit CA, or the SSH keys. It does not stop Caddy or PHP-FPM on the source, so clients that still use the old address keep working. [Relocate the gateway role](/solutions/relocate-gateway-role) gives the full order.

For `websocket`, Orbit copies the Reverb server's Laravel `APP_KEY` only when the target lacks one. The [Reverb apps](/reference/websocket-apps) stay in the Gateway database, so every app keeps its credentials. Orbit builds a new Reverb release on the target as the Node's user, so the target needs Git, PHP and Composer, as an `app-dev` or `app-prod` Node has them. For `metrics`, Orbit copies role credentials that the target lacks, without overwriting any, and applies the same role setup as `metrics:enable` on the target. It then removes the runtime and publication from the source as `node:role:remove` does, but keeps the fleet exporters and the `metrics.orbit` name and certificate, which the moved role uses.

Both Nodes need recorded SSH management. [Native role relocation](/reference/node-provisioning#native-role-relocation) lists every step.

`swamp` can't be relocated: it stays on its Node. The command answers `node.role_relocate_swamp_held` before it records anything.

Only one add, converge, remove or relocate runs on the target Node at a time; a second call is refused with `operation.target_busy`. The CLI follows the Operation and prints the final result with the request ID.

When a step on the target or the source fails, the role already belongs to the target and stays `active`, so a role such as `gateway` is never taken out of service by a failed move. The Operation fails with the step's own code, and the failed step stays on it: `converge:STEP`, or `remove:Remove from the source` when the source removal failed. After a target step failure the source still serves; after a source removal failure the target serves. Finished steps stay and nothing is rolled back. Run the same command with `--from` after you fix the cause. A cancelled or interrupted run leaves the claim `provisioning`, and the same retry takes it over.

Repeating a completed move without `--from` is refused with `validation.failed`, because the target now holds the role and the source does not. A `--from` is accepted for a target that already holds the role only after an earlier relocation of this role from that Node.

Relocation does not reconcile Metrics. When a Metrics role exists and `websocket` or `gateway` moved, `follow_up` names the `orbit node:role:add <metrics-node> metrics --converge` command.

## Errors

| Code | When |
| --- | --- |
| `node.id_invalid` | The Node is missing or is not a positive integer, and the CLI cannot prompt. |
| `node.role_relocate_swamp_held` | The role is `swamp`. |
| `validation.failed` | The role is not relocatable or not assigned, it cannot be relocated from its status, the role or `--force` is missing without a terminal, `--from` is unknown, or `--from` does not own the move. |
| `node.role_conflict` | The target holds a role that conflicts with the moved role. |
| `operation.kind_unavailable` | The target or the source is not an active Linux Node with recorded SSH management. |
| `operation.target_busy` | Another add, converge, remove or relocate holds a Node. |
| `node_access.required` | The caller has no access grant to the Gateway Node. |
