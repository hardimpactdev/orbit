# Human Renderer: `orbit update:all`

[Back to `update:all` technical contract.](1_update-all.md)

This page describes the human-rendered terminal output for `update:all`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update:all` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

`update:all` performs local update work, starts a durable gateway operation,
and may take longer than one second. The human renderer must show an
in-progress tree before local update work starts. The tree begins with the
caller-local checkout row and is extended with gateway and workload rows after
the gateway authorizes the fleet update, before fleet side effects begin.
Gateway-owned progress is rendered from the operation event journal.

```text
┌ Updating Orbit nodes
○ local   Updating CLI
○ gateway Queued
○ app-1   Waiting
└ Working...
```

Each row represents one Orbit checkout target. While a target is being updated,
the row keeps the node name in the first column and changes the stage in the
second column. The node-name column is padded to the longest rendered node name
so stages align vertically:

```text
┌ Updating Orbit nodes
● local   Done
◉ gateway Updating gateway service
○ app-1   Waiting
└ Working...
```

This example shows an operator peer whose local checkout is not the gateway. The non-local target list is populated after the gateway returns its configuration; until then, the caller-local checkout is shown by its local target row.

Valid in-progress stages are:

- `Updating CLI`;
- `Starting operation`;
- `Acquiring leases`;
- `Updating gateway service`;
- `Stopping scheduler`;
- `Running gateway migrations`;
- `Starting scheduler`;
- `Updating node CLI`;
- `Pulling required images`;
- `Verifying`.

Rows for selected targets whose update has not started yet show `Waiting`.
`Waiting` is not an active update stage and must not use the active spinner.

When a target succeeds, its stage changes to `Done`. When it fails, its stage
changes to `Failed` and the command prints the captured failure output below
the tree.

For operator peers, gateway-owned work is streamed back over the typed Gateway
API as durable operation events. The CLI renders those events locally so the
operator sees gateway and app-role targets move through role-aware stage labels
without waiting for one blocking response. If the gateway service is replaced
mid-stream, the CLI reconnects with `Last-Event-ID` and resumes from the event
journal without duplicating rendered events.

For operator peers, the caller-local row and gateway row may advance
simultaneously. After the gateway row succeeds, app-role rows may advance
simultaneously, up to four nodes at a time. The renderer must preserve one
row per selected target and must not reorder final rows based on which parallel
worker finishes first.

If the caller-local checkout fails while gateway work is already in flight, the
human renderer reports the local failure and does not accept the gateway result
as fleet success. It does not cancel gateway checkout work that is already in
flight.

## Success Output

On full success:

```text
┌ Updating Orbit nodes
● local   Done
● gateway Done
● app-1   Done
└ Successfully updated 3 nodes
```

The exact target labels come from the caller-local target and gateway node configuration. The success output must not claim that app deployments, state-family drift, or runtime readiness have been verified.

## Failure Output

Human-rendered failures must show:

- every target that succeeded;
- every target that failed;
- the failed update output when available;
- no JSON envelope.

When the local checkout fails, remote app-role targets are not attempted:

```text
Failed to update local Orbit CLI.
local Orbit entry point did not respond to the version check
```

When a remote target fails, later targets continue:

```text
┌ Updating Orbit nodes
● local   Done
● gateway Done
● app-1   Failed
● app-2   Done
└ Failed
Failed to update node app-1.
Permission denied (publickey).
```
