An Instance is one copy of a Project on one Node. On an `app-dev` Node it owns a checkout or worktree, or an [Instance container](/reference/development-containers) on a Node on the build list. A container runs the Project's development Process definitions with its own Process records. On an `app-prod` Node it owns a Unix user and a production home with releases. The [Project type](/reference/projects#project-types) decides whether it gets a Route.

[Applications](/domains/applications) walks through the lifecycle. [Production release layout](/reference/deployments), [Instance setup and teardown](/reference/instance-setup), [Instance cloning](/reference/instance-cloning), [Instance transfer](/reference/instance-transfer), [Instance removal](/reference/instance-removal), and [Database connections](/reference/database-connections) own the contracts behind these commands.

## Commands

Instance JSON includes nullable `seed_path` and `seed_commit`. On `default`, these name its checkout and the last commit that deployed there. Read them before creating a linked worktree for `instance:register`; use that commit rather than a newer `origin/main`. Human tables keep their existing columns.

`instance:create`, `instance:register` and `instance:transfer` accept any active `app-dev` Node that the request names; a Project keeps no list of Nodes it may not use.

`instance:migrate` reports `untracked_files_copied` in its Operation result and the copied count in human output: untracked files that Git does not ignore. See [migration](/cli/instance/migrate) for the seed and later checkout consequences.

Human transfer and destroy results identify checkouts that could not be checked; `--json` retains each structured warning.

Every command accepts `--json`. Machine output never supplies consent. Human list commands use tables, with labeled records when the terminal is too narrow; detail commands show a tree and slow requests show progress.

Placement commands create, adopt, inspect, and remove an Instance on one Node. Instance names use lowercase letters, digits and hyphens, contain 1–63 characters, and start and end with a letter or digit. Conn checks the same format with its [name check](/reference/conn#threads-in-an-orbit-project). Its Project directory reports the shared read-only clone admission result before a name is chosen. A web Instance create also checks the [live certificate limit](/reference/routes#certificate-request-forms) before it starts an Operation.

`instance:create`, `instance:clone`, `instance:transfer`, `instance:migrate`, and `instance:destroy` return an Operation. `instance:rename` records the branch at once from the Node agent's report and returns the Instance. `instance:register` returns the Instance at once when the checkout's `.env` is absent or private, and otherwise an Operation for the run that protects `.env`. The Gateway validates and records intent, then queues the native start. The API returns the Operation before that start runs. Swamp executes the work. The CLI follows the Operation and prints its final receipt in JSON mode. `--idempotency-key=KEY` retries the same admission without creating another Operation. Ctrl+C stops following; it leaves the Operation running. Use `operation:show` to read it again.

`instance:migrate` reports `moved` and `restored` in its Operation result. Human output also shows the mailer outcome or advisory mail warning. A mail warning does not block cutover or retirement. A failure after cutover can leave the container serving.

On a Node of the build list, a Project's first `default` Instance runs in a container, and every other Instance of the Project is a [clone](/reference/development-containers#create) of it, with its own T3 server. See [the default Instance](/reference/development-containers#the-default-instance).

Conn can also [create a thread clone on a selected branch](/reference/conn#threads-in-an-orbit-project). That optional API selection reserves a branch before creation and freezes its source commit. The CLI keeps its existing create rules.

## Related

- [`project`](/cli/project) owns the repository and source defaults that an Instance inherits.
- [`route`](/cli/route) shows and changes the domain of an Instance.
- [`env`](/cli/env) imports, updates, and synchronizes the stored environment that deployments render.
- [`process`](/cli/process) and [`schedule`](/cli/schedule) run services and timers on an Instance.
- [`database`](/cli/database) registers the connections that `instance:database:add` attaches.
- [`analytics`](/cli/analytics) pins the Plausible version that the tracking hosts send visits to.

Repair development mail with [`instance:mail:update`](/cli/instance/mail-update).

A checkout can record an explicit [Node service target](/cli/instance/node-service-attach) before migration. For a running container, [detach](/cli/instance/node-service-detach) withdraws its scoped loopback access before removing the record. The environment file and Node Process stay unchanged.

Migration reports named environment warnings in human output and retains their `code` and `message` in the Operation result. See [migration warnings](/cli/instance/migrate#warnings).

Nested-fleet creation requires both the Project setting and the Node hosting switch. Checkout migration into that project is unavailable. See [nested fleet](/reference/development-containers#nested-fleet).

Nested create and clone use the nested image only on switched-on build-list Nodes. Each create or retry must resolve to a container in the nested project; a checkout default or source is refused before reservation. Migration remains unavailable for nested Projects.
