---
title: "orbit node:wireguard-key"
sidebarTitle: "node:wireguard-key"
description: "Set or replace the WireGuard public key of an existing unmanaged Node. Use this when the operator manages the peer's tunnel outside Orbit. The command does not generate a key pair, accept a private key, or configure the target machine."
---

```bash
orbit node:wireguard-key <node> <public-key> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Numeric Node ID. |
| `public-key` | yes | Canonical base64 encoding of exactly 32 bytes: 44 characters ending in `=`. Whitespace, malformed base64, an empty value, and null are invalid. The key must not belong to another Node or the WireGuard hub. There is no unset mode. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--json` | off | Print the final Operation as JSON. |

```bash
orbit node:wireguard-key 5 'AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE='
```

A terminal prompts for an omitted Node with an interactive list, then for an omitted key with the text prompt `WireGuard public key`, with no default. An invalid prompted key is requested again. Cancelling a prompt exits 1 with `input.cancelled` and changes nothing. A noninteractive or `--json` call without the Node is refused with `node.id_invalid`, and one without the key with `node.wireguard_key_required`. A supplied invalid key is refused with `validation.failed`. A refused call starts no Operation.

Orbit refuses any Node holding the `gateway` role. It also refuses a managed Node: a Linux or macOS Node with both a nonempty WireGuard address and a pinned SSH host fingerprint, regardless of its status. A Node with only one of the two is unmanaged. The target needs an existing WireGuard address; the command does not allocate one or change the Node's status, roles, endpoint, address, or SSH identity.

WireGuard identifies peers by public key, not by Node ID. Before it changes anything, Orbit rejects a key assigned to any other Node, regardless of that Node's status or the caller's access to it, or equal to the hub's public key, with `node.wireguard_key_conflict` (HTTP 409). The check and the assignment are atomic across concurrent assignments. The refusal leaves the stored key and the hub unchanged and does not expose the other Node's identity. Supply the public key of a distinct key pair configured on the target.

Orbit stores the public key and updates only that peer on the WireGuard hub: it writes the peer's file, removes the previous key from the live hub and adds the new one. The other peers keep their keys, allowed addresses and settings. Only one `node:wireguard-key`, `node:converge`, add or remove runs on the Node or the hub at a time; another call is refused with `operation.target_busy`, so an older run cannot write an old key back. It does not contact the target, run its footprint, or alter its host tunnel. Replacing the key can interrupt the target's connectivity until its locally configured key pair matches. No `--force` or confirmation is required, because this is an explicit setting, not a removal.

The CLI follows the Operation and prints the final result with the request ID. A hub failure is not success: the stored key remains and the Operation fails with the failed step. After a failed write the old peer file stays; after a failed apply the new file is on disk and the live hub still has the old key. Nothing is rolled back. Run the same command again after fixing the hub; sending the same key again repeats the update, and a `node:converge` of the hub publishes the stored key too. A cancelled, interrupted or timed-out run (`operation.timed_out`) ends the same way. Ctrl-C stops following and leaves the Operation running; `operation:show` follows it again. If you run the command from the peer itself, its tunnel can drop after the hub update; follow the Operation from another peer. Activity records the admission with the caller, the target Node and the request ID, never the key material; the outcome is on the Operation.

## Errors

| Code | Meaning |
| --- | --- |
| `node.id_invalid` | The Node is missing or is not a positive integer, and the CLI cannot prompt. |
| `node.wireguard_key_required` | The key is missing and the CLI cannot prompt. |
| `validation.failed` | The key is not canonical base64 for 32 bytes. Nothing changes. |
| `node.wireguard_key_managed` | The target has verified SSH management. Use the managed Node's normal provisioning path. |
| `node.wireguard_key_gateway` | The target holds `gateway`. |
| `node.wireguard_key_conflict` | The key belongs to another Node or the hub, including a concurrent assignment. |
| `node.wireguard_ip_required` | The target has no WireGuard address. Enroll the Node with an address first. |
| `node.provisioning_busy` | Another lifecycle operation holds the Node's name lock. |
| `operation.target_busy` | A `node:wireguard-key`, `node:converge`, add or remove holds the Node or the hub. |
| `swamp.ssh_target_unavailable` | The hub's SSH target is unavailable (503). The stored key remains. |
| `operation.native_failed` | A hub step or the check failed. The stored key remains. |
| `operation.timed_out` | The budget expired. The stored key remains. |
| `http.404` | The Node is unknown. |
| `node_access.required` | The caller has no access grant to the Node. |
