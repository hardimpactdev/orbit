# Command development pipeline

The command development pipeline is the stages every command goes through during development, from prep to a per-host refresh after release. A command goes through them one at a time. Stages 1 to 4 happen in one PR per command change: the spec, the code and the runnable proof cases land together. Each stage below shows its status on `main`, its flow chart, and links to its pages, skill and key files. The stage charts are drafts of the target design; they live in `docs/reference/pipeline/`. The [feature flow](/reference/feature-flow) holds the proof CI job and the case selection list.

## When each flow runs

Each flow has its own trigger. The first three run for a task. The others keep a host ready.

- **Task start.** `task:start` runs for every task group. It takes a free slot in the host's task pool, mints a new identity for it, copies the host's base VM snapshot with that identity and adds its hub peer, runs the release's converge (a no-op on a current image) and starts the task branch. The containers start with the VM.
- **`base` restore.** It runs for each proof batch, and when the author wants a clean fleet.
- **Release.** Publication of the PR, or the end of a group, deletes its VM, seed clone and identity volume, removes its hub peer and deletes its Node.
- **Refresh (stage 6).** It runs in every release, from the step that follows the Swamp load, and daily. It converges the host's base VM, snapshots it and proves the snapshot with one task start.
- **Image build from the recipe.** It runs only for a new host or a new base OS.

## 1. Prep

**Partly built.** A command has one PR, and prep starts it. The chart, docs page and verification cases (the spec) are the first commit of a draft PR. A merged docs PR does not make a command ready. The spec is approved in the draft, and the PR stays one PR through code, proof and merge. Prep changes no code. Swamp owns the flow and its state and the Gateway only authorizes it: an author agent drafts the spec in a task VM, a separate review agent checks it, and Swamp opens the draft PR as the Orbit App. One of two modes, set per flow, decides what happens next. In manual mode there is an optional spec checkpoint: Nick reviews the chart, docs and cases in the draft before code is written, and may check out a development Instance on the PR branch and review there with an agent. In automatic mode there is no checkpoint. The code and the runnable proof cases then follow in the same PR ([stage 4](#4-pr-and-ci)). Built: [`task:prep`](/cli/task/prep) admits one run for a task group and Swamp runs it as one workflow. Its children provision the task VM, run the author turn, up to three review rounds, and open the draft PR as the Orbit App. Built: [`task:prep-fix`](/cli/task/prep-fix) claims a task place for the group, applies the review of the owner as a new commit, checks it, pushes it to the same draft PR and releases the VM again. Not built: the automatic mode, and the detection of the owner's review by the gate check.

About 74 commands have a chart and a page from earlier docs-only PRs. Their old case tables are deleted. When a command's turn comes, its PR reviews and updates the chart and page, and writes the cases file from them.

## 2. Development environment

A task claims one place in the host's task pool and gets a fresh VM and Node identity. The start copies the host's base snapshot and seed, writes the identity and Pi credentials, converges the VM and checks out the task branch. The base holds the agent, Pi, tools, Swamp, a warm checkout of main with its dependencies, and a nested fleet of three Incus containers: Gateway, app-dev and app-prod. Before running cases, the shared proof runner installs the checkout's pinned Ansible collections, renders its Swamp grants and reloads them, so new callbacks and vault key patterns do not depend on the base image's age. Its proof-only Ansible play also records the tested Gateway revision and configures the existing static CLI release catalog from `swamp/proof/cli-release.json`. This checksum-pinned published binary supplies the installable release a real Gateway has; a PR commit has no published release. The CLI under test still runs from the candidate checkout. The static catalog is never configured on a real Gateway. Publication releases the VM, workspace, Node, keys and hub peer. A later build, fix or review round claims again from the base at the published task head. [Capacity ideal state](#capacity-ideal-state) defines the separate CI pool and proof queue.

The Gateway and app-dev see the outer VM's checkout as an Incus disk device, so the author's changes reach them at once. A restore of `base` is a reboot of the containers.

## 3. Proof

**Partly built, with one case so far.** The cases of a command run on that topology. The target: Orbit's own Swamp runs the proof directly and reaches into the task VM over SSH, like every other step. A run restores `base`, syncs the author's code and takes `base` again when something changed. Each batch then restores `base` once, and its cases run one after another without undo, each on its own resources. A case that does not pass triggers a restore. Each case calls the real CLI, checks the real effect and prints a verdict. The first case is the `firewall:allow` traffic case. Built: [`orbit proof COMMAND`](/cli/proof/proof) runs the cases of one command on the author's own task VM, restores `base` first and leaves a clean fleet on the latest code after the last batch. Not built: the converge of the nested Nodes.

## 4. PR and CI

**Partly built.** This stage continues the same PR that stage 1 opened as a draft. The author pushes the command code and the runnable proof cases to its branch, so a reviewer can check that the chart, docs, cases, code and proof cases match. There is one CI: the fast checks (about 2 minutes) plus, for command code, the proof CI (`proof:run` for the affected commands). It runs on every push. The proof CI starts only when a changed path selects a command in `swamp/proof/selection.txt`. Docs, charts and case descriptions never start it. A new push cancels the proof run of the previous push on that PR. When everything is green, the PR leaves draft. In manual mode, Swamp also requests Nick's review, so GitHub notifies him. Then comes the gate: in manual mode, Nick's approving review on the exact head; in automatic mode, a final self-review by a fresh review agent, with at most 3 rounds before the PR switches to manual mode. After the gate, Swamp merges the PR straight into `main` with a squash merge, using a Gateway-minted App token. There is no merge queue and no GitHub auto-merge. CI then runs on `main`. A red `main` is fixed forward and never released. The proof runs only on the PR head, never again before or after the merge. Two PRs for the same command normally conflict, because each edits the command's chart, page and cases file. The second PR rebases, which reruns CI and the proof. Built for manual mode: the ready step ([`task:pr-ready`](/cli/task/pr-ready)), the merge step with the manual gate ([`task:pr-merge`](/cli/task/pr-merge)), and the gate check that calls them. The gate check is the Gateway command `task:pr-gate`. Every minute, like the release check of stage 5, it reads with read-only App tokens the open external Task groups of review-and-merge Projects that have a published PR. A draft PR with a green CI result on its head and a passed handoff check on that commit gets the ready step; a spec-only draft stays a draft. A PR out of draft whose head Nick approved gets the merge step. In automatic mode, a PR out of draft gets a review round, and the merge step once the round on the exact head passed. Each admission is keyed by group and head, so a repeat tick is a no-op, and each starts its own Swamp run. In automatic mode, the Gateway also posts the verdict of each round as a PR comment of the App. In automatic mode, findings start the fix: the author turn, the handoff check and a push, then the next round on the new head. Not built: the proof CI job. A PR that is not in a Task group is outside this flow: the author opens it as `nckrtl` and squash-merges it with `gh pr merge <n> -R hardimpactdev/orbit --squash` when CI is green on the head (the interim).

## 5. Automatic Swamp release

**Built.** The Gateway looks for the newest green commit on `main` and starts one Swamp run: build, snapshot and migrate, switch, load the new workflows and check health. A green commit has `Required checks` and `Gateway release inputs` green in its CI run on `main`. There is no merge queue, so a red `main` commit is never released; `main` is fixed forward. A failed check switches back.

## 6. Per-host task image and seed refresh

**Being rebuilt to the target (Nick, 2026-11-07).** There is no image build per release. Each task VM host (Linux only: beast and shark) bakes its next image from its current one, and the hosts work in parallel. Nothing is copied between hosts. The trigger is every release, from the step that follows the Swamp load, plus a daily run. Per host, Swamp starts one VM from the current image, and one Ansible run converges everything: the outer VM, the warm checkout, and each container, which then gets a new `base` snapshot. The VM is published as the candidate image, with its container disk as the candidate's seed. One idle slot re-enrols from the candidate and passes the claim's ready check; then the candidate is promoted, and the other idle slots re-enrol one at a time. The target is about 3 minutes. A recipe build runs only for a new host or a new base OS.

## Capacity: ideal state

Task work and CI proofs use separate fixed pools on every host. Beast and Shark each have two task places and two CI places. Sabre has zero task places and two CI places. A place holds one VM; VM size does not change the place count. The request kind chooses the pool. Only `proof.run` from an authenticated active `ci-runner` Node and base refresh proofs use the CI pool. Other work uses the task pool.

The pool migration converts the existing Beast and Shark hosts to two task and two CI places each, and Sabre to zero task and two CI places. It removes the replaced host capacity keys. No manual settings change is required.

A task waits for a task place, starts from the base, and deletes its VM after it publishes its PR. A build, fix turn or review round that needs a VM claims a task place again and restores the task branch on a fresh VM from the base. A published PR holds no VM, identity, workspace or place through review. Between two steps the VM stays for the next one, but a group that runs no Operation for 30 minutes loses it, once origin has its approved work ([Release an idle task VM](/reference/tasks#release-an-idle-task-vm)).

CI proofs wait in one first-come-first-served queue. The first PR takes every free CI place, with at least one VM and no more VMs than its batches. Each VM starts fresh from the base. Whole batches are balanced across VMs by measured case times. Each VM restores its fleet and runs its share. Orbit merges every case verdict into one report, then deletes the VMs.

Full pools cause a wait, never a capacity refusal. A two-hour total admission budget ends a wait with a clear timeout. The proof job belongs to `Required checks`: every selected command needs case verdicts, and every case must pass. A PR that selects no command passes without starting a VM. There is no shared reserve, task VM cap layered over resource units, or CI preemption path.

## Change the development pipeline

Change a stage in the place that owns it, and update this page in the same PR.

- **This page:** the stages, their order, their status and their links. Edit `docs/reference/command-development-pipeline.mdx`. A stage that gets built changes its status here.
- **The charts:** edit the `.mmd` file next to the command page, chart first. The stage charts are `docs/reference/pipeline/<n>-<stage>.mmd`, placed on this page with a `flow-at` placement, as the CLI pages rules describe. Run `bin/check-flows`. The rules are in [CLI pages and flow charts](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/README.md).
- **The skills:** `preparing-commands` for stage 1, `verifying-commands` for stages 2 and 3, and `developing-commands` for stage 4 and the code. They link here and to the charts and keep only what an agent must do at its own step.
- **The proof CI job and the selection list:** [Feature flow](/reference/feature-flow).
