# Swamp proof

The flow is stages 2 and 3 of the [command development pipeline](../../docs/reference/command-development-pipeline.mdx); the stage charts own the steps. This page documents the code that runs them today.

## What runs today

Not built: the reset. The code that built the nested fleet in a task VM, took the memory snapshot `base` and restored it was removed. Its replacement is rebuilt as Swamp steps, and until it lands a `proof:run` has no reset behind it. The case runner and the cases below stay. To prove a command, follow [verifying-commands](../../.agents/skills/verifying-commands/SKILL.md).

The target nested fleet inside a task VM is a Gateway that also runs Swamp, `app-dev` and `app-prod`, on a real WireGuard network `10.45.0.0/24` with the hub on the nested Gateway. [`selection.txt`](selection.txt) maps changed paths to the commands whose cases a commit needs; [`orbit proof:run`](../../docs/cli/proof/run.mdx) reads it.

Cases are written in `swamp/proof/<family>/<command>.cases.yaml` and run by the shared runner in [`runner/`](runner/runner.py) ([format](../../docs/reference/verification-cases.mdx)). A case calls the real candidate CLI, checks the real effect and prints a verdict. The first file is [`firewall/allow.cases.yaml`](firewall/allow.cases.yaml): a real `firewall:allow` opens real traffic. `orbit proof:run` selects a command with [`selection.txt`](selection.txt) and runs its cases file; a command without one is uncovered.

## Ready copies: the contract

One step makes ready copies, in stage 6. Anything else that stores or restores a nested fleet (the topology seed, B3) uses these names and keys.

- **Names:** `fleet-ready-gateway`, `fleet-ready-app-dev`, `fleet-ready-app-prod`. Stopped Incus VM copies in the same project and pool as the fleet.
- **Keys** on each copy: `user.ready.set` (one identity for the three), `user.ready.role`, `user.ready.made` (UTC, the copy), `user.ready.minted` (UTC, when the fleet's credentials were minted: the 20 h age counts from this), `user.ready.attempt`, `user.ready.inputs` (a digest of the build inputs and the agent pin; a different digest makes the set stale), `user.ready.hwaddr`, `user.ready.ipv4`, `user.ready.subnet` (the network's `ipv4.address`). The Gateway copy also has `user.ready.nodes` (JSON of Node name to Gateway Node id). `user.ready.complete` equals `user.ready.set` and is written by the last step of `ready`, after the restarted fleet passed its checks; a failed `ready` deletes its half-made set, and a set without it is not used. `ready` copies only a fleet whose readiness check passed.
- **Not on a copy:** no `user.orbit.e2e.*` label, no `eth0` device, no `orbit-source` device and no `user.ready.mounts` key. A restore adds the label and the NIC for the generation it restores into. A copy holds its own checkout at `/home/orbit/orbit`; a restore syncs the candidate's code into it by rsync.
- **Stateful, no snapshots.** The guests have `migration.stateful=true` and a root `size.state` equal to `limits.memory`, set while they are stopped (`ready` on the originals, a restore on each restored guest). A copy and a restore use `incus copy --instance-only`, so a copy never carries the `base` snapshot of an earlier fleet.
- **No secret.** The proof Swamp Club key is never in a copy. `ready` deletes it from the running Gateway, scans every file of all three guests (`find / -xdev`, no size limit, a grep error fails) for the key and stops with the paths if one holds it (the running fleet gets its key back either way), runs `fstrim -av` under `timeout` so the freed blocks of the deleted key are discarded from the disk image that every task VM clones (the output is in the receipt), and checks that all three guests report `Stopped` before it copies. The restore pushes the key in after the Gateway agent is up, as the full build does, then restarts Swamp serve and the worker.
- **Source.** The Gateway's database and its `.env` key belong to the source tree it was built from. Today the fast reset takes that state (`.env`, `storage`, `bootstrap/cache`, the agent manifest) and the attempt lease from the source of the active generation, so it needs an active generation whose network has the subnet of the copies. A fresh task VM with only seed copies is not covered yet: it needs the runtime state of the source stored with the copies and a network and lease created for it.
