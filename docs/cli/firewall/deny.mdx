Deny incoming traffic on one active Linux Node. Without a source or protocol, the rule denies both TCP and UDP from anywhere, including WireGuard peers. It does not restrict ports published by Docker; see the [firewall overview](/cli/firewall).

## Usage

```bash
orbit firewall:deny <port> --node=ID [--from=SOURCE] [--protocol=PROTO] [--label=TEXT] [--idempotency-key=KEY] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `port` | yes | Destination port from 1 through 65535, or an inclusive ordered range such as `8000:8100`. Service names are not accepted. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--node=ID` | required | Positive numeric target Node ID. The calling Node needs an access grant to it. |
| `--from=SOURCE` | `any` | Source IPv4 or IPv6 address, CIDR, or `any`. An address or CIDR affects its address family only; `any` affects both. |
| `--protocol=PROTO` | both | `tcp` or `udp`. Omit it for both; `any` is not an accepted value. |
| `--label=TEXT` | none | Description of at most 255 characters. See [labels and comments](/cli/firewall#rule-identity). |
| `--idempotency-key=KEY` | automatic | Override the transport retry key to replay a start with the same key, target and input, rather than start another Operation. See [keyed starts](/reference/operations#retry-a-start-with-a-key). Normal repeats need no key. |
| `--json` | off | Print the final Operation or admission error as JSON, without prompts or progress output. |

```bash
orbit firewall:deny 25 --node=7 --from=203.0.113.9 --label=scanner
orbit firewall:deny 6000:6100 --node=7 --protocol=udp
```

In a terminal, an omitted port is prompted for and an invalid answer is asked again. An omitted Node is selected from an interactive data list of active Linux Nodes. Ctrl-C or end of input at either prompt exits 1 with `input.cancelled` and creates no Operation. Without a terminal, or with `--json`, a missing port or Node is refused with `firewall.port_invalid` or `firewall.node_id_invalid`.

<Warning>
Orbit refuses a deny whose port or range includes SSH port 22, the recovery SSH port, the WireGuard port, or a port needed by one of the target Node's roles (`firewall.protected_port`). This applies to every source and protocol, even a single unrelated address: a source range can cover the Gateway or another Node. Protection is based on the port, not an assumption about which source is safe to block.
</Warning>

Only one firewall change can run on a Node at a time (`operation.target_busy`). An allow with the same port, protocol and normalized source conflicts with the deny (`firewall.rule_conflict`). A both-protocol rule and a single-protocol rule on the same port and source also conflict (`firewall.rule_overlap`), with either action and in either creation order. To change the scope or action of a recorded rule, remove it and create it again. Labels do not identify rules. Changing only the label reuses the record. If the rule is already correct, its UFW lines keep their comments and the command succeeds with `firewall.rule_exists`.

Narrower sources take precedence over broader sources, regardless of action. An allow for one source can override a broad deny; a deny for one source can override a broad allow. Operator rules sit above Orbit's broad managed rules, so a deny without `--from` also blocks WireGuard peers. To restrict a port without an exposure window, add the allows first, then the deny. See [rule ordering](/cli/firewall#order-on-the-node).

Orbit records the rule and follows the Operation to its final outcome. Human output shows progress, the result, and the Operation and request IDs. Piped output has no animation or escape codes. JSON contains one final Operation, including a successful skip reason or execution failure; a refusal before admission is an error envelope. Success exits 0; a handled failure exits 1.

Repeating the same rule reuses its record and checks the Node in a new Operation. Correct lines are left untouched; missing or misplaced lines are repaired. Only a fully correct rule succeeds with `Skipped — already applied (firewall.rule_exists)`. UFW must still be active and the final check must pass. An inactive firewall is refused, not enabled.

Orbit manages transport retries with one key per logical start. An intentional new attempt gets a new key; ordinary use does not require managing keys.

A failure keeps the rule visible as failed. Lines added before the failure remain, and a line deleted for reordering may be absent. Nothing is rolled back. After fixing the cause, repeat the command to repair the rule without duplicates. A keyed replay returns the old Operation, including a failure; omit the old key or use a new key for a repair attempt.

## Errors

Input and admission refusals create no Operation or rule and change nothing on the Node. Execution failures keep the failed rule and any partial changes. Shared response details are defined by [Operations](/reference/operations#start-an-operation) and the [firewall family](/cli/firewall#error-codes).

| Code | Meaning |
| --- | --- |
| `input.cancelled` | Ctrl-C or end of input at a prompt; no request to create a rule is sent. |
| `firewall.node_id_invalid` | Missing noninteractive Node, invalid positive numeric ID, or no active Linux Node available for selection. |
| `firewall.port_invalid` | Missing noninteractive port, a service name, an out-of-bounds port, or an invalid or reversed range. |
| `firewall.source_invalid` | The source is not `any`, an IP address, or a valid CIDR. |
| `firewall.protocol_invalid` | The supplied protocol is not `tcp` or `udp`. |
| `validation.failed` | Invalid request input, such as a label longer than 255 characters or a malformed idempotency key. |
| `node_access.required` | The calling Node has no access grant to the target; the response identifies the serving Node. |
| `firewall.platform_unsupported` | The target is not Linux; refused before storing a rule or contacting the Node. |
| `firewall.protected_port` | The port or range intersects a protected port, with any source or protocol. |
| `firewall.rule_conflict` | An allow already has the same port, protocol and source. |
| `firewall.rule_overlap` | A both-protocol rule overlaps a single-protocol rule on the same port and source. |
| `operation.target_busy` | Another firewall change holds the Node; `details.operation_id` identifies it. |
| `operation.idempotency_conflict` | The key was used for another target or input; no new Operation starts. |
| `firewall.backend_inactive` | UFW is inactive; no rule is applied on the Node. |
| `firewall.verify_failed` | The final check does not find every expected line in the required order. |
| `operation.native_failed` | SSH, a UFW mutation, or another execution step fails before returning a public check result. |

`firewall.rule_exists` is a successful skip reason, not an error.
