Change only the supplied fields of an installed Process, keeping its ID, name, owner, and desired state. A running Process restarts in place; a stopped Process stays stopped. This is not destroy followed by create. It can interrupt a running service and discard a replaced Docker container's writable layer. It does not delete named volumes or require destructive consent. Back up and migrate container-layer data before updating a stateful container; see [Move data before removing an override](/reference/processes-and-schedules#move-data-before-removing-an-override).

```bash
orbit process:update <process> [--runtime=systemd|docker] [--command=ARG ...] [--image=IMAGE] [--working-directory=PATH] [--environment=NAME=VALUE ...] [--port=HOST:CONTAINER ...] [--volume=SOURCE:TARGET ...] [--restart=POLICY] [--keep-alive] [--no-restart-on-deploy] [--user=NAME] [--idempotency-key=KEY] [--json]
```

| Argument or option | Default | Meaning |
| --- | --- | --- |
| `process` | required | Numeric Process ID for an installed Process. |
| `name` | required with `--project` | Definition name in the Project form. |
| `--project=ID` | none | Select the Project-definition form instead of an installed Process. |
| `--for=production` | none | Required only with `--project`; refused for an installed Process. |
| Runtime options | unchanged | Only supplied options change an installed Process. Omitted runtime, command, image, restart policy, keep-alive, and restart-on-deploy settings keep their values. `--keep-alive` sets true; `--no-restart-on-deploy` sets false. |
| `--working-directory=PATH` | unchanged | Set an explicit directory. Use API `working_directory: null` to restore the runtime default. |
| `--environment=NAME=VALUE` | unchanged | Repeat for each Docker variable. Replaces the whole map when supplied. Values can contain `=`. |
| `--port`, `--volume` | unchanged | Supplied bindings or mounts replace that whole list. Use the API or SDK to send an empty list to clear it. |
| `--user=NAME` | unchanged | Accepted only for an installed Node systemd Process. Refused for Project definitions. |
| `--json` | off | One final JSON response, without prompts or progress output. |

The command uses the runtime fields and validation of [`process:create`](/cli/process/create), but sends only supplied options. It accepts no `--instance`, `--node`, `--preset`, or `--start`. The Gateway validates the resulting specification before mutation. Both forms refuse supplied redaction markers before a request (`process.redacted_value`). A Docker ports-only update needs no image, command, or runtime option. The Gateway API is `PATCH /api/v1/processes/{process}`; the SDK preserves omission, explicit false, and empty lists. See [Update in place](/reference/processes-and-schedules#update-in-place) for locks, ownership checks, and runtime failures.

For example, change a Docker binding while retaining its restart policy, environment, mounts, and working directory:

```bash
orbit process:update 41 --port=10.44.0.20:6380:6379
```

This example updates an ordinary Process. A [Valkey Database server](/reference/database-servers#update-a-valkey-servers-image) keeps its ACL command, mounts and health check during an image update. Its owning page describes the allowed update and the validation order.

In an interactive terminal, an omitted target uses a finite `Process` selector (`process.update.target`) populated by the read-only Process list, with choices labeled by ID, name, and owner and no default. Selection returns the numeric ID. With `--project`, use a `Process definition` selector populated by that Project's definitions and return the name. An empty list reports `No Processes found.` (or `No Process definitions found.`) and returns `process.id_invalid` (or `process.name_required`) without mutation. A slow lookup shows indeterminate waiting feedback. Updates do not prompt for omitted runtime fields, including in the Project-definition form. Ctrl-C or EOF returns `input.cancelled` before mutation. JSON and noninteractive calls never prompt. Invalid supplied fields use the create validation codes, including `process.command_invalid`, `process.environment_invalid`, and `process.option_invalid`.

The synchronous Gateway request shows one indeterminate operation with labels `Update Process`, `Updating Process`, and `Updated Process`. It does not invent separate remote stop, install, or start progress stages. Human success uses the Process detail renderer with `ID`, `Name`, owner, runtime, desired state, runtime status, working directory, restart policy, and keep-alive; it never prints environment values. JSON success uses the existing Process response shape with the same ID, lifecycle fields, redacted `runtime_config.environment` map, and request ID. Failure uses the standard failure renderer or JSON `error` envelope, returns nonzero, and prints no success result. Success returns zero. `process.operation_busy` and `process.runtime_lock_failed` retain their existing meanings.

An update preserves every targeting public or private Process Route when its single resolved TCP listener keeps the same address and host port. Otherwise `process.route_upstream_changed` (409) names the blocking Route and changes nothing. Environment-only and image-only updates keep the Route active. Destroy still returns `process.has_routes` while a Route targets the Process.

After the Gateway accepts an update, the new specification remains stored even if runtime convergence fails. A lost response or Gateway crash can leave convergence incomplete. Inspect the Process and retry the identical request after the lock is available; equality with the stored specification must not skip stale or unfinished runtime work. An already completed identical retry does not restart an unchanged runtime. If someone has since changed the specification, resolve that newer intent before replaying an old update. See [Persisted intent and retry recovery](/reference/processes-and-schedules#persisted-intent-and-retry-recovery) for the guarantees and limits.

With `--project`, the CLI sends only runtime options you supply. Omitted command, runtime, restart policy and other fields keep their stored values, including captured preset metadata. The command reads no definition and sends no redaction marker. `--for` remains required. The definition UUID stays the same. A different `--runtime` replaces the runtime specification, so supply the new command and other required fields.

These clear options require `--project`. A set option and its clear option cannot be combined.

| Option | Result |
| --- | --- |
| `--clear-working-directory` | Restore the runtime's default directory. |
| `--clear-restart` | Restore restart policy `never`. |
| `--clear-keep-alive` | Restore `keep_alive: false`. |
| `--clear-restart-on-deploy` | Restore `restart_on_deploy: true`. |
| `--clear-environment-file` | Restore the owner's default environment file. |
| `--clear-environment` | Clear the entire environment map. |
| `--clear-ports`, `--clear-volumes`, `--clear-required-mount-paths` | Clear that entire list. |

To remove one environment key, supply the remaining map with repeated `--environment=NAME=VALUE` options. Keys you omit are removed; supply the actual remaining values. The CLI does not fetch or replay private values. The same replacement rule applies to supplied port and volume lists. Required runtime fields and captured preset metadata cannot be cleared.

A definition edit records intent only. A later deployment of the default development container applies it to that Instance's linked Processes; new clones inherit it, while existing clones keep their Processes. Production copies keep their captured specification. Progress labels and the Project-definition response stay the same.

This CLI requires a Gateway release containing PR #3412. An older Gateway treats the body as a replacement and can silently erase omitted fields. Release that Gateway and pass its health checks before releasing this CLI. Gateway status reports a commit SHA, without an ordered contract version or sparse-update capability flag; the CLI cannot establish commit ancestry from that response alone.

```bash
orbit process:update <name> --project=ID --for=production [--runtime=systemd|docker] [--command=ARG ...] [--image=IMAGE] [--working-directory=PATH] [--environment=NAME=VALUE ...] [--port=HOST:CONTAINER ...] [--volume=SOURCE:TARGET ...] [--restart=POLICY] [--keep-alive] [--json]
orbit process:update <name> --project=ID --for=development [--clear-working-directory] [--clear-restart] [--clear-keep-alive] [--clear-restart-on-deploy] [--clear-environment-file] [--clear-environment] [--clear-ports] [--clear-volumes] [--clear-required-mount-paths]
orbit process:update vp-dev --project=1 --for=development --keep-alive
orbit process:update queue --project=1 --for=development --clear-working-directory --clear-environment
orbit process:update queue --project=1 --for=production --command=/usr/bin/php --command=artisan --command=queue:work --restart=on-failure
```

Development container definitions accept the supported runtime command names described in [create](/cli/process/create). The rendered unit resolves each name using the current runtime.
