Does: change these recorded fields, preparing the apps folder or withdrawing obsolete task-host input rules when needed. Does not: enroll or upgrade a Node, change roles or Instances, move checkouts, drain or delete VMs, or accept arbitrary settings.

## Usage

```bash
orbit node:update <node> [--name=NAME] [--platform=PLATFORM] [--apps-path=PATH] [--task-vms=JSON] [--idempotency-key=KEY] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Positive numeric Node ID; omission follows the shared [finite searchable selector contract](/reference/cli-ux#prompt-selection). |

| Option | Default | Meaning |
| --- | --- | --- |
| `--name=NAME` | unchanged | Unique registry label: ASCII letters, digits, dashes and underscores, at most 63 characters. |
| `--platform=PLATFORM` | unchanged | `linux`, `macos` or `ipados`, only on an unmanaged Node with no pinned SSH host fingerprint and no role. |
| `--apps-path=PATH` | unchanged | Set the [apps folder](/reference/node-settings#set-the-apps-root); `--apps-path=` unsets the stored path. |
| `--task-vms=JSON` | unchanged | Replace the [typed host settings](/reference/node-settings#task-vm-fields); `--task-vms=null` removes the setting. |
| `--idempotency-key=KEY` | none | Shared [request retry contract](/reference/operations#retry-a-start-with-a-key). |
| `--json` | off | Shared [machine-output contract](/reference/cli-ux#input-and-output-modes); the result is the updated Node for a record save, or the terminal Operation for Node work. |

```bash
orbit node:update 3 --name=vpn
orbit node:update 5 --platform=ipados
orbit node:update 7 --apps-path=/mnt/apps
orbit node:update 9 --task-vms='{"cidr":"10.251.77.0/24","task_places":2,"ci_places":2,"pool":"orbit-tasks","image_alias":"orbit-task-base"}'
orbit node:update 7 --apps-path=
```

Supply at least one field option. Omitted fields stay unchanged. Target access follows [Node authority](/cli/node#authority), and edits use the existing [lifecycle locks](/reference/node-provisioning#one-lifecycle-owner-per-node-name) for the current name and any new name.

### Record-only changes

A name or unmanaged-platform edit, adding task-host settings, or changing host settings without removing the host or changing its bridge or CIDR saves at once without contacting the Node or starting an Operation. Unsetting the apps path without an active `app-dev` role also needs no Node work. A name is only a label: addresses, keys, SSH identity and roles stay the same.

Task-host settings use the selected Node's identity and accept only the fields in the linked table. Preserve the current host values when replacing the object. `task_places` and `ci_places` are separate counts from 0 to 64; lowering either count removes no live VM claim. An `app-dev` role alone does not make a task VM host. [Host retirement](/reference/compute-drivers#add-a-task-vm-host) owns VM cleanup; this command does not perform it.

### Changes that need Node work

Orbit prepares a changed apps folder and withdraws old task-host input rules when removing the host settings or changing its bridge or CIDR. Both actions require Linux. Settings in such a request commit only after all required work succeeds; a name or platform supplied in the same request commits immediately.

Folder preparation creates missing parents and the folder, then checks that it is a real directory owned by the managed user and group with mode `0755`. It changes the folder itself, not its contents. Unsetting the path with active `app-dev` prepares the default, `<managed-user-home>/apps`, without storing the default path. Existing Instance checkouts stay where they are; new development Instances use the effective folder. [Node settings validation](/reference/node-settings#validation) owns path restrictions.

Task-host withdrawal removes only firewall rows carrying the catalog's task-host DHCP/DNS input comments, including duplicate and IPv6 rows, and checks that none remain. It does not repair other firewall rules. When both actions are needed, withdrawal completes before folder preparation begins.

On failure, old deferred settings remain, but an already committed name or platform does not roll back. Completed harmless folder work and any rules already withdrawn remain. After fixing the cause, the same command makes a fresh attempt and completes the remaining work safely.

A request whose values are all already stored succeeds with `Skipped — already set (node.unchanged)`, with no write, Operation or Node contact.

## Errors

Admission refusals create no Operation and leave records unchanged.

| Code | Meaning |
| --- | --- |
| `node.reference_required` | The required Node was omitted; input handling follows the [CLI standard](/reference/cli-ux#input-and-output-modes). |
| `node.id_invalid` | The supplied Node ID is not a positive integer. |
| `http.404` | No Node has the supplied ID. |
| `node_access.required` | The caller has neither Gateway authority nor a grant to the target; see [Node authority](/cli/node#authority). |
| `node.option_required` | No field option was supplied. |
| `node.name_required`, `node.platform_required` | The supplied name or platform is empty. |
| `node.setting_invalid` | The task-host option is not a typed JSON host object or `null`. |
| `validation.failed` | The name is malformed or taken, or the platform is unknown. |
| `node.platform_managed` | A platform edit targets a Node with a pinned SSH host fingerprint or a role. |
| `node.provisioning_busy` | Another lifecycle change holds the current or requested name's lock. |
| `node.settings_*` | A setting fails the [owning validation and failure-code tables](/reference/node-settings#failure-codes); `node.settings_platform_unsupported` refuses Node work outside Linux, and `node.settings_root_failed` reports failed folder preparation. |

Execution failures retain the failed phase and error in the Operation.
