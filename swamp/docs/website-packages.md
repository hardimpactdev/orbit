# Manifest range policy

Maintenance policy is non-secret project data. Execution follows the binding
[Swamp shape guide](swamp-shape.md); the old task-driver and receipt lifecycle
is retired.

## Manifest range styles

Batch targets choose exact locked versions while preserving each direct
requirement's operator and precision: `~7.4` becomes `~8.0`, `^1` becomes `^2`,
and a pin stays a pin. A major target already admitted by the declaration keeps
it unchanged, including unions, lower bounds and wildcards. Routine updates also
keep the declaration. Security updates raise the floor to the fixed version; if
the existing precision cannot express that floor, the target stays blocked.
Prerelease/build metadata, uppercase `V`, and compound ranges that do not admit
the target also stay blocked. A bare Composer partial pin must admit the exact
target: `1.2` can become `2.3` for `2.3.0`, but blocks `2.3.4`. The same npm
partial accepts `2.3.4`.

Planning filters every eligible version for a writable declaration before the
joint solve. Age and major eligibility apply first. Unsupported Expo-aligned
ranges block that SDK candidate before resolution; unrelated updates remain
eligible. A typed range, alignment or registry-miss rejection permits an older
release. Invalid target data and deterministic registry misses block only their
candidate. Transient registry failures during candidate metadata lookup stop
planning instead of selecting an older SDK; aborts always propagate. Errors
during the joint resolver or audit remain solver exclusions. Each JavaScript
plan reads a package's release metadata and each Expo version's catalog once per
configured path, reusing them through solving. A new plan or batch reads fresh
metadata. Blocked records retain distinct reasons from the newest rejected
options.

JavaScript refreshes lock metadata through the package manager; any resolved
version movement fails the batch.
