With signed power enabled, the Gateway sends the wake to the Node once, over its WebSocket, in one `instance.wake` Operation. A Route visit waits while that Operation runs, up to `ORBIT_VISIT_WAKE_WAIT_SECONDS` (30 s by default), and then gets the app's own response to the original request.

Wake one sleeping development container Instance: a clone, a Project's default, or a nested-fleet Instance. A visit to its Route does the same, so you rarely need this command. Planned: a production Instance's live release container wakes the same way, and Caddy holds its visitor instead of the Gateway ([Production containers](/reference/production-containers#sleep-and-wake)). A deployment of a sleeping Instance wakes it too. After an [automatic deployment](/reference/deployments#automatic-development-defaults), a default may sleep again at the next sweep. A clone or a task copy of an asleep default needs no wake: it copies the default's seed snapshot. [Sleep and wake](/reference/development-containers#sleep-and-wake) explains the lifecycle.

## Usage

```sh
orbit instance:wake 42
orbit instance:wake 42 --json
```

| Argument or option | Meaning |
| --- | --- |
| `instance-id` | Numeric Instance ID. |
| `--idempotency-key=KEY` | Reuse a key to retry this operation start. |
| `--json` | [Machine output](/reference/cli-ux#input-and-output-modes). |

Orbit resumes a frozen container: its processes continue where they stopped, and nothing boots. First, while the container is still frozen, Orbit reads back from swap the pages its processes had resident when it fell asleep, within 2 seconds ([Prepared restore](/reference/prepared-restore)). The Gateway first asks the Node to do this and resume it, within 6 seconds, unless it is a nested-fleet Instance: that takes the run below. When that works, the Operation in the answer has already succeeded, and its result has `trigger_seconds` and `confirm_seconds` instead of the resume's seconds. A visit waits for this in its own request and then gets the app. Otherwise the wake runs as below, in the same Operation. When FrankenPHP does not answer after 10 tries one second apart (about 20 seconds at most), Orbit stops the container and starts it. A container found stopped (after a host reboot, or a sleep that fell back to a stop) is started: T3, FrankenPHP and each Process that ran before the sleep start with it; a stopped Process stays stopped. Orbit waits until each of them runs and the app answers. An answer of 500 or above gets up to 5 more seconds to clear; after that the app is served as it is. Then it removes the asleep marker, and the Route serves the app again. In an Instance with a T3 server, such as a clone, the wake then waits until T3 answers, and a visit waits for it too. A default has no T3 server, so its wake ends when the app answers. The result names the path: `wake` is `resumed`, `restarted_after_resume`, `started` or `already_running`; `marker_found` says whether the marker was there; a resume adds `resume_seconds` and `web_probe_seconds`. `restore_mode` is `prepared` or `ordinary`, and `prepared_restore.status` is `complete`, `partial`, `skipped`, `timed_out` or `not_applicable`; a restore that falls short never fails the wake. `ready_at` is when the app answered and the marker went, with its resolution in `ready_at_resolution_seconds`; it is not the Operation's end, and Operation list and show return it. A successful wake also renews the Gateway's T3 session at once when it ends within 7 days or ended during the sleep, and the T3 sessions Orbit holds for Nodes there ([held sessions](/reference/conn#held-sessions)) that end within 7 days. The [idle sleep](/reference/development-containers#sleep-and-wake) counts the end of a wake as activity, so a woken Instance gets a full idle window before it can sleep again. A wake does not restart the idle sleep's watch of the Instance: that watch starts once.

The Gateway setting `ORBIT_EXECUTOR_WAKE_ENABLED`, off by default, selects the [executor wake](/reference/executor#the-wake-inside-the-request) for container Instances. When enabled, Orbit records or joins the wake before sending its signed order. A Route visit waits for that wake, as above. Background work finishes the Operation without a deferred wake or Python/SSH path.

With [signed power routing](/reference/executor#signed-power-delivery), the WebSocket is the only way the order reaches the Node. If the Node has not accepted the order after 6 s, the order has expired and the wake fails with `executor.not_accepted`. If the Node accepted it but sent no result, the wake ends `interrupted` with `executor.result_unknown`. A known frozen Instance wakes through the engine that froze it, even if the settings change. The Node-level Process wake keeps its existing behavior.

There is one wake per Instance at a time. A second caller joins the open wake and gets the same Operation.

Waking an Instance that is awake changes nothing and also succeeds, except a nested-fleet default: one that no sleep froze, running or stopped, is refused with `instance.sleep_unsupported`. A running nested-fleet clone takes its start, which checks it and changes nothing that runs. A failed wake keeps the asleep marker. A visit gets a plain-text `503`, such as `The wake failed (instance.container_start_failed). Reload the page to try again.` A reload, or this command, starts a new wake. [Wake](/reference/app-dev-runtime-hibernation#wake) lists every answer.

The API is `POST /api/v1/instances/{instance}/wake`; it starts an `instance.wake` Operation, or an `instance.start` Operation for a stopped clone of a nested-fleet default. The MCP tool is `instance-wake`.

## A nested-fleet Instance

A nested-fleet Instance, the default or a clone, sleeps frozen and never stopped. The freeze keeps its inner fleet, its tunnel `wg-nested` and the Club key in the container's `/run`, so its wake's run resumes it and starts no fleet. The run also closes the swap that the sleep opened for the inner fleet's cgroups. Orbit takes this path while the Instance's last sleep froze it and no wake since found it stopped.

A wake never boots a stopped nested-fleet container: a boot without the Club key and the tunnel gives an inner fleet that cannot become ready. When a host reboot ended the freeze, the wake fails with `instance.nested_fleet_stopped`, and the marker stays. The next wake of a clone then takes the start below, which removes the marker. A nested-fleet default starts only through its [deployment](/cli/instance/deploy), which removes the marker too.

**Known limit.** On a Route visit after such a reboot, a reload starts the clone's start (about 90 seconds). The visit waits only 30 s, so it gets `The Instance is still waking. Reload the page in a moment.` until the start ends. Follow the start with [`operation:show`](/cli/operation/show), or wake the clone with this command.

## A stopped nested-fleet clone

A host reboot, an out-of-memory kill or a stop by hand can leave a clone of a nested-fleet default stopped, and its container does not start at boot. For such a clone, this command starts an `instance.start` Operation instead of a wake. Orbit starts the container through the same checks as a deployment's start, puts the nested Gateway's Club key into the container's `/run`, and then starts the inner fleet as the clone's create does: the nested containers, the operator tunnel `wg-nested`, and a wait for Doctor and the three agents. The result gives `power_state`, `nested_fleet_club_key` (what the start did with the key) and `fleet_seconds` (the time of the fleet start). It also writes the copy's proxy bypass for units and login shells; when that changed something and this start booted the copy, T3 restarts once to read it. A start of a copy that runs changes nothing that already runs, and keeps its T3. [A stopped nested-fleet clone starts](/reference/development-containers#a-stopped-nested-fleet-clone-starts) has the details.

A stopped nested-fleet default does not take this path: it starts only through its deployment.

When signed power routing is on (`ORBIT_EXECUTOR_POWER_ENABLED`, off by default), the wake runs through the Rust executor on the same Operation: the Gateway sends a signed order on the Node's WebSocket and waits up to six seconds for the result ([Signed power delivery](/reference/executor#signed-power-delivery)). An executor refusal or failure fails the wake; it is never shown as success. When the executor finds the container stopped, Orbit boots it in the same Operation. An Instance that a Python sleep froze still wakes through Python. With routing off, this command uses the Python path unchanged, except for an Instance that the executor froze: it still wakes through the executor ([Switching engines](/reference/executor#switching-engines)).

## Errors

| Code | Meaning |
| --- | --- |
| `instance.id_invalid` | The Instance ID is not a positive number. |
| `operation.kind_unavailable` | The Instance has no container. |
| `instance.sleep_unsupported` | The Instance is not a development Instance, or it is a nested-fleet default that its last sleep did not freeze. Such a default starts only through its deployment. |
| `instance.nested_fleet_stopped` | The wake found a nested-fleet container stopped, for example after a host reboot. Nothing booted, and the marker stays. Wake a clone again to start it; deploy a default. |
| `instance.start_unsupported` | The start of a nested-fleet clone was called for another Instance. |
| `instance.nested_club_key_missing` | The start of a nested-fleet clone found no Club key on the Gateway. Its inner fleet cannot become ready, so the run did not start. |
| `instance.container_fleet_check_failed`, `instance.container_fleet_resume_failed` | The inner fleet of a nested-fleet clone did not start or did not become ready. The failure's detail says why. |
| `instance.lifecycle_busy`, `operation.target_busy` | Other lifecycle work runs on the Instance. |
| `instance.container_start_failed` | The container or one of its units did not start, or the asleep marker could not be removed. |
| `instance.power_helper_busy` | Another power action on the Instance's Node stayed busy past the wait, for example a restore stuck in disk I/O. The marker stays. |
| `instance.power_helper_failed` | The power helper refused its input or crashed. The asleep marker stays; the run's output has the helper's error. Retry, or read the Node's journal. |
| `instance.web_unready` | FrankenPHP gave no answer within about 30 seconds. The marker stays. |
| `instance.container_frozen_unmanaged` | The kernel held the container frozen while Incus called it running, and the thaw did not end within 5 seconds. Nothing ran in the container, and the marker stays. See [a freeze that Incus lost](/reference/prepared-restore#a-freeze-that-incus-lost). |
| `instance.container_exec_timeout` | A nested-fleet container did not answer a command within 10 seconds at its start. The marker stays. |
| `instance.t3_unready` | T3 did not answer within about 30 seconds. The app already serves: the marker is gone, and the Instance is recorded as running. |
| `executor.wake_refused` | Executor wakes are enabled and the Node refused the order. The Operation keeps the refusal reason. |
| `executor.wake_failed` | Executor wakes are enabled and the Node reported a failure. The Operation keeps the executor result. |
| `executor.wake_timeout` | No executor result confirmed the wake before its queued completion. The Node may still finish; a later result does not reopen the Operation. |
| `executor.sign_failed` | The Gateway could not sign an order. Nothing was sent. |
| `executor.publish_failed` | The Gateway could not send the signed order. Nothing reached the Node, and the Instance is free for a new wake. |
| `executor.not_accepted` | The Node did not accept the signed order before it expired. It cannot act any more, and the Instance is free for a new wake. |
| `executor.result_unknown` | The Node accepted the order but sent no result within 6 seconds. The Operation ends `interrupted`, and the Instance stays locked until a late result settles it. |
