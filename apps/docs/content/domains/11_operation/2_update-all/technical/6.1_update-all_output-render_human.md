# Human Renderer: `orbit update:all`

[Back to `update:all` technical contract.](1_update-all.md)

This page describes the human-rendered terminal output for `update:all`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update:all` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

The header is `Updating Orbit nodes`. `update:all` always begins with two check
steps before any side effect, so the tree renders immediately with both steps
idle:

```text
  ┌  Updating Orbit nodes
  │
  ○  Checking for updates
  │
  ○  Checking fleet versions
  │
  └  Working...
```

### Check steps

| Step | Active | Settled |
| --- | --- | --- |
| `Checking for updates` | Blinking row with `Checking` | `Done: latest version is <latest_version>` |
| `Checking fleet versions` | Blinking row with `Checking` | `Done: all nodes running on <latest_version>` when current, or `Done: <outdated_node_number> outdated nodes found` |

Each check row blinks while active and shows the `Checking` message beside the
row label. `Working...` is only the dim pending footer.

### All-current short-circuit

When the fleet-version probe finds 0 outdated nodes, the gateway and workload
phases are skipped entirely. Only the two check rows appear; no gateway or node
rows are added. The footer settles to `Skipped: <version> is already installed
on all nodes`:

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: all nodes running on 0.1.131
  │
  └  Skipped: 0.1.131 is already installed on all nodes
```

### Per-node update rows

When outdated nodes are found, the tree is extended as soon as the fleet check
settles. The `check-fleet-versions` done step carries `update_targets`: a typed
list of row names in stable selected order from the gateway probe —
`gateway`, `local`, then selected workload node names in
`FleetUpdateTargetSelector` order (the keys from `FleetVersionReport::nodeVersions`).
When the caller is a registered non-gateway node, that node name appears in
the workload list in addition to the `local` CLI row.
The renderer reveals every listed row immediately and preserves that workload
order in the tree. Revealed local and workload
rows stay dim on `Waiting` until the gateway row succeeds. The gateway updates
first as the fleet version ceiling. While the gateway row is active, revealed
local and workload rows do not animate.

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ○  gateway
  │
  ○  local                    Waiting
  │
  ○  agent                    Waiting
  │
  ○  beast                    Waiting
  │
  └  Working...
```

Once the gateway phase starts, the gateway row animates while local and workload
rows remain on `Waiting`:

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ◉  gateway                  Downloading 0.1.131 assets
  │
  ○  local                    Waiting
  │
  ○  agent                    Waiting
  │
  ○  beast                    Waiting
  │
  └  Working...
```

After the gateway succeeds, fan-out rows advance in parallel:

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ●  gateway                  Done
  │
  ◉  local                    Downloading 0.1.131
  │
  ◉  beast                    Downloading 0.1.131
  │
  └  Working...
```

#### Per-node sub-stage vocabulary

Each node row advances through sub-stages as the gateway emits ordered journal
sub-steps. The active sub-stage is shown in the row; when the node settles the
row shows `Done`, `Done (<n> issues)`, `Skipped: already up to date`,
`Skipped: Orbit Desktop is not running`, or
`Skipped: Orbit Agent is not running`.

| Node kind | Sub-stages (in order) | Settled |
| --- | --- | --- |
| gateway | `Downloading <v> assets` → `Updating gateway app` → `Replacing cli binary` → `Running doctor` | `Done` or `Done (<n> issues)` |
| local / workload node | `Downloading <v>` → `Replacing cli binary` → `Running doctor` | `Done`, `Done (<n> issues)`, `Skipped: already up to date`, `Skipped: Orbit Desktop is not running`, or `Skipped: Orbit Agent is not running` |

The gateway row represents the packaged gateway app update and the CLI binary
replacement on the gateway. Each updated CLI node (gateway, local, and
workload) runs a post-update `orbit doctor` verify; a non-zero issue count is
folded into the node's `Done (<n> issues)` settle text and never fails the node.

A node already on the desired CLI artifact settles immediately to `Skipped:
already up to date` (orange `●`) and runs no download. A selected Mac whose
Orbit Desktop/Agent is unreachable before mutation settles to `Skipped: Orbit
Desktop is not running` (orange `●`) without failing the fleet update. If a
selected Linux or other non-macOS node cannot reach its Agent listener before
mutation, the row settles to `Skipped: Orbit Agent is not running` (orange `●`)
and the fleet continues. A `topology-candidate` manifest with the same semantic
version still updates when the desired CLI hash or gateway image digest differs
from tracked installed state. The gateway is the version ceiling, so no node is
updated ahead of it. Fan-out rows may show `Waiting` while the gateway row is
active; they advance only after the gateway row succeeds. After the gateway row
succeeds, the local node and up to four workload nodes advance simultaneously.
The renderer preserves one row per node and must not reorder rows by which
parallel worker finishes first.

Every row is preceded by a vertical spacer (`│`), including the footer row.
Doctor issue counts are non-fatal row results; the footer fails only for actual
update failures, not doctor issue counts alone.

Gateway-owned work is streamed back over the typed Gateway API as durable
operation events; the CLI renders those events locally. Each persisted event
has a monotonic operation-local `event_sequence` resume cursor; its global
journal row `event_id` is not a resume position. This command's exact-marked
transitional SSE adapter temporarily carries `event_sequence` as
`Last-Event-ID`; after gateway
replacement, the CLI resumes without duplicating rendered events. The adapter
is removed when `update:all` follows live frames through the private operations
WebSocket/Reverb plane.

## Success Output

On full success the footer names the fleet-wide version:

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ●  gateway                  Done
  │
  ●  local                    Done
  │
  ●  beast                    Done
  │
  └  Success: All nodes are running on version 0.1.131
```

When nothing needed updating, the footer is
`Skipped: 0.1.131 is already installed on all nodes` (no gateway or node rows
appear). The success output must not claim that app deployments, state-family
drift, or runtime readiness have been verified beyond each node's `Running
doctor` stage.

## Failure Output

Human-rendered failures must show:

- every node that succeeded, was skipped, or failed;
- the failed update output when available;
- no JSON envelope.

The gateway is the ceiling: if the gateway row fails, the local and workload
nodes are not updated (they would exceed the gateway version), and the footer
reports the gateway failure. If a workload node fails after the gateway
succeeded, later nodes continue and the failed node's output is printed below
the tree:

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ●  gateway                  Done
  │
  ●  beast                    Failed
  │
  ●  local                    Done
  │
  └  Failed
Failed to update node beast.
Agent listener unreachable over WireGuard.
```

If the gateway update fails, the footer is the gateway failure. Local and
workload rows remain on `Waiting` and do not advance past download or replace
stages.

### Start-time or operation-level update lease conflict

When either the gateway start response or the gateway terminal frame is
`update_lease_conflict` for a fleet, gateway, or scheduler resource, the human
renderer shows only the two check rows and a single failed `gateway` row. It
does not reveal or keep `local` or workload `Waiting` rows. A start-time
conflict occurs before the runner can settle the check steps, so the final
frame returns those rows to idle; a terminal-frame conflict preserves their
settled state.

The `gateway` row uses concise operator wording derived from the gateway's
structured conflict fields. `data.conflicting_node` in a terminal frame names
the conflicting operation's `caller_node_id` node when available; a start
response carries its conflict fields in `error.meta`. The renderer falls back
to `another node` when no node name is available. It must not print the raw
lease exception in the progress row or as a trailing human error line after the
tree.

```text
  ┌  Updating Orbit nodes
  │
  ●  Checking for updates     Done: latest version is 0.1.131
  │
  ●  Checking fleet versions  Done: 3 outdated nodes found
  │
  ●  gateway                  Failed: update:all is still being performed by ingress
  │
  └  Failed
```

Node-level `update.node_locked` conflicts during workload fan-out follow the
gateway-ceiling failure rules above: earlier rows stay settled, the failed node
row shows its workload failure, and captured remote output may appear below the
tree when available.
