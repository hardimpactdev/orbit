```bash
orbit gateway:release:deploy [<commit>] [--reconcile] [--json]
```

| Argument | Meaning |
| --- | --- |
| `commit` | The full 40-character SHA. In a terminal, an omitted value is asked for. |

The container Gateway updates the checkout and dependencies in its permanent preparation container, installs the verified web build and promotes that container itself to the candidate. The candidate migrates the shared database and passes private readiness before Orbit switches traffic. Existing Swamp runs continue during deployment. New requests and jobs go to the selected release. After the new release passes its public check, Orbit deletes the earlier old. The former release finishes its HTTP requests and Horizon jobs, then stops as old with `boot.autostart=false` for [rollback](/cli/gateway/release-rollback). Orbit then recreates preparation from the new live. A drain timeout keeps the container and journal for another attempt. The Gateway never holds more than three containers. A release that fails its public check keeps the earlier verified releases. Migrations are expand-only, so old runs on the current database.

After cutover, roll back to the stopped old release or deploy a corrective commit. If the new release failed its public check, it holds the preparation slot: roll back first, or fix the cause and run `--recover`. Before cutover, repair preparation and deploy again. A change to the production database survives either outcome. See [Gateway recovery](/reference/gateway-recovery#move-the-gateway-to-release-containers).

Use `orbit gateway:release:deploy <full-serving-sha> --reconcile` to reload Swamp from the selected release. It verifies the exact live commit, applies its workflows and checks the release again. This does not deploy a commit or change traffic.

The CLI reads the record every 2 seconds until the run ends. The record shows the run's Operation under `phases.run` and gets its outcome from the run's end. JSON prints the final record. A successful deployment ends as `verified`. A successful reconciliation ends as `reconciled`. Both exit with status 0. The fleet pass continues in the background. Read `phases.fleet` with `gateway:release:show` to see each Node and confirm that the release is fleet current.

Interrupting the CLI stops following, not the release. Read the outcome later with `gateway:release:show <id>`. The CLI keeps reading while the Gateway reloads. It gives up with `gateway.release_follow_failed` after 30 failed reads in a row, or once 65 minutes have passed, whatever the reads return.

## Errors

| Error code | Meaning |
| --- | --- |
| `gateway.release_commit_invalid` | The commit is not a full 40-character SHA. |
| `gateway.release_in_progress` | Another release is queued or running. |
| `gateway.release_busy` | On the host PHP-FPM path, protected Operations remain active after 10 minutes. The record names their IDs; the old release stays live and automatic releases pause. |
| `gateway.release_not_adopted` | The Gateway does not run from a release yet. |
| `gateway.release_web_build_missing` | CI published no web build for the commit. A commit that reached `main` without the merge queue never gets one; release the next queued commit ([Web build](/reference/gateway-recovery#web-build)). |
| `gateway.release_follow_failed` | The CLI stopped reading the record. The release continues on the Gateway. |
