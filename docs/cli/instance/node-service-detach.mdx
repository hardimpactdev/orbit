```bash
orbit instance:node-service:detach <instance> <target> [--yes] [--json]
```

```bash
orbit instance:node-service:detach 12 4 --yes
```

In a human terminal, omitted Instance and attachment IDs use registry data lists. The attachment choices come from the selected Instance's [Node service list](/cli/instance/node-service-list). JSON and noninteractive calls require both IDs explicitly. A supplied attachment ID must use ASCII digits and fit the positive integer range, without a sign or surrounding whitespace. `--yes` confirms withdrawal and deletion of this attachment. Without it, a terminal asks for confirmation with No selected after both IDs are resolved; JSON and noninteractive calls refuse with `instance.node_service_confirmation_required`. Declining, cancelling a selection or confirmation, Ctrl-C or end of input returns `input.cancelled` before the delete request. The confirmation states that container access is withdrawn before deletion, while environment and the Process stay unchanged.

`--json` follows a pending Operation and writes its terminal receipt as one JSON object without prompts or progress. Human output follows pending work and shows the Operation ID and request ID; a completed checkout receipt needs no follow. Failure exits nonzero and preserves its stable code. The CLI generates one idempotency key for its delete request. Ctrl-C after admission stops following; the Operation continues and can be read with `orbit operation:show ID`.

The API is:

```http
DELETE /api/v1/instances/{instance}/node-service-targets/{target}
```

The MCP tool is `instance-node-service-detach`:

```json
{"instance": 12, "target": 4}
```

| Input | Meaning |
| --- | --- |
| `instance` | Positive numeric Instance ID. |
| `target` | Positive numeric attachment ID returned by attach or list. It must belong to this Instance. |

The caller must be an active WireGuard peer authorized for the Instance's Node. [Node access](/cli/node/access-add) defines that authority. The optional `Idempotency-Key` header follows the shared [Operation replay contract](/reference/operations#retry-a-start-with-a-key).

HTTP 202 returns an `instance.node_service_detach` Operation. For a checkout Instance, record deletion and the succeeded receipt commit together. For a container Instance, Orbit withdraws only the selected endpoint’s per-Instance network grant and input rule; another attachment using the same endpoint keeps that shared access. The bridge rule remains while another container uses the endpoint, and newer admissions are preserved. The record is deleted only after withdrawal succeeds; its terminal result includes the attachment identity and `detached: true`. No reach probe runs. Environment values, workload files, the Node Process and other attachment records stay unchanged.

Detach works for a checkout Instance and after successful migration, including a default Instance. It releases that record's [Process dependency](/reference/processes-and-schedules#node-service-target-records). A missing target or another Instance's target returns 404 without a new receipt or deletion. A repeat without the original idempotency key therefore returns the same missing-target refusal; a matching keyed replay returns the original receipt.

A running lifecycle operation refuses detach. If a failed migration retained its runtime, retry `orbit instance:migrate INSTANCE` to finish or restore the move before detaching. Both refusals keep the attachment and create no receipt.

For a checkout, receipt creation and attachment deletion commit in one transaction; failure rolls back both. For a container, admission records intent without deleting the attachment. Terminal success and deletion commit together. A failed or interrupted withdrawal retains the attachment even if some access has already been removed. Read the Operation, then submit detach again with a new idempotency key to finish withdrawal; replaying the failed key returns its original failure. A stopped service does not prevent cleanup: retained bridge endpoints use their last confirmed translated addresses.

## Errors

| Code | HTTP | Meaning |
| --- | --- | --- |
| `instance.id_invalid` | — | The CLI Instance ID is invalid, missing noninteractively, or no Instance is available to select. |
| `instance.node_service_target_id_invalid` | — | A supplied attachment ID is invalid, the ID is omitted in JSON or noninteractive mode, or the selected Instance's attachment list is empty. |
| `instance.node_service_confirmation_required` | — | A JSON or noninteractive CLI call omits `--yes`. |
| `input.cancelled` | — | A terminal selection or confirmation was cancelled, or consent was declined; no delete request was sent. |
| `peer.identity_unknown` | 403 | The caller is not an active WireGuard peer. |
| `node_access.required` | 403 | The caller lacks authority for the Instance's Node. |
| `http.404` | 404 | The Instance or its Node does not exist. |
| `validation.failed` | 422 | The optional request key is malformed. |
| `operation.idempotency_conflict` | 409 | The key already belongs to another target or input. |
| `instance.lifecycle_busy` | 409 | The Instance is not active, migration is running, or another detach on this Instance’s Node is running. |
| `instance.node_service_runtime_cleanup_required` | 409 | An unfinished move retained its runtime. Retry migration to finish or restore it first. |
| `instance.node_service_target_missing` | 404 | The target is missing or belongs to another Instance. Nothing is deleted and no new receipt is created. |
| `swamp.ssh_target_unavailable` | 503 | Container withdrawal needs the stored target address, account and SSH host key. |
| `swamp.ssh_identity_unavailable` | 503 | The worker execution identity is not configured. |
| `swamp.node_missing` | 409 | No Node holds the execution role. |
| `operation.target_busy` | 409 | Another Operation holds the Instance lock. Nothing is deleted and no new receipt is created. |

A container withdrawal can also fail with `instance.node_service_runtime_missing` if its container is missing, `instance.bridge_busy` if another bridge writer owns the lock, or a named bridge failure such as `instance.bridge_state_unresolved`. The failed Operation retains the attachment. No listener probe or fresh Docker publication resolution is needed for withdrawal.
