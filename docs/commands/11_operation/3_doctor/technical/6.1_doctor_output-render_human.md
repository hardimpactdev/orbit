# Human Renderer: `orbit doctor`

[Back to `doctor` technical contract.](1_doctor.md)

This page describes the human-rendered terminal output for `doctor`.

**Renderer:** Human renderer.

## Primitive

- Progress/result frame: doctor check-up frame.
- Inline category tables: [Table](../../../ux/lists/table.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `doctor` has optional filters
and fails invalid combinations before probes or side effects.

## Output Contract

Human output is an operator report, not a terse status line. It must make these
facts visible without requiring JSON:

- selected verify scope;
- resolved scope: family list, node, app, workspace, and whether `--self`
  resolved the caller identity;
- whether the final result is healthy;
- one visible row per checked category;
- live per-category state while checks run;
- issue and action details inline under the category that owns them;
- final summary prose for issue count, category count, and next action.

Healthy output must not imply that unselected families, nodes, apps, or
workspaces were inspected. When the resolved scope is narrow, the scope line
must stay narrow.

## Category Catalog

The renderer maps canonical state families to operator-facing category labels.
The canonical family keys stay visible in JSON; human output uses the labels
below.

| Family key | Human category |
| --- | --- |
| `node` | `Nodes` |
| `app` | `Apps` |
| `workspace` | `Workspaces` |
| `process` | `Processes` |
| `proxy` | `Proxy routes` |
| `firewall_rule` | `Firewall` |
| `tool` | `Tools` |
| `schedule` | `Scheduling` |

When a future DNS/TLD diagnostic source exists, it may render as `DNS/TLD`.
Until then DNS/TLD must not appear as an always-present row; node-owned local
TLD drift remains part of `Nodes`.

Rows are populated from resolved scope. Omitted `--family` renders every
doctor-supported family. Narrow family scopes render only selected families;
they must not show placeholders for unselected categories.

## Framed Panel Contract

Human output is one framed panel. This single panel serves as both the
in-progress and final result display. The panel is re-rendered during progress
as each category completes, then replaced by the final result panel. The frame
uses a fixed-width terminal layout when possible:

- top border contains the spaced panel title;
- second divider contains the target line;
- category rows appear in family order;
- issue/action tables appear inline immediately after the category row that owns
  them;
- final divider is `S U M M A R Y`;
- summary prose is centered when it fits.

The target line is:

```text
Performing check-up on <target>
```

for in-progress output, and:

```text
Successfully performed check-up on <target>
```

for final output when all selected probes completed. If a probe cannot complete,
use:

```text
Check-up on <target> could not complete
```

`<target>` is the resolved node name when the run targets one node; otherwise it
is `selected scope`.

## Progress Tree

The framed panel renders as a single unified display that updates or replaces during execution:

```
┌──────────────────────────────────────────┐
│  D O C T O R  [R E S U L T | I N G]     │
├──────────────────────────────────────────┤
│  [Performing | Successfully performed |  │
│   Check-up on <target>                   │
├──────────────────────────────────────────┤
│  ●  Family1         [Status]             │
│  ├─ [Optional issue table]               │
│  ├─ [Optional action table for fix modes]│
│  ●  Family2         [Status]             │
│  ...                                     │
├──────────────────── S U M M A R Y ────────┤
│  [Summary prose centered when possible]  │
└──────────────────────────────────────────┘
```

The panel structure remains consistent across in-progress and final states; only the
status text and content rows update.

## In-Progress Panel

`doctor` may perform gateway, remote probe, and repair/adoption work, so the
human renderer must show the in-progress panel after scope authorization and
before probes or side effects begin. Each category row starts as `Queued`, then
updates in place:

| State | Status text |
| --- | --- |
| Queued | `Queued` |
| Probe running | `Checking` |
| Result aggregation | `Gathering results` |
| Healthy category | `OK` |
| Issue category | `<n> issue detected` or `<n> issues found` |
| Empty category | `Skipped, no <category data> configured` |
| Probe unavailable | `Unavailable, <reason>` |
| Action running | `Fixing` or `Adopting` |
| Action complete | `<n> fixed`, `<n> adopted`, `<n> skipped`, or `<n> failed` |

The summary line updates as categories finish:

```text
<n> issues detected so far across <m> categories
```

When no completed category has issues yet, render:

```text
No issues detected so far
```

## Result Panel

The final human result is the same frame with title:

```text
D O C T O R  R E S U L T     (for verify mode)
D O C T O R  I N T E R A C T I V E     (for interactive mode)
D O C T O R  R E S T O R E     (for restore mode)
D O C T O R  A D O P T     (for adopt mode)
```

Final category statuses use:

| Final condition | Status text |
| --- | --- |
| Category checked and healthy | `OK` |
| Category has issues | `<n> issue detected` or `<n> issues found` |
| Category has no configured rows | `Skipped, no <category data> configured` |
| Category probe failed | `Unavailable, <reason>` |

When a category has issues, render its table directly below the category row.
Tables are compact and category-specific. They must not force every family into
the same generic `NODE / KEY / SUMMARY / NEXT` shape when a clearer table is
available.

Preferred issue columns:

| Family | Columns |
| --- | --- |
| `node` | `NODE`, `ISSUE`, `SUMMARY` |
| `app` | `APP`, `ISSUE`, `SUMMARY` |
| `workspace` | `WORKSPACE`, `ISSUE` |
| `process` | `APP`, `PROCESS`, `ISSUE`, `SUMMARY` |
| `proxy` | `DOMAIN`, `ISSUE`, `SUMMARY` |
| `firewall_rule` | `NODE`, `RULE`, `ISSUE`, `SUMMARY` |
| `tool` | `NODE`, `TOOL`, `ISSUE`, `SUMMARY` |
| `schedule` | `NODE`, `SCHEDULE`, `ISSUE`, `SUMMARY` |

Workspace names include the app suffix, such as `abc123.nckrtl.test`, so the
workspace table does not need a separate `APP` column. If a value does not exist
for a family, omit that column instead of rendering an empty column. If a manual
next step is present, render a `NEXT` column.

Action results are rendered inline below categories only when in `--fix` modes
(interactive, restore, or adopt). Verify mode must not render action tables.

Issue categories sort by family order. Within a category, sort by issue kind
order: `unverifiable`, `missing`, `divergent`, `extra`, then preserve probe
order.

For verify mode, the summary line when unhealthy is:

```text
<n> issues detected across <m> categories
```

And the next-action line is shown when issues remain:

```text
Run doctor --fix to restore, adopt, or skip findings
```

For fix modes, the summary line depends on remaining issues:

```text
No issues remaining; <n> actions completed     (healthy)
<n> issues remaining across <m> categories     (unhealthy)
<n> actions failed; review remaining issues    (failed actions)
```

## Empty Scope Output

When the selected scope has no rows for a family, the category row remains
visible if that family was selected and uses a skip status:

```text
●  Apps           Skipped, no apps configured
```

An empty-scope row is informational and does not make the run unhealthy.

## JSON Boundary

The framed panel is human-only. JSON output keeps the existing
`success.data.doctor` / `error.data.doctor` payload. The renderer may derive
category status text and inline tables from the JSON payload, but it must not
change JSON field names to satisfy human layout needs.

## Failure Output

Validation failures, authorization failures, unsupported family selections, and
gateway connection failures occur before the framed panel can render. They keep
the shared human failure style from the command contract.

Probe failures inside a selected family render the framed result panel. The
category row status is `Unavailable, <reason>`, and the summary counts the
category as an issue category.

Action failures occur in `--fix` modes and are rendered inline below the owning
category in the same framed panel.
