# instance:auto-deploy:enable verification cases

The proof runs the built CLI against a fresh nested topology with a Gateway, an `app-prod` Node with production Instances of a Project whose repository the proof controls (with and without a `merge_check`, readable and unreadable), and CI results the proof can set. It checks the Gateway records, the schedule, the deployments and the Node's releases. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Enable | Enable an active production Instance that has a succeeded deployment and a readable `merge_check`. | The result is at once, with no task. `auto_deploy` is on and unpaused, a check of the branch runs for the Instance every minute, and nothing deploys and no Node changes. The detail shows `Auto deploy: on, after <merge check> passes`. Fails today: the Gateway records the flag and one fleet-wide workflow discovers enabled Instances; it publishes no schedule for the Instance. |
| Deploy a green commit | Merge a commit whose check passed, then wait one minute. | The next check deploys exactly that commit with the steps of `instance:deploy`. The deployment row has the origin `automatic`, one Activity entry `auto_deploy.<result>` is recorded, and the next check compares against the new deployed commit. Fails today: the Gateway republishes no per-Instance inputs. |
| Red and pending | A commit whose check failed, then one still pending. | Neither deploys. The pending one shows `gate_pending` with no history row and no Activity entry. The failed one shows `gate_failed` with one Activity entry. |
| Failed deploy | Make an automatic deploy fail before any step ran, three times, and once after a step ran. | A deployment row and a release alert are recorded each time. The first two failures are retried at least 10 and then at least 20 minutes later, the third blocks the commit, and the failure after a step ran blocks it at once. |
| No merge check | A Project with no `merge_check`. | Enabling succeeds with the warning that every commit deploys without a check. The detail shows `on, without a merge check`. |
| Unreadable check | A `merge_check` on a Project that reads through the GitHub CLI or is not on `github.com`. | `instance.auto_deploy_gate_unreadable`. Nothing is recorded. |
| Pause | Run `instance:deploy`, then `instance:rollback`, each once with success and once with failure. | Automatic deployment is paused at once and no check deploys. A rollback blocks the commit it moved away from. An automatic deploy never pauses itself. Fails today: the pause is computed from the history, and no schedule trigger is removed. |
| Resume | Enable after a pause. | Automatic deployment resumes from the commit that is live. The rolled-away commit stays blocked. |
| Repeat | Enable an Instance that is already on, paused and not paused. | It succeeds. The resume point moves to the newest deployment, which clears a pause, and nothing else changes. |
| No deployment yet | An active production Instance that never deployed. | Enabling succeeds and the check reports `not_deployed` until a deploy succeeds. |
| Not available | A development `default` Instance, a development Instance, a production Instance that is neither source-resolved nor active, and one whose `app-prod` role is not active. | `deployment_config.unavailable` for the first three, with nothing recorded. Fails today for a source-resolved Instance and one without an active role: enabling succeeds and records it as on, and nothing deploys. |
| No overlap | Fire an automatic deploy while a manual deploy runs. | One lock for the Instance means the two never overlap: the fire reports `busy`, or ends with `deployment.paused` when a manual row appeared after the check. |
| Missing input | In a terminal, run the command with no argument and cancel the list. Then run it noninteractively and with `--json`. | The terminal lists Instances by name. Cancel ends with `input.cancelled` and no request. The noninteractive calls are refused with `instance.id_invalid`, with no request. Fails today: the Instance is a required argument, so every call without it is refused by the parser. |
| IDs only | An Instance by name, the ID `0`, the ID `-1` passed after `--`, and `abc`. | `instance.id_invalid`, with no request. Fails today: `-1` without `--` is read as an option and gives a parser error. |
| Unknown and access | An ID that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing is recorded. |
| Output forms | A wide and a narrow terminal, output piped to a file, and `--json`. | A detail `Instance: <name>` with ID, the `Auto deploy` fields, the warning when there is one, and the request ID at the wide width, and labeled records at the narrow one. The piped output has no animation or escape codes. With `--json`, stdout holds the Instance with `auto_deploy` and `request_id`. Fails today: the detail shows no Project or Node. |
