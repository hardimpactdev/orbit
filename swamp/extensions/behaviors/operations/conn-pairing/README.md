# Conn pairing data

One plain, bounded curl command calls T3's pairing-token API on the Swamp role worker. The official SSH, cfgmgmt and vault behaviors do not implement the T3 API. curl takes its admin session from the native vault-backed step environment and writes the reply in a private directory. No script is shipped and no Node is contacted.

This type only reads and shapes the private response. It parses T3's pairing result (`id`, `credential`, `expiresAt` and the echoed `label`) and ignores fields a newer T3 adds. The label must match the admitted one. A refusal or an invalid reply fails with its final `conn.*` code: `conn.session_rejected`, `conn.request_refused` or `conn.response_invalid`. It stores the credential with Swamp's native sensitive-field resource. The resource instance is `pairing-<pairing_id>`; the behavior name stays fixed. The resulting vault key is unique to the admitted pairing, so concurrent issues cannot overwrite an unread token. Public metadata contains only the pairing ID, link ID, expiry and vault locator.

Gateway projection reads that exact key once on successful delivery, encrypts the credential for its caller and deletes the key through the existing native vault-delete helper. Its normal owner endpoint returns the link once and clears the record. The native workflow declares cleanup after failure and uses an assert as its end check. No HTTP implementation, input callback, result callback or custom transport remains in this type.
