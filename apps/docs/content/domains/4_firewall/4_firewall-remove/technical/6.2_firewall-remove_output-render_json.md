# JSON Renderer: `orbit firewall:remove`

[Back to `firewall-remove` technical contract.](1_firewall-remove.md)

**Renderer:** JSON renderer.

## Primitive

None. JSON output is emitted as a machine-readable envelope via `$this->line(...)`.

## Selection

Use this renderer when `--json` is present.

## Envelope

This renderer uses the shared [JSON Envelope](../../../README.md#json-envelope).

## Success Shape

```json
{
  "success": {
    "data": {
      "rule": {
        "name": "local-vite",
        "node": "app-1",
        "direction": "incoming",
        "action": "allow",
        "source": "10.6.0.0/24",
        "destination": null,
        "port": 5173,
        "protocol": "tcp",
        "address_family": "v4",
        "interface_scope": null,
        "owner": "user",
        "protected": false,
        "reason": "local development server",
        "status": "removed"
      }
    },
    "meta": []
  }
}
```

For idempotent absence, `success.data.rule.status` is `already_absent`.

## Error Shape

Cleanup failure after the rule has been resolved includes the retained gateway configuration:

```json
{
  "error": {
    "code": "firewall_rule.cleanup_failed",
    "message": "The backend firewall rule could not be removed, so gateway configuration was kept.",
    "data": {
      "rule": {
        "name": "local-vite",
        "node": "app-1",
        "direction": "incoming",
        "action": "allow",
        "source": "10.6.0.0/24",
        "destination": null,
        "port": 5173,
        "protocol": "tcp",
        "address_family": "v4",
        "interface_scope": null,
        "owner": "user",
        "protected": false,
        "reason": "local development server",
        "status": "expected"
      }
    },
    "meta": {
      "next_command": "doctor --family=firewall_rule --restore --node=app-1"
    }
  }
}
```

Validation errors use metadata only:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Use --force to remove this firewall rule.",
    "meta": {
      "field": "force",
      "reason": "destructive_consent_required"
    }
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `error.code` | `validation_failed`, `gateway_unavailable`, `authorization_failed`, `firewall_rule.baseline_conflict`, `firewall_rule.cleanup_failed` | Stable command failure code. |
| `error.message` | string | Human-readable failure summary. |
| `error.data.rule` | object | Retained firewall rule configuration when backend cleanup failed. |
| `error.meta` | object | Field, node, caller, or recovery context for automation. |

## Test Mapping

| Path | Coverage |
| --- | --- |
| `apps/cli/tests/Feature/Commands/Firewall/FirewallWriteCommandTest.php` | JSON `firewall:remove` destructive consent failure, forced DELETE success envelope, and gateway error passthrough. |


Documented `error.code` values named for coverage tracking:
`validation_failed`, `gateway_unavailable`, `authorization_failed`,
`firewall_rule.baseline_conflict`, and `firewall_rule.cleanup_failed`.
Destructive consent is classified by
`error.meta.reason=destructive_consent_required` and is asserted through the
forced and unforced `firewall:remove` CLI paths. Linked tests cover only the
mapped assertions above; remaining assertions for renderer codes, idempotent
absence shape, and partial-cleanup `error.data.rule` placement stay as
coverage gaps until focused tests land.

There is no gateway-side coverage for this command-local mapping: input handling and renderer behavior live in `apps/cli`. Gateway API behavior is mapped in the command contract file when a gateway-side surface exists.
