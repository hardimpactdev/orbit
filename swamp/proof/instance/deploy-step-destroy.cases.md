# instance:deploy-step:destroy verification cases

`instance:deploy-step:destroy` removes a step of a production Instance and has no chart. The proof runs the built CLI against a fresh nested topology with production Instances that have steps in both phases and a development Instance, and compares the output with the Gateway records. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Remove a step | Remove the middle step of three in a phase, with `--yes`. | The step is gone from `deploy-step:list`. The others keep their order, and the total timeout drops by the step's timeout. The result is at once, with no task and no file written on any Node. |
| Remove the only step | Remove the last step. | The list is empty and the next `instance:deploy` runs only Orbit's own steps. |
| Earlier deployments | Remove a step after a deploy ran it. | The earlier release keeps what the step did. |
| Unknown step | A name the Instance does not hold, a repeat after a success, two destroys of the same step at once, and a name that is not a valid step name, with and without `--yes`. | `deploy_step.not_found` for the first two and for the invalid name without `--yes`, with nothing changed and no prompt in a terminal. One of the two concurrent destroys succeeds and the other gets `deploy_step.not_found`. The invalid name with `--yes` gives `http.404`. Fails today: that last case is not `deploy_step.not_found`. |
| Not available | A development Instance, and a production Instance that is neither source-resolved nor active. | `deployment_config.unavailable`. Nothing is removed. |
| Competing changes | Remove a step while another change to the Instance's steps runs. | The removal waits for the Instance row lock. |
| Consent | In a terminal answer the prompt with No, Enter, Ctrl-C and end of input. Then run it noninteractively and with `--json` without `--yes`, also for an unknown step. | The prompt names the step, the Instance by name and the effect, with No selected. Each decline ends with `input.cancelled` and removes nothing. The noninteractive and `--json` calls are refused with `input.confirmation_required`, or with `deploy_step.not_found` for an unknown step, and remove nothing. With `--yes` there is no prompt, also with `--json`. Fails today: the prompt does not state the effect, and the CLI reads the Instance and the list before it refuses. |
| Output forms | A wide and a narrow terminal, output piped to a file, and `--json`. | A detail `Removed deploy step: <name>` with Phase, Command, Timeout (seconds) and the request ID at the wide width, and labeled records at the narrow one. The piped output has no animation or escape codes. With `--json`, stdout holds the removed step with `request_id`. Fails today: the output is `Destroyed deploy step <name>.` and a `Request ID:` line, with no detail. |
| Activity | After a successful removal and a failed one. | Activity and the error hold no command text. |
| Missing input | In a terminal, run the command with no arguments and cancel each list. Then run it noninteractively and with `--json`. | The terminal lists Instances and then the Instance's deploy steps by name. Cancel ends with `input.cancelled` and no request. The noninteractive calls are refused with `instance.id_invalid` or `deploy_step.name_required`, with no request. Fails today: both are required arguments, so every call without them is refused by the parser. |
| IDs only | An Instance by name, the ID `0`, the ID `-1` passed after `--`, and `abc`. | `instance.id_invalid`, with no request. Fails today: `-1` without `--` is read as an option and gives a parser error. |
| Unknown Instance and access | An ID that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing is removed. |
