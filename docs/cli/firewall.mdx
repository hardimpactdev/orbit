Every managed Node runs Uncomplicated Firewall (UFW). Orbit owns the rules it needs for public SSH recovery, WireGuard member trust, and each role. Those rules carry an `orbit:` prefix. The rule `orbit:wireguard-members` admits every WireGuard member on the Node's WireGuard address, as [private network trust](/reference/routes#private-network-trust) describes. The `firewall` family adds operator rules beside them, each identified by a stable name on one Node.

The Gateway validates and records named rule intent, then returns an Operation with `202 Accepted`. Swamp receives the complete admitted rule and SSH target, runs its native DAG from Node 209, and returns typed output for terminal projection. The target needs no worker. The CLI follows the Operation until it ends. The Gateway projects the managed row without inspecting execution again. There is no agent action, child Operation or polled writer.

Named rules use the official firewall model and its UFW defaults. orbit-agent will be the only collector of live UFW facts, with `observed_at`, and the Gateway will read its latest observation. Until the agent reports UFW, the Gateway has no live firewall observation. [Doctor](/cli/doctor) still reports firewall drift from its own read; it compares exact tuples for named rules, including numeric contributions to a range, and keeps comment ownership for role and Router rules.

[Database servers](/reference/database-servers#private-publication) publish only on explicit WireGuard and LAN addresses. Ports published by Docker bypass UFW. These servers trust the private Orbit networks and have no port firewall; named UFW rules do not restrict their Docker publications.

## Commands

| Command | Result |
| --- | --- |
| [`firewall:allow`](#orbit-firewallallow) | Create or converge one named allow rule. |
| [`firewall:allowlist`](#orbit-firewallallowlist) | Replace the sources allowed to reach a port before broad peer trust. |
| [`firewall:deny`](#orbit-firewalldeny) | Create or converge one named deny rule. |
| [`firewall:list`](#orbit-firewalllist) | List the named rules of one Node. |
| [`firewall:remove`](#orbit-firewallremove) | Remove one named rule. |

The `ci-runner` role owns the routed allowance on `orbitci0`, with the comment `orbit-ci-runners`. This is the same comment used by the former host setup step, so adding the role adopts that rule through the managed catalog. Role removal closes it; the Incus ACL enforces the runner egress boundary.

## Read the managed and live rules

The Gateway serves three read-only lists. The CLI has no command for them. The web app's Node page and the MCP tools use them.

| Request | Result |
| --- | --- |
| `GET /api/v1/firewall-rules` | The operator rules of every Node the caller may address. |
| `GET /api/v1/nodes/{node}/managed-firewall-rules` | The `orbit:` rules that Orbit intends on one Node: WireGuard member trust, public SSH recovery while the Node has no active role, then each active role's rules and the Metrics rules, with the role named. It uses no SSH. |
| `GET /api/v1/nodes/{node}/live-firewall-rules` | Until orbit-agent reports UFW, returns `backend_status` `unverifiable`, no `observed_at`, and every desired managed and operator rule in `live` with `match` `unverifiable`. It never contacts the Node. |

Role convergence passes desired and removed shapes to the canonical Swamp `convergeFirewall` lower. Its fixed program holds the shared host firewall lock through inspection, mutation and confirmation. It replaces a prior single-port shape only when the catalog record declares its port mutable. The Analytics local PostgreSQL and ClickHouse records declare this because their ports come from the selected storage Processes. The exact `orbit:` comment identifies the managed rule: it deletes the old numbered rules, applies the desired rule, and verifies the exact result. A replaceable old rule must keep the catalog record’s action, direction, source, destination, protocol, interfaces, and address families, with one valid single port per family. Fixed-port drift, unreadable rules, duplicate families, port ranges, and operator comments are refused. The comment and the catalog’s declared mutable field form the ownership contract; Orbit does not keep applied-shape history. The live list can show the old port until convergence replaces it.

The first role convergence removes `orbit:public-ssh-recovery`. So a Node with an active role does not list public port 22 as intended. The managed list comes from the same catalog that convergence applies.

In the live list, each live rule has a `match` value. `exact` means it equals a managed or operator rule. `drift` means its comment names such a rule but the rule differs. `unmanaged` means neither its comment nor its tuple matches recorded intent. A managed or operator rule that is absent from UFW is listed as missing. An inactive, absent, or unreachable UFW returns no live rows. `unverifiable` means no observation exists. The web app lists the live rules, shows `drift` and `unmanaged` rules in red, and flags missing rules. When it cannot read live UFW, it shows the operator rules and the managed catalog instead.

## Router LAN member rules

An active `router` role admits eligible Cluster members to the Router LAN address through three managed IPv4 families. `<node-id>` identifies the source member, not the Router. Each rule is an inbound allow from one exact member LAN IPv4 address to one exact Router LAN IPv4 address; it is not a subnet, interface-wide, or public allowance.

| Comment | Protocol | Destination port |
| --- | --- | --- |
| `orbit:router-lan-https:<node-id>` | TCP | 443 |
| `orbit:router-lan-dns-udp:<node-id>` | UDP | 53 |
| `orbit:router-lan-dns-tcp:<node-id>` | TCP | 53 |

The Router must belong to an active Cluster and have valid LAN and WireGuard IPv4 addresses and a nonempty WireGuard public key. A source must be a different, registered, active Node in that same Cluster, with valid LAN and WireGuard IPv4 addresses and a nonempty WireGuard public key. Roleless members qualify; an access grant, a shared subnet, or membership of another Cluster does not qualify. The Router does not get a source rule for itself: its local queries use loopback, which stock Ubuntu UFW rules accept. No rule is generated for a missing or invalid address, an inactive member, or an inactive Cluster.

All three families use the same eligibility policy, desired-rule catalog, and expand/prune lifecycle. Node provisioning, membership changes, Cluster activation changes, Router role convergence and removal must not leave DNS with a separate source policy. Transitions evaluate proposed membership, addresses, and state before committing them:

1. Expand admits and verifies the proposed eligible sources before the operation moves its dependent traffic. It retains old source rules during the transition.
2. On success, prune removes obsolete sources and old address shapes after the operation commits. Router role removal prunes all three families. Deactivation or losing the last eligible source leaves no member rules.
3. Before membership or Cluster state commits, a failed transition leaves the previous state authoritative; cleanup reconciles against that state. An expansion failure must not make the proposed membership or activation authoritative.
4. After the commit, a cleanup failure does **not** roll back membership or Cluster state. For example, a detached member stays detached and a deactivated Cluster stays inactive if pruning fails. The command reports the failure; obsolete firewall rules can remain as residue until reconciliation succeeds against the current committed state.

Separately, a failed firewall mutation attempts to restore its preceding managed family snapshot before reporting failure. Recovery preserves every distinct observed shape, even when several rules share a comment. Repeated identical shapes cannot be recreated separately through UFW, so reconciliation refuses that snapshot before mutation. Numbered removal deletes each original rule number only once. That snapshot can contain rules made obsolete by an already committed detach or deactivation. Restoring it is firewall error recovery, not a database rollback or proof that the rules match current intent. A failed snapshot restore remains a visible error to inspect, not a successful transition.

After fixing the reported firewall or connectivity failure, read current membership and Cluster state and compare managed/live rules. For an active Router that remains a member of its Cluster, repeat [`cluster:node:add`](/cli/cluster#orbit-clusternodeadd) with that **existing Cluster ID and Router Node ID**: `orbit cluster:node:add <current-cluster-id> <current-router-node-id>`. The action accepts a Node already in that same Cluster and runs Router LAN expansion and pruning against current authoritative state. This works on a Router that hosts Instances and on an inactive Cluster: it neither moves membership nor activates the Cluster, removes workloads, or uses `node:add`. It can also resume pending Route placement cleanup; inspect any reported Route or DNS failure rather than bypassing it.

The existing Router's normal [`node:add` convergence](/cli/node#orbit-nodeadd) is an alternative only when its provisioning guards permit it. With unchanged configuration it refuses a Node that owns Instances with `node.has_instances`; do not remove workloads or change the TLD merely to bypass that guard. `node:converge` does not include a Router LAN firewall artifact, and repeating `cluster:router:set` for the current Router does not run this firewall reconciliation.

After recovery, verify the rules with `orbit doctor --family=firewall`. Do not reattach the detached member, reactivate the Cluster, or edit the database to make stale rules look eligible. Repeating a completed detach is not the cleanup path: it can fail with `cluster.membership_missing`. Retain diagnostics for residue or snapshot-restore failures until the current desired rules are verified.

Reconciliation changes only these managed families. It preserves loopback, WireGuard trust, other role rules, operator rules, unmanaged rules, and the existing DNS service. It never installs a DNS listener, changes member resolver selection, or cuts over VPN DNS. Those are later [ADR 0219 build steps](/decisions/0219-answer-cluster-names-from-a-dns-on-the-router#build-order).

The observed family inventory includes rules with a port or port range but no explicit protocol. These admit both transports and do not match a transport-specific member rule. An unreadable rule with an exact owned family comment stops reconciliation before mutation; it is never treated as an empty inventory. Similarly named comments outside the owned families remain untouched.

The managed read lists all three families from the same catalog used by convergence. The live read compares their source, destination, protocol, port, direction, and comment against that intent. A stale source is not intended merely because its comment starts with `orbit:`. Native reconciliation verifies missing or different rules and ineligible-source residue in each family, including a leftover source after the desired set becomes empty. Doctor does not duplicate this firewall validation.

A failed apply or verification reports `node.firewall_convergence_failed`. Failure to restore the preceding Router LAN family reports `router.lan_ingress_recovery_failed`; inspect the observed rules and operation diagnostics before retrying. Do not treat a failed restore as permission to delete other rules.

### Safe DNS firewall rollout

Member rules alone do not enforce member-only DNS if a broader allow still overlaps port 53. A positive query from an already allowed member is not proof of LAN isolation. The following is an authorized **postmerge rollout**, not a fleet mutation during authoring or review. Rehearse it first on the group's allocated native disposable topology through normal Orbit commands. Keep rehearsal evidence separate from live results.

1. Before any change, inventory the current Router, Cluster and eligible source IDs and addresses. Record the deployed commit, UFW active/default policy, ordered IPv4 and IPv6 rules with comments, interfaces, destinations, protocols and port ranges, persistent UFW configuration, and named operator-rule records and statuses. Retain the exact previous inventory and the commands needed to restore it outside the repository; a screenshot or a list of port 53 rules alone is not sufficient rollback evidence. Keep credentials out of shared evidence.
2. Deploy step 1 normally. The next Router LAN reconcile, such as Node enrollment, attach/detach, or `node:add`, adds two DNS rules per eligible member beside unchanged HTTPS rules. Use the managed and live reads above to compare intended and actual rules. Check loopback, HTTPS, WireGuard access, and the existing DNS service too. Do not enable Cluster DNS or change a member resolver in this step.
3. Before any later Cluster DNS enablement, review every operator or unmanaged allowance that can reach Router LAN port 53, including protocol-wide allows, port ranges and subnet/any-source rules. Record an individually authorized narrowing and its inverse against the saved inventory. These rules are not automatically pruned by Orbit. Do not add a deny and assume it overrides an earlier allow, reset UFW, or delete unrelated rules.
4. Preserve Incus DNS before withdrawing an overlap. Add and verify the required UDP and TCP rules scoped to the actual Incus bridge **input interface and bridge destination address**, with the required bridge client sources. A source-subnet-only rule that also admits the Router LAN destination is not sufficient. Verify real bridge client DNS over both transports, then narrow/remove only the inventoried overlapping allowances. If an operator rule cannot express the required interface/destination scope, use a separately authorized host firewall change rather than a broader replacement. Retain both the previous and replacement inventories.
5. Prove authorized DNS success and unauthorized LAN denial over **both UDP and TCP** at the Router LAN address. Use a healthy existing DNS listener in rehearsal; if no listener exists, record the missing prerequisite, not a successful firewall test. Use a fresh query/connection per transport, an eligible member and a controlled LAN requester that fails the eligibility policy. Record source/destination addresses, query, response or bounded timeout, and firewall observations that distinguish denial from a dead listener. Repeat the authorized control while the unauthorized request fails. Recheck Incus bridge DNS, loopback and HTTPS. Later Cluster DNS rollout must repeat this matrix against its actual listener before members switch.

For the task-owned rehearsal, the harness provides a [lease-scoped Router LAN acceptance fixture](/reference/incus-topologies#router-lan-firewall-acceptance-fixture). It supplies healthy DNS/HTTPS endpoints, exact member and nonmember LAN sources, and a real nested bridge DNS client. It records inventories before mutations, adds and narrows only fixture-owned overlaps, and verifies exact inventory rollback and cleanup. Bind overlap or unexpected intervening changes refuse the operation. The fixture never changes the topology host's Incus bridge or live firewall. Its bridge evidence and firewall-checkpoint rollback do not replace live Incus bridge acceptance or a deployment/code rollback. Independent native review must reproduce it before publication.

The design inventory for beast anticipated two eligible members, sabre and shark, hence four new DNS rules. Re-read live state rather than treating those names or counts as current truth. Until authorized live narrowing and the transport matrix pass, live isolation acceptance is outstanding. Code tests and disposable topology results do not satisfy it.

### Roll back step 1

Roll back later DNS service/member steps first if any have shipped, keeping the last usable resolver throughout. For step 1 alone, revert the firewall code, then explicitly remove every `orbit:router-lan-dns-udp:<node-id>` and `orbit:router-lan-dns-tcp:<node-id>` rule from each affected Router. The reverted code does not own these new names and cannot prune them. Re-read numbered UFW rules before deleting by number and verify no DNS-family residue remains; do not remove `orbit:router-lan-https` or other managed rules.

If authorized overlap narrowing occurred, restore the exact previous operator records and unmanaged rules from the saved inventory, including their scope and ordering, and remove only the replacement rules introduced by that narrowing. Do not restore an entire old firewall snapshot over unrelated intervening changes; compare inventories and stop for ownership review if they differ. Verify the previous DNS path, required Incus bridge DNS, loopback, HTTPS, and managed/live agreement. Record that restoring a previous broad allow also restores its previous exposure; it is rollback, not successful member-only isolation.

## Rules and names

The [allowlist design](/decisions/0241-firewall-source-allowlists) defines the closed source-set contract.

Every command accepts `--json` and requires `--node` with a numeric Node ID. A rule name is 1 through 63 characters of lowercase letters, digits, dots, underscores, and hyphens, starting and ending with a letter or digit; it cannot contain a colon, so an operator name never collides with an `orbit:` rule. The name identifies a Gateway intent record. The official model converges its tuple; old `orbit:node:<node-id>:firewall:<name>` comments are removed when the last contribution to their tuple is removed.

All targets and rule values are explicit; these commands do not prompt for missing arguments or options. Human requests follow the Operation steps and show the final status and request ID. Piped output has no animation or escape codes. Write-command JSON contains the final Operation or an admission error.

## orbit firewall:allow

Allow traffic to one destination port or port range, optionally from one source.

```bash
orbit firewall:allow <name> --node=ID --port=PORT [--from=SOURCE] [--protocol=PROTO]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Stable rule name, unique per Node. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--node=ID` | required | Numeric target Node ID. |
| `--port=PORT` | required | Destination port from 1 through 65535, or an ordered range such as `8000:8100`. |
| `--from=SOURCE` | `any` | Source IPv4 or IPv6 address, a CIDR such as `10.6.0.0/24`, or `any`. |
| `--protocol=PROTO` | `tcp` | `tcp` or `udp`. |

```bash
orbit firewall:allow office-postgres --node=7 --port=5432 --from=10.6.0.0/24
orbit firewall:allow media-udp --node=7 --port=6000:6100 --protocol=udp
```

Repeating the same command with the same values admits an Operation that converges the existing rule. A running Operation keeps its Node firewall target and returns `operation.target_busy` to another admission. The same name with different values returns `firewall.name_taken`; remove the rule and create it again to change it. Human output follows the UFW step and reports `Firewall rule succeeded.` with the Operation and request IDs.

Use `--idempotency-key=KEY` to retry the same admission without creating another Operation. Keep the same key, Node, rule name and input.

## orbit firewall:deny

Deny traffic to one destination port or port range, optionally from one source. It accepts the same argument and options as `firewall:allow`.

```bash
orbit firewall:deny <name> --node=ID --port=PORT [--from=SOURCE] [--protocol=PROTO]
```

```bash
orbit firewall:deny block-scanner --node=7 --port=22 --from=203.0.113.9
```

<Warning>
The Gateway refuses a deny rule whose port contains the Node's public SSH port for any source that would cover it with `firewall.public_ssh_deny_forbidden`, because that port is the recovery path after a failed provisioning. A deny rule and an allow rule with the same source, protocol, and port cannot coexist on one Node; the second one returns `firewall.action_conflict`.
</Warning>

Use `--idempotency-key=KEY` to retry the same admission without creating another Operation. Keep the same key, Node, rule name and input.

## orbit firewall:allowlist

Admit only selected source IPv4 addresses or CIDRs to a port or range. This block precedes other UFW rules, including `orbit:wireguard-members`. Source allows come first, followed by a deny for everyone else. Existing connections can survive through connection tracking; verify with new connections.

```bash
orbit firewall:allowlist rex --node=7 --port=7297 --from=10.44.0.6 --from=10.44.0.9
orbit firewall:allowlist rex --node=7 --port=7297 --from=10.44.0.0/28
```

| Input | Meaning |
| --- | --- |
| `name` | Stable name, unique among all named firewall rules on the Node. |
| `--node=ID` | Required numeric Linux Node ID. |
| `--port=PORT` | Required port or ordered range, such as `7297` or `7297:7299`. |
| `--from=SOURCE` | Required, repeatable IPv4 address or CIDR. At least one source. |
| `--protocol=PROTO` | `tcp` by default, or `udp`. |

The API is `POST /api/v1/nodes/{node}/firewall-rules/allowlist` with `name`, `port`, optional `protocol`, and a `sources` array. MCP exposes `firewall-allowlist` from the same contract. Up to 64 sources are normalized, deduplicated and sorted. Repeating a name replaces the complete source list; omitted old sources are withdrawn. The port and protocol cannot change under the same name. An allowlist exclusively owns its port or range and protocol among named operator rules. Overlapping ordinary allows, denies or allowlists refuse with `firewall.allowlist_overlap`.

The Gateway refuses SSH port 22, the Node's recovery SSH port, the configured WireGuard port, and bounded ports in its managed firewall catalog, including ports reserved by assigned roles even before they have traffic with `firewall.protected_port`. This includes a protected port inside a requested range, regardless of protocol. The broad WireGuard trust rule does not reserve all ports. Invalid or empty sources return `validation.failed` from the API.

Use `firewall:list` to read the complete source set and `firewall:remove` to remove all lines owned by the allowlist. Removal restores the underlying firewall policy. Run `orbit doctor --family=firewall --node=<id>` to check source lines, the final deny and their order. A block after broad trust reports drift. Doctor reports missing lines, drift, inactive UFW and failed rule lifecycle.

Use `--idempotency-key=KEY` to retry the same admission. A changed source set needs a new key. Human and JSON output follow the same Operation as other firewall writes. An unowned identical UFW tuple refuses before mutation with `firewall.rule_collision`; UFW cannot keep two separately owned copies of that tuple.

## orbit firewall:list

List the named rules recorded for one Node with their action, source, port, protocol, and lifecycle status.

```bash
orbit firewall:list --node=ID
```

| Option | Meaning |
| --- | --- |
| `--node=ID` | Numeric target Node ID. |

Human output uses a read-only table with NAME, ACTION, SOURCE, PORT, PROTOCOL, and STATUS columns. Values wrap inside their cells; below the minimum width, labeled records retain every field. An empty result says `No firewall rules.`.

A rule's `status` is `provisioning`, `active`, `failed`, or `removing`. A failed rule keeps `failed_step` and `error_code` so the same command can be repeated after the cause is fixed. Orbit-owned `orbit:` rules are not part of this list.

## orbit firewall:remove

Remove one named rule from UFW and delete its record. Before prompting, the CLI resolves the rule with a read-only lookup unless a retry key is supplied, then asks `Remove firewall rule [name] from Node #ID?` with No selected. Supply `--yes` for automation, including JSON; JSON never implies consent.

```bash
orbit firewall:remove <name> --node=ID [--yes] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Stable rule name. |

| Option | Meaning |
| --- | --- |
| `--node=ID` | Numeric target Node ID. |
| `--yes` | Confirm rule removal without prompting. |

```bash
orbit firewall:remove office-postgres --node=7
orbit firewall:remove office-postgres --node=7 --yes --json
```

The Gateway marks the rule `removing` and returns its Operation. Swamp removes the named contribution through the official firewall model on Node 209. Another recorded name or the canonical Node firewall catalog keeps any shared tuple. A visible official SSH step removes the selected old named rule when its tuple has ports to withdraw, before tuple convergence; no target worker or agent action runs. Completion removes the Gateway record. A failure leaves the rule `failed` with the step that stopped; repeat the command with a new admission key after fixing the cause.

Declining, Ctrl-C, or end of input before removal exits 1 with `input.cancelled`. Noninteractive removal without `--yes` exits 1 with `input.confirmation_required` and an instruction to supply `--yes`. Refused confirmations send no removal request. Existing lookup, authorization, and safety errors retain their codes.

Use `--idempotency-key=KEY` to retry the same admission without creating another Operation. Keep the same key, Node, rule name and input.

## Error codes

The CLI validates the name, source, protocol, and port before it sends a request. The Gateway returns admission errors. Native diagnostic reasons appear in Swamp history. If execution stops before the result step, the final Operation reports `operation.native_failed`.

| Error code | Meaning |
| --- | --- |
| `firewall.node_id_invalid` | `--node` is not a positive integer. |
| `firewall.rule_name_required`, `firewall.rule_name_invalid` | The name is missing or outside the accepted form. |
| `firewall.source_invalid` | The source is not `any`, an IP address, or a valid CIDR. |
| `firewall.protocol_invalid` | The protocol is not `tcp` or `udp`. |
| `firewall.port_invalid` | The port is outside 1 through 65535 or the range is not ordered. |
| `firewall.name_taken` | The name exists on the Node with different values. |
| `firewall.action_conflict` | An opposite rule with the same source, protocol, and port exists. |
| `firewall.public_ssh_deny_forbidden` | The deny rule would cover the public recovery SSH port. |
| `firewall.known_hosts_unpublished` | The worker snapshot has no matching admitted target pin, or has an additional different pin for that address. |
| `firewall.backend_inactive` | UFW is inactive on the Node. |
| `firewall.platform_unsupported` | The Node is not a Linux Node. macOS is refused before SSH and before a rule is stored. |
| `firewall.apply_failed`, `firewall.verify_failed` | UFW did not accept the rule or the verification did not find it. |
| `firewall.remove_failed`, `firewall.remove_verify_failed` | UFW did not remove the rule or the verification still found it. |
| `firewall.node_unreachable` | The Gateway could not reach the Node over SSH. |

## Execution and ownership

The official `@swamp/cfgmgmt/firewall` model manages source, protocol, action and numeric port tuples. Names remain Gateway intent labels. Port ranges fan out into numeric tuples; removal retains ports contributed by another recorded name. The native result proves tuple presence or absence, not that a broader earlier rule permits traffic. The official model appends new rules; new allow rules use this ordering.

Before any remote action, the Node 209 worker requires the admitted target key in its published `~/.ssh/known_hosts` snapshot. Missing or different entries fail with `firewall.known_hosts_unpublished`. The official model uses its standard SSH connection and host-key defaults; this port does not add a custom transport or update known_hosts. A pinned official SSH read then refuses inactive UFW before the model can select another backend. Native steps return the final result; they never fetch intent or post progress to the Gateway.

## Why it works this way

The managed list is the set that convergence keeps, not every rule Orbit can write. A Node with roles has closed public SSH, so listing it as intended would advertise a path that is gone. Hiding it only in the web app is rejected, because every other client would still read the wrong intent. The native live inspection is separate from the intended rules on the Node page. The live read never changes UFW.
