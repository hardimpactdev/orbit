# One project batch per update group

Each project gets one package group with one child and one PR containing every
eligible major and advisory fix from its latest successful detection. Shared
ecosystem extensions select exact stable targets and solve them together against
the project manifests, lockfiles, platform and peer constraints. Major updates
change only the selected direct ranges. No package gets its own task group.

Detection keeps candidate evidence, eligible exact targets and blocked reasons
in Swamp data. It runs resolution and audits in a disposable copy of the tracked
checkout, without dependency installation or changes to the source checkout.
Targets must satisfy the configured release age, including security targets;
a finding never authorizes an age exception. Missing release dates, unsupported
sources, unsatisfied constraints and unverified advisory fixes remain recorded.
The native resolver chooses versions jointly from all eligible releases. If
the whole set cannot resolve, keep current versions as optional choices and
require each upgrade in security order while allowing the resolver to adjust
other versions. Coupled updates remain together; unresolved requests keep their
solver reason.
All selected updates are applied together per ecosystem/path, not through a
sequence of individual package installations. Expo SDK alignment remains the JS
extension's responsibility. Post-update audit verifies selected advisory fixes. The fresh checkout also
refuses stale advisory identities and downgrades before changing files; exact
target retries remain valid after repair. Release-age validation covers changed
transitive packages as well as selected targets.

Admission uses the existing orbit-gateway behavior lock. Findings remain data
until capacity is reserved. Only then does the shared scheduler create one
immutable batch group and start the official dependency-package factory.
Security batches go first; within each priority class, the least recently
admitted project goes next, with Project ID as a stable tie breaker. Routine and
detect intents share admission and the same global budget.

At most four maintenance groups may hold or reserve a VM across routine, detect
and package work. Provisioning, parked, assistance and open-PR groups retain a
reservation until Orbit confirms VM destruction and terminal cleanup. Existing
work above the limit is left intact; no new work is admitted until room exists.
Orbit remains the only VM allocator: its provision operation waits for actual
free host capacity. The Swamp budget never bypasses that allocator or promises
four free Orbit slots. One project cannot admit another package batch until its
previous batch has merged and completed, or was cancelled, cleaned and acknowledged.
Routine/detect work for the same project also finishes before its batch starts.

Creation records intent before POST. An uncertain response is reconciled by the
saved brief; it is never blindly retried. A reservation is durable before a
create or factory start, so retries and lost replies consume the same place.
An immutable batch is identified by its detection receipt and targets. Repeated
ticks cannot create duplicate groups or change targets of an admitted run.
Blocked findings are visible alongside the eligible targets in Swamp resources;
no placeholder backlog groups are created for them.

The unchanged package factory drives provision → worker batch → handoff →
publish → wait for merge → completion and cleanup. A red worker command or
check gets one normal Orbit repair turn in the same VM, then the same full batch
is checked again. A second failure or operator/safety assistance parks. Publish
requires a passed check. Detection uses provision → script → finish and has no
handoff, repair, agent turn or PR.

Production resumes only after the orchestrator merges, deploys and explicitly
unpauses maintenance-projects and the project detect schedules. Deploying code
does not remove Swamp schedule pauses. Existing handoff-era detect groups need
operator reconciliation; deployment never rewrites their jobs or deliverables.
