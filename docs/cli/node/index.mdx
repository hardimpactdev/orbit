A Node is a machine that the Gateway manages over SSH and reaches over WireGuard. The `node` family adds a machine, converges it again, updates its name, platform and settings, assigns and moves its roles, records which Node may act on which, and removes it.

[Node provisioning](/reference/node-provisioning) explains what add, converge, role changes, and removal do on the machine. [Node settings](/reference/node-settings) owns the apps root and operator-approved task VM host configuration.

A Node's `updating` field is set only while a Gateway release runs on the Gateway Node ([Nodes being updated](/reference/gateway-recovery#nodes-being-updated)).

`node:add` returns an enrollment Operation. The CLI follows its native result; JSON mode returns the terminal Operation, and `node:show` returns the enrolled Node.

## Commands

| Command | Result |
| --- | --- |
| [`node:add`](/cli/node/add) | Add a machine, or converge an existing Node. |
| [`node:converge`](/cli/node/converge) | Re-apply the Gateway-rendered Orbit footprint of a Node. |
| [`node:list`](/cli/node/list) | List the Nodes and their agent state. |
| [`node:show`](/cli/node/show) | Show one Node, with agent liveness. |
| [`node:metrics`](/cli/node/metrics) | Show one metrics snapshot of a Node. |
| [`node:update`](/cli/node/update) | Change the name, platform, apps folder, or task VM host settings of a Node. |
| [`node:wireguard-key`](/cli/node/wireguard-key) | Set an unmanaged Node's WireGuard public key and update its hub peer. |
| [`node:role:add`](/cli/node/role-add) | Add a role, or converge an existing role. |
| [`node:role:list`](/cli/node/role-list) | List the roles of a Node. |
| [`node:role:relocate`](/cli/node/role-relocate) | Move `gateway`, `websocket`, or `metrics` to another Node. |
| [`node:role:remove`](/cli/node/role-remove) | Remove a role. |
| [`node:access:add`](/cli/node/access-add) | Grant one Node access to another. |
| [`node:access:remove`](/cli/node/access-remove) | Remove an access grant. |
| [`node:remove`](/cli/node/remove) | Remove a Node and hand the machine back. |

Every command accepts `--json`. Every command that targets an existing Node takes its numeric Node ID, as the API and the MCP tools do; a name is only the label that `node:add` and `node:update` set. In a terminal, an omitted Node is chosen from an interactive list.

Lists use tables. Below the minimum table width, each row becomes a labeled record. Details use an aligned tree, with an em dash for an empty value. While the Gateway works, the CLI shows one progress indicator per request, because it does not receive the steps. JSON output contains only the response.

Destructive commands ask for confirmation. The default answer is No. Declining, Ctrl-C, or end of input exits 1 and changes nothing. Without a terminal, and with `--json`, pass `--force`. `--offline` and `--purge-data` never give consent.

Set `task_vms.task_max_vms` through `node:update --task-vms` to cap task-work VM claims on a host. Parked claims count; authenticated CI and base refresh proofs are exempt. See [Task VM fields](/reference/node-settings#task-vm-fields) for the count and resource limits.

## Node access

The Gateway enforces one shared authority rule. Its active Gateway Node and its recorded serving host have fleet-wide authority. A Node with an access grant to the active Gateway also has fleet-wide authority. Otherwise, the caller needs an access grant to the target Node. Without either authority or a target grant, Orbit refuses with `node_access.required`.

## Recorded role assignments

[`node:role:list`](/cli/node/role-list) reads every assignment, including `active`, `provisioning`, `failed`, and `removing` records. It starts no Operation and contacts no Node or external service. Missing or stale agent facts do not change the result.

The JSON field `role_assignments` on [`node:list`](/cli/node/list) and [`node:show`](/cli/node/show) uses the same projection as the role list's `assignments`: `id`, `role`, `status`, `failed_step`, and `error_code`. Unset failure fields are `null`; recorded failure details stay visible even on an active assignment. Native step labels, such as `converge:Check the role`, keep their original case and spaces. All three lists use role-registry order, then assignment ID. The Node's `roles` field remains the role-name summary in that order.

## Why it works this way

These reasons explain the design. Check them before you propose a change.

### A dedicated relocate for gateway

The Gateway process serves the API. Removing the last `gateway` assignment and adding it again would drop the Gateway's authority and the `gateway.orbit` DNS record in between, so the second request might not run. Relocate keeps one active assignment for the whole move. Two active `gateway` assignments are rejected, because the fleet needs one authority and one address. The machine that runs the Gateway process keeps its authority during a move, because the bootstrap records it as the serving host.

### One relocate action for every relocatable role

Each role definition states whether the role is relocatable. Orbit does not infer it from singleton and mutable, because generic add and remove is a wider contract than a move. `gateway`, `websocket`, and `metrics` are relocatable. One relocate action runs the shared steps for all three: the singleton lock, the source check, the settings copy, and the assignment transfer. Role-specific work runs as a step for that role inside the same action. A new relocatable role adds the flag and its step, not a new command.

### The target's credentials win

A target that already holds working role credentials keeps them. Relocate copies only the credentials the target lacks, because overwriting a working identity would break its clients.

### Relocate moves no secrets

The checkout, the SQLite database, the Orbit CA, and the SSH keys live on the machine that runs the Gateway process. Copying them inside relocate would turn it into a secret-moving installer. You copy that state yourself and then converge the Gateway web stack on the new machine.

### vpn does not move

The WireGuard hub and private DNS stay on their original Node. `vpn` is protected from `node:role:add`, `node:role:remove`, and relocate.

### One update for a Node's fields

`node:update` is a partial patch: it changes only the fields you name. The name, the platform, and the task VM host settings are records, so the Gateway saves them at once. Only the apps folder changes the machine, so only it starts a run. One command keeps one place for a Node's fields. A rename does not touch WireGuard: removing and adding the Node again would delete its WireGuard peer and records.

Set `task_vms.ci_only` through `node:update --task-vms=JSON` to admit only authenticated CI proofs and the host’s own refresh proof. CI prefers these hosts. The [host settings reference](/reference/node-settings#task-vm-fields) lists capacity units and validation.

Role addition returns one queued Operation for every mutable role. `node:role:add` follows it to completion and prints any follow-up warning. Use `--converge` to converge an existing assignment and `--idempotency-key` to retry the same request.

Task VM host settings include `pool_size` for a new loop-backed ZFS pool. Existing pools keep their size. See [task VM host settings](/reference/node-settings#configure-a-task-vm-host).
