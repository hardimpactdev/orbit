The `task` family runs the operations of the Gateway [tasks extension](/reference/tasks) from the command line. Task VMs are [off in the live fleet](/reference/old-paths#off-in-the-live-fleet), so no task group runs on a VM today. Agents usually use the [MCP server](/reference/mcp); the CLI offers the same operations when MCP is unavailable. Each command name equals its Gateway route name, and its MCP tool name uses hyphens instead of colons, so `task:create` is the MCP tool `task-create`. Some operations have no CLI command. Use the MCP tool `task-check-cancel` to stop a running task check. The two merge steps of a task pull request, [`task:pr-ready`](/cli/task/pr-ready) and [`task:pr-merge`](/cli/task/pr-merge), are API and MCP only. The agent thread stream, `GET /api/v1/tasks/{task}/agents/{session}/stream`, serves the web app; [`task:agent:show`](/cli/task/agent-show) reads the same recorded snapshot. The stream sends one snapshot and ends; output updates when each turn ends. Reads never contact a task VM or Pi server.

A task is one feature. A subtask is one ordered child of that task, and a subtask has no children. A task stands alone with its own deliverables, or has at least two subtasks; a [task with no subtask](/reference/tasks#a-task-with-no-subtask) takes the subtask commands by its own ID. A command build verifies its runner plan as a deliverable; handoff runs the configured Project check once before the deliverables. The [tasks reference](/reference/tasks) owns the lifecycle, the scheduler, and every Gateway rule that these commands reach.

To inspect resource use on the task's Node, use [`node:metrics`](/cli/node/metrics) with its numeric Node ID. See [task VM resource observations](/reference/tasks#every-task-group-runs-on-its-own-task-vm).

| Command | Result |
| --- | --- |
| [`task:status`](/cli/task/status) | Show whether the tasks extension is on, list tasks asking for assistance, and list open review-and-merge pull requests. |
| [`task:list`](/cli/task/list) | List tasks, newest first, one page at a time, optionally for one Project or status. |
| [`task:show`](/cli/task/show) | Show one task with its brief and subtasks, or with its own deliverables. |
| [`task:create`](/cli/task/create) | Create a task in Backlog or Todo, with `--subtasks` or its own `--deliverables`; `--current-recipe` makes its VM wait for the current recipe image; `--review=automatic` is accepted, but its review rounds are removed: the gate check switches the group to manual mode. |
| [`task:update`](/cli/task/update) | Change a task's title, brief, status, or copy turn agents. A task with no subtask also takes `--deliverables` and `--work-status`. |
| [`task:cancel`](/cli/task/cancel) | Cancel a task and remove its Instance. |
| [`task:complete`](/cli/task/complete) | Complete a settling task, or a running or reviewing task whose watched pull request ended, and remove its Instance. |
| [`task:create`](/cli/task/create) | Append a subtask to a task. |
| [`task:update`](/cli/task/update) | Change a subtask's title, brief, position, or deliverables. In a task copy, correct a started subtask's deliverables after a failed check, with `--reason`. |
| [`task:destroy`](/cli/task/destroy) | Delete a subtask. |
| [`task:cancel`](/cli/task/cancel) | Cancel a Todo or running subtask. |
| [`task:comment:create`](/cli/task/comment-create) | Request group direction or record an answer after all subtasks end; start no work. |
| [`task:comment:list`](/cli/task/comment-list) | Read group-owned comments, including after completion. |
| [`task:comment:create`](/cli/task/comment-create) | Ask for assistance on a subtask or resolve a request. |
| [`task:comment:list`](/cli/task/comment-list) | List a subtask's comments. |
| [`task:question:list`](/cli/task/question-list) | List the questions agents asked, across tasks. |
| [`task:question:close`](/cli/task/question-close) | Close an open or escalated question as answered or superseded. |
| [`task:agent:list`](/cli/task/agent-list) | List a task's agent threads. |
| [`task:egress`](/cli/task/egress) | List the outside hosts a task's VM connected to. |
| [`task:agent:show`](/cli/task/agent-show) | Show one redacted read of an agent thread's conversation. |
| [`task:start`](/cli/task/start) | Start a task as a copy of its Project's default Instance, and wait until the copy is active. |
| [`task:turn`](/cli/task/turn) | Run one agent turn on a subtask, or on a task with no subtask. |
| [`task:check`](/cli/task/check) | Run a baseline or handoff check of a subtask, or of a task with no subtask. |
| [`task:publish`](/cli/task/publish) | Push a checked commit and optionally open or update its pull request. |
| [`task:sync`](/cli/task/sync) | Bring the Project's default branch into the task copy as `refs/remotes/origin/<default branch>`, and print how far behind the branch is. |

Every command accepts `--json`. JSON output is the Gateway record with `request_id` beside its fields. A list holds its records under `task_groups`, `comments`, `questions`, `agents`, or `hosts`. The [PHP SDK](/api/php-sdk) task responses return those same records, including `assistance_kind` and `assistance_question` on a task and a subtask.

Direct `task:*` calls send their request without discovering extension switches first, even when discovery is denied or times out. The Gateway enforces the extension switch and Node access.

`task:list`, `task:show`, and `task:question:list` accept any authorized peer. `task:update` and the `task:*` commands need access to the Node that holds the task's Instance, or to the Gateway for a task without one. The remaining commands need Gateway access too: run them on the Gateway, or on a Node with an access grant to the Gateway. Other callers receive `node_access.required`. While the extension is off, every command except enable, disable, and status fails with `extension.disabled`.

[Trusted GitHub requested changes](/reference/tasks#trusted-github-feedback) can append a normal fixup subtask. `task:show --json` exposes its source review and findings in the existing `brief`. The Gateway API's `fixup_problem` is `review:{reviewer_id}`; the CLI keeps its existing brief and deliverable fields without adding an identity field. Use the existing cancel or operator-subtask commands when that scope needs intervention. No command configures reviewer trust, submits a GitHub review, requests external re-review, or merges a pull request. In a Project with [review and merge](/reference/tasks#review-and-merge) on, the Gateway itself reviews and merges; the CLI only shows that state. The Gateway's automatic findings packet has its own 64 KiB bound; the CLI's 8,000-character input limit remains unchanged.

A subtask [declares no topology](/reference/compute-drivers#declare-a-topology). The CLI has no `--topology` option, and it ignores a `topology` key in a `--subtasks` file.

## Select a task or subtask

A `group` argument is a numeric task ID, and a `subtask` argument is a numeric subtask ID. When you omit either in a terminal, the CLI lists the candidates and you select one. The task list shows the ID, title, Project, and status. The subtask list shows the position, ID, title, and status of the task's subtasks. An empty list stops the command with `No matching records were found.`

With `--json` or `-n`, an omitted task fails with `task.task_required` and an omitted subtask fails with `tasks.subtask_required`. A value that is not a positive integer fails with `task.task_invalid` or `tasks.subtask_invalid`.

Human output names a task by its Project code and ID, such as `ORB-13`, as the web task board does. The CLI accepts only the numeric ID. Human output shows times to the minute in the Gateway's time zone; JSON keeps the full timestamps.

The CLI checks prompted text when you submit it. A title holds 1 to 160 characters, and a brief holds 1 to 8,000 characters. The brief prompt is a multiline text area. Pressing Ctrl-C or reaching the end of input at a prompt stops the command before any change.

## Select a task

Every command belongs to `task:*`. Select either level with its existing Task ID. A parent owns the Project, VM and publication; its ordered children are subtasks. REST uses `/api/v1/tasks` and `/tasks/{task}`. Parent responses expose `parent_id: null` and `subtasks`, and `work` for a task with no subtask; child responses expose their `parent_id`.

| Command | Selection and behavior |
| --- | --- |
| `task:create <title> --project=ID` | Create a parent, in Backlog by default. No VM starts. |
| `task:create <title> --parent=ID` | Create a child of that parent. The Project and workspace are inherited. A child cannot own children. |
| `task:list [--parent=ID] [--limit=N] [--cursor=CURSOR]` | List a page of the board's parents, or all of one parent's children. |
| `task:show <task>`, `task:update <task>` | Read or update either level using its own fields and statuses. |
| `task:start <task>` | Start a parent as a copy of its Project's default Instance, and wait until the copy is active. |
| `task:cancel <task>` | Cancel the selected parent or child. Parent cancellation releases owned work and its VM; child cancellation affects that child's work only. |
| `task:destroy <task>` | Delete a child while its parent is in Backlog. Parent deletion is refused. |
| `task:check <task>`, `task:turn <task>` | Select the child directly. Orbit derives the parent and preserves current-child and check receipt guards. |
| `task:publish <task>`, `task:complete <task>` | Require a parent. |
| `task:comment:create <task>`, `task:comment:list <task>` | Select either level. Parent assistance requires an open external parent with all children ended. Comments never start work. History remains readable after completion. |
| `task:agent:list <task>`, `task:agent:show <task> <session>` | Require the parent and verify session ownership. The transcript stream stays outside MCP. |

This is a hard switch. Old command names and `/task-groups` URLs have no aliases or adapters. Internal `tasks.*` operation kinds, workflow IDs, vault schemas, receipts and idempotency identities retain their names.
