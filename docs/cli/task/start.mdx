```bash
orbit task:start <task> [--idempotency-key=KEY] [--json]
```

Start the work place of a parent task in Todo. The task must use external orchestration and have no claimed workspace. The command follows the Operation it gets until that Operation ends. It starts no subtask, check, turn, or publication.

A task runs only as a copy. A Project whose default Instance is a container, or that has the [`nested_fleet`](/reference/projects#nested-fleet-setting) flag on, gets a task copy. Any other Project is refused: see [No container default](#no-container-default).

## A task copy

The task starts as a copy of the Project's default Instance. Orbit clones the default into the Instance `task-<id>`, on the new branch `task-<id>`, as [`instance:create`](/cli/instance/create) clones it. The task owns the copy. Orbit returns the `instance.create` Operation. The task is `running` once that Operation succeeded and the copy is `active`, which is fully set up. The copy's T3 server registers with Conn as every clone's does, labelled with the Project name and `task-<id>`. The copy has its own database, Route and Processes, as every clone does. Only a copy of a nested-fleet Project carries an inner fleet.

Orbit refuses the start at once and records nothing in these cases:

| Code | When |
| --- | --- |
| `tasks.copy_source_unavailable` (409) | The default Instance is missing, not active, stopped by hand, or has no seed snapshot. One read of its container, at most about 6 s, confirms that it runs or sleeps, whatever its record says: a container that does not run and has no asleep marker, or that cannot be read, refuses. An asleep default is a valid source and stays asleep |
| `tasks.copy_name_taken` (409) | An Instance named `task-<id>` exists |
| `tasks.copy_capacity_full` (409) | Nested-fleet Project only: the default's Node holds as many nested-fleet task copies as the Gateway allows. There is no wait |
| `tasks.copy_id_range_full` (409) | With the copy placed, the default's Node would keep no free [isolated ID range](/reference/development-containers#isolated-id-ranges) for the next seed of a default on it. The details name `free`, `size` and `seed_sizes_short`. There is no wait |
| `tasks.copy_id_ranges_unreadable` (409) | One bounded read of the Node's ID ranges, at most about 4 s, did not answer. Without it no free range can be shown |

Every copy takes an isolated ID range of the Node, and the default's next seed needs one for a moment. So each start reads the Node's real ranges and keeps one free for the seed ([isolated ID ranges](/reference/development-containers#isolated-id-ranges)). The Gateway setting `ORBIT_TASKS_COPIES_MAX` in the Gateway's `.env` is an upper bound on top of that: how many nested-fleet task copies one Node holds at once. The default is 1. Every nested copy that a task owns counts, also one whose create failed or that is being destroyed. A copy kept after a failed completion counts too, until it is destroyed: a retried completion that succeeds does not free its place. A copy of any other Project is a plain clone: it does not count and has no task cap. Turns and proofs in two copies on one Node do not wait for each other ([turn](/cli/task/turn#in-a-task-copy), [proof](/cli/proof/proof#the-run)).

### When the start fails

The copy is set up in two Operations, and a failure of each ends differently:

- **The create fails.** It failed, was refused by Swamp, or was cancelled before its run started. The task is `failed`, and Orbit removes the copy with `instance:destroy` with force only when no agent could have worked in it. That is so when the create did not succeed and no T3 server was registered for the copy. Otherwise Orbit first reads the copy's work as `task:cancel` does and destroys only a clean copy. A copy with work that origin lacks, or a read that does not answer, stays. The task asks for assistance with kind `removal_failure`: the reason names the counts and `orbit task:cancel <task-id>`, with `--discard` if the work is not wanted.
- **The completion fails.** The create succeeded, so the copy's thread was usable and an agent may already have worked in it. The `instance.complete` that starts its database, Processes and inner fleet failed, was cancelled or interrupted, or could not be admitted. Orbit keeps the copy and the task stays `reserved`. The task asks for assistance, unless a direction request is already open. The reason names the completion Operation, its failed step, its error code and the retry, `orbit instance:complete <copy-id>`. [`task:show`](/cli/task/show) and [`task:status`](/cli/task/status) show it. `task:start` keeps refusing the reserved task: run the retry. When the retry succeeds, the task runs and the assistance request goes. While the retry runs, a turn, a check, a publish and a proof answer `tasks.copy_not_ready`.

While the completion is failed, a turn, a check, a publish and a proof of the task answer `tasks.copy_completion_failed` (409). The copy's Processes and inner fleet did not start, and a retry may run at the same time. The details name `operation_id`, `failed_step`, `error_code` and `retry`, and `requires` when the retry needs a changed Process definition first.

When the run budget of the create or the completion expires, the task stays `reserved` with its copy, because the run may still be stopping. If a destroy fails, the task also keeps owning the copy. Run `task:cancel` to end the task. It reads the copy's work first and refuses to discard work that origin lacks unless you pass `--discard`. `orbit instance:destroy <copy-id> --yes --force` removes the copy without that read.

The copy's agent gets the fixed task model key, as every clone does; the key is not per task. Per-task model keys are an open decision. A stopped copy, for example after a reboot of its Node, stays stopped until Orbit starts it.

## No container default

Task VMs are removed. Orbit refuses the start of a task whose Project has no default container Instance with HTTP 422 `tasks.vm_runtime_removed` and records nothing: the task stays in Todo with no workspace, and no Operation exists. The CLI prints the message, and `--json` prints the code with it:

```text
Task VMs are removed. A task runs only in a copy of its Project's default Instance, and that default must be a container. Move a checkout default into a container with instance:migrate, or create a container default with instance:create; then start the task and work in its copy with task:turn, task:check and task:publish.
```

Move a checkout default into a container with [`instance:migrate`](/cli/instance/migrate), or, for a Project without a default, create one with [`instance:create`](/cli/instance/create). Then start the task again. Conn and the API show the same code and message. Every former task VM command answers the same refusal; see [Task runtime](/reference/tasks#task-runtime).

`--idempotency-key` reuses the same operation for a transport retry, also the `instance.create` of a task copy. Ctrl-C stops following and leaves the operation running. Use `task:cancel` to end the parent task.
