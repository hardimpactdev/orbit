# Human Renderer: `orbit doctor`

[Back to `doctor` technical contract.](1_doctor.md)

This page describes the human-rendered terminal output for `doctor`.

**Renderer:** Human renderer.

## Primitive

- Progress/result frame: doctor check-up frame.
- Inline verify issue details: dim dashed separator with human-readable bullets.
- Inline resolution action tables: [Table](../../../../ux/commands/lists/table.md)

## Selection

Use this renderer when neither `--json` nor `--stream-json` is present.

The human renderer does not own input prompting. `doctor` has optional filters
and fails invalid combinations before probes or side effects.

## Output Contract

Single-node human output is an operator report, not a terse status line. It must make these
facts visible without requiring JSON:

- selected verify scope;
- resolved scope: target node, active-role category set, app, workspace, and
  whether `--self` resolved the calling peer's identified node;
- whether the final result is healthy;
- one visible row per checked category;
- live per-category state while checks run;
- issue and action details inline under the category that owns them;
- final summary prose for issue count and next action.

Healthy output must not imply that unselected categories, apps, or workspaces
were inspected. Doctor output targets only the resolved node, and the rendered
category set is derived from that target node's active roles.

## Category Catalog

The renderer maps canonical state families to operator-facing category labels.
The canonical family keys stay visible in JSON; human output uses the labels
below.

| Family key | Human category |
| --- | --- |
| `node` | `Node` |
| `app` | `Apps` |
| `workspace` | `Workspaces` |
| `process` | `Processes` |
| `proxy` | `Proxy routes` |
| `firewall_rule` | `Firewall` |
| `tool` | `Tools` |
| `schedule` | `Scheduling` |
| `database_connection` | `Databases` |

`Node` is rendered singular because each run targets one node.

A future `DNS/TLD` row (operator/app targets) and `DNS` row (gateway target)
will be a renderer-only slice of `node` family probe results, pulling
resolver-specific findings into their own row. Until a DNS diagnostic source
lands, those facts stay inside the `Node` row and no separate DNS row is
emitted.

### Role-Aware Category Set

The visible rows are derived from the target node's active role assignments.
Family keys outside the active-role set are not probed and not rendered. Every
node with at least one active role assignment includes `Processes`. A
client/operator identity with no active role assignment renders only `Node`.

| Target role assignment state | Rendered categories |
| --- | --- |
| client with no active role | `Node` |
| active `gateway` role | `Node`, `Processes`, `Scheduling` |
| active `database` role only | `Node`, `Tools`, `Processes` |
| active `agent` role | `Node`, `Tools`, `Processes` |
| active `router` role | `Node`, `Proxy routes`, `Processes` |
| active `app-dev` role | `Node`, `Apps`, `Workspaces`, `Processes`, `Proxy routes`, `Firewall`, `Tools`, `Scheduling`, `Databases` |
| active `app-prod` role | `Node`, `Apps`, `Processes`, `Proxy routes`, `Firewall`, `Tools`, `Scheduling`, `Databases` |
| active `ingress` role | `Node`, `Proxy routes`, `Firewall`, `Tools`, `Processes` |
| active `websocket` role | `Node`, `Tools`, `Processes` |
| active `s3` role | `Node`, `Tools`, `Proxy routes`, `Processes` |
| active `metrics` role | `Node`, `Tools`, `Processes`, `Proxy routes` |
| active `vpn` or `analytics` role without another role-specific category | `Node`, `Processes` |

When the target is the calling peer's identified node (default or `--self`),
that node's active roles drive the category set. When `--node=<other>` selects
a different node, the *target* node's active roles drive the category set; the
calling peer's role only governs who is allowed to ask. Narrow `--family`
scopes intersect with the active-role set; families outside that set are
rejected before probes.

## Framed Panel Contract

Single-node and fleet (`--all`) human output share one bordered doctor panel
primitive. Each run uses one framed panel for in-progress and terminal display.
In decorated TTY output, the panel updates in place as rows complete, then
settles as the terminal result. In non-decorated output, progress snapshots are
suppressed and only the terminal panel is printed so logs stay readable. The
frame uses a fixed-width terminal layout when possible:

- top border contains the spaced panel title;
- second divider contains the scope target line;
- content rows appear in scope order (category rows for single-node, node rows
  for fleet);
- verify issue details appear inline immediately after the owning row;
- resolution action tables appear inline immediately after the owning row;
- terminal panels end with a `S U M M A R Y` divider and centered summary
  prose;
- in-progress panels omit the `S U M M A R Y` divider and all summary prose.

Panel titles use the renderer's existing centered spaced-letter convention:

| State | Verify-mode title |
| --- | --- |
| In progress | `D O C T O R` |
| Terminal result | `D O C T O R - R E S U L T` |

Restore, adopt, and interactive runs keep their existing terminal titles:
`D O C T O R  R E S T O R E`, `D O C T O R  A D O P T`, and
`D O C T O R  I N T E R A C T I V E`. While any of those runs is in progress,
the panel title is `D O C T O R`.

Single-node target lines:

```text
Performing check-up on <target>
Successfully performed check-up on <target>
Check-up on <target> could not complete
```

Fleet target lines:

```text
Performing check-up on fleet
Successfully performed check-up on fleet
Check-up on fleet could not complete
```

`<target>` is the resolved single-node name. Fleet mode never renders a fake
single-node target such as `this node`.

## Progress Tree

The framed panel renders as a single unified display that updates in place
during execution:

```
┌──────────────────────────────────────────┐
│  D O C T O R                             │  (in progress)
│  D O C T O R - R E S U L T               │  (terminal verify)
├──────────────────────────────────────────┤
│  [Scope target line]                     │
├──────────────────────────────────────────┤
│  ●  Row1            [Status]             │
│  ├─ [Optional verify issue details]      │
│  ├─ [Optional action table for resolution modes] │
│  ●  Row2            [Status]             │
│  ...                                     │
├──────────────────── S U M M A R Y ────────┤  (terminal only)
│  [Summary prose centered when possible]  │
└──────────────────────────────────────────┘
```

`RowN` is a category label in single-node output and a node name in fleet
output. The panel structure stays consistent across in-progress and terminal
states; only the title, target line, row statuses, issue details, and summary
section update. A run must not print repeated full framed panels in sequence.

## In-Progress Panel

`doctor` may perform gateway, remote probe, restore, and adopt work, so the human renderer must show the in-progress panel after scope authorization and before probes or side effects begin. Each category row starts as `Queued`, then
updates in place:

| State | Status text |
| --- | --- |
| Queued | `Queued` |
| Probe running, check total unknown | `Checking` |
| Probe running, check total known | `Checking - N%` |
| Result aggregation | `Gathering results` |
| Healthy category | `OK` |
| Issue category | `<n> issue detected` or `<n> issues found` |
| Empty category | `Skipped, no <category data> configured` |
| Probe unavailable | `Unavailable, <reason>` |
| Action running | `Restoring` or `Adopting` |
| Action complete | `<n> restored`, `<n> adopted`, `<n> skipped`, or `<n> failed` |

### Active Family Check Progress

While a family probe is running, the gateway may attach real completed and total
check counts on that family's `doctor.progress.families[]` entry as integer
`completed` and `total` fields. When both counts are present, `total` is greater than zero, `completed` is
strictly less than `total`, and the family status is a running probe state, the
renderer shows `Checking - N%` instead of plain `Checking`. Active rows must
not show `Checking - 100%`; when the final check unit completes, the gateway
omits the terminal running snapshot and the family transitions to its done
state in the next frame.

`N` is count-based only: integer percent from completed checks divided by total
checks for that family, truncated toward zero
(`floor(completed × 100 ÷ total)`). The renderer must not derive `N` from
elapsed time, weighted steps, interpolated liveness between
gateway frames, or invented sub-progress inside one opaque check.

When a family cannot expose a knowable check total, the gateway omits these
counts and the renderer keeps plain `Checking`. That omission is an explicit
implementation constraint for this slice; the renderer must not fabricate a
percentage. An opaque composite probe counts as one real check unit for this
slice; deeper sub-progress inside that unit is deferred.

The active family row keeps the existing blinking spinner glyph while its
status is `Checking`, `Checking - N%`, `Gathering results`, `Restoring`, or
`Adopting`. Static documentation samples do not override that runtime glyph
behavior.

In-progress panels for single-node and fleet runs must not render a `S U M M A R Y`
divider or interim summary prose such as `No issues detected so far` or
`<n> issues detected so far`. Summary prose appears only on terminal panels.

## Fleet Output

`--all` is verify-only fleet mode. Human output for `--all` uses the same
bordered doctor panel as single-node `doctor`. It must not use a separate
step-tree progress surface, `Check <node>` row labels, or a standalone
`F L E E T  D O C T O R  R E S U L T` block after the panel.

Fleet panel rows are keyed by gateway-known node names in probe order. Node row
status text reuses the same vocabulary as single-node category rows where
applicable (`Queued`, `Checking`, `Checking - N%`, `OK`, issue-count summaries,
and unavailable states).

When a node has issues in verify mode, append `:` to the node status and render
a dim dashed separator followed by one flat human-readable bullet list for that
node. Bullets may span all families checked on that node; per-family subsections
are not required in fleet human output.

Fleet in-progress panels may render issue details for nodes whose fleet probe
has already completed while later nodes remain `Queued` or `Checking`. The
gateway streams a partial fleet doctor snapshot on each completed-node step
when real report data exists. The CLI renders that doctor payload instead of
synthetic status-only progress. Each active node's `Checking - N%` is driven
by the progress of that node's own family checks (family-weighted); per-family
rows are not rendered in fleet output. Active nodes never show `Checking - 100%`.
When per-node progress is unknowable, the node shows plain `Checking`.

Example in-progress fleet output:


## Result Panel

The terminal human result uses the same framed panel. Verify-mode terminal
title:

```text
D O C T O R - R E S U L T
```

Interactive, restore, and adopt runs use these terminal titles:

```text
D O C T O R  I N T E R A C T I V E     (for interactive mode)
D O C T O R  R E S T O R E     (for restore mode)
D O C T O R  A D O P T     (for adopt mode)
```

Final category statuses use:

| Final condition | Status text |
| --- | --- |
| Category checked and healthy | `OK` |
| Category has issues | `<n> issue detected` or `<n> issues found` |
| Category has no configured rows | `Skipped, no <category data> configured` |
| Category probe failed without inline issue details | `Unavailable, <reason>` |

When a category has issues in verify mode, append `:` to the category status and
render a dim dashed separator followed by one human-readable bullet per issue.

Probe failures (`unverifiable` issues) follow the same shape. The category row
still uses `<n> issue detected` or `<n> issues found`, and the unavailable
reason renders in the bullet detail below the separator instead of inline on
the category row.

Long category status text and long issue detail bullets wrap inside the panel.
No human-output line may run into the right border.

The bullet text uses the issue summary when it is already human-readable. When
the summary is missing or is only the machine issue key/code, the renderer
derives a short human-readable fallback from the key/code instead of printing
the raw identifier.

If issue metadata contains an affected resource label, prefix the bullet with
that resource, such as `App nckrtl:`, `Workspace abc123.nckrtl.test:`,
`Process queue-worker for app nckrtl:`, `Proxy route nckrtl.test:`,
`Firewall rule allow-https:`, `Tool caddy:`,
`Schedule app:docs:laravel-scheduler:`, `Database connection ditis_hr:`, or
`Database connection REPORTING for app nckrtl:`.

Issue detail rows align to the first content column of the category row (the
same column as the category label), not the status column. The dim dashed
separator and bullet rows use that first-column alignment so issue text keeps
maximum horizontal room. The outer panel outline and dim issue separator
styling stay unchanged when issues exist.

Verify mode must not render nested issue tables. Single-node runs target one
node and the category row already names the family, so human detail lines do
not include repeated `NODE`, `APP`, `WORKSPACE`, or `ISSUE` headers. Fleet runs
render one flat bullet list per node across families. Resource labels appear
inline inside bullet text, not as table columns.

### Human Issue Bullet Truncation

Human output may truncate long issue bullet lists. Truncation is human-only;
`--json` and `--stream-json` payloads remain complete and stable.

| Scope | Bucket | Cap | Overflow line |
| --- | --- | --- | --- |
| Single-node | Per family category | 10 bullets | `+ 1 more issue` or `+ <n> more issues` |
| Fleet (`--all`) | Per node row | 10 bullets | `+ 1 more issue` or `+ <n> more issues` |

The overflow line uses existing Orbit issue-count pluralization (`1 more issue`
for a single omitted bullet; `<n> more issues` otherwise). Truncation must not
drop issues from machine payloads or change issue ordering in JSON/stream-json
output.

Node issue rows may wrap long summaries instead of truncating them. In
particular, `node.updates_reboot_required` must render this operator guidance
in human output:

```text
This node requires an explicit reboot to finish installed updates.
Orbit will not reboot it automatically. Reboot this server as soon as possible.
```

Action results are rendered inline below categories only when in resolution modes (interactive, restore, or adopt). Verify mode must not render action tables.
Dry-run resolution renders planned actions in the same action table area with `planned` status, while leaving the matching issues visible.

Issue categories sort by active-role-derived order. Within a category, sort by issue
kind order: `unverifiable`, `missing`, `divergent`, `extra`, then preserve probe
order.

For verify mode, the summary line when unhealthy is:

```text
<n> issue detected     (one issue)
<n> issues detected    (multiple issues)
```

The summary line never includes `across <m> categories`. Issue counts are
totals across the rendered categories for the targeted node.

Fleet verify-mode terminal summary uses the same issue-count pluralization and
adds the affected-node count:

```text
1 issue detected among 1 node
<n> issues detected among <m> nodes
```

`m` counts fleet nodes with at least one rendered issue, not every node in the
fleet panel. Healthy fleet runs keep `No issues detected` without an `among`
clause.

The next-action line is shown when issues remain:

```text
Run doctor --fix manually or through an LLM to resolve issues
```

For resolution modes, the summary line depends on remaining issues:

```text
No issues remaining; <n> actions completed     (healthy)
<n> issues remaining                           (unhealthy)
<n> actions failed; review remaining issues    (failed actions)
```

Action verbs in the summary use `restored` for restore-mode actions and `adopted` for adopt-mode actions. Interactive mode mixes both verbs based on per-finding operator choice.

## Empty Scope Output

When the selected scope has no rows for a family, the category row remains
visible if that family was selected and uses a skip status:

```text
●  Apps           Skipped, no apps configured
```

An empty-scope row is informational and does not make the run unhealthy.

## JSON Boundary

The framed panel is human-only. `--json` and `--stream-json` keep the existing
complete `success.data.doctor` / `error.data.doctor` payloads and stream
frames. Human truncation, panel titles, row layout, and bullet caps must not
remove issues from machine output or change JSON field names to satisfy human
layout needs.

## Failure Output

Validation failures, authorization failures, unsupported family selections, and
gateway connection failures occur before the framed panel can render. They keep
the shared human failure style from the command contract.

Probe failures inside a selected family render the framed result panel. In
verify mode the category row uses the issue-count summary and the unavailable
reason appears in the bullet detail below the separator. In resolution modes
the category row may use `Unavailable, <reason>` inline when issue bullets are
not rendered. The summary counts the category as an issue category.

Action failures occur in the resolution modes (`--fix`, `--restore`, `--adopt`)
and are rendered inline below the owning category in the same framed panel.
