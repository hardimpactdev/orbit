# node:add verification cases

The proof runs the built CLI against a fresh nested topology with a Gateway, a VPN hub Node and a blank Linux machine to add, plus a macOS-like peer. It checks the Gateway record, the machine state and real traffic. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| New Linux Node | Add the blank machine with its approved fingerprint. | The Operation succeeds and the Node is active with its architecture, host key pins and WireGuard key. The managed user logs in over SSH and runs sudo without a password. Packages, the public recovery SSH rule and the firewall are in place. No staged sudo file is left. |
| Tunnel | After the add. | The Node has a unique WireGuard address and the hub lists it as a peer. A packet crosses the tunnel in both directions and the handshake is recent. |
| Node agent | After the add. | The agent runs, reports to the Gateway, and `node:show` shows `online`. The observer secret is private. |
| Fingerprint mismatch | Approve a fingerprint that is not the machine's. | `node.ssh_host_key_mismatch`. The Operation fails before any change: no user, package, firewall rule or tunnel exists on the machine. |
| Fingerprint missing | A new Node without `--host-key-fingerprint`. | `node.ssh_host_fingerprint_required`. No Operation, no Node record, no change. |
| Existing unpinned peer | Enroll an existing Node that has no pinned host key, without and then with host and fingerprint. | The first is refused with `node.ssh_host_fingerprint_required`. The second succeeds and pins the key. |
| Existing Node, other fingerprint | Run the command for an existing Node with a fingerprint that differs from the recorded one. | `node.ssh_host_key_mismatch` at admission. No Operation and no change. |
| Unsupported architecture | A machine that reports another architecture, and `--architecture` that differs from the observed one. | `node.architecture_unsupported`. Nothing is recorded as active. |
| Roles | Add with `--role=app-dev --tld=...`. | The role is active and its services run. |
| First role | After a Node with a role is added. | The public recovery SSH rule is gone and public SSH is closed. The Node is reachable over WireGuard. |
| First VPN hub | Add the first Node with `--role=vpn`. | Forwarding is enabled on the hub, its DNS listener answers, private DNS records are published, and the hub public key is unchanged. The handshake check does not apply to the hub. |
| TLD and Cluster | `app-dev` without a TLD and without a Cluster TLD, then with a Cluster that has one. Also a TLD equal to `orbit`, an ancestor or descendant of it, and one another Node uses. | `node.tld_required`, then success, then `node.tld_invalid`, `node.tld_conflict` or `node.tld_taken`. A refusal creates no Operation and no change. An unknown Cluster is `cluster.not_found`. |
| Bootstrap options | `--ssh-port` that is not 22, a non-root `--user` with sudo, and a custom `--orbit-user`. | The bootstrap uses that port and user. The managed account has the custom name, with SSH and passwordless sudo. A malformed port or user is refused with `node.ssh_port_invalid` or `node.invalid_linux_user` before any request. A malformed platform or fingerprint gives `node.platform_invalid` or `node.host_key_fingerprint_invalid`. |
| Network options | `--wireguard-ip`, `--lan-ip`, `--wireguard-endpoint` and `--dns-server`. | The tunnel file and the hub peer entry carry the given address, endpoint and DNS server. A LAN address already used in the Cluster is refused with `cluster.lan_ip_conflict`. Malformed values are refused with `node.wireguard_ip_invalid`, `node.lan_ip_invalid` or `vpn.endpoint_override_invalid`. |
| Apps folder setting | `--setting=apps.path:/path`, then an unknown path and a repeated setting. | The folder exists on the Node, owned by the managed user. The others are refused with `node.setting_unknown` and `node.setting_duplicate`, and an invalid value with `node.setting_invalid`. |
| Other refusals | A role that conflicts with the Node's roles, a Cluster the Node cannot join, a changed managed user on an existing Node, and a host key that differs from the pinned one. | `node.role_conflict`, `cluster.membership_conflict`, `node.user_change_unsupported` and `node.ssh_host_key_changed`. No Operation and no change. |
| Run cannot start | An unreachable host, a bootstrap account that does not exist, and a failure the run cannot classify. | The Operation fails with `node.ssh_host_key_scan_failed`, `node.bootstrap_account_unavailable` or `node.enrollment_failed`. A new Node is marked failed and nothing else changes. |
| Hub peer | Add a Linux Node that joins the hub, then fail a later step. | The hub keeps the peer entry. A rerun reuses it and adds no second peer. |
| Unique tunnel key | Add a machine that has the same WireGuard public key as a Node. | The Operation fails at the key check and the Node is marked failed. No peer is added for it. |
| macOS peer | Add with `--platform=macos` and the same `--user` and `--orbit-user`. | The Node is active. No Linux package, user or firewall step ran on it. |
| macOS refusals | A macOS Node with a role, with a TLD, Cluster or storage setting, without `--user` and `--orbit-user`, with different ones, and without an existing WireGuard address. | `node.platform_unsupported` before SSH, then `node.macos_account_required`, `node.macos_account_mismatch` and `node.wireguard_required`. Nothing changes. |
| Orbit CLI | An eligible plan with the CLI present, then with its publishing made to fail. | The CLI is published, or its failure does not fail the add. The Node is active either way. |
| Failed run | Make a step fail after the baseline. | The Operation fails with the failed step. The new Node is marked failed and stays. Finished work stays on the machine. |
| Failed role | Make a requested role fail. | The role the request created stays marked failed. The rerun converges it and the Node becomes active. |
| Rerun after failure | Fix the cause and run the same command. | The Operation succeeds, the Node is active, and nothing is duplicated: one user, one control key, one tunnel interface, one hub peer, one agent. |
| Existing Node | Run the command for an active Node with a changed TLD or an added role. | The Node converges to the new settings and passes its check. A failed run leaves the earlier record and the Node stays active. |
| Repeat unchanged | Run the same command again for an active Node. | It converges, passes its check and succeeds. Nothing is duplicated. |
| Node with Instances | Run the command for a Node that owns Instances. | `node.has_instances`. No Operation and no change. |
| Busy name | Start a second add for the same name while one runs. | `node.provisioning_busy`. The first run is unaffected. |
| Missing input | In a terminal, run the command with no arguments. Then run it noninteractively and with `--json` without the name, without the host, and without the fingerprint. | The terminal asks for the name, host and fingerprint, and asks again for an invalid value. Ctrl-C ends with `input.cancelled` and no request. The noninteractive and `--json` calls are refused with `input.invalid` for the name or host and `node.ssh_host_fingerprint_required` for the fingerprint, with no request. Fails today: the host is only checked for a new Node and nothing prompts. |
| Progress and output | A wide and a narrow terminal, output piped to a file, and `--json`. | One progress indicator, then the final result with the Operation and request IDs. The piped output has no animation or escape codes. With `--json`, stdout holds only the final Operation. |
