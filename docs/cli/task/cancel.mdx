title: "orbit task:cancel"
sidebarTitle: "task:cancel"
description: "Cancel the selected task or subtask. The Gateway removes the task's workspace and task VM when it has them and marks the task `cancelled`. Subtasks, comments, and agent thread records stay as history. Cancellation does not stop the external agent conversation."
---

```bash
orbit task:cancel [task] [--yes] [--discard] [--idempotency-key=KEY] [--json]
```

| Option | Meaning |
| --- | --- |
| `--yes` | Confirm without a prompt. Required for `--json` and `-n` calls. It never discards work. |
| `--discard` | Destroy a task copy that holds work that is not on the default branch or published, or whose workspace cannot be read. The API and MCP field is `discard: true`. |
| `--idempotency-key=KEY` | Reuse a key to retry this operation start. |

In a terminal, the task list leaves out `settling`, `waiting_for_review`, and `completed` tasks. Before it asks, the CLI reads the task and names it and its Instance in the question. The question defaults to No. A `--json` or `-n` call without `--yes` fails with `input.confirmation_required`. Declining fails with `input.cancelled`. Neither changes the task. A `completed` task, or a `settling` task with a pull request, fails with `tasks.not_cancellable`; complete a settling task instead. Pass the task ID to cancel a `settling` task without a pull request. When the task holds a workspace or a task VM, origin's task branch must already reach its latest approved commit, or, for a task copy, the copy's latest read must find that commit's work on the default branch. Otherwise the call fails with `tasks.approved_work_unpublished`, names the commit, and changes nothing; run [`task:publish`](/cli/task/publish) first, which resumes a parked VM. A failed GitHub read fails the same way. The [tasks reference](/reference/tasks#cancel-a-stuck-task) describes the rule.

When the task has a running Operation, such as its task start, the cancel asks it to stop and answers `operation.target_busy` with its id if it is still running. Run the cancel again once that Operation has ended. An Operation that timed out can still hold the task while nothing proves that its run ended, for up to an hour. The cancel then answers `operation.target_busy` with its id too, before it admits the destroy of the task's copy.

When the task owns a task copy (see [`task:start`](/cli/task/start#a-task-copy)), the cancel keeps the work that only the copy holds. Work counts as published when its content is on the default branch, or in a commit that a succeeded `task:publish` of the task pushed. Commit SHAs do not matter, so a squash-merged or hand-carried branch is published. The [tasks reference](/reference/tasks#published-work-of-a-copy) defines the rule.

Without `--discard`, the cancel records its `tasks.cancel` Operation under the task's lock, answers HTTP 202, and starts a Swamp run. The run brings the current default branch into the copy, as [`task:sync`](/cli/task/sync) does, then reads the copy's `work`:

| Copy reads | Without `--discard` | With `--discard` |
| --- | --- | --- |
| `clean`: every committed change is on the default branch or published, and no uncommitted or untracked file or stash | The cancel admits the copy's destroy and succeeds. | The cancel goes on. |
| `dirty`: a committed path differs from the default branch, or uncommitted or untracked files, or stashes | The cancel fails with `tasks.copy_unpublished_work`. Its details carry the `head`, the differing `paths` and the counts. | The cancel goes on and the work goes with the copy. |
| unreadable: the copy is stopped or asleep, or the run failed | HTTP 409, or a failed cancel, with `tasks.copy_workspace_unknown` and its `reason`. | The cancel goes on. |

`--yes` only confirms the question; it never means discard. A failed cancel leaves the task running with its copy; only the copy's `origin/<default>` ref moved. Publish the work, or cancel again with `--discard`. The run holds the task's lock, so no turn, check or publish starts while it reads.

When the read is `clean`, the cancel admits `instance:destroy` of the copy with force. The destroy's checks and the Schedule stop come first: its replication slot check, then the stop of the copy's Schedules, which writes `schedule.destroy` Operations and removes the Schedules in Swamp. The cancel's result names the destroy Operation as `destroy_operation_id` and holds the read as `workspace`. The cancel does not wait for the destroy, and nothing is pushed first.

With `--discard`, the cancel reads nothing and starts no run. It records itself under the task's lock and admits the destroy in the destroy's one transaction, after the destroy's checks and the Schedule stop. An Operation that takes the task's lock first refuses the cancel with `operation.target_busy`, and no destroy is admitted. The copy's Schedules then stay stopped. The cancel is recorded as succeeded at once.

When the destroy succeeds, a task that still runs becomes `cancelled` and lets go of the copy; a task that is already `failed` stays `failed` and lets go of it. While the copy's create or an earlier destroy still runs, the cancel answers `operation.target_busy` with that Operation's id. When the destroy fails, the task keeps the copy and runs on; cancel again. The copy may then be stopped or half removed and cannot be read, so the second cancel may need `--discard`.

A child ID cancels only that child’s turn/check and keeps its parent workspace. It destroys nothing, so it ignores `--discard`. The Gateway derives ownership from the selected row.
