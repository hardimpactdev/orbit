# Realtime events

The Gateway broadcasts an event whenever a record changes so clients such as the [web app](/reference/web-app) stay current without polling. HTTP remains the only way to mutate state; events only notify clients that data they fetched has changed.

## Transport

The Gateway publishes to Laravel Reverb at `wss://reverb.orbit` on the Node holding the active `websocket` role ([Realtime events with Reverb](/solutions/realtime-reverb)). Without an active `websocket` role, the Gateway broadcasts nothing. Clients connect directly to Reverb; the Gateway acts only as a Pusher-protocol publisher.

The Gateway resolves the `websocket` Node's WireGuard address at most once per request, verifies `reverb.orbit` against `ORBIT_HOME/ca/root.pem` with system CAs disabled, and shares one empty private CA directory per PHP process (cleaned up on normal exit by the process that created it).

API requests dispatch broadcasts after sending the HTTP response, in commit order, so callers never wait on Reverb. Queued jobs, console commands, and fatal-error Activity finalizers broadcast immediately. Executor wake notices are persisted in SQLite with the state change and relayed via `operations-prompt` so activation workers never block on Reverb. Rolled-back changes broadcast nothing.

Broadcasts time out after 2 seconds to connect and 5 seconds total. Failures are logged and never fail the triggering request. During a `websocket` role move, the Gateway publishes to both servers, giving the old server 0.3 seconds to connect, 0.5 seconds total, and a 30-second skip after any failure.

## Channel and authorization

Gateway record events go to one private channel, `orbit`. Operation progress also broadcasts on `private-operation.{id}`. Clients authenticate subscriptions through `POST /api/v1/broadcasting/auth`, which identifies the caller by WireGuard address and requires Gateway access:

| Code | HTTP | Meaning |
| --- | --- | --- |
| `peer.identity_unknown` | 403 | The caller's address does not belong to an active Node |
| `node_access.required` | 403 | The caller lacks an access grant to the Gateway |
| `realtime.not_configured` | 404 | No `websocket` role is active |
| `broadcast.channel_forbidden` | 403 | Forbidden channel name, missing Operation, or unsupported presence/private channel |

The same endpoint authorizes `private-operation.{id}` for existing Operations and `viewer.*` membership on `presence-node.{id}` ([Node agent channels](#node-agent-channels)).

## Discovery

Clients query `GET /api/v1/realtime` (with Gateway access) to locate Reverb:

```json
{
  "data": { "url": "wss://reverb.orbit", "key": "<reverb-app-key>", "channel": "orbit" },
  "meta": { "request_id": "..." }
}
```

`url` and `key` are `null` when no `websocket` role is active. `channel` is always `orbit`, `key` is public, and the Reverb app secret never leaves the Gateway.

## Envelope

Every Gateway event uses the same envelope except [`conn.profile.updated`](#conn-profile), which sends only its raw payload. The broadcast event name equals `type`:

| Field | Contract |
| --- | --- |
| `type` | `<family>.<verb>`, such as `node.created` |
| `id` | Record ID (or step name for deploy steps) |
| `at` | ISO 8601 timestamp in the Gateway's timezone |
| `data` | Full API resource payload unless noted as a short snapshot or notice |

```json
{
  "type": "process.status",
  "id": 42,
  "at": "2026-09-18T10:15:00+00:00",
  "data": { "id": 42, "name": "web", "status": "active", "runtime_status": "running" }
}
```

`deleted` events carry a minimal identifying snapshot. Task, Activity, and Process usage events are lightweight notices; clients refetch full records over HTTP when needed.

## Event catalogue

### Node

Node events broadcast lifecycle, settings, role, and update-state changes:

| Type | Fires when | Data |
| --- | --- | --- |
| `node.created` | A Node is provisioned for the first time | `NodeData` |
| `node.updated` | A Node is re-enrolled, renamed, retargeted, changes settings or roles, or its [`updating`](/reference/gateway-recovery#nodes-being-updated) state changes | `NodeData` |
| `node.deleted` | A Node is removed | `{ id, name }` |

### Project

Project events track Project registration, updates, and deletion:

| Type | Fires when | Data |
| --- | --- | --- |
| `project.created` | A Project is created | `ProjectData` |
| `project.updated` | A Project changes | `ProjectData` |
| `project.deleted` | A Project is removed | `{ id, name, slug }` |

### Instance

Instance events track creation, branch changes, and deletion:

| Type | Fires when | Data |
| --- | --- | --- |
| `instance.created` | An Instance is created | `InstanceData` |
| `instance.updated` | An Instance is registered (synchronously or on native registration completion), its deployment branch changes, or removal returns while the record remains | `InstanceData` |
| `instance.deleted` | An Instance is removed | `{ id, name }` |

Transfers, clones, environment syncs, and deployments do not emit `instance.*`; deployments emit [`deployment.*`](#deployment).

### Process

Process events track Process definitions and control actions:

| Type | Fires when | Data |
| --- | --- | --- |
| `process.created` | A Process is added | `ProcessData` |
| `process.status` | A Process is started, stopped, or restarted | `ProcessData` |
| `process.deleted` | A Process is removed | `{ id, name }` |

`process.status` includes the stored status, desired state, and `runtime_status` observed when the action ended. Subsequent runtime changes arrive on [Node agent channels](#node-agent-channels).

### Process usage

The agent view subscriber emits `process.usage` every 15 seconds while at least one `viewer.*` member is connected to a Node agent channel ([Process usage](/reference/node-agent#process-usage)):

| Type | Fires when | Data |
| --- | --- | --- |
| `process.usage` | Every 15 seconds while a viewer watches | `{ part, parts, processes }` |

`id` is the Unix sample timestamp. `processes` holds up to 200 `[id, cpu, memory_bytes]` tuples per part, with `null` values when no sample exists.

### Schedule

Schedule events track Schedule creation, updates, runs, and removal:

| Type | Fires when | Data |
| --- | --- | --- |
| `schedule.created` | A Schedule is added | `ScheduleData` |
| `schedule.updated` | A Schedule activates, records a run, or begins removal | `ScheduleData` |
| `schedule.deleted` | A Schedule is removed | `{ id, name }` |

### Database connection

Database connection events track connection registration, edits, and deletion:

| Type | Fires when | Data |
| --- | --- | --- |
| `database.created` | A Database connection is registered | `DatabaseConnectionData` |
| `database.updated` | A Database connection changes | `DatabaseConnectionData` |
| `database.deleted` | A Database connection is removed | `{ id, slug }` |

### Firewall rule

Firewall rules are immutable once stored, so only create and delete events exist:

| Type | Fires when | Data |
| --- | --- | --- |
| `firewall.created` | A firewall rule is stored | `FirewallRuleData` |
| `firewall.deleted` | A firewall rule is removed | `{ id, port, protocol, source }` |

### Route

Route events track explicit Route API changes and analytics tracking Routes:

| Type | Fires when | Data |
| --- | --- | --- |
| `route.created` | A Route is created via the Routes API or analytics | `RouteData` |
| `route.updated` | A Route's domain, publication, or target changes | `RouteData` |
| `route.deleted` | A Route is removed | `{ id, domain }` |

Routes created or replaced implicitly by Instance creation, cloning, transfer, or domain/target switches do not emit `route.created`.

### Deploy step

Deploy step events use the step name as `id` and omit the Instance ID:

| Type | Fires when | Data |
| --- | --- | --- |
| `deploy_step.created` | A deploy step is added | `DeploymentStepData` |
| `deploy_step.updated` | A deploy step changes | `DeploymentStepData` |
| `deploy_step.deleted` | A deploy step is removed | `DeploymentStepData` of the removed step |

### Deployment

Deployment events track deploy and rollback runs without including run output:

| Type | Fires when | Data |
| --- | --- | --- |
| `deployment.created` | A deploy or rollback starts | `InstanceDeploymentData` |
| `deployment.updated` | The run finishes with success or failure | `InstanceDeploymentData` |

The Gateway retains the 50 newest deployment rows per Instance and prunes older rows silently.

### Operation

Operation events are notices that never carry inputs, steps, output, or results:

| Type | Channel | Fires when | Data |
| --- | --- | --- | --- |
| `operation.created` | `orbit` | An Operation is queued | `{ id, kind, target_type, target_id, status, sequence, current_step }` |
| `operation.updated` | `orbit` | An Operation starts, ends, or receives a cancel request | Same fields |
| `operation.updated` | `private-operation.{id}` | The Operation or any of its steps changes | Same fields |

On `private-operation.{id}`, output changes throttle to once per second while status and step transitions fire immediately. Clients drop events whose `sequence` is not greater than their last seen value and fetch updates with `after_sequence` ([Follow an operation over Reverb](/reference/operations#follow-an-operation-over-reverb)).

[Conn launches](/reference/conn#durable-launches-v1) do not use Operation channels; launch invalidations reach only peers matching the profile binding and target Node access.

### Conn profile

Conn profile updates bypass the standard envelope and never publish on `orbit`:

| Event | Channel | Fires when | Payload |
| --- | --- | --- | --- |
| `conn.profile.updated` | `private-conn-profile.{key}` | A Conn profile write commits | `{ profile_id, version }` |

Only `POST /api/v1/conn/broadcasting/auth` authorizes `private-conn-profile.{key}` for the bound Node ([Profile events](/reference/conn#profile-events)).

### Tasks

Task events notify clients of group, comment, thread, and extension changes:

| Type | Fires when | Data |
| --- | --- | --- |
| `task_group.created` | A task is created | `{ id, status }` |
| `task_group.updated` | A task, subtask, check, or workspace diff changes | `{ id, status, lines_added, lines_deleted, line_diff }` |
| `task_comment.created` | A comment or turn receipt is stored | `{ id, task_group_id, task_id }` |
| `agent_thread.updated` | An agent thread is created, admits a turn, or records a terminal observation | `{ id, task_group_id, task_id, state }` |
| `tasks.updated` | The Tasks extension is enabled or disabled (`id` is `0`) | `{ enabled }` |

Top-level task threads carry a `null` `task_id`, while subtask threads carry the subtask ID. Reserved threads (`pending:*`) emit nothing. Changes only to token counts, line counts, or duration during a request or tick emit nothing; workspace publish runs always emit `task_group.updated`. The Gateway coalesces task changes per request, tick, or publish run and broadcasts each record once at the end.

### Activity

Activity events track audited requests without ever deleting rows:

| Type | Fires when | Data |
| --- | --- | --- |
| `activity.created` | An Activity row is stored | `{ id, request_id, command, status, caller_node_id, target_node_id, error_code, duration_ms, occurred_at }` |
| `activity.updated` | A `running` row records its outcome | Same fields |

Commands starting with `activity:` and writes that touch only `properties` emit nothing. Removing a Node clears `caller_node_id` and `target_node_id` to `null`.

## When no event fires

Events fire only after an action commits, except for failed deployments and failed Activity rows. Unchanged idempotent creates emit nothing, and runtime state changes outside `node.updating` emit no record event (hibernation awake state lives outside Instance and Process records).

## Node agent channels

Each managed Linux Node has a presence channel `presence-node.{id}` where its [Node agent](/reference/node-agent) publishes presence, Process state, workspace updates, and `client-executor-result` replies. The Gateway publishes the server event `executor-order` (`{ operation, order }`) on `presence-node.{id}` for signed executor orders ([The observer pass-through](/reference/executor#the-observer-pass-through)), and its agent view subscriber joins every channel to maintain the [Gateway view](/reference/node-agent#gateway-view).

### Membership

Reverb announces members on first join (`pusher:member_added`) and last disconnect (`pusher:member_removed`):

| Member ID | Who | Signed by |
| --- | --- | --- |
| `agent.{id}` | Agent on Node `{id}` (`{ kind: "agent", node_id, version }`) | `POST /api/v1/agent/broadcasting/auth` with Node IP and [agent secret](/reference/node-agent#agent-secret) |
| `gateway.{socket id}` | Gateway agent view subscriber (`{ kind: "gateway" }`) | Subscriber itself with the Reverb app secret |
| `viewer.{socket id}` | Any viewer such as the web app (`{ kind: "viewer", node_id }`) | `POST /api/v1/broadcasting/auth` |

`POST /api/v1/broadcasting/auth` never authorizes `agent.*` or `gateway.*` members.

### Events

The agent sends Pusher client events (`accept_client_events_from: members`), and Reverb stamps each event with the sender's `user_id`. Subscribers ignore any event on `presence-node.{id}` whose `user_id` is not `agent.{id}`:

| Event | Cadence | Data |
| --- | --- | --- |
| `client-heartbeat` | Every 5 seconds | `{ sequence, at }` |
| `client-snapshot` | On join, member join, Docker reconnect, and every 60 seconds | `{ sequence, at, docker, part, parts, units }` |
| `client-process` | On unit or container change (250 ms debounce) | `{ sequence, at, unit }` |
| `client-workspaces` | After each snapshot, watch list change, or read error | `{ sequence, at, part, parts, workspaces }` |
| `client-workspace` | When a watched task checkout changes | `{ sequence, at, workspace }` |

Key fields follow these contracts:

| Field | Contract |
| --- | --- |
| `sequence` | Monotonic counter per agent run, restarting at 1 on restart. If it drops without a member event, subscribers discard state and wait for a snapshot |
| `at` | ISO 8601 UTC timestamp |
| `docker` | `available` or `absent` |
| `part`, `parts` | 1-based pagination keeping messages under Reverb's 10,000-byte limit; applied once all parts arrive |
| `units` / `unit` | `{ name, runtime, runtime_status }` for `orbit-process-*` units (`systemd` or `docker`), without `.service` |
| `workspaces` / `workspace` | `{ instance_id, base, start, branch, head, dirty, commits, diff }` ([Task workspaces](/reference/node-agent#task-workspaces)) |

A complete snapshot replaces known units (missing units read as `inactive` for systemd or `exited` for Docker), and a complete `client-workspaces` replaces known workspaces. Subscribers match `unit` entries only to Processes on Node `{id}` with matching runtime and `orbit-process-{process id}-{process name}`.

### Presence

Subscribers treat an agent as online while `agent.{id}` is present and an event arrived within the last 15 seconds. After `pusher:member_removed` or 15 silent seconds, the agent is treated as lost.

## Log channels

[Live logs](/reference/live-logs) use dedicated channels so log lines never enter `orbit` or `presence-node.{id}`:

| Channel | Members | Signed by |
| --- | --- | --- |
| `presence-node-logs.{id}` | `agent.{id}` and `gateway.{socket id}` | `POST /api/v1/agent/broadcasting/auth` for the agent; subscriber signs itself |
| `private-log-stream.{stream}` | The single client that opened the stream | Stream-open response for that client's `socket_id` |

The agent publishes `client-log` (with `first_done: true` on the final initial-batch event) and `client-log-end` on `presence-node-logs.{id}`. The Gateway publishes `log-streams.changed` with empty data when streams open or close, prompting the agent to fetch its [stream list](/reference/node-agent#stream-list), and relays `log.lines` and `log.ended` on `private-log-stream.{stream}` using the standard envelope.

## Why it works this way

Running Reverb on its own `websocket` role keeps long-lived WebSocket connections out of the Gateway API workers. Using a single `orbit` channel for record events avoids redundant authorization rules because every subscriber already has Gateway read access, while per-Operation channels keep high-frequency step updates off unrelated clients. Presence channels per Node let Reverb stamp each client event with `agent.{id}` so a Node can only report state for itself, and a 15-second heartbeat timeout detects lost agents far faster than Reverb's default connection sweep.
