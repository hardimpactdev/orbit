sidebarTitle: "task:complete"
description: "Complete a `settling` or `waiting_for_review` task after its pull request is reviewed and merged. Also complete a `running` or `reviewing` task whose watched pull request has merged or closed, or whose task copy's work is already on the default branch. The Gateway marks the task `completed` and removes its shared Instance."
---

On the `running` or `reviewing` path it stores the ended state, stops the running implementer or reviewer and any running check, then cancels each open subtask and marks the task `completed` in one transaction. A failed stop returns `tasks.subtask_interrupt_failed`, keeps the task and its subtasks open, and leaves the stored completion for retry. The [tasks reference](/reference/tasks#complete-and-cleanup) defines how a crash resumes without another GitHub read. Completing a completed task whose checkout is already gone succeeds and changes nothing. Completing a completed task that still has its Instance retries removal. There is no `task:continue` command.

```bash
orbit task:complete [task] [--yes] [--json]
```

| Option | Meaning |
| --- | --- |
| `--yes` | Confirm without a prompt. Required for `--json` and `-n` calls. |

In a terminal, the task list shows only `settling` tasks. Pass the task id to complete a `running` or `reviewing` task whose watched pull request has ended. The question names the task and its Instance and defaults to No. Consent failures match `task:cancel`. A `running` or `reviewing` task with a [task copy](/cli/task/start#a-task-copy) and no ended watched pull request completes when its work was carried to the default branch another way, such as a pull request opened by hand. The copy's latest read decides, as [published work of a copy](/reference/tasks#published-work-of-a-copy) defines: it must be of the copy's current head, find every committed path on the default branch, and not be empty. A [`task:sync`](/cli/task/sync) of the copy makes that read. A task that is not one of those ready cases fails with `tasks.not_settling`, and its `reason` detail says why:

| `reason` | Meaning |
| --- | --- |
| `status` | The task is in no ready state, or its state changed while complete ran. |
| `pull_request_not_ended` | The watched pull request is missing, open, or unreadable, and the task has no task copy. |
| `work_unread` | No read of the copy's current head. Run `task:sync`, then complete again. |
| `work_not_on_default` | A committed path of the copy differs from the default branch. |
| `work_empty` | The copy changed nothing. Cancel the task instead. |

Completion that was already recorded skips these checks. When the task holds a workspace or a task VM, origin's task branch must already reach its latest approved commit, or, for a task copy, the copy's latest read must find that commit's work on the default branch. Otherwise the call fails with `tasks.approved_work_unpublished`, names the commit, and changes nothing; run [`task:publish`](/cli/task/publish) first, which resumes a parked VM. A failed GitHub read fails the same way. When removal fails, for example while the task VM resumes, the task is still marked `completed`, the Instance stays attached, and a later complete retries removal, as the [tasks reference](/reference/tasks#complete-and-cleanup) describes.

When the task owns a [task copy](/cli/task/start#a-task-copy), complete removes it with the normal `instance:destroy` of the copy, with force, as `task:cancel` does. It needs no `--discard`: complete already proved that origin, or the default branch, has the approved work. Complete first reads the copy as `task:cancel` does, and never destroys a copy that holds uncommitted, untracked, stashed or other-branch work: it fails with `tasks.copy_unpublished_work` and the read's counts, or `tasks.copy_workspace_unknown` when the copy cannot be read, and changes nothing. Publish or remove that work, then complete again. A copy task whose watched pull request merged completes by itself; see [A copy group settles on merge](/reference/tasks#a-copy-group-settles-on-merge). The task is `completed` at once and still names the copy until the destroy succeeds; then it lets go of the copy. When the destroy fails, the task stays `completed` with its copy, and a later complete admits the destroy again. The failure is recorded on the destroy, not on the task: [`operation:list`](/cli/operation/list) shows the copy's failed `instance.destroy`, and [`task:show`](/cli/task/show) still names the copy as the task's Instance. Run complete again to retry. An open destroy of the copy is reused, so a repeated complete admits no second one. A running implementer turn in a copy is its `tasks.copy_turn` Operation, which complete stops as it stops any running Operation. Its `t3` thread has no interrupt, so the subtask stop sends none: complete stops the group's open Operations first, and the destroy ends a T3 run that outlived its Operation.

When the task has a running Operation, complete asks it to stop and answers `operation.target_busy` with its id if it is still running. Run complete again once that Operation has ended.
