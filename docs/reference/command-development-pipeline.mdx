# Command development pipeline

The command development pipeline is the stages every command goes through during development, from prep to a per-host refresh after release. A command goes through them one at a time. Stages 1 to 4 happen in one PR per command change: the spec, the code and the runnable proof cases land together. Each stage below shows its status on `main`, its flow chart, and links to its pages, skill and key files. The stage charts are drafts of the target design; they live in `docs/reference/pipeline/`. The [feature flow](/reference/feature-flow) holds the proof CI job and the case selection list.

## 1. Prep

**Partly built.** A command has one PR, and prep starts it. The chart, docs page and verification cases (the spec) are the first commit of a draft PR. A merged docs PR does not make a command ready. The spec is approved in the draft, and the PR stays one PR through code, proof and merge. Prep changes no code. Swamp owns the flow and its state and the Gateway only authorizes it: an author agent drafts the spec in a task VM, a separate review agent checks it, and Swamp opens the draft PR as the Orbit App. One of two modes, set per flow, decides what happens next. In manual mode there is an optional spec checkpoint: Nick reviews the chart, docs and cases in the draft before code is written, and may check out a development Instance on the PR branch and review there with an agent. In automatic mode there is no checkpoint. The code and the runnable proof cases then follow in the same PR ([stage 4](#4-pr-and-ci)). Not built: the Swamp prep flow, PRs opened by the App, and the approval-triggered continuation.

About 74 commands have a chart and a page from earlier docs-only PRs. Their old case tables are deleted. When a command's turn comes, its PR reviews and updates the chart and page, and writes the cases file from them.

## 2. Development environment

**Built, with a slot pool still to come.** A task VM, started with `tasks:provision`, holds a nested topology: a Gateway with Swamp, an `app-dev` Node and an `app-prod` Node. They share a real nested WireGuard network, `10.45.0.0/24`, and the outer VM is the operator. Each task VM host keeps ready copies of this topology in its topology seed, so a reset takes about 75 seconds instead of a 230-second build. An agent, or Nick, develops a command here, and the proof cases run here too.

The target: the nested VMs hold their own checkout, with no code share from the outer VM. `orbit-nested` syncs the author's changes into them before each call. At task start, Swamp takes an Incus memory snapshot `base` of the three VMs; restoring it takes about 16 seconds until the fleet is healthy. Built: the sync, the snapshot and the restore. A call that syncs nothing adds about 0.3 seconds; a change that reaches the Gateway adds about 1 more second for the apply step. `orbit-nested exec NODE -- CMD` syncs and then runs a direct command in a nested VM. Not built: the converge step for playbook and pin changes.

## 3. Proof

**Partly built, with one case so far.** The cases of a command run on that topology. The target: Orbit's own Swamp runs the proof directly and reaches into the task VM over SSH, like every other step. A run restores `base`, syncs the author's code and takes `base` again when something changed. Each batch then restores `base` once, and its cases run one after another without undo, each on its own resources. A case that does not pass triggers a restore. Each case calls the real CLI, checks the real effect and prints a verdict. The first case is the `firewall:allow` traffic case. Not built: that direct Swamp run; today `bin/proof-fleet verify` starts a local Swamp in the VM.

## 4. PR and CI

**Partly built.** This stage continues the same PR that stage 1 opened as a draft. The author pushes the command code and the runnable proof cases to its branch, so a reviewer can check that the chart, docs, cases, code and proof cases match. There is one CI: the fast checks (about 2 minutes) plus, for command code, the proof CI (`proof:run` for the affected commands). It runs on every push. The proof CI starts only when a changed path selects a command in `swamp/proof/selection.txt`. Docs, charts and case descriptions never start it. A new push cancels the proof run of the previous push on that PR. When everything is green, the PR leaves draft. In manual mode, Swamp also requests Nick's review, so GitHub notifies him. Then comes the gate: in manual mode, Nick's approving review on the exact head; in automatic mode, a final self-review by a fresh review agent, with at most 3 rounds before the PR switches to manual mode. After the gate, Swamp merges the PR straight into `main` with a squash merge, using a Gateway-minted App token. There is no merge queue and no GitHub auto-merge. CI then runs on `main`. A red `main` is fixed forward and never released. The proof runs only on the PR head, never again before or after the merge. Two PRs for the same command normally conflict, because each edits the command's chart, page and cases file. The second PR rebases, which reruns CI and the proof. Built for manual mode: the ready step ([`tasks:pr-ready`](/cli/tasks/pr-ready)), the merge step with the manual gate ([`tasks:pr-merge`](/cli/tasks/pr-merge)), and the gate check that calls them. The gate check is the Gateway command `tasks:pr-gate`. Every minute, like the release check of stage 5, it reads with read-only App tokens the open external Task groups of review-and-merge Projects that have a published PR. A draft PR with a green CI result on its head gets the ready step. A PR out of draft whose head Nick approved gets the merge step. Each admission is keyed by group and head, so a repeat tick is a no-op, and each starts its own Swamp run. Not built: PRs opened by the App, the automatic review gate, and the proof CI job. A PR that is not in a Task group is outside this flow: the author opens it as `nckrtl` and squash-merges it with `gh pr merge <n> -R hardimpactdev/orbit --squash` when CI is green on the head (the interim).

## 5. Automatic Swamp release

**Built.** The Gateway looks for the newest green commit on `main` and starts one Swamp run: build, snapshot and migrate, switch, load the new workflows and check health. A green commit has `Required checks` and `Gateway release inputs` green in its CI run on `main`. There is no merge queue, so a red `main` commit is never released; `main` is fixed forward. A failed check switches back.

## 6. Per-host task image and seed refresh

**Partly built.** There is no image build per release. Each task VM host (Linux only: beast and shark) refreshes its own task image and topology seed, and the hosts work in parallel. Nothing is copied between hosts. The trigger is a release that changed playbooks, pins or lock files, plus a daily run. Per host, Swamp starts a refresh task VM from the current image and seed, then resets and syncs the release commit. It converges once if playbooks or pins changed. It re-mints the nested Swamp tokens. Then it saves the outer VM as the new task image and the nested VMs as new ready copies, key-free. It boot-checks both and promotes them. A recipe build runs only for a new host or a new base OS.

<div className="flow-at" data-chart="reference/pipeline/6-task-image-seed-refresh"></div>

- Interim, until the stage 6 refresh exists: the recipe image build, and a seed refresh that an operator starts with `php artisan task-vms:refresh-seed <host>`. The stage 6 refresh replaces both.
- Not built: the release trigger, the daily schedule (B8), and the refresh from a running task VM instead of a build.
- Charts: the stage chart above, the [task VM slot pool](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/tasks/vm-slots.mmd) (draft; a refresh replaces ready slots built from the old image, one at a time).

## Change the development pipeline

Change a stage in the place that owns it, and update this page in the same PR.

- **This page:** the stages, their order, their status and their links. Edit `docs/reference/command-development-pipeline.mdx`. A stage that gets built changes its status here.
- **The charts:** edit the `.mmd` file next to the command page, chart first. The stage charts are `docs/reference/pipeline/<n>-<stage>.mmd`, placed on this page with a `flow-at` placement, as the CLI pages rules describe. Run `bin/check-flows`. The rules are in [CLI pages and flow charts](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/README.md).
- **The skills:** `preparing-commands` for stage 1, `verifying-commands` for stages 2 and 3, and `developing-commands` for stage 4 and the code. They link here and to the charts and keep only what an agent must do at its own step.
- **The proof CI job and the selection list:** [Feature flow](/reference/feature-flow).
