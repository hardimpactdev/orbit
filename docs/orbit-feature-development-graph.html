PROVE sequence: current enforcement vs proposed target

Current enforcement
  1. Focused checks, then diff-routed broader gate
  2. Commit exact candidate; clean worktree
  3. Derived-venue proof (and any required decisive live proof) on the single runtime receipt
  4. General reviewer PASS only after that decisive runtime receipt is already present
  5. Candidate-bound evidence → ACCEPT

Today’s reviewer contract and loop.md have one runtime receipt. Tooling does not support a second post-review runtime receipt.

Proposed / target (not enforced yet)
  1. Focused checks, then broader gate
  2. Commit exact candidate; clean worktree
  3. Pre-live venue proof (usually dev-fixture)
  4. Reviewer PASS on that exact HEAD
  5. Conditional live-environment proof with the same reviewed candidate when the Goal requires it
  6. Candidate-bound evidence → ACCEPT

Visible as the agreed target. Do not treat it as current tooling behavior.

Same-candidate retry keeps Review and the reviewed tip. Any code change returns to BUILD, invalidates review, and requires all affected proof plus re-review.

Three different ideas (do not collapse them)

  • Live proof — in PROVE: exercise the exact feature candidate against the live environment when the Goal claims live reachability/convergence (currently must be the decisive pre-PASS receipt when required).
  • Fleet rollout / live update:all acceptance — in the release lifecycle after LAND: fleet-wide update:all of the candidate (mandatory if you enter release; not a feature-loop step).
  • Public release — after live update:all acceptance and explicit human publish approval: publish the exact tested artifacts.

Protection ladder (HARNESS Feedback And Protections)

After diagnosing and repairing the immediate problem, promote reusable protection in this order:

  1. test, linter, schema, or state check
  2. tool, safe default, generated contract, or template
  3. cheap calibrated UX check
  4. targeted context for the general reviewer
  5. concise instruction
  6. extra ceremony only when unavoidable

Incus is not a ladder rung. A chosen protection is proved through the normal diff-routed proof, so retained Incus is used only when the protection genuinely requires integrated topology. Every promoted protection names one rejected and one accepted example and runs through normal diff-routed proof; there is no second receipt gate. Unknown cause → improve evidence; do not add speculative protection.

Responsibilities

This is the HARNESS-defined role policy. The orchestrating session (Codex or Claude) that the human started is the sole feature owner. Grok worker via bin/orbit-worker-spawn at the exact worktree; Claude Opus general reviewer is reused for the review cycle.

  • User Supplies the goal and human judgment when required.
  • Orchestrating session (Codex or Claude) Frames, coordinates Grok implementation, integrates, and verifies.
  • Grok worker via bin/orbit-worker-spawn Owns substantive edits in the exact feature worktree.
  • Claude Opus general reviewer Issues PASS, FIX, or ESCALATE (and human-judgment decision).
  • Orbit harness Records state and evidence; gates transitions (.orbit/loop.md, acceptance, finalization).

HARNESS defines this split and forbids direct Codex implementation or Codex worker substitution.
