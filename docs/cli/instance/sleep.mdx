Put one development container Instance to sleep now. Orbit freezes the whole container and moves its memory to swap, so it holds almost no RAM. Its processes, disk, databases, Route, T3 threads and sessions stay. [Sleep and wake](/reference/development-containers#sleep-and-wake) explains the lifecycle.

With signed power enabled, the command and idle sweep use the same executor and record the same `instance.sleep` Operation. The Gateway chooses the engine at admission and sends the signed order to the Node once, over its WebSocket.

Every development container sleeps the same way: a clone, its Project's default, and an Instance of a nested-fleet Project. What keeps an Instance awake is data, never its name: a keep-alive Process, a Node service, an open Operation, a task, the never-sleep list, or recent traffic.

**This command does not check T3.** If an agent turn runs in the Instance, the freeze holds it, and a model provider may drop its connection during a long sleep. T3 continues the turn when the Instance wakes. The result says `t3_turn: not_checked`. The [idle sleep](/reference/development-containers#sleep-and-wake) after an idle hour does check T3 first, never cuts a turn, and admits the same Operation; its result says `t3_turn: idle`. An Instance without a T3 server, such as a default, has no turn to check: either result says `t3_turn: no_server`. It never puts an Instance to sleep before it has watched it for one idle window, and never one that uses a Node service.

## Usage

```sh
orbit instance:sleep 42
orbit instance:sleep 42 --json
```

| Argument or option | Meaning |
| --- | --- |
| `instance-id` | Numeric Instance ID. |
| `--idempotency-key=KEY` | Reuse a key to retry this operation start. |
| `--json` | [Machine output](/reference/cli-ux#input-and-output-modes). |

Orbit first writes the asleep marker on the Node. From then on, each request to the Route waits while the Instance wakes. Then Orbit lets the container's memory go to swap and freezes the container (`incus pause`). While it is frozen, Orbit records which pages of each of its processes were resident, and then it reclaims all of its memory. The wake reads those pages back before the container resumes, so the app answers sooner ([Prepared restore](/reference/prepared-restore)). The record holds addresses only. It sends no request to the app and picks no process by name. The result's `prepared_restore` says whether a plan is `ready`, with its size and `prepare_seconds`, and how much memory stayed in RAM. A nested-fleet Instance gets no plan yet. In a nested-fleet Instance, swap opens for the inner fleet's containers too. When swap cannot take it, Orbit stops the container instead. The result says which: `sleep: frozen` or `sleep: stopped`. A nested-fleet Instance is never stopped: a stop would lose the inner fleet's Club key and its tunnel. Orbit resumes it instead, and the sleep fails with `instance.container_freeze_failed`. A visit to the Route, or [`instance:wake`](/cli/instance/wake), resumes or starts it again. The wake removes the marker as soon as the app answers, before it waits for T3.

Before Orbit admits the sleep of an Instance with a T3 server, the [Conn thread index](/reference/conn#thread-index) reads the container's T3 threads one last time, while its switch is on. It reads after the refusals, so a refused or repeated request does not wait, and it waits at most 3 seconds. A device then still lists the asleep Instance's threads. A failed read does not stop the sleep.

When a sleep stops rather than freezes the container, the command says that its next wake starts it without restoring memory. In JSON, `sleep: stopped` and `prepared_restore.status: skipped` distinguish this from a frozen sleep.

The Instance must be a development container. No other lifecycle work and no task may run in it. Planned: a production Instance is accepted too, and the command puts its live release container to sleep ([Production containers](/reference/production-containers#sleep-and-wake)).

Sleeping an Instance that already sleeps runs again and changes nothing. If the freeze fails and the container still runs, Orbit removes the marker. If signed sleep fails after freezing, it reports the failure and keeps the marker and swap state. Wake the Instance through the same engine.

The API is `POST /api/v1/instances/{instance}/sleep`; it starts an `instance.sleep` Operation. The MCP tool is `instance-sleep`.

The command uses [signed power routing](/reference/executor#signed-power-delivery) when `ORBIT_EXECUTOR_POWER_ENABLED` is on. It defaults to off and keeps the Python path when off.

## Errors

| Code | Meaning |
| --- | --- |
| `instance.id_invalid` | The Instance ID is not a positive number. |
| `operation.kind_unavailable` | The Instance has no container. |
| `instance.sleep_unsupported` | The Instance is not a development Instance. |
| `instance.lifecycle_busy`, `operation.target_busy` | Lifecycle work, Process work or a task runs on the Instance. |
| `instance.sleep_route_unready` | Caddy's loaded site of the Instance has no asleep rule yet. Nothing changed. Publish the Node's Caddy sites and retry. |
| `instance.container_asleep_failed` | The asleep marker could not be written. The container still runs. |
| `instance.power_helper_busy` | Another power action on the Instance's Node stayed busy, such as a wake still at work. The asleep marker stays. Retry later. |
| `instance.power_helper_failed` | The power helper refused its input or crashed. The asleep marker stays; the run's output has the helper's error. Retry, or read the Node's journal. |
| `instance.container_frozen_unmanaged` | The kernel already holds the container frozen while Incus calls it running. The sleep changed nothing and the marker stays, so the next visit wakes it. See [a freeze that Incus lost](/reference/prepared-restore#a-freeze-that-incus-lost). |
| `instance.container_freeze_failed` | The container could not be frozen, the stop after a full swap failed, or swap could not take a nested-fleet Instance's memory. The marker is gone when the container still runs. |
| `instance.container_sleep_incomplete` | The signed sleep failed after the Instance became unavailable. The executor keeps the marker and saved swap limits so it can wake the Instance. |
| `executor.sign_failed` | The Gateway could not sign an order. Nothing was sent. |
| `executor.publish_failed` | The Gateway could not send the signed order, and the Node's journal shows it never arrived. Nothing changed, and the Instance is free. |
| `executor.not_accepted` | The Node's journal has no record of the signed order after it expired. The Node never acted, and the Instance is free. |
| `executor.order_expired` | The signed order expired on the Node while it waited for another order on the same Instance. The Node never acted, and the Instance is free. |
| `executor.result_unknown` | No result arrived within 6 seconds, and the Gateway could not read the Node's journal, or the journal cannot prove the order never arrived (an older executor, or an order older than 24 hours). The Operation ends `interrupted`. The Instance stays locked, and the Gateway reads the journal again every 10 seconds until it settles the Operation. |
