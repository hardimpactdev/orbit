# Verification cases

A verification case proves one command behavior on the nested test fleet ([stage 3](/reference/command-development-pipeline#3-proof)). Cases are declarative YAML specs executed by one shared runner (`swamp/proof/runner/`).

## Trust boundary and preparation

The proof copy is the trust boundary: candidate code runs inside its disposable, credential-free, egress-restricted nested fleet. Every `runner.py batch`, `runner.py case`, and `runner.py setup` prepares the fleet before running cases, with no preparation caching between commands:

- Reads `apps/gateway/resources/agent/frozen-manifest.json` from the candidate checkout and installs the pinned observer with checksum verification on all three nested Nodes (`proof-gateway.yml`, `proof-observers.yml`).
- Restarts observers, discards stale receipts, and waits up to 18 checks (every 5 seconds) for the nested Gateway to record matching versions, digests, and fresh host facts.
- Enforces a 330-second hard preparation deadline (`timeout 330`) and a separate 120-second setup budget; failures stop cases as `infrastructure`.

## Outer machine and nested Nodes

The runner runs on the outer machine hosting `nested-gateway`, `nested-app-dev`, and `nested-app-prod` and drives them via local `incus exec`. It resolves its runtime paths from the process rather than hardcoded constants:

| Fact | Source |
| --- | --- |
| Checkout | Path of `runner.py` |
| User and home | `pwd.getpwuid(os.getuid())` (ignores `HOME`) |
| CLI home and CA | `~/.orbit` and `~/.orbit/nested-ca.pem` (ignores `ORBIT_HOME`) |
| Pinned Ansible tools | `/opt/orbit-shape-gate` ([pinned shape tools](/reference/development-containers#the-pinned-shape-tools)) |
| Terminal width | `COLUMNS=240` for noninteractive human output checks |

On every nested Node, the managed user is `orbit` (`/home/orbit`). When a case sets `cli.as` to another Node, the runner mounts the checkout there, copies `nested-ca.pem`, adds a CLI profile, and runs `php apps/cli/orbit` once before scheduling.

## The case file

Each command has one file at `swamp/proof/<family>/<command>.cases.yaml`, derived from its chart and CLI page. Missing files report `no cases file for COMMAND` ([Choose the cases](/reference/feature-flow#choose-the-cases)).

### File keys

Top-level keys configure target placement, shared fixtures, and exclusions:

| Key | Meaning |
| --- | --- |
| `command`, `chart` | Command name (for example `firewall:allow`) and chart path under `docs/cli`. |
| `target`, `sources` | Default target Node and probing source Nodes. |
| `spread`, `parallel` | Nodes cases rotate across (`spread`), and max concurrent cases (`1`–`16`, default `4`). |
| `baseline` | State captured before `act` for `unchanged` assertions. |
| `vars`, `fixtures` | Reusable argument lists (`"@name"`) and step lists (`use:`). |
| `uncovered`, `waits` | Uncovered paths/codes with reasons, and named deferrals (`waits`). |
| `cases` | List of case definitions. |

### Case keys

Each entry in `cases` defines one independent test (no cleanup needed because batches restore `base`):

| Key | Required | Meaning |
| --- | --- | --- |
| `id`, `batch`, `covers`, `summary` | Yes | Unique verdict ID, batch name from `swamp/proof/batches.yaml`, chart path IDs (`[]` for refusals), and one-line summary. |
| `setup` | No | Precondition steps; failures mark the case `unrun` (`precondition`). |
| `act`, `expect` | Yes (or `stages`) | Command under test and assertions (all `expect` steps run so one verdict lists every failure). |
| `stages` | No | Sequence of `act`/`expect` pairs for multi-round checks on one long Operation. |
| `variants` | No | Variable sets producing separate verdicts (`id[variant]`). |
| `node`, `exclusive` | No | Explicit target Node (overrides `spread`) and `exclusive: true` to force running alone. |
| `read_only` | No | `true` for no-op/refusal cases (no `setup`/`negative`, `request: none`, read steps only). |
| `fails_on_base`, `fails_today`, `negative` | No | Merge-base replay opt-in, temporary failing-today marker, and negative-test mutation block. |
| `timeout`, `waits` | No | Per-case timeout in seconds (default `180`) and deferral name from file `waits`. |

## Steps

The runner supports a closed set of steps (`swamp/proof/runner/spec.py`):

| Step | Phase | Purpose |
| --- | --- | --- |
| `use` | Any | Expand a named `fixture` with parameters. |
| `listener` | `setup` | Start TCP/UDP listeners on free ports (or consecutive `block` ranges). |
| `ufw_rule`, `ufw_delete` | `setup`, `negative` | Insert or delete test-owned UFW rules directly on a Node. |
| `fault`, `busy_node` | `setup`, `act` | Inject `ufw` command failures or hold a firewall write lock (cleaned up on case exit). |
| `agent_report`, `node_down` | `setup` | Wait for fresh agent facts, or stop agent + SSH until offline. |
| `node_access_remove`, `ipv6_addresses` | Batch setup | Remove a Node access grant, or assign IPv6 addresses on the proof bridge. |
| `node_fixture`, `recorded_request` | `setup`, `act` | Seed a recorded Node fixture or send a request through the candidate Gateway HTTP kernel. Runs alone. |
| `executor_key`, `executor_order`, `executor_publish`, `executor_round_trip`, `executor_power`, `executor_lost_result` | `setup`, `act`, `expect` | Provision the proof-only executor key (`executor_key`, runs alone) and exercise signed orders, WebSocket delivery, power ops, and lost-result recovery. |
| `cli` | `setup`, `act` | Run candidate `orbit` (`run`, `forms: [json, human]`, `tty`, `save`, `as`, and `expect`: `exit`, `status`, `code`, `skipped`, `steps`, `request: none`, `human`, `json`). |
| `probe`, `ufw`, `record`, `doctor`, `unchanged` | `expect` (or any for `probe`) | Check TCP/UDP reachability, numbered UFW rows, CLI list counts, Doctor drift, and baseline stability. |
| `service`, `package`, `ansible_changes` | `setup`, `act`, `expect` | Check or stop a systemd unit (`service`), verify an installed package (`package`), or assert zero Ansible changes from saved Operation step artifacts (`ansible_changes`). |

### Signed clone lifecycle

Run `orbit proof instance:destroy --group=ID --json` to prove the signed lane beside Swamp. The `clone_fixture` step builds the locked executor in the task copy and records its source tree and digest under `.orbit-artifacts/proof-clones`. It reuses a staged binary only when its source tree and digest match, and fetches a pinned Rust toolchain in a temporary directory on copies without Cargo. To build the artifact separately, run `python3 tools/swamp-proof-guest/clone_lifecycle.py` in the copy. The fixture refuses an already configured engine, starts the pinned NATS server and the built executor on the disposable nested fleet, enables the create and destroy routes there, and creates an unrouted default from a public repository.

The `clone_create` and `clone_destroy` steps use the public Gateway API. The destroy fixture adds an owned test volume and files at both power stores' real paths; it does not put the clone to sleep. One fault drops only the admitted destroy's saved JetStream receipt before restarting the Gateway consumer. A separate request with the original key checks HTTP admission replay, not transport redelivery. Another fault holds the test volume past container deletion, then retries with a new admission key. The `clone_compare` step uses the same request-to-terminal clock for clean signed and Swamp runs. The signed journal's `done` timestamp comes from before execution; the signed step's Gateway row measures dispatch to receipt application. The `clone_work` step reads one clone's unsaved work through Conn's `GET /api/v1/conn/instances/{id}/work` from the outer operator Node, first by the signed executor read and then by the SSH reader (the executor reports `instance.work_read` or not), in clean, dirty, stopped and asleep states, and requires both answers to match. A watcher on the Gateway's bus records every signed read order to the Node and its reply, so each read, the 12 timed samples of each reader included, is tied to its executor order or to none; the executor unit's CPU time agrees. It pauses the executor through the first send's wait so the Gateway sends again with a fresh nonce, and through the whole budget for `unknown` `timeout`. The unacknowledged destroy POST must refuse on its own fresh read: the workspace turns dirty after a clean GET, and the clone is also posted stopped and asleep. It enables the Conn extension only when it was off, and `clone_cleanup` puts back the switch it found. The `clone_cleanup` step removes the disposable Project, Instances and temporary services and restores the nested Gateway settings.

Run `orbit proof route:destroy --group=ID --json` for the Route withdrawal. The `route_fixture` step is `clone_fixture` with the `route.destroy` route and the `route` family enabled. Its Project's web root is `src`, unless it names a `project_type` and a `root`: `laravel-app` with `root: public` makes clones that are active with a Route of their own, the shape of a second `--web-root=public` Route on a live app. Such a sibling has no known page behind it: its site, leaf and DNS answer, and its own page with HTTP 200, stand for it. It also runs the executor with the `dns` family on the VPN Node, which is the nested Gateway, behind the bus guard that admits the Gateway's `orbit` user. The `route_create` step makes a clone's own Route, or with `web_root` another site of it, through the public API; `route:destroy` removes only such a site from a live Instance. The `route_destroy` step reads the Caddyfile, Caddy's admin API, the leaf folder, the DNS records and a DNS answer from the VPN Node, and a TLS request trusting the nested root. A sibling Route must keep all of them and its first HTTP status before, during and after. Its `receipt` fault drops the saved receipt of the Caddy withdrawal, `dns-conflict` adds an unrendered line to the live records, and `via: swamp` turns the `dns` family off. Its `restart` fault restarts `orbit-gateway-engine` 12 seconds into the DNS grace and requires one withdrawal within 36 seconds of the DNS receipt. Its `cancel` fault samples the sibling during the grace, cancels 10 seconds into it, requires nothing withdrawn after the grace, then removes the Route again. Its `projection` fault adds a database trigger that refuses the delete of that one Route: the Operation must fail once, after three projection attempts, with `engine.projection_failed` at the step `projection` and no lock, the newest `laravel*.log` must hold at most six lines of the fault and none more 30 seconds later, and the same command must then remove the Route. The `route_main_serves` step requires a clone's one authoritative Route to be active and to answer its page with HTTP 200, and no refused Route delete in the log. Each check keeps its own receipt, `<clone>-main-route-<n>`, naming the last `route.destroy` before it. Every removal compares `dig +short` answers before and after for the `.orbit` service names, a name under `.nested-prod` and `.nested-dev`, and every other Route's name; each must answer, unchanged. The `route_clone_destroy` step destroys a clone that owns a Route, and `route_compare` compares request-to-terminal times of a signed and a Swamp run.

Run `orbit proof route:update --group=ID --json` for a domain change. The `update_fixture` step is `route_fixture` with the `route.update` route. The `route_create_tld` step makes a clone's own Route under a name inside the Node's TLD, which moves no DNS record, and serves a known page behind it; a clone serving `src` writes no `APP_URL`. The `route_update` step moves that Route through the public API, or through the CLI for the clean engine run, and with `dns` to a name outside the TLD, which moves the VPN Node's records. Before, during and after, a sibling Route must keep its DNS answer and its own known page. The old name must answer the target's known page before the update; afterwards it and its staging leaf are gone and the new name answers that page. Two faults hold the Node's publication lock, which only the withdrawal takes. `receipt` stops the engine while the withdrawal waits on the lock, then drops its receipt. `partial` adds an unrendered Caddyfile line while the withdrawal waits on the lock, then retries the same update forward. `probe` drops the Gateway's TLS connections on the Route Node, so the probe fails before the cutover, then retries. `feature` rewrites the VPN Node's report without `dns.guarded_records`. `via: swamp` turns the Route Node's `route` family off. `update_compare` compares request-to-terminal times of a signed and a Swamp update.

During an open copy turn, use `python3 swamp/proof/runner/runner.py batch fresh-fleet --file swamp/proof/instance/destroy.cases.yaml --evidence PATH` from the same copy. It runs the same case on the copy's fleet without the outer command's batch reset. Keep the evidence directory for the source and artifact identities, Operation IDs, receipts and timing comparison.

`swamp/proof/task/sync.cases.yaml` proves `task:sync` of a task copy the same way. The `sync_fixture` step is `clone_fixture` with the `tasks.sync` route enabled too. The `sync_copy` step creates a sibling and a clone through the engine, binds the clone to a new external group as its copy, as `task:start` leaves one, and gives it a local branch, staged, unstaged, untracked and stashed work and a stale `origin/<default>`. Each `task_sync` step moves that ref back, posts `tasks/{group}/sync`, and checks that only the ref moved, to the mirror head the result names, with no root-owned file, no credential form in the copy's processes, files or Git configuration or in the Operation record, no base scratch, and the sibling unchanged. Its `receipt` fault drops the fetch receipt; its `held-ref` fault holds the ref's lock so the import fails after the fetch, then retries. The `sync_compare` step compares the signed and Swamp syncs of the same copy.

`swamp/proof/task/cancel.cases.yaml` proves `task:cancel` of a group that owns a copy. The `cancel_fixture` step is `sync_fixture` without the `tasks.sync` route. The `cancel_copy` step starts a new external group with `task:start`. The `task_cancel` step runs the real CLI. Its `held-receipt` fault stops the engine's receipt consumer around the cancel, checks that the cancel runs without a lock beside its unended destroy, and that `operation:cancel` on it and a repeat `task:cancel` name the destroy in human and JSON output; after the consumer starts, each sample reads the CLI's exit and then one atomic Gateway snapshot of the cancel, its destroy and the copy's runtime row: a snapshot that shows the cancel ended must show the destroy succeeded and the record gone, an exit read before a snapshot that shows the cancel unended fails, and only then is the Node's container checked absent. The exit counts as after the end only when a poll after the terminal snapshot still saw the CLI running; otherwise no order is claimed. The CLI's own answer must show the cancel ended. Its `removal` fault holds the copy's inner volume so the destroy fails: the cancel fails with the destroy's code, the group stays bound, and a second cancel with `--discard` succeeds.

`swamp/proof/process/start.cases.yaml` proves `process:start`, `process:stop` and the Node-timer `schedule:enable` on the `process` executor family the same way. The `process_fixture` step is `clone_fixture` without a Project, with the `process.start`, `process.stop` and `schedule.enable` routes enabled; it switches the family on and off on app-dev. The `process_create` step makes a host systemd or Docker Process on app-dev through the public `process:create`. Each `process_control` step stops, then starts a Process through the public CLI on the engine or on Swamp, and reads back the unit's `ActiveState`, `UnitFileState` and `LoadState`, or the container's status, image and exact name, with a sibling Process unchanged. The `process_replay` step drops a stop's receipt, checks that `process:destroy` and `process:start` of the Process are refused with `operation.target_busy` until a second send replays the journal with one Node execution. The `process_retry` step adds a drop-in whose `ExecStartPre` fails, so a start enables the unit and then fails (`process.apply_failed`); it records that half-applied state, removes the drop-in, and starts again. Fixture names must be free before each create, and a create counts only when its Operation made a new row. The `process_cleanup` step removes only the Processes and Schedules the case made, and checks that each Schedule's Swamp workflow and command copy are gone and that each fixture timer was stopped and disabled before its files went, with no boot link and no failed unit left. When the copy has no C linker, `clone_fixture` installs `gcc` for the executor build and purges the packages it added. The `host_instance` step adds a host (non-container) app-dev Instance as a fixture row with its own Project and Git checkout; `schedule_create` with `retained` turns the case's own new Schedule into a retained Node timer, and each `schedule_enable` step reads back the timer's `ActiveState`, `UnitFileState` and `NextElapseUSecRealtime`; its `receipt` fault drops the enable receipt. A `process_replay` step with a `parent` also checks that the parent Instance's destroy is fenced. Each `process_refused` step checks that a shape outside the signed contract starts one Operation with no engine step; for a native cron Schedule it also checks that serve now holds the Schedule's cron trigger.

`swamp/proof/process/restart.cases.yaml` proves `process:restart` on the same family. The `restart_fixture` step is `process_fixture` with only the `process.restart` route enabled; with the family off, the Node reports no `process.read_instance` or `process.restart`. Each `process_restart` step restarts a Process through the public CLI on the engine or on Swamp and compares its run before and after: a unit's `InvocationID`, main PID and activation time, or a container's ID, start time and PID. The run must change once and still be the same three seconds after the terminal receipt; the boot policy reads back as admitted, and a sibling keeps its main PID and activation time. The `restart_replay` step drops the restart step's receipt after the Node ran it (a unit gets a drop-in that delays its start, so the engine stops first), checks that `process:destroy`, `process:stop` and another restart are refused with `operation.target_busy`, and requires a second send with one Node execution and the run the first send started. The `restart_retry` step adds a drop-in whose `ExecStartPre` fails, so a restart fails after its stop (`process.apply_failed`), then restarts again without it. The `restart_refused` step checks that a Horizon-shaped restart runs on Swamp with no engine step while the family is advertised.

The case `production-process-stays-on-swamp` in `swamp/proof/process/start.cases.yaml` proves the non-production limit. The `production_fixture` step is `process_fixture` with the `process.start`, `process.stop` and `process.restart` routes enabled. The `prod_executor` step also installs the executor on app-prod with the `process` family on. It requires app-prod's only Gateway role to be `app-prod` and the Node to report every process action. `process_create` with `node: app-prod` makes the Process there. The `prod_refused` step stops, starts and restarts it through the public CLI while app-prod still reports the actions. Each Operation must run its Swamp workflow with no engine step, and the unit must follow the verb (a restart on a new `InvocationID`). The cleanup also removes the executor and its NATS rule from app-prod.

## Batches and concurrency

`swamp/proof/batches.yaml` defines shared batches and their setup steps. Each batch starts from a `base` restore (45-second health bound); read-only cases with no setup run first on a fresh copy so the copy only resets after a mutating batch.

The runner assigns every case one lock class:

- **Alone (`alone`):** Uses `node_down`, `agent_report`, `node_access_remove`, `ipv6_addresses`, `node_fixture`, `recorded_request`, `executor_key`, cross-Node/unresolved CLI calls, or `exclusive: true`.
- **Reader (`reads its Node`):** Only read steps (`probe`, `ufw`, `record`, `doctor`, `unchanged`, `package`) and CLI calls expecting `request: none`. Multiple readers share a Node.
- **Writer (`alone on its Node`):** Any other case; runs exclusively on its placed Node while other Nodes run concurrently.

Noninteractive `node:converge` and `node:role:add` calls on copies with unshifted checkouts (`checkout.shift=false`) get a 600-second CLI limit (240 seconds otherwise). A CLI timeout fails the active case as `infrastructure` and marks remaining waiting cases in that batch `unrun` (`infrastructure`).

## The run

Each case emits one JSON verdict line (at most 1 KB, including up to 3 failed `calls` with `run`, `exit`, `code`, and truncated `stderr`):

| Verdict | Cause | Meaning |
| --- | --- | --- |
| `passed` | | All steps passed. |
| `failed` | `assertion` | An `act` or `expect` step failed. |
| `failed` | `infrastructure` | Execution or transport failed (for example, unreachable fleet or CLI timeout). |
| `unrun` | `precondition` | A `setup` step failed. |
| `unrun` | `infrastructure` | A restore failure or shard budget stopped the batch before the case ran. |

`runner.py` subcommands are `plan` (`--json`, `--steps`, `--lines`), `batch`, `case` (`--negative` to verify `must_fail` assertions detect broken effects), `setup`, and `replay`. Exit codes are `0` (passed), `1` (failed), `2` (unrun), and `3` (spec error). Guest helpers live in `tools/swamp-proof-guest/`.

### Opt into merge-base replay

Set `fails_on_base: true` on a new or changed case that proves behavior absent from the merge base. When replay runs (`runner.py replay`), every eligible flagged case must fail on the merge base with cause `assertion`; a passing or unrun result fails the proof with `CASE@merge-base`. In container copies, merge-base replay is not yet wired into `proof:run`, so `fails_on_base` currently acts as case metadata ([old paths](/reference/old-paths#the-task-vm-proof-run)).
