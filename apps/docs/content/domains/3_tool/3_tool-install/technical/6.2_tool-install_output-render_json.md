# JSON Renderer: `orbit tool:install`

[Back to `tool-install` technical contract.](1_tool-install.md)

**Renderer:** JSON renderer.

## Primitive

None. JSON output is emitted as a machine-readable envelope via `$this->line(...)`.

## Selection

Use this renderer when `--json` is present.

Use `--stream-json` instead of `--json` only when callers need
newline-delimited progress frames. That renderer follows the shared
[Stream JSON Frames](../../../README.md#stream-json-frames) contract.

## Envelope

This renderer uses the shared [JSON Envelope](../../../README.md#json-envelope).

## Success Shape

```json
{
  "success": {
    "data": {
      "tool": []
    },
    "meta": []
  }
}
```

Command-specific result data uses the canonical tool entity from [`README.md`](../../README.md#tool-json-entity) unless the command returns credentials.

## Error Shape

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Required input is missing or invalid.",
    "meta": {
      "field": "tool"
    }
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `error.code` | `validation_failed`, `gateway_unavailable`, `authorization_failed`, `tool.not_found`, `tool.unsupported_action`, `tool.constraint_unsatisfied`, `tool.remote_action_failed` | Stable command failure code. |
| `error.message` | string | Human-readable failure summary. |
| `error.meta` | object | Field, target, caller, or remote-action context for automation. |

Unsupported status example:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Invalid --status value 'foo'. Valid values: installed, running.",
    "meta": {
      "field": "status",
      "value": "foo",
      "reason": "unsupported_value"
    }
  }
}
```

Missing target example:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "A node or instance target is required. Provide --node, --instance, configure node:default, or select a target interactively.",
    "meta": {
      "fields": ["target"]
    }
  }
}
```

Install preflight failures use `tool.constraint_unsatisfied`. Its metadata
always includes `tool`, `node`, `action=install`, `constraint`, `required`, and
`actual`; failed remote read-only probes also include `exit_code` and `stderr`.

## Test Mapping

| Path | Coverage |
| --- | --- |
| `apps/cli/tests/Feature/Commands/Tool/ToolStreamCommandTest.php` | `--json` final complete frame shape, canonical gateway stream request shape, and pre-stream gateway error envelope pass-through. |
| `apps/cli/tests/Feature/Commands/Tool/ToolWriteCommandTest.php` | `--json` renderer selection, success data shape, unsupported `--status` (`validation_failed`) metadata, and gateway install error envelope pass-through. |
| `apps/cli/tests/Feature/Commands/StreamsGatewayProgressTest.php` | Shared `--stream-json` newline-delimited frame behavior and `--json`/`--stream-json` conflict validation for eligible gateway streaming commands, including `tool:install`. |
| `apps/gateway/tests/Feature/Http/Api/ToolInstallControllerTest.php` | Gateway error envelope for `tool.constraint_unsatisfied`, including stable local and remote preflight metadata. |

Gateway controller coverage asserts the `tool.constraint_unsatisfied` envelope
and its stable constraint metadata. CLI renderer coverage remains focused on
selection, validation failures, and gateway error-envelope pass-through. The
linked tests do not exhaustively assert every documented `error.code` value:
`validation_failed`, `gateway_unavailable`, `authorization_failed`,
`tool.not_found`, `tool.unsupported_action`, `tool.constraint_unsatisfied`, and
`tool.remote_action_failed`.
