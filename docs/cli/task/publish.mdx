Push an [eligible checked candidate's](/reference/tasks#check-an-external-group) commit for an external group. When hosted CI is required, the owning handoff operation must have succeeded with passed CI on that check/commit. Optionally open or update its pull request. See [Publish an external group](/reference/tasks#publish-an-external-group).

```bash
orbit task:publish 42 --check=17 --title="Deliver the feature" --body="Adds the feature."
```

The optional `task` argument is the numeric task group ID. `--check` supplies the eligible handoff check ID. Supply `--title` and `--body` together to publish a pull request, or omit both to push only. Add `--draft` to open a new pull request as a draft; it needs `--title` and `--body`, and an open pull request keeps its state. `--idempotency-key` reuses an operation start. The command follows the operation with the shared display and supports `--json`.

In a group whose workspace is a [task copy](/reference/tasks#task-copy), `--check` without `--title` and `--body` opens the pull request too when the check is the group's reviewed done check: the same Operation pushes it and opens a ready pull request with the [reviewer's title and body](/reference/tasks#the-reviewers-pull-request-text), as the release below does. Any other check, such as a newer one the reviewer has not approved, or a done check without the reviewer's text, only pushes, and the result's `pull_request_withheld` says why no pull request opened; human output prints it as `No pull request:`. A group that has its pull request only pushes, and the pull request shows the new commits.

A group whose workspace is a [task copy](/reference/tasks#task-copy) publishes the same way and gets the same result. Its commit leaves the copy as a bundle; the push and the pull request run on the Swamp worker, so the copy never holds a token. A range from the copy's start that holds the copy's `.env` in any commit fails with `tasks.publish_secret_path`, and nothing is pushed. A range that holds the `.env` content or one of its values under another name fails with `tasks.publish_secret_content`, which names the commit; a content check that cannot run fails with `tasks.publish_secret_unchecked`. [The copy check](/reference/tasks#the-copy-check) then reads the copy's other secrets in the container: a range or proposed body that holds one of their values, or a private key block, fails with `tasks.publish_secret_value`. It names its items in the result's `refused`, never a value, and nothing is pushed. A copy publishes only for a nested-fleet Project, such as the Orbit Project, or a Project on the Gateway's `ORBIT_TASKS_COPY_PUBLISH_PROJECTS` list. Any other copy publish fails at once with HTTP 409 `tasks.copy_publish_held`; the checked commit stays in the copy until the Project is released for publishing. A copy whose last completion failed answers HTTP 409 `tasks.copy_completion_failed` until a [retried completion](/cli/task/start#when-the-start-fails) succeeds. A copy that is not `active` yet answers `tasks.copy_not_ready`. Each long step of a copy's publish names its Swamp behavior by the group, so publishes of two groups whose copies share a Node never wait for each other ([Two groups on one Node](/reference/tasks#two-groups-on-one-node)). A step that still waits too long for a behavior lock fails with `tasks.publish_lock_timeout`; run the command again.

For a group whose workspace is a task copy, `task:publish <group>` without `--check`, `--title` and `--body` releases the group once its work is done. It publishes the group's done check with the [reviewer's title and body](/reference/tasks#the-reviewers-pull-request-text), and opens a ready pull request, as the [automatic publish](/reference/tasks#publish-by-itself) of a `pr_when_done` group does. It fails with `tasks.not_done` (409) while the work is not done, with `tasks.pr_text_missing` (409) while the group is `waiting_for_pr_text`, and a group without a task copy still needs `--check` (422). `task:show` reports the group as `waiting_for_release` until then. On a group that has its pull request, the same call publishes the done check again: it pushes the newer checked commit to the pull request's branch and keeps the pull request's title and body. It still fails with `tasks.not_done` when the newest check is not the reviewed done check. A done check whose automatic publish failed on a lock timeout is started again by the tick, up to 3 attempts; this release publishes it at once, whatever the tick does.

```bash
orbit task:publish 42
```

A task copy's publish also carries the waiver lines of its proposed pull request body, `.git/orbit/proposed-pr-bodies/task-<id>.md`, into the body: each `Docs-unaffected:` line that the body lacks is appended while the body stays within the limit, and the `.env` content check reads the final body. See [Docs-impact waivers in a copy](/reference/tasks#docs-impact-waivers-in-a-copy).

Orbit merges no pull request of a group whose workspace is a task copy; a person merges it on GitHub. See [No merge](/reference/tasks#no-merge).

A copy's publish also states its base. Right before the push it reads the default branch head on origin and reports `base_commit`, the merge base of the checked commit and that head, `default_commit`, `behind_by`, `overlapping_paths`, the paths that both sides changed since the base, at most 100 in at most 3,000 bytes, with `overlapping_more` counting the rest, and `merged_default`, the head the worker merged at publish, or null. A pull request body gets a fixed `## Base` section with the same facts after your text. Being behind, with or without overlapping paths, never refuses.

The same read judges the copy's own workflow changes: the paths under `.github/workflows/` that the checked commit changed since the merge base, as `git diff <default>...<commit>` lists them. Such a path fails with `tasks.publish_workflow_change`, which names the paths in `refused`, with `refused_more` counting the rest, and nothing is pushed. The publish token cannot change workflows: a person makes a workflow change of the copy's own in a pull request of their own. A commit that the default branch already holds is never a change of the copy, whether `task:sync` brought it or it was carried in by hand.

A copy that is only behind a workflow change of the default branch publishes. GitHub compares the pushed branch's tree with the default branch, so the worker merges the default head into the checked commit at publish and pushes that merge, `Merge main <sha> at publish`. The result's `merged_default` names that head, and the `## Base` section adds `- Merged main <sha> at publish`; `commit` stays the checked commit. A later publish of a newer checked commit adds the earlier publish merge as a third parent, so its push is a fast-forward.

After that, only a real merge conflict fails, with `tasks.publish_conflict`, which names the conflicting paths in `conflicting_paths`, and nothing is pushed: bring main into the copy with [`task:sync`](/cli/task/sync#a-task-copy), merge or rebase, check again and publish. See [the base of a copy publish](/reference/tasks#the-base-of-a-copy-publish).
