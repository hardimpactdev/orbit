Run [`conn:environment-restart`](/cli/conn/environment-restart) for each container Instance on one Node, in order of Instance ID. Run it once on each app-dev Node after the release that brought the [machine name](/reference/development-containers#the-machine-name).

## Usage

```sh
orbit conn:node-environments-restart 7
orbit conn:node-environments-restart 7 --json
```

| Argument or option | Meaning |
| --- | --- |
| `node` | Numeric Node ID. |
| `--json` | [Machine output](/reference/cli-ux#input-and-output-modes). |

The command prints one line for each container Instance on the Node, with the same answers as `conn:environment-restart`: `restarted`, `current`, `busy`, `skipped` or `failed`, with their reasons.

The Gateway reads every T3 label at once, in at most 5 seconds. Then it reads each candidate's threads right before it admits that Instance's own `conn.environment_restart` Operation, so the read is as close to the restart as for one Instance. One busy, sleeping or failed Instance does not hold back the others.

One call admits at most four restarts, so a large Node does not fill the Swamp workers and widen the window with a queue wait. Later candidates answer `skipped` with `next_run`. A call also stops reading after 120 seconds, well inside the request's limit; the Instances left answer `skipped` with `deadline`. Run the command again until no Instance answers `busy`, `next_run` or `deadline`.

The API is `POST /api/v1/conn/nodes/{node}/t3-restart`. The Conn extension must be on.

## How it works

Each Instance follows the [`conn:environment-restart` chart](/cli/conn/environment-restart#how-it-works). The Node form only walks the Node's container Instances.

## Errors

| Code | Meaning |
| --- | --- |
| `extension.disabled` | The Conn extension is off. |
| `node.not_found` | No Node has that ID. |
