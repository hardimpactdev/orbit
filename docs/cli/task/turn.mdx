Run one turn on the current subtask of an external group, or on a [task with no subtask](/reference/tasks#a-task-with-no-subtask) by its own ID. Orbit records the thread's state and transcript without advancing the lifecycle. See [Run an external turn](/reference/tasks#run-an-external-turn).

```bash
orbit task:turn <task> --role=implementer --prompt="Implement the brief." --thread=new --idempotency-key=feature.implement.c1
orbit task:turn <task> --role=implementer --prompt="Fix the failing test."
orbit task:turn 43 --role=reviewer --prompt="Review the checked commit." --thread=new --check=19 --json
```

Each role gets its own fixed text around your prompt: the group's and the subtask's briefs, the deliverables, the role's rules, then your prompt and the end of the turn. The implementer's rules tell it to run the Project check before it hands off and what its handoff note holds. The reviewer's text names the check, its commit and base, each deliverable's result in that check and the implementer's handoff note. It also says whether this is the first review or a re-review, and with which earlier commit. [Run an external turn](/reference/tasks#run-an-external-turn) lists both texts. Send only what this turn adds: do not paste the briefs, the handoff note or the rules, and do not ask for a verdict line, since the reviewer's text fixes it.

The last line gives the end of the turn's bound: `Orbit ends this turn at 2026-11-16T11:00:00Z.` It is one hour after Orbit admitted the turn, in UTC.

`--role` is `implementer` or `reviewer`. A turn without `--thread` continues the role's thread, `--thread=new` starts a new thread, and `--thread=ID` names the thread the turn continues. A new thread takes its role's model; a continued thread keeps its model.

The role `consult` and `--model` belonged to the turn on a task VM, which is removed with the Pi task loop ([old paths](/reference/old-paths#the-pi-task-loop)). This CLI does not offer them. A Gateway answers an older CLI that sends either with `validation.failed` (422) on that field.

### A task that runs in a copy

A task that owns a [task copy](/reference/tasks#task-copy) runs its turns in it. `task:start` makes one for a Project whose default Instance is a container or that has a nested fleet; a nested-fleet task without a copy refuses with `tasks.no_workspace`. Its turn is the Operation `tasks.copy_turn`: Swamp runs the turn with T3's own CLI in the copy, as `agent`, and the Gateway records it on the thread. How it works:

- The implementer and the reviewer each keep one ongoing T3 thread, so the agent keeps the whole earlier conversation. A turn without `--thread` continues its role's thread: the implementer's thread of the current subtask, or the group's reviewer thread. The first turn of a role starts it. `--thread=new` starts a new thread, which later turns then continue. `--thread=ID` must name the thread the turn would continue. A thread continues only in the copy that started it.
- A reviewer turn names the subtask's checked candidate with `--check`, and its prompt names that commit. The reviewer works on the candidate: Orbit checks it out, detached, before the turn, and checks the task branch out again after it, at the commit it had, so nothing the reviewer changed stays. A checkout that is not clean on that branch and commit afterwards, also after a failed or cut turn, holds the group like a turn that may still run. A checkout with uncommitted changes refuses the reviewer turn with `tasks.copy_tree_dirty`. The group records the reviewer's thread.
- The turn's admission moves the current subtask from `todo` to `running`. No turn completes it: run `task:update <subtask> --status=completed` once the reviewer's turn on the done check ended, or `task:update <task> --work-status=completed` for a task with no subtask. See [subtask status in a task copy](/reference/tasks#subtask-status-in-a-task-copy).
- A new thread takes its role's provider, model and effort from the task, else the Project's default, else the Gateway's `ORBIT_TASKS_COPY_*` settings, which ship `claude` and `claude-opus-5-5` at `medium` effort for the implementer and `high` for the reviewer. A provider and effort with no instance in the copy's T3 answer `tasks.copy_turn_unoffered`. Orbit checks the model before it starts the thread. An unlisted Codex model needs confirmation from the copy's Codex provider. A continued thread keeps its model and effort. See [copy turn agents](/reference/tasks#copy-turn-agents).
- T3 applies the effort through its own settings: the copy's create gives T3 one Claude provider instance per effort level, and the thread starts on the instance of its provider and effort. That Claude Code takes the instance's `CLAUDE_CODE_EFFORT_LEVEL` over the `--effort` T3 passes was verified with Claude Code 2.1.311 and T3 0.1.7. A copy made before this lacks those instances, so T3 refuses its new threads. Cancel it and start the task again.
- The transcript is the whole thread's message text, the newest kept within its bound.
- The turn's result names the provider instance, the model and the effort the thread started with, such as `claudeMedium`, `claude-opus-5-5` and `medium`. A refused turn names them too, although nothing was launched.
- The turn's result holds `agent_id`, the ID of the agent thread that `task:agent:list` lists and [`task:agent:show`](/cli/task/agent-show) reads, and `reply`, the agent's reply: the text of the transcript's last entry that the agent wrote, labelled `assistant`. The transcript is the whole thread's, so a turn in which the agent wrote nothing, such as one T3 failed at once, shows an earlier turn's reply. A reply longer than 16,384 characters keeps its first 16,384 and ends with ` [cut: N more characters; read task:agent:show <group> <agent_id>]`. A turn with no assistant entry has `reply: null`, also when Orbit's own truncation notice is the only other entry. The transcript itself stays out of the result.
- Human output prints `Agent thread: ID` and the reply under the outcome, or `Reply: none` when `reply` is null. A result without `agent_id`, such as a run that Swamp failed before the turn's result, prints neither. `--json` carries `agent_id` and `reply` in the Operation's `result`.
- The implementer's prompt says how to ask: with the agent's question tool.
- A question ends the turn. Orbit first stores the question, then stops the run. The Operation succeeds with the state `asking_for_input`. Its result holds each question with its header and options, in the agent's words, and `task:agent:list` shows them on the thread until its next turn.
- The role's next turn answers the question. Orbit first resolves the stored question requests, then sends the prompt, which quotes the questions first and your prompt as the answer. Requests already resolved need no action. If Orbit cannot confirm resolution, it launches nothing and fails with `tasks.copy_question_unresolved`; the thread keeps its questions for the next attempt. A message to the thread from a T3 client answers it too.
- A question Orbit could not read, or a run that Orbit could not stop, fails the Operation and holds the group like a turn that may still run.
- The turn ends after one hour with `tasks.turn_timeout`. Orbit does not stop the run: the start printed no run ID, so Orbit cannot prove which run is the turn's. The turn holds the group until T3 lists its thread, by its ID, in a state that runs nothing. A reviewer's checkout stays detached until then. The work stays in the copy. A stored question without an owner run stays unanswerable by design.
- `operation:cancel <turn>` ends a running turn's Operation. Its run may go on in the copy until the next turn stops it, so a cancel and a new turn stop a run.
- The next turn settles an earlier turn that may still run. Its phase first reads T3 in the copy, and finds the earlier turn's thread by its ID. For a recorded run, it reads that exact run: it stops a run that still goes on and waits for its end. The earlier turn is settled only when T3 shows that run ended, or, for a turn with no recorded run, its thread with no active run. An accepted stop, or a run or thread T3 does not show, settles nothing. For a reviewer's turn whose detach the copy still marks, the phase then restores the checkout and requires it clean on the task branch at the commit it had; without that mark it touches nothing. Then the turn runs. When a stop fails, the turn touches nothing, launches nothing and fails with `tasks.copy_turn_unended`.
- A check, a publish or a proof of the copy cannot read T3. While an earlier turn is not settled, it answers `tasks.copy_turn_unended` and waits for the next turn: run the role's next turn, which stops the earlier run and settles it.
- When the last subtask is completed and a fix is needed, after the review or after the pull request, reopen it with `task:update <subtask> --status=running`, or the work of a task with no subtask with `task:update <task> --work-status=running`. Its turns then continue its implementer thread and the group's reviewer thread. See [reopen the last subtask](/reference/tasks#reopen-the-last-subtask).
- A completed subtask that cannot reopen takes no turn: `task:cancel` is then the only way out, and it ends the copy with its work.
- Orbit stops a run that asks only while it waits for exactly the questions Orbit stored. A run that someone answered meanwhile, or that now asks for an approval or something else, goes on, and the turn fails with `tasks.copy_question_unstopped` or `tasks.copy_question_unread`.
- The transcript holds message text only.
- The thread's token metrics are the sum over every provider turn that T3 holds for its T3 thread. When a provider turn has no complete usage, or the read fails, they stay as they were: null on a new thread, never 0.


## How it works

### In a task copy

<div className="flow-at" data-chart="task/copy-turn"></div>

Swamp locks the step that runs the turn for the whole turn, and a second run that needs the same lock waits 60 seconds and then fails. The lock carries the copy's Instance id: a turn acts only inside its copy and its own run folder. So turns in two copies on one Node run side by side, and one copy still takes one turn at a time.

## Errors

A turn of a group that owns no task copy answers `tasks.vm_runtime_removed` (422) and records nothing: task VMs are removed ([Task runtime](/reference/tasks#task-runtime)).

A turn in a task copy adds these answers and Operation errors:

| Code | When |
| --- | --- |
| `tasks.no_workspace` (409) | The group owns no task copy. |
| `tasks.copy_not_ready` (409) | A turn, a check, a publish or a proof of the copy: the copy is not `active` yet, because its create, its completion or a retry of the completion still runs. |
| `tasks.copy_completion_failed` (409) | A turn, a check, a publish or a proof of the copy: its last completion failed, was cancelled or interrupted, so its Processes and inner fleet did not start. The details name `operation_id`, `failed_step`, `error_code` and `retry`, the command `orbit instance:complete <copy-id>`, and `requires` when the retry needs a changed Process definition first. See [when the start fails](/cli/task/start#when-the-start-fails). |
| `validation.failed` (422) | The request names the role `consult` or a `model`, as an older CLI may send. Both were options of the removed task VM turn. |
| `tasks.thread_role_mismatch` (422) | `--thread=ID` is not the role's thread that the turn would continue in this copy. |
| `tasks.commit_not_checked` (422) | A reviewer turn's `--check` is not the subtask's checked candidate. |
| `tasks.copy_turn_unended` (409) | A check, a publish or a proof of the copy: an earlier turn is not settled; `details.operation_id` names it. The next turn stops its run and settles it. |
| `tasks.copy_turn_unoffered` (422) | A new thread's provider and effort, from the group, the Project or the Gateway, name no provider instance that the copy's T3 has. `details.offered` lists each provider with its efforts. Nothing is recorded. |
| `tasks.copy_turn_model_invalid` (503) | The role's `ORBIT_TASKS_COPY_IMPLEMENTER_MODEL` or `ORBIT_TASKS_COPY_REVIEWER_MODEL` is not a model name. |
| `tasks.copy_turn_model_unoffered` | The Codex provider rejected the model, or another driver has a cached catalog that omits it. Nothing was launched. |
| `tasks.copy_turn_model_unverified` | Orbit could not resolve the provider instance's driver, or the catalog did not confirm a Codex model and its probe was inconclusive. Nothing was launched. |
| `tasks.copy_thread_missing` | The Operation's error: T3 in the copy holds no single thread of the title to continue. Nothing was launched. A first turn that T3 refused leaves such a thread recorded: `--thread=new` starts a new one. |
| `tasks.copy_tree_dirty` | The Operation's error: the copy's checkout had uncommitted changes or no branch before a reviewer turn. Nothing was launched. |
| `tasks.copy_turn_unended` | The Operation's error: Orbit could not stop an earlier turn's run, or a reviewer left the checkout unclean or off the task branch. Nothing was launched, and the work in the copy stays. |
| `tasks.copy_review_unrestored` | The Operation's error: after a reviewer turn, the checkout is not clean on its branch at the commit it had before. The next turn settles it once the checkout is clean on the task branch. |
| `tasks.copy_question_unread` | The Operation's error: the run asked, but Orbit could not read the question, so it did not stop the run. The group holds. |
| `tasks.copy_question_unstopped` | The Operation's error: Orbit stored the question but could not stop the run that asked. The result keeps the question, and the group holds. |
| `tasks.copy_question_unresolved` | The Operation's error: Orbit could not confirm that the previous turn's stored question requests are resolved. Nothing was launched; the thread keeps its questions. |
| `tasks.turn_timeout` | The Operation's error: the turn ran past its one-hour bound. `ended` says whether its run stopped; a run that did not stop is stopped by the next turn. |
| `tasks.turn_failed` | The Operation's error: T3's run ended with a status other than `completed` or `waiting`. |
| `tasks.copy_turn_failed` | The Operation's error: T3 did not report the turn's end, for example while its server was down or when it refused the start, or could not list its threads to find the one to continue. A refused start's error holds no text of T3. |

A turn's error is the fixed sentence of its code, never T3's or a provider's own text, which may quote the prompt. Nothing is parsed from that text; it stays in the turn's private run folder. When the turn has not ended, the error adds that the group holds. A code the Gateway does not know is recorded as `tasks.copy_turn_failed`.
