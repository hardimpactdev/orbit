A Node is a machine that the Gateway manages over SSH and reaches over WireGuard. The `node` family adds a machine, converges it again, renames it, assigns and moves its roles, records which Node may act on which, sets its apps root, and removes it.

[Node provisioning](/reference/node-provisioning) explains what add, converge, role changes, and removal do on the machine. [Node settings](/reference/node-settings) owns the apps root and operator-approved task VM host configuration.

Every command accepts `--json`. `node:show`, `node:remove`, and `node:access:*` take a numeric Node ID. The other commands also accept a Node name.

Lists use tables. Below the minimum table width, each row becomes a labeled record. Details use an aligned tree, with an em dash for an empty value. While the Gateway works, the CLI shows one progress indicator per request, because it does not receive the steps. JSON output contains only the response.

Destructive commands ask for confirmation. The default answer is No. Declining, Ctrl-C, or end of input exits 1 and changes nothing. Without a terminal, and with `--json`, pass `--force`. `--offline` and `--purge-data` never give consent.

## orbit node:add

Add a machine to the fleet. For an existing Node, the same command converges it again after you change its TLD, roles, or settings.

```bash
orbit node:add <name> [host] [options]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Unique Node name. |
| `host` | for a new Node | Public SSH host. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--host-key-fingerprint=SHA256` | none | Approved SSH host key fingerprint. Required for a new Node. |
| `--ssh-port=PORT` | `22` | Public SSH port. |
| `--user=USER` | `root` for a new Node, the managed user for an existing Node | Bootstrap SSH user. |
| `--orbit-user=USER` | `orbit` for a new Node | Managed user that every later Gateway command uses. |
| `--platform=PLATFORM` | `linux` | `linux` for Ubuntu service Nodes, or `macos` for tools on an existing account and tunnel. |
| `--architecture=ARCH` | the observed value | Machine architecture. A given value must equal the observed one. A Linux Node accepts only `x86_64`; another value, or a Linux machine that reports another architecture, fails with `node.architecture_unsupported`. |
| `--tld=TLD` | none | Node TLD. Required for `app-dev`, unless the Node joins an active Cluster with a TLD. A production Node needs it for [clone](/cli/instance#orbit-instanceclone) preview domains. It cannot equal, be an ancestor of, or be a descendant of `orbit` or the configured VPN domain. Comparisons ignore case and the VPN domain’s optional root dot, and use DNS label boundaries. |
| `--role=ROLE` | none | Role to assign. Repeat for more roles. Without it, see [Nodes without roles](/reference/node-provisioning#nodes-without-roles). |
| `--cluster=ID` | none | Cluster to join. |
| `--wireguard-ip=IP` | generated | Stable WireGuard address. |
| `--lan-ip=IP` | none | LAN IPv4 address that a Cluster Router uses to reach this Node. |
| `--wireguard-endpoint=HOST:PORT` | generated | WireGuard endpoint override. See [WireGuard endpoints](/reference/wireguard-endpoints). |
| `--dns-server=IP` | Orbit VPN DNS | A WireGuard-subnet DNS server for the complete Orbit private-name set. Public names keep the normal resolver. Existing overrides are cleared on upgrade. See [Private DNS](/reference/private-dns). A [Node without roles](/reference/node-provisioning#nodes-without-roles) does not use it. |
| `--setting=PATH:VALUE` | none | Node setting. The only path is `apps.path`. |

`--role` accepts `app-dev`, `app-prod`, `database`, `metrics`, `websocket`, `gateway`, and `vpn`. Add `ingress` and `analytics` with [`node:role:add`](#orbit-noderoleadd). A Cluster Router comes from [`cluster:router:set`](/cli/cluster#orbit-clusterrouterset).

```bash
orbit node:add beast beast.example.com \
  --host-key-fingerprint=SHA256:... \
  --role=app-dev \
  --tld=test \
  --setting=apps.path:/srv/orbit/apps

orbit node:add beast --role=app-dev --role=database
```

For macOS, use `node:add` with `--platform=macos` and set `--user` and `--orbit-user` to the same existing account. The machine must already join WireGuard and accept the Gateway's SSH key. No role is required. A role request fails with `node.platform_unsupported` before SSH. This path also enrolls an existing roleless peer whose SSH identity is not pinned, and it can correct that peer's platform and architecture from the machine. See [macOS Nodes](/reference/node-provisioning#macos-nodes).

## orbit node:metrics

Show one metrics snapshot of an active Node: CPU per core, memory, swap, load, uptime, pressure, and disks.

```bash
orbit node:metrics <node> [--json]
```

The Gateway reads the snapshot from the [Metrics role](/reference/metrics#read-node-metrics) through Grafana. It runs four queries for the Node's exporter: one for memory, swap, load, and uptime, and one each for cores, pressure, and disks. Only the first decides whether the Node has metrics. The Gateway stores no sample.

| Field | Meaning |
| --- | --- |
| `cores` | The busy ratio of each core, from 0 to 1. |
| `memory`, `swap` | Used and total bytes. |
| `load` | The 1, 5, and 15-minute load averages. |
| `uptime_seconds` | Time since boot. |
| `pressure` | The `some` `avg10` value for CPU, memory, and I/O. `0` when the kernel has no pressure data. |
| `disks` | Mount, used bytes, and total bytes. Pseudo filesystems such as `tmpfs` and `proc` are left out. `/` comes first. |

Human output shows bytes and durations in readable units. JSON keeps the raw numbers.

| Code | HTTP | Meaning |
| --- | --- | --- |
| `node.metrics_unavailable` | 422 | The Node is not active or has no WireGuard address. |
| `metrics.assignment_missing` | 409 | No Node has the Metrics role. |
| `node.metrics_unreachable` | 502 | Grafana could not answer, or Prometheus has no samples for the Node yet. |

## orbit node:converge

Re-apply the Gateway-rendered Orbit footprint of a Node: its agent files, Caddyfile, PHP runtime policy, temporary-file cleanup and applicable network artifacts. Only an active VPN owner receives the private DNS listener; a Gateway-only Node is a resolver client. It never changes an Instance or a role, so it works on a Node that owns Instances, unlike `node:add`.

```bash
orbit node:converge <node> [--force] [--idempotency-key=KEY] [--json]
```

| Option | Meaning |
| --- | --- |
| `--force` | Re-apply every artifact, not only the ones whose digest changed. Each artifact still leaves a matching live copy alone |
| `--idempotency-key=KEY` | Reuse the same key to repeat admission safely |

The Gateway returns HTTP 202 with an Operation for every admitted target. The CLI follows its steps and prints the final Operation with `--json`. Worker-backed standalone requests use one native Swamp DAG. Workerless Nodes 1 and 18 and existing parent callers keep their current execution path. Unsupported applicable artifacts refuse before native Node effects; a matching digest does not prove an unsupported action. A Node that is not an active, managed Linux Node fails with `node.converge_unsupported`. [Converge the Orbit footprint](/reference/node-provisioning#converge-the-orbit-footprint) lists the artifacts and error codes.

```bash
orbit node:converge beast
```

## orbit node:migrate-docker

Plan or run a migration from Docker CE to the recipe's Ubuntu `docker.io`, or restore container restart policies after manual CE recovery. This is a maintenance action that can stop containers. Follow the [Docker migration procedure](/reference/docker-provider-migration) before changing a Node.

```bash
orbit node:migrate-docker <node> [--dry-run] [--yes] [--fallback] [--restore-policies] [--recipe=RECIPE] [--idempotency-key=KEY] [--json]
```

`node` accepts an ID or exact Node name. The command records and follows one native Operation.

| Option | Meaning |
| --- | --- |
| `--dry-run` | Read the migration plan without changing the Node. |
| `--yes` | Confirm migration or policy recovery without a prompt. Required for mutations in noninteractive and JSON modes. |
| `--fallback` | Authorize a fresh Docker engine if the recorded metadata is unreadable. |
| `--restore-policies` | Restore policies after manual CE recovery. Cannot be combined with `--dry-run` or `--fallback`. |
| `--recipe=RECIPE` | Require the exact serving recipe identity. |
| `--idempotency-key=KEY` | Retry the same Operation admission after a lost response. |

## orbit node:rename

Change the name of a Node. The name is only a registry identifier. Keys, addresses, SSH identity, and roles stay the same.

```bash
orbit node:rename <node> <name> [--json]
```

The new name uses ASCII letters, digits, dashes, and underscores, at most 63 characters, and must be unique. Repeating the current name succeeds and writes nothing. The Gateway holds the [lifecycle lock](/reference/node-retarget#one-lifecycle-owner-per-node-name) for the current name and then for the new name, so a concurrent `node:add` cannot take the new name.

```bash
orbit node:rename gateway vpn
```

After a rename, callers must use the new name or the numeric ID. The WireGuard hub configuration names each peer in a comment. That comment keeps the old name until the Gateway next projects the hub, for example on the next `node:add` of any Node. [Relocate the gateway role](/solutions/relocate-gateway-role) uses a rename to free the name `gateway` for a new machine.

## orbit node:settings

Set the apps root of a Node, the directory under which the Gateway creates development Instance checkouts.

```bash
orbit node:settings <node> --setting=apps.path:/mnt/apps [--idempotency-key=<key>] [--json]
```

Configure a task VM host with `--setting='task_vms:{"cidr":"10.251.77.0/24","max_vms":4,"pool":"orbit-tasks","image_alias":"orbit-task-base"}'`. The JSON object supports the [typed host fields](/reference/node-settings#configure-a-task-vm-host); it has no `node_id` because the selected Node supplies its identity. This example is not the live configuration of any host. Preserve the host's current values when changing it. Use `--setting=task_vms:null` to remove host intent after destroying its task VMs. An `app-dev` role alone never makes a Node a task VM host.

The command needs at least one `--setting`. It sends `{"apps":{"path":"/mnt/apps"}}` to the settings API, without a `settings` wrapper. An empty value unsets the path: `--setting=apps.path:` sends `{"apps":{"path":null}}`. The [API reference](/api/overview) and [MCP](/reference/mcp) publish the same nullable path inside a closed `apps` object. A change never moves an existing checkout. [Node settings](/reference/node-settings#validation) lists the validation rules and failure codes.

When the apps-root change needs a filesystem check, the API returns a `node.settings` Operation. The CLI follows it and returns its final receipt. Reuse `--idempotency-key` to recover the same admission after a lost reply. A task VM host settings patch remains a synchronous Node response.

## orbit node:wireguard-key

Set or replace the WireGuard public key of an existing unmanaged Node. Use this when the operator manages the peer's tunnel outside Orbit. The command does not generate a key pair, accept a private key, or configure the target machine.

```bash
orbit node:wireguard-key <node> <public-key> [--json]
```

| Argument or option | Meaning |
| --- | --- |
| `node` | Existing Node ID or exact name. No current-Node default. |
| `public-key` | Required canonical base64 encoding of exactly 32 bytes: 44 characters ending in `=`. Whitespace, malformed base64, an empty value, and null are invalid. The key must not belong to another Node or the WireGuard hub. There is no unset mode. |
| `--json` | Follow the Operation and return its terminal receipt and request ID. |

```bash
orbit node:wireguard-key laptop 'AQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQEBAQE='
```

A terminal prompts for an omitted Node with the shared Node data list labeled `Node`, then for an omitted key with the text prompt `WireGuard public key`, with no default. An invalid prompted key is requested again. With `--json` or without interactive input, missing arguments fail before mutation. Cancelling a prompt exits 1 and changes nothing. A supplied invalid key also fails before mutation.

The Gateway refuses a managed Node: a Linux or macOS Node with both a nonempty WireGuard address and a pinned SSH host fingerprint, regardless of its lifecycle status. It also refuses any Node holding the `gateway` role, regardless of that role's status. These guards cannot be overridden. The target needs an existing WireGuard address; the command does not allocate one or change the Node's status, roles, endpoint, address, or SSH identity.

WireGuard identifies peers by public key, not by Node ID. Before changing anything, the Gateway rejects a key assigned to any other Node, regardless of that Node's status or the caller's access to it, or equal to the hub's public key, with `node.wireguard_key_conflict` (HTTP 409). The collision check and assignment are atomic across concurrent key assignments; the target's name lock alone is not sufficient. The refusal leaves the stored key and hub unchanged and does not expose the other Node's identity. Supply the public key of a distinct key pair configured on the target, rather than removing or changing another peer. The target's own current key is allowed unless it also collides with another Node or the hub, so valid identical-key retries remain supported.

The Gateway captures the prior peer and admits a `node.wireguard_key` Operation with HTTP 202. It leaves the stored key unchanged while Swamp publishes the exact context through the stable hub model. Terminal success records the admitted key. Failure and cancellation keep the previous key. A repeated identical key still runs publication. The command never contacts or configures the unmanaged target.

The CLI follows the Operation. Human output shows its native progress and terminal result; JSON returns the Operation receipt. Success exits 0; validation, refusal or native failure exits 1. After a lost connection, inspect the Operation before starting another attempt. Native resume and terminal projection retain the original admission; Activity alone does not establish the live hub state.

A successful publication preserves unrelated newer peers. Replacing the key can interrupt the target until its locally configured pair matches. There is no force or confirmation option for this explicit setting.

### WireGuard key errors

| Code | Meaning and recovery |
| --- | --- |
| `node.reference_required` | The CLI got no Node in noninteractive or JSON mode. Supply an ID or name. |
| `node.wireguard_key_required` | The CLI got no public key in noninteractive or JSON mode. Supply the public key. |
| `validation.failed` | The key is not canonical base64 for 32 bytes, or the API body is invalid. Nothing changes. |
| `node.wireguard_key_managed` | The target has verified SSH management. Nothing changes; use the managed Node's normal provisioning/convergence path instead. |
| `node.wireguard_key_gateway` | The target holds `gateway`. Nothing changes; Gateway key changes are outside this command. |
| `node.wireguard_key_conflict` | The key belongs to another Node or the hub, including a concurrent assignment. Nothing changes. Use a distinct key pair on the target; do not alter the other peer. |
| `node.wireguard_ip_required` | The target has no WireGuard address. Nothing changes; enroll the Node with an address first. |
| `node.provisioning_busy` | Another lifecycle operation owns this Node's name lock. Nothing changes; retry when it finishes. |
| `operation.native_failed` | The native publication failed. The stored key remains unchanged; inspect the Operation and native run before recovery. |
| `wireguard.hub_conflict` | The current context differs from the admitted pair. Capture a fresh intent after reconciling its owner. |

The API also uses the shared identity, access, and not-found errors described in [Using the API](/api/overview#read-an-error).

## orbit node:platform

Set the platform of an unmanaged Node. Use it to record what an operator-owned peer runs, such as an iPad on `ipados`. The command changes only the stored platform. It does not contact the machine.

```bash
orbit node:platform <node> <platform> [--json]
```

| Argument or option | Meaning |
| --- | --- |
| `node` | Existing Node ID or exact name. No current-Node default. |
| `platform` | `linux`, `macos`, or `ipados`. |
| `--json` | Follow the Operation and return its terminal receipt and request ID. |

```bash
orbit node:platform ipad ipados
```

A terminal prompts for an omitted Node with the shared Node data list labeled `Node`, then for an omitted platform with the list labeled `Platform`. With `--json` or without interactive input, a missing argument fails before the request. Cancelling a prompt exits 1 and changes nothing.

The target must be an unmanaged Node: it has no pinned SSH host fingerprint and no role assignment. The Gateway refuses any other Node with `node.platform_managed` (HTTP 409) and changes nothing. A managed Node's platform comes from enrollment, which observes the machine. Repeating the stored platform succeeds and writes nothing.

`ipados` is only for unmanaged peers. `node:add` does not accept it, and Orbit runs nothing on an `ipados` Node. [iPadOS peers](/reference/node-provisioning#ipados-peers) lists what the Gateway refuses or skips.

Progress uses `Set Node platform`, `Setting Node platform`, and `Set Node platform`. Success prints `Platform set to <platform> for Node #<id> [<name>].` and `Request ID: <uuid>`. JSON emits only the standard Node response. Errors use the standard error envelope and exit 1.

### Platform errors

| Code | Meaning and recovery |
| --- | --- |
| `node.reference_required` | The CLI got no Node in noninteractive or JSON mode. Supply an ID or name. |
| `node.platform_required` | The CLI got no platform in noninteractive or JSON mode. Supply `linux`, `macos`, or `ipados`. |
| `validation.failed` | The platform is not one of the three values, or the API body is invalid. Nothing changes. |
| `node.platform_managed` | The Node has a pinned SSH host fingerprint or a role. Nothing changes. Enrollment owns a managed Node's platform. |
| `node.provisioning_busy` | Another lifecycle operation owns this Node's name lock. Nothing changes; retry when it finishes. |

## orbit node:role:add

Add one role to a Node, or converge an existing role again.

```bash
orbit node:role:add <node> <role> [--converge] [--postgres-process=ID] [--clickhouse-process=ID] [--json]
```

| Option | Meaning |
| --- | --- |
| `--converge` | Converge an existing role again. It works for a role that is `active`, `failed` at a `converge:` step, or `provisioning` for more than 11 minutes with no operation holding the Node's role lock. |
| `--postgres-process=ID` | For `analytics` only: the PostgreSQL 16 Process that holds the Plausible accounts. |
| `--clickhouse-process=ID` | For `analytics` only: the ClickHouse Process that holds the events. |

```bash
orbit node:role:add beast database
orbit node:role:add beast metrics --converge
orbit node:role:add services analytics --postgres-process=41 --clickhouse-process=42
```

`vpn` and `router` fail with `validation.failed` and `Role [ROLE] is protected from generic mutation.` A role that conflicts with one the Node holds fails with `validation.failed` before anything changes. [Role compatibility](/reference/node-provisioning#role-compatibility) lists the pairs. For `analytics`, a terminal lists the Docker Processes that run the right image and asks for each missing option. With `--json` or without a terminal, the command refuses. The [Analytics role](/reference/analytics) page describes that role.

Role operations on one Node run one at a time. A command that waits more than 2 minutes fails with `node_role.convergence_failed`, `details.step` `converge:node-lock`, and `details.error_code` `node_role.node_busy`. Run it again.

Some steps report a failure without failing the role. The role stays `active`, and `follow_up` in the response names the failure and the retry. The CLI prints it as a warning. The `gateway` role's [private DNS route](/reference/private-dns#the-gateway-machine) reports this way.

The [`ci-runner` role](/reference/node-provisioning#ci-runner-role) prepares the Incus host boundary without creating or registering containers. It cannot share `gateway` or `vpn`. Add it to CI-only hosts and alongside Beast's existing roles through this command.

Adding `gateway` grants the new Gateway Node access to the active `vpn` and `metrics` Nodes, when they are other Nodes. Prefer [`node:role:relocate`](#orbit-noderolerelocate) to move `gateway`, `websocket`, or `metrics`.

Use `--idempotency-key=KEY` to retry the same native role admission.

## orbit node:role:relocate

Move `gateway`, `websocket`, or `metrics` from its current Node to another Node. One assignment stays active for the whole request.

```bash
orbit node:role:relocate <node> <role> [--from=NODE] [--force] [--json]
```

| Argument or option | Meaning |
| --- | --- |
| `node` | Target Node ID or name. It must be active and hold no conflicting role. |
| `role` | `gateway`, `websocket`, or `metrics`. |
| `--from=NODE` | Source Node. Omit it to use the current holder. When the target already holds the role, `--from` names the Node whose leftovers to remove. |
| `--force` | Confirm the move. Required without a terminal and with `--json`. |

```bash
orbit node:role:relocate beast gateway --force
orbit node:role:relocate services websocket --from=beast --force
```

For `gateway`, the Gateway opens the `orbit:gateway-https` firewall rule on the target and moves the assignment. It grants the new Gateway Node access to the `vpn` and `metrics` Nodes, publishes private DNS on the `vpn` Node, and adds the [private DNS route](/reference/private-dns#the-gateway-machine) on the target. It then removes that route and the firewall rule from the source. A failed route on the target reports `follow_up` and does not stop the move.

Relocating `gateway` does not move `vpn`, the Gateway checkout, its SQLite database, the Orbit CA, or the SSH keys. It does not stop Caddy or PHP-FPM on the source, so clients that still use the old address keep working. [Relocate the gateway role](/solutions/relocate-gateway-role) gives the full order.

For `websocket`, the Gateway copies the Reverb server's Laravel `APP_KEY` only when the target lacks one. The [Reverb apps](/reference/websocket-apps) stay in the Gateway database, so every app keeps its credentials. For `metrics`, the Gateway copies role credentials that the target lacks, without overwriting any. It moves the assignment, converges the target, and removes the runtime and publication from the source.

When a step on the target or the source fails, the role already runs on the target. The command fails with its usual code, `details.step` set to `converge:STEP` or `remove:STEP`, and `details.error_code` set to the step's own code. The message names the `--from` command that finishes the move. The Gateway reconciles Metrics once, after the source is done. A failed reconcile does not fail the move: `follow_up` names the Metrics Node and the `orbit node:role:add <metrics-node> metrics --converge` command.

Use `--idempotency-key=KEY` to retry the same native role admission.

## orbit node:role:remove

Remove one role from a Node.

```bash
orbit node:role:remove <node> <role> [--force] [--purge-data] [--offline] [--json]
```

| Option | Meaning |
| --- | --- |
| `--force` | Confirm the removal and its dependent cleanup. |
| `--purge-data` | Also delete role data. For `metrics`, the Prometheus and Grafana volumes and the stored credentials. For `websocket`, the Reverb checkout. |
| `--offline` | Remove the role from a Node the Gateway cannot reach. |

```bash
orbit node:role:remove beast database --force
```

`app-dev` cannot be removed while the Node owns Instances, and no role can be removed while a Route depends on it. Removing the last role restores public SSH first, as [Public SSH](/reference/node-provisioning#public-ssh) describes.

The command removes a role that is `active` or `failed`. Each removal step is safe to repeat over what a failed convergence left. A role that is `provisioning` or `removing` is refused until its claim is stale. A failed removal leaves the role `failed` at `remove:STEP` and returns the step's own code in `details.error_code`. Run the same command again.

When two removals of one role run together, the second waits for the role lock. If the first finished meanwhile, the second fails with `node_role.already_removed` (HTTP 409). A role the Node never had returns `http.404`, except `ingress`: a confirmed removal of an `ingress` role that the Node does not hold succeeds and changes nothing.

Use `--idempotency-key=KEY` to retry the same native role admission.

## orbit node:access:add

Grant one Node access to act on another Node through the Gateway. An access grant authorizes Gateway commands. It does not change network reachability, which WireGuard membership already gives.

```bash
orbit node:access:add <consumer> <serving> [--json]
```

| Argument | Meaning |
| --- | --- |
| `consumer` | Numeric ID of the Node that sends commands. |
| `serving` | Numeric ID of the Node that the commands act on. |

Both Nodes must be active. Adding a grant that exists reports that it already exists. A [task VM](/reference/compute-drivers#placement-invariant) Node never consumes a grant: the command fails with `task_vm.access_refused`.

A grant to the active `gateway` Node lets the consumer act on every Node. The `gateway` Node itself, and the machine that the Gateway bootstrap recorded as its serving host, act on every Node without a grant.

## orbit node:access:remove

Remove one access grant.

```bash
orbit node:access:remove <consumer> <serving> [--force] [--json]
```

Removing a grant to the Gateway Node also revokes Grafana access that depends on it. The CLI warns when you removed your own access to the Gateway Node.

## orbit node:remove

Remove a Node through one native Swamp Operation. The Gateway keeps the Node record until cleanup succeeds. The CLI follows the Operation and reports its final result.

```bash
orbit node:remove <node> [--force] [--offline] [--idempotency-key=KEY] [--json]
```

| Option | Meaning |
| --- | --- |
| `--force` | Confirm removal without a prompt. Required without a terminal and with `--json`. |
| `--offline` | Remove an unreachable Node. Swamp probes it first. A reachable Node keeps every online guard. |
| `--idempotency-key=KEY` | Recover the same Operation after a lost start response. |

```bash
orbit node:remove 7
orbit node:remove 7 --offline --force
```

Remove Instances, Database servers, Schedules, active Routes and firewall rules first. Online removal also requires no roles or Processes. The caller, Gateway and VPN Nodes are protected. Drain task VMs and clear the task VM host setting before removing their host.

An unreachable Node keeps its host state. The final Operation result lists `roles_shed` and `retained_on_node`. Human output shows the same retained state. macOS retains `user`, `package-managers` and `host-wireguard`. An iPadOS peer retains `host-wireguard`. Online Linux removal retires its observer and worker only after the serving fleet is clean.

A failed cleanup retains the Node record. Swamp restores membership and serving publications in the same run. If restoration fails or retirement has an uncertain outcome, the Operation reports `node.removal_rollback_failed`. Ctrl-C stops following; it leaves the Operation running. Use `operation:show` to follow it again.

[Remove a Node](/reference/node-provisioning#remove-a-node) describes placement, cleanup and restoration.

## Why it works this way

These reasons explain the design. Check them before you propose a change.

### A dedicated relocate for gateway

The Gateway process serves the API. Removing the last `gateway` assignment and adding it again would drop the Gateway's authority and the `gateway.orbit` DNS record in between, so the second request might not run. Relocate keeps one active assignment for the whole move. Two active `gateway` assignments are rejected, because the fleet needs one authority and one address. The machine that runs the Gateway process keeps its authority during a move, because the bootstrap records it as the serving host.

### One relocate action for every relocatable role

Each role definition states whether the role is relocatable. Orbit does not infer it from singleton and mutable, because generic add and remove is a wider contract than a move. `gateway`, `websocket`, and `metrics` are relocatable. One relocate action runs the shared steps for all three: the singleton lock, the source check, the settings copy, and the assignment transfer. Role-specific work runs as a step for that role inside the same action. A new relocatable role adds the flag and its step, not a new command.

### The target's credentials win

A target that already holds working role credentials keeps them. Relocate copies only the credentials the target lacks, because overwriting a working identity would break its clients.

### Relocate moves no secrets

The checkout, the SQLite database, the Orbit CA, and the SSH keys live on the machine that runs the Gateway process. Copying them inside relocate would turn it into a secret-moving installer. You copy that state yourself and then converge the Gateway web stack on the new machine.

### vpn does not move

The WireGuard hub and private DNS stay on their original Node. `vpn` is protected from `node:role:add`, `node:role:remove`, and relocate.

### Rename is its own verb

A rename changes one identity field and does not touch WireGuard. Removing and adding the Node again would delete its WireGuard peer and records. `node:update` is rejected as a name, because update means a partial field patch.

Role addition returns one queued Operation for every mutable role. `node:role:add` follows it to completion and prints any follow-up warning. Use `--converge` to converge an existing assignment and `--idempotency-key` to retry the same request.

## orbit node:network:converge

Converge a Node's WireGuard peer and publish the current peer list on the VPN hub.
The Gateway captures the Node's saved network policy and admits one native Swamp
Operation. The CLI follows that Operation to its terminal result.

```bash
orbit node:network:converge <node> [--idempotency-key=KEY] [--json]
```

`node` accepts an ID or exact Node name. Reuse `--idempotency-key` to retry the
same admission. This command accepts no credentials, scripts, pins, or placement
options. It requires an active managed peer selected for worker rollout. The VPN
hub uses its exact logical worker; it never runs on another Node as a fallback.
A failed publication restores the saved peer configuration and resolver policy.
An interrupted publication restores its transaction baseline before reapplying
the complete desired configuration and DNS policy.

Role removal and relocation return one native Operation. The CLI follows the parent through all source and target work. `node:role:add --converge` selects `node.role_converge` and uses the same target DAG. Each command accepts `--idempotency-key` for an admission retry. A confirmed relocation target remains active if later source cleanup fails; the parent reports that cleanup failure. Offline cleanup is unavailable until its owning native path can prove the retained effects.


## orbit node:wireguard-hub:converge

Publish the current admitted peer inventory on the active VPN hub in one native Operation. This changes no peer key or address. VPN1 runs through its approved SSH proxy worker with exact logical `node=1` placement.

```bash
orbit node:wireguard-hub:converge 1 --idempotency-key=hub-reconcile-once
```

The command accepts a Node ID or name, `--idempotency-key=KEY`, and `--json`. It follows the recorded Operation and returns a nonzero exit status for a failed or cancelled run. Missing proxy readiness refuses or leaves the placed work waiting; it never selects another host. See [WireGuard hub convergence](/reference/wireguard-endpoints#converge-the-hub).
