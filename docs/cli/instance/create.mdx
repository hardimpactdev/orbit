```bash
orbit instance:create <project> <node> <name> [--root=PATH] [--domain=HOST] [--branch=BRANCH] [--database-server=SLUG] [--wait-active] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `project` | yes | Numeric Project ID. |
| `node` | yes | Numeric ID of an active Node with the `app-dev` role. |
| `name` | yes | Instance name. `default` is the Project's default development source. A name that equals the Project `default_branch`, such as `main`, creates the `default` Instance. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--root=PATH` | the Project root | Relative web-root override for this Instance. |
| `--domain=HOST` | generated | Route domain. Without it, Orbit generates one from the active Cluster TLD, then the Node TLD. |
| `--branch=BRANCH` | see [branch selection](#branch-selection) | Source branch. |
| `--database-server=SLUG` | none | Create the Instance's database on this [Database server](/reference/database-servers) before setup. See [database on a server](/domains/applications#database-on-a-server). |
| `--idempotency-key=KEY` | generated | Reuse a key to retry the same [Operation start](/reference/operations#start-an-operation). |
| `--wait-active` | off | After the create, follow the clone's completion too. Exit 0 only when the Instance is `active`. See [fully set up](#fully-set-up). |
| `--json` | off | Print the result as JSON. |

In a terminal, an omitted project and node are chosen from interactive lists, with the Nodes limited to active `app-dev` Nodes, and an omitted name is asked for with the default `default`. A noninteractive or `--json` call that omits one is refused with `input.invalid`, naming the input, and sends no request.

```bash
orbit instance:create 4 7 default
orbit instance:create 4 7 feature-one --branch=release --domain=feature.example.test
orbit instance:create 4 7 t3-1a2b3c4d --branch=t3code/1a2b3c4d
```

In a terminal, the CLI shows the run's steps as a progress tree, then the result with the task and request IDs. It names the Project and the Node, not only their IDs. On a host checkout, create runs these steps on the Node, in order. Steps 1 and 2 run together as the `checkout` phase and step 5 runs as the `setup` phase. A failed setup step stops the run, and its name is in the failed step's log.

1. Clone the repository and check out the branch. Orbit mints a read token for this one repository, valid one hour. The token is never part of a command line and is removed from the Node after the clone.
2. Write `.env` from the Project's env template, with `APP_URL`, a new `APP_KEY` and the database keys. The file has mode 0640 and group `orbit-env`. An owned MySQL or PostgreSQL database also gets `.env.testing`.
3. When the Project's `default` Instance has a SQLite database, copy it to the same path in the new checkout. The copy is the Instance's own `<project>-<instance>` connection, and `.env` already names it.
4. With `--database-server`, or when the `default` Instance's database is MySQL on a Database server, create the Instance's owner, database and test database there, as [`database:create --instance`](/reference/database-servers#create-a-database-on-a-server) does. A MySQL `default` database is then copied in.
5. Run the Project setup steps, such as `composer install` and `php artisan migrate`, in order, as the Node's configured user.
6. Create and start the Processes from the Project's development Process definitions.
7. For a web-serving Project, create its Route (its key, CSR and signature are made at the start, beside the checkout) as [`route:create`](/cli/route/create) does, and probe the site over TLS. When this run starts every Process of the Instance, the Instance also becomes awake, so the first request reaches the application and not the wake page.

A host checkout's run has 60 seconds, plus the setup step timeouts, 30 seconds for the Processes, 180 seconds for the Route, and 180 seconds for a database copy or a database on a server.

A clone's create captures its Route publication at its admission; a Route that cannot be captured, such as a Cluster Route without a recorded Router (`cluster.router_required`), refuses the create before anything is recorded. A Project that serves no web pages has no Route and takes no `--domain` (`instance.route_unserved`). A domain that another Route owns, or a reserved name such as `gateway.orbit`, is refused with `route.domain_conflict`.

## On a container Node

On a Node of the [build list](/reference/development-containers#the-build-list), the Project's first `default` Instance is a container, not a checkout ([chart](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/instance/container/create-default.mmd)). Orbit creates the container from the Node's image and fetches the default branch into a mirror on the Node. It pushes the branch in, writes `.env`, and runs the Project's [development deploy steps](/reference/deployments#development-deploy-steps) as `orbit`; there are no setup steps. Then it starts FrankenPHP, publishes the Route to it, and takes the first seed snapshot. A Project has one `default` in the fleet, and its other Instances are made on that `default`'s Node. [The default Instance](/reference/development-containers#the-default-instance) has the details and what a container default cannot run yet.

Every other Instance of the Project is a clone of that `default` ([chart](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/instance/container/create.mmd)). Orbit copies the default's newest seed snapshot, a ZFS clone, and gives the copy its own address, ACL and T3 port. It brings in the Instance's branch, and writes `.env`, the agent settings and `/etc/orbit/instance`. The clone's `.env` is the default's, with the clone's own keys in place of the default's ([the environment of a clone](/reference/development-containers#the-environment-of-a-clone)); a connection that the default marks shared stays attached. Then it starts T3 and records the T3 server with the [Conn layer](/reference/conn#instance-servers). Beside the copy, it publishes the clone's address when no other Route write holds the Route's Nodes; with a Node held it never waits, and the completion publishes the address. The result's `route_publication` says which: `published`, `deferred` or `failed` ([the address during the create](/reference/development-containers#the-address-during-the-create)). The address answers TLS when the create succeeds, and the app answers once the completion has started it. The branch is the matching origin branch, or a new branch at the seed's commit. [Create](/reference/development-containers#create) has the details.

A clone's create ends there, when the user can start a thread. In the same transaction the Gateway starts the clone's completion, [`instance:complete`](/cli/instance/complete). The completion clones the default's database, starts a nested fleet, starts FrankenPHP and the Processes, publishes the Route when the create did not, and checks the clone. A publication that failed in the create does not fail it: the create still succeeds, and the completion publishes again.

### Fully set up

A clone is fully set up only when its `status` is `active`. A succeeded create leaves it `source_resolved`; only a succeeded completion makes it `active`. The create's result names the completion in `completion_operation_id`. Follow that Operation, or read the Instance until its `status` is `active`. In a terminal, the result names it as `Completion: <id>`. With `--wait-active`, the command follows the create, then the completion, then reads the Instance. It exits 0 only when the Instance is `active`; with `--json` it prints the last Operation it followed. A create that has no completion, such as the create of a `default`, is fully set up when it succeeds.

A clone is fully set up about 10 seconds later than when one create did every step: two runs start and stage their folders. The thread is usable about 10 seconds sooner.

A failed or cancelled create keeps its reservation, runtime, and any container, workspace, owned databases, test databases and role until the owner acts. A refused retry removes none of them. After work starts, Orbit attempts to stop the container and to withdraw a Route that the run published. A clone's create withdraws only a publication that did not succeed; an address it published stays until a retry or `instance:destroy`. Compensation can fail; its step then stays failed. Shared service endpoint records and rules may remain even after destroy until endpoint lifecycle work is live.

Its Operation result names `recovery.state=retained_for_retry`, the create identity and the destroy path. Retry with a new idempotency key and the original options, including the source selection and Database server.

At retry admission, Orbit derives the Processes from the Project's current development definitions. Changed definitions update their Processes; removed definitions remove theirs. Orbit replaces their units and environment files in the run that installs them: the create for a `default`, the completion for a clone. A retry of a clone's create admits a new completion when it succeeds. A dead Process of a clone fails its completion with `instance.container_process_inactive`, not the create. A clone can be removed with `instance:destroy INSTANCE --yes --force`; container-default removal remains unavailable.

The API answers `202` with a queued Operation after recording the create, before work on the Node starts. Clients follow that Operation as usual. While it waits to start, another create for the same name is refused with `operation.target_busy`; a replay with the same Idempotency-Key returns the original Operation.

## Branch selection

| Creation input | Checkout | Selected branch |
| --- | --- | --- |
| `default` or the default branch name, without `--branch` | `<node-apps-root>/<project-slug>/default` | The Project `default_branch`. |
| Another name without `--branch` | `<node-apps-root>/<project-slug>/<name>` | The matching origin branch, otherwise the existing local branch, otherwise a new branch from the fetched `default_branch` commit. |
| Any name with `--branch` | The checkout for the requested name | The requested origin branch, otherwise the existing local branch, otherwise a new branch from the fetched `default_branch` commit. It need not match the Instance name. |

An existing local branch is not reset. If the fetched `default_branch` is needed and missing, create fails. An invalid Git branch name is refused with `validation.failed` before anything changes. When the name equals the default branch, the result carries `name_converted_from` with the requested name, and `--branch` keeps its meaning. See [a default-branch name means default](/domains/applications#a-default-branch-name-means-default).

## Repeat and failure

The Instance and its Route become active only after every step succeeds: for a clone, every step of its completion. A clone's Route is the exception: it turns active as soon as the create has published it. A successful create means every setup step succeeded; an empty list counts as success. The application can still fail for other reasons.

Repeating the command for an Instance that is already created succeeds with `Skipped — already created (instance.exists)`.

A failed create attempts to withdraw the Route it published: the Caddy site, the PHP pool, the private DNS records and the certificate folders. Compensation can fail; its step then stays failed. It keeps the Instance, its checkout, its Processes and its database for retry. The Instance stays `reserved` or `source_resolved`, with its failed step and error code; an unactivated Route stays `pending`. The task keeps the failed step and its error code, so nothing on the Node is needed to see what failed. A setup step that is missing or not executable fails with `instance.setup_step_unavailable`, naming the step and the Node. Any other setup failure is `instance.setup_step_failed`.

Run the command again with a new idempotency key once the task has ended, or run `instance:destroy` first.

If the cleanup does not finish, the Instance stays marked failed with `details.cleanup = "incomplete"`. Run the same command again to finish the cleanup and create the Instance, or run [`instance:destroy`](/cli/instance/destroy). A changed `--root` or `--branch` is refused with `instance.placement_conflict` until the cleanup is done.

## Errors

| Error code | Meaning |
| --- | --- |
| `instance.candidate_required` | The Node is a production Node. Create a production Instance with [`instance:clone`](/cli/instance/clone). |
| `instance.node_inactive`, `instance.node_not_app_dev` | The Node is not active, or has no active `app-dev` role. |
| `instance.task_vm_node` | The Node is a task VM. A task gets its workspace from [`task:start`](/reference/tasks#provision-an-external-group). |
| `instance.default_path_occupied`, `instance.path_taken` | The checkout path is in use on the Node. |
| `instance.placement_conflict` | A repeat changed the root or branch while an earlier failed create is still being cleaned up. |
| `instance.removal_conflict` | The Instance is being removed. |
| `instance.route_unserved` | `--domain` was given for a Project that serves no web pages. |
| `route.domain_conflict` | Another Route owns the domain, or the name is reserved. |
| `instance.database_server_existing` | `--database-server` was given for an Instance that finished its first setup. |
| `instance.database_slug_taken` | The database connection name belongs to another owner. |
| `instance.setup_step_failed`, `instance.setup_step_unavailable` | A setup step failed, or its command is missing. |
| `operation.target_busy` | Another change to the Instance is running. |
| `instance.default_missing` | The Project's `default` runs in a container on another Node, is not active or has no seed snapshot yet, or a build-list Node has no `default` of the Project yet. |
| `instance.database_clone_unsupported` | The default's database cannot be cloned: a clone in a container names another Database server, or the database is not on a server. |
| `instance.create_agent_failed`, `instance.t3_unready` | A clone's T3 step failed; `failed_step` is `t3` for both, because one step writes the agent's files and then starts T3. The first code means the agent part failed or timed out; the second means T3 did not answer within 30 seconds of its start, T3's CLI failed to issue a session or add the project, or that part failed or timed out. |
| `instance.create_register_failed` | A clone's T3 server refused a session the run issued, or the Gateway's session lacks `access:read` and `access:write`. The step's report names the `conn.*` code. |
| `instance.workspace_baseline_unavailable` | The run of a clone succeeded, but the Gateway could not read the workspace baseline before it ended the create. `failed_step` is `register`. The T3 server is not recorded, no completion starts, and the container keeps running. Retry the same command, or destroy the clone. |
| `instance.host_unavailable` | The container Node is not prepared, its bridge or its T3 ports are full, or its runtime folder lacks the Project's PHP build. |
| `project.source_defaults_incomplete` | The Project's source defaults are incomplete, or a web-serving Project in a container has no PHP version. |
| `operation.kind_unavailable` | The request needs a part of the container runtime that is not built yet, or a clone needs Conn or the model router guard. |
| `instance.nested_fleet_host_unavailable` | The Project has `nested_fleet` on, and the Node has nested-fleet hosting off. Orbit records nothing. See [Nested fleet setting](/reference/projects#nested-fleet-setting). |
| `instance.nested_fleet_container_required` | The Project has `nested_fleet` on, and the result would not be a container: the Node is not on the build list, or the default is a host checkout. Orbit records nothing. |
| `instance.nested_fleet_image_unavailable` | The Project has `nested_fleet` on, and the Node's last converge failed to build the nested-fleet image. The create of the default makes no container. Converge the Node again; see [The nested-fleet image](/reference/development-containers#the-nested-fleet-image). |
| `instance.nested_club_key_unsafe_transfer`, `instance.nested_club_key_not_tmpfs`, `instance.nested_club_key_delivery_failed` | A nested-fleet clone could not get its Club key into `/run`. The workspace phase did not run. See [the Club key of the nested Gateway](/reference/development-containers#the-club-key-of-the-nested-gateway). |
