# Swamp proof topology

`bin/swamp-proof` proves a Swamp kind against a real Gateway, real Swamp and a real Node on one disposable VM on Beast or Shark. The topology is minimal (Nick, 2026-11-01): grow it only when a kind needs more.

```sh
bin/swamp-proof up                 # provision (or keep the held VM), stage this commit, bring the topology up
bin/swamp-proof run firewall.allow firewall.deny firewall.remove firewall.remove-ambiguous firewall.deny-peer firewall.deny-ssh
bin/swamp-proof receipt            # path of the latest receipt
bin/swamp-proof down               # cancel the task group; the VM is destroyed
```

A lane runs its consecutive kinds on one `up`: `run a b c` and later `run d` reuse the held VM, and `down` comes at the end. A fixture with `"clean": true` needs a clean end state: when another fixture ran since the last `up`, `run` first restages the held VM with new nested Nodes and a fresh Gateway database. Only a fixture that a leftover would change marks itself clean.

Provision checks the Operation's compact input summary for an Incus placement on Beast or Shark and matches its admitted image fingerprint to the terminal image result. It does not read nested execution payloads. Guest setup then verifies the nested topology. Repeating `up` follows the existing provision Operation under its original key and reuses its VM.

Always finish with `down`. Proof VMs do not outlive the proof. Two mechanisms catch a lane that forgets:

- The `proof-reaper` schedule runs on Node 209 every 10 minutes for every machine. The Gateway publishes the open Project 62 groups as its inputs, with each running VM's pinned SSH target. Swamp reads each heartbeat with one official `@swamp/ssh exec` (`stat -c %Y /home/orbit/swamp-proof-activity`) and chooses a group when the heartbeat is older than 60 minutes, when the file is missing and the group started more than 60 minutes ago, or when a newer open group of the same lane exists. A group older than 90 minutes is chosen too, unless a heartbeat from the last 60 minutes renewed it: that catches groups whose VM has no pinned key, an unreadable heartbeat or no VM at all. Otherwise an unreachable VM is left alone. The Gateway then cancels each chosen group with the normal cancel intent, which destroys the VM. No Swamp step calls the Gateway.
- `up` and `run` touch the heartbeat at their start and end. It lives outside `/home/orbit/swamp-proof`, which every `up` replaces.
- Each group is titled `swamp-proof <host>:<session> <topology>@<version>`. The lane is `<host>:<session>`: one machine and session hold one VM at a time, so an older open group of the lane is a leftover.
- Before `up` or `run` takes a slot, the tool also takes down every other local session that ran nothing for 60 minutes or is older than 8 hours; a session whose command is running is skipped. A cancel that ended without success is not replayed: the next `down` admits a new one under the next idempotency key, because the Gateway replays a key's original Operation. It then trusts only the Gateway's group record: cancelled, with the VM destroyed. `--session NAME` (default `minimal`) gives each user of the tool its own VM and session file.

## Topology `minimal`

[`topologies/minimal/topology.json`](topologies/minimal/topology.json) holds its version. One shared version serves every lane; the proof topology owner changes it, and lanes request changes instead of versioning it themselves. A topology change bumps the version. A receipt records the version it ran on and stays valid for that version.

- One task VM in Project 62 (`swamp-proof`), provisioned through the normal Gateway API. It boots with a clone of its host's topology seed and receives the proof club key at `/home/orbit/.config/swamp/club-api-key`.
- The task VM runs the Gateway from the staged commit (SQLite, Gateway queue on its database driver) and the pinned Swamp serve with one worker, `orbit-node-209`, with production's 16 dispatch slots (two workers of 8 there). It is seeded as Node 209 with the `gateway` and `swamp` roles (F14), because the Gateway places every native step on Node 209. Serve terminates TLS itself on `swamp.orbit:443` with a leaf signed by a VM-local CA. Serve fires schedules, as on 209, so a Schedule's own workflow fires; `up` pauses every checked-in schedule first, so fleet upkeep does not run in a proof. The Gateway starts runs as `user:orbit-gateway` and reads history as `user:orbit-gateway-read`, as in [gateway-environment](../../docs/reference/gateway-environment.md).
- The Gateway has an Orbit root CA in `~/.orbit/ca` with `keyUsage` (`keyCertSign`, `cRLSign`), also in the VM's system trust, and the frozen agent delivery manifest. It runs as production does (version 12): the gateway and websocket role certificates from that root sit in `/etc/caddy/orbit-cert-current` and `/etc/caddy/orbit-websocket-cert-current`, PHP-FPM serves `/run/php/orbit-gateway.sock`, `ORBIT_GATEWAY_CHECKOUT` names the staged Gateway, and the VPN subnet is the topology network. Caddy loads the Node's complete Caddyfile from the Gateway's own Caddy build renderer with its admin endpoint on localhost, so a later Caddy build, Metrics publication or certificate reload on Node 209 works unchanged. The worker key logs in to the VM's own address, as on any Node.
- Each entry under `nodes` is a nested VM, a copy of the seed's `node-template` on the bridge `oeproof`, seeded as a Node record named by its `key`, with its `roles` and `settings`. Every Node has the `orbit` user, the worker's and the Gateway's SSH keys authorized, UFW active with an unmanaged `proof-ssh` rule, the managed `orbit:wireguard-members` rule exactly as the Gateway renders it (`allow in on orbit`), and an unmanaged `proof-network` rule that admits the proof network, which has no `orbit` interface (version 15), and a Node agent key in `/etc/orbit/agent/secret` whose verifier the Gateway records. No Node has a WireGuard key, so none is a private DNS peer.
  - `target` (`app-dev`) is the fixtures' default target. As after app-dev role convergence, it has an Orbit-managed Caddyfile, `/data/caddy/orbit/hibernation`, and active Caddy and PHP-FPM 8.5 and 8.4.
  - `metrics` (2 GiB, version 15: Grafana and Prometheus together need more than 1 GiB) has no role. A fixture that needs the metrics role enables it in `prepare` through the normal API (`metrics/enable` with `${node.metrics}`), so Prometheus runs as that role starts it.
  - `target` also has `agent`: `up` converges it through the real `node:converge`, so `orbit-agent.service` runs the pinned release with the seeded secret and verifier, and reaches the Gateway and Reverb over the proof network. `bin/swamp-proof up --agent-delivery DIR` takes a `build-delivery` directory; `up` installs its `orbit-agent-linux-x86_64` over the pinned binary on every agent Node and restarts the agent.
- With `websocket`, the VM (Node 209) holds the `websocket` role as its convergence leaves it (version 11). The Gateway issues the server credentials and renders Reverb's `.env` and `orbit-websocket.service`; the pinned `orbit-reverb` release serves `wss://reverb.orbit` behind the VM's Caddy, and its registry reports confirm it. The role's own convergence needs a per-Node worker the topology has not, so `up` runs those steps.
- The operator (`10.231.0.2`) is a caller-only peer: an active WireGuard address with Node access, but no SSH host key or fingerprint, so no publication treats it as a managed Node (version 13).
- The VM runs the agent-view subscriber (`php artisan orbit:agent-view`) as `orbit-proof-agent-view.service` (version 11).
  - `peer` has no role. It is a second plain Node, such as a WireGuard peer beside a hub on `target`.
- An `operator` Node record (no VM) is the caller. It has access to the Gateway and every Node.

`up` stages `git bundle HEAD`, so commit first. Each `up` starts fresh Swamp credentials and a fresh Gateway database. Run `up` again on a held VM to restage it at a new commit. `run` moves the held VM forward by itself only when fixtures or the harness driver changed; the receipt lists those refreshes.

## Fixtures

`<kind>.json` declares `topology` (default `minimal`), `clean` (see above), `prepare` and `request` (API calls, or for a Gateway-host operator command `{artisan, arguments}`, with `${node.<key>}` and `${proof.run}` bindings; a record request's `bind` names its reply's `id`, or for a list the first item's that equals `match`; an Operation request's `bind` names the Operation's target), `clean_target` and `before_target` (argv run on the target; `before_target` takes the same bindings), `before_node` (`{"<node key>": [argv, ...]}`, run as root on that Node before `prepare`, with bindings, such as a package a kind needs there), `before_gateway` (argv run as root on the task VM from the staged checkout, with bindings, before `prepare`: for Node records a fixture needs through `gateway.php fixture`, such as `replace_roles: {node_id: [role]}` for an app-prod placement or `node_updates: [{id, attributes}]` for a Node's `lan_ip`, `gateway_settings: [{key, value, secret?}]` for settings an extension's setup leaves, or `task_vm_image_builds: [attributes]` for a promoted image build, or a service the topology lacks; its last stdout line may be `{"secrets": {name: value}}`, test credentials it made, which bind as `${secret.<name>}` into requests only, never a receipt), `after_prepare` (argv run like `before_gateway`, after `prepare` and with its bindings, such as `gateway.php fixture` with `routes: [{id, attributes}]` or `instance_updates: [{id, attributes}]` to change a prepared Route or Instance, or `analytics_tracking: [{instance_id, domain}]` for the tracking Route and site binding a finished `analytics.enable` leaves (with an active `analytics` role through `roles`), such as a failed Route whose sites stay published), `expect`, `phases` (native job, step and budget), `budget_seconds` and `parity`, a script path or `[script, args...]` that checks the legacy contract on the real target. `expect` is `{status}` for a run, or `{http_status, error_code}` for an admission refusal: the receipt then proves the code, that no Operation was created, and the parity check. Each API call goes through the Gateway's HTTP kernel with the operator's address, or with the address of the Node its `caller` key names, such as `target` for `instance.register`. So peer identity, Node access and admission run as in production. [`gateway.php`](../../tools/swamp-proof-guest/gateway.php) then drives the production `SwampRunSubscriber` and fires its `operations` jobs until the Operation is terminal.

Parity reads the full Operation from the JSON file named by `PROOF_OPERATION_FILE`. The runner passes paths for large data, so recipe intents do not exceed the operating system environment size limit.

A `before_gateway` or `after_prepare` hook may also end with `{"bindings": {"operation": 73}}`. These public scalar values bind only under `${fixture.operation}`; they cannot replace Node or secret bindings. An internal kind such as `project.observe` uses its normal Schedule admission action in a hook and follows the returned Operation through the API. Private values still use the separate `secrets` channel.

## Receipts

`run` writes `~/swamp-execution/evidence/proof/<kind>/<UTC>-minimal.json`. A receipt names the topology and version, the commit, the VM, the Operation and native run, per-step and phase timings, parity, `up` to receipt time and time since first provision. `proof_pass` is true only when the Gateway and native status match `expect.status`, parity passes and every budget holds.

## Limits

- No WireGuard, Router, ingress, Reverb, Horizon or Caddy. Reverb drives the subscriber and Horizon works the queue in production; here `gateway.php` does both, paced below serve's per-IP WebSocket burst limit.
- The Gateway runs from source with `composer install --no-dev --no-scripts`; the release runner is not exercised.
