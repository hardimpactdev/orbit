# Swamp proof

## Current path: reset a fleet, run cases

[`reset/`](reset/README.md) is the proof path for new work. From the task VM, `bin/proof-fleet reset GROUP` builds a nested fleet inside that VM: a Gateway that also runs Swamp, `app-dev` and `app-prod`. The fleet has a real WireGuard network, `10.45.0.0/24`, with the hub on the nested Gateway. The outer task VM is the operator: its candidate CLI (`/usr/local/bin/orbit-nested`) talks to the nested Gateway as the WireGuard member `10.45.0.10`, as an operator machine does in the fleet. `bin/proof-fleet verify GROUP CASE...` runs one or more cases in order against that ready generation and prints a verdict for each. [`selection.txt`](selection.txt) maps changed paths to the commands whose cases a commit needs; [`orbit proof:run`](../../docs/cli/proof/run.mdx) reads it. `bin/proof-fleet release GROUP` removes it. The outer VM, its observer and its checkout stay as they were.

A build takes about 230 s. Ready copies make the next reset about 75 s, of which the boot is about 50 s: `bin/proof-fleet ready GROUP` copies a healthy fleet to stopped `fleet-ready-*` copies, and `bin/proof-fleet reset GROUP --from-ready` replaces the three guests with them, applies the candidate and checks readiness. `verify` uses the copies by itself when they can replace the active fleet, and builds as before when they cannot. If `reset --from-ready` finds no usable copies it builds, then makes them. See [Ready copies](reset/README.md#ready-copies-and-the-fast-reset).

A reset from ready copies ends with an Incus memory snapshot `base` of the three nested VMs (phase `base-take`, about 17 s, the VMs keep running). The phase `base-restore` puts them back to `base` in one 30 s limit (restore about 9 s, healthy about 20 to 26 s on a task VM), sets the guest clocks from the outer VM, and fails with an infrastructure error, without a retry, past the limit or on any error. See [The base snapshot](reset/README.md#the-base-snapshot).

The boot fixes that keep a reset near 50 s (agent after the tunnel, cloud-init off, the hosts line, Swamp serve and worker at boot, 2 vCPUs for the Gateway, dev-safe opcache and no Laravel caches) are code in [`tools/swamp-proof-guest/boot.py`](../../tools/swamp-proof-guest/boot.py). A fresh build writes them; nobody edits a VM by hand.

Cases live under `swamp/proof/<family>/cases/`. A case calls the real candidate CLI, checks the real effect and exits 0 (pass), 1 (fail) or 2 (unrun). The first one is [`firewall/cases/allow-fresh-ipv4-tcp.sh`](firewall/cases/allow-fresh-ipv4-tcp.sh): a real `firewall:allow` opens real traffic.

## Ready copies: the contract

`bin/proof-fleet ready GROUP` is the one way to make ready copies. Anything else that stores or restores a nested fleet (the topology seed, B3) uses these names and keys.

- **Names:** `fleet-ready-gateway`, `fleet-ready-app-dev`, `fleet-ready-app-prod`. Stopped Incus VM copies in the same project and pool as the fleet.
- **Keys** on each copy: `user.ready.set` (one identity for the three), `user.ready.role`, `user.ready.made` (UTC, the copy), `user.ready.minted` (UTC, when the fleet's credentials were minted: the 20 h age counts from this), `user.ready.attempt`, `user.ready.inputs` (a digest of `boot.py`, `fixture.py` and the agent pin; a different digest makes the set stale), `user.ready.hwaddr`, `user.ready.ipv4`, `user.ready.subnet` (the network's `ipv4.address`). The Gateway copy also has `user.ready.nodes` (JSON of Node name to Gateway Node id). `user.ready.complete` equals `user.ready.set` and is written by the last step of `ready`, after the restarted fleet passed its checks; a failed `ready` deletes its half-made set, and a set without it is not used. `ready` copies only a fleet whose readiness check passed. A full `reset` deletes existing copies.
- **Not on a copy:** no `user.orbit.e2e.*` label, no `eth0` device, no `orbit-source` device and no `user.ready.mounts` key. A restore adds the label and the NIC for the generation it restores into. A copy holds its own checkout at `/home/orbit/orbit`; a restore syncs the candidate's code into it by rsync.
- **Stateful, no snapshots.** The guests have `migration.stateful=true` and a root `size.state` equal to `limits.memory`, set while they are stopped (`ready` on the originals, a restore on each restored guest). A copy and a restore use `incus copy --instance-only`, so a copy never carries the `base` snapshot of an earlier fleet.
- **No secret.** The proof Swamp Club key is never in a copy. `ready` deletes it from the running Gateway, scans every file of all three guests (`find / -xdev`, no size limit, a grep error fails) for the key and stops with the paths if one holds it (the running fleet gets its key back either way), runs `fstrim -av` under `timeout` so the freed blocks of the deleted key are discarded from the disk image that every task VM clones (the output is in the receipt), and checks that all three guests report `Stopped` before it copies. The restore pushes the key in after the Gateway agent is up, as the full build does, then restarts Swamp serve and the worker.
- **Source.** The Gateway's database and its `.env` key belong to the source tree it was built from. Today the fast reset takes that state (`.env`, `storage`, `bootstrap/cache`, the agent manifest) and the attempt lease from the source of the active generation, so it needs an active generation whose network has the subnet of the copies. A fresh task VM with only seed copies is not covered yet: it needs the runtime state of the source stored with the copies and a network and lease created for it.

# Swamp proof topology (superseded)

`bin/swamp-proof` proves a Swamp kind against a real Gateway, real Swamp and a real Node on one disposable VM on Beast or Shark. The topology is minimal (Nick, 2026-11-01): grow it only when a kind needs more.

```sh
bin/swamp-proof up                 # provision (or keep the held VM), stage this commit, bring the topology up
bin/swamp-proof run firewall.allow firewall.deny firewall.remove firewall.remove-ambiguous firewall.deny-peer firewall.deny-ssh
bin/swamp-proof receipt            # path of the latest receipt
bin/swamp-proof down               # cancel the task group; the VM is destroyed
```

A lane runs its consecutive kinds on one `up`: `run a b c` and later `run d` reuse the held VM, and `down` comes at the end. A fixture with `"clean": true` needs a clean end state: when another fixture ran since the last `up`, `run` first restages the held VM with new nested Nodes and a fresh Gateway database. Only a fixture that a leftover would change marks itself clean.

Provision checks the Operation's compact input summary for an Incus placement on Beast or Shark and matches its admitted image fingerprint to the terminal image result. It does not read nested execution payloads. Guest setup then verifies the nested topology. Repeating `up` follows the existing provision Operation under its original key and reuses its VM.

Always finish with `down`. Proof VMs do not outlive the proof. The scheduled reaper catches a lane that forgets:

- The `proof-reaper` schedule runs on Node 209 every 10 minutes for every machine. The Gateway publishes the open Project 62 groups as its inputs, with each running VM's pinned SSH target. Swamp reads each heartbeat with one official `@swamp/ssh exec` (`stat -c %Y /home/orbit/swamp-proof-activity`) and chooses a group when the heartbeat is older than 60 minutes, when the file is missing and the group started more than 60 minutes ago, or when a newer open group of the same lane exists. A group older than 90 minutes is chosen too, unless a heartbeat from the last 60 minutes renewed it: that catches groups whose VM has no pinned key, an unreadable heartbeat or no VM at all. Otherwise an unreachable VM is left alone. The Gateway then cancels each chosen group with the normal cancel intent, which destroys the VM. No Swamp step calls the Gateway.
- `up` and `run` touch the heartbeat at their start and end. It lives outside `/home/orbit/swamp-proof`, which every `up` replaces.
- Each group is titled `swamp-proof <host>:<session> <topology>@<version>`. The lane is `<host>:<session>`: one machine and session hold one VM at a time, so an older open group of the lane is a leftover.
`up` and `run` never expire another local session; the scheduled reaper owns that cleanup. A cancel that ended without success is not replayed: the next `down` admits a new one under the next idempotency key, because the Gateway replays a key's original Operation. It then trusts only the Gateway's group record: cancelled, with the VM destroyed. `--session NAME` (default `minimal`) gives each user of the tool its own VM and session file.

## Topology `minimal`

[`topologies/minimal/topology.json`](topologies/minimal/topology.json) holds its version. One shared version serves every lane; the proof topology owner changes it, and lanes request changes instead of versioning it themselves. A topology change bumps the version. A receipt records the version it ran on and stays valid for that version.

- One task VM in Project 62 (`swamp-proof`), provisioned through the normal Gateway API. Project 62 is in the Gateway's `ORBIT_TASK_VMS_LARGE_PROJECTS`, so the VM is a [large task VM](../../docs/reference/compute-drivers.md#size-of-a-task-vm) (12 GiB, 6 CPUs, since 2026-11-03): its three 2 GiB Nodes beside Gateway and Swamp ran a medium 8 GiB VM out of memory. It boots with a clone of its host's topology seed and receives the proof club key at `/home/orbit/.config/swamp/club-api-key`.
- The task VM runs the Gateway from the staged commit (SQLite, Gateway queue on its database driver) and the pinned Swamp serve with one worker, `orbit-node-209`, with production's 16 dispatch slots (two workers of 8 there). It is seeded as Node 209 with the `gateway` and `swamp` roles (F14), because the Gateway places every native step on Node 209. Serve runs as the swamp role leaves it (version 17): on loopback port 9418, behind `swamp.orbit`, a private custom proxy Route on Node 209 as an operator records it, which Caddy serves with a certificate from the Orbit root. The Gateway reaches it by the production defaults. Its `ORBIT_SWAMP_SSH_PUBLIC_KEY` is the public half of that node-proxy key, which admission sends to the swamp role (version 18). The role's prerequisites are in place too: the node-proxy key at `/etc/orbit/node-proxy/id_ed25519`, its identity at `/etc/orbit/swamp-role-worker/ssh-identity` (root, the `orbit` group, `0440`), and enrollment and server tokens for `orbit-swamp-worker@a` and `@b` under `/etc/orbit/swamp-role-worker/<a|b>/`. So a `swamp` role converge on Node 209 starts both workers against this serve. Node 209 also runs its own agent: the unit `node:converge` renders for Node 209, as `orbit-agent.service` in root's user manager (the agent starts only in a cgroup of that name, and the task VM's own observer holds the system unit), with its configuration and secret bound over `/etc/orbit/agent` in the unit's own mount namespace. Doctor reads 209's role and firewall facts from it, and the task VM's own `orbit-agent` keeps reporting the VM to the fleet. A VM-local CA remains for fixtures that sign their own sites. Serve fires schedules, as on 209, so a Schedule's own workflow fires; `up` pauses every checked-in schedule first, so fleet upkeep does not run in a proof. The Gateway starts runs as `user:orbit-gateway` and reads history as `user:orbit-gateway-read`, as in [gateway-environment](../../docs/reference/gateway-environment.md).
- The Gateway has an Orbit root CA in `~/.orbit/ca` with `keyUsage` (`keyCertSign`, `cRLSign`), also in the VM's system trust, and the frozen agent delivery manifest. It runs as production does (version 12): the gateway and websocket role certificates from that root sit in `/etc/caddy/orbit-cert-current` and `/etc/caddy/orbit-websocket-cert-current`, PHP-FPM serves `/run/php/orbit-gateway.sock`, `ORBIT_GATEWAY_CHECKOUT` names the staged Gateway, and the VPN subnet is the topology network. Caddy loads the Node's complete Caddyfile from the Gateway's own Caddy build renderer with its admin endpoint on localhost, so a later Caddy build, Metrics publication or certificate reload on Node 209 works unchanged. The worker key logs in to the VM's own address, as on any Node.
- Node 209 admits the isolated proof subnet on `oeproof` through an unmanaged `proof-network` rule (version 19). The rule is limited to that bridge, source subnet and Gateway address. It lets nested Nodes reach Gateway-hosted services, including exporters. Product firewall rules still use `orbit`, as in the fleet. The Gateway starts with its baseline and Gateway-role rules from the shared catalog, and the app-dev peer starts its observer. Restaging removes the earlier proof-only HTTPS allowance.
- Each entry under `nodes` is a nested VM, a copy of the seed's `node-template` on the bridge `oeproof`, seeded as a Node record named by its `key`, with its `roles` and `settings`. Every Node has the `orbit` user, the worker's and the Gateway's SSH keys authorized, UFW active with an unmanaged `proof-ssh` rule, the managed `orbit:wireguard-members` rule exactly as the Gateway renders it (`allow in on orbit`), and an unmanaged `proof-network` rule that admits the proof network, which has no `orbit` interface (version 15), and a Node agent key in `/etc/orbit/agent/secret` whose verifier the Gateway records. No Node has a WireGuard key, so none is a private DNS peer.
  - `target` (`app-dev`) is the fixtures' default target. As after app-dev role convergence, it has an Orbit-managed Caddyfile, `/data/caddy/orbit/hibernation`, and active Caddy and PHP-FPM 8.5 and 8.4.
  - `metrics` (2 GiB, version 15: Grafana and Prometheus together need more than 1 GiB) has no role. A fixture that needs the metrics role enables it in `prepare` through the normal API (`metrics/enable` with `${node.metrics}`), so Prometheus runs as that role starts it.
  - `target` also has `agent`: `up` converges it through the real `node:converge`, so `orbit-agent.service` runs the pinned release with the seeded secret and verifier, and reaches the Gateway and Reverb over the proof network. `bin/swamp-proof up --agent-delivery DIR` takes a `build-delivery` directory; `up` installs its `orbit-agent-linux-x86_64` over the pinned binary on every agent Node and restarts the agent.
- With `websocket`, the VM (Node 209) holds the `websocket` role as its convergence leaves it (version 11). The Gateway issues the server credentials and renders Reverb's `.env` and `orbit-websocket.service`, and `up` writes that `.env` unchanged (version 16); the pinned `orbit-reverb` release serves `wss://reverb.orbit` behind the VM's Caddy, and its registry reports confirm it. The role's own convergence needs a per-Node worker the topology has not, so `up` runs those steps.
- The operator (`10.231.0.2`) is a caller-only peer: an active WireGuard address with Node access, but no SSH host key or fingerprint, so no publication treats it as a managed Node (version 13).
- The VM runs the agent-view subscriber (`php artisan orbit:agent-view`) as `orbit-proof-agent-view.service` (version 11).
  - `peer` has no role. It is a second plain Node, such as a WireGuard peer beside a hub on `target`.
- An `operator` Node record (no VM) is the caller. It has access to the Gateway and every Node.

`up` stages `git bundle HEAD`, so commit first. Each `up` starts fresh Swamp credentials and a fresh Gateway database. Run `up` again on a held VM to restage it at a new commit; it keeps the nested Nodes and starts any that stopped. When a nested Node stops while it boots, or its agent or cloud-init fails, `up` fails with the Node's Incus status and console tail. `run` moves the held VM forward by itself only when fixtures or the harness driver changed; the receipt lists those refreshes.

## Fixtures

`node.add` uses a prepared candidate with the observer group already present. [Stock Node enrollment](#stock-node-enrollment) proves the later consumer creates that group on an unprepared Ubuntu VM.

`<kind>.json` declares `topology` (default `minimal`), `clean` (see above), `prepare` and `request` (API calls, or for a Gateway-host operator command `{artisan, arguments}`, with `${node.<key>}` and `${proof.run}` bindings; a record request's `bind` names its reply's `id`, or for a list the first item's that equals `match`; an Operation request's `bind` names the Operation's target), `clean_target` and `before_target` (argv run on the target; `before_target` takes the same bindings), `before_node` (`{"<node key>": [argv, ...]}`, run as root on that Node before `prepare`, with bindings, such as a package a kind needs there), `before_gateway` (argv run as root on the task VM from the staged checkout, with bindings, before `prepare`: for Node records a fixture needs through `gateway.php fixture`, such as `replace_roles: {node_id: [role]}` for an app-prod placement or `node_updates: [{id, attributes}]` for a Node's `lan_ip`, `gateway_settings: [{key, value, secret?}]` for settings an extension's setup leaves, or `task_vm_image_builds: [attributes]` for a promoted image build, or a service the topology lacks; its last stdout line may be `{"secrets": {name: value}}`, test credentials it made, which bind as `${secret.<name>}` into requests only, never a receipt), `after_prepare` (argv run like `before_gateway`, after `prepare` and with its bindings, such as `gateway.php fixture` with `routes: [{id, attributes}]` or `instance_updates: [{id, attributes}]` to change a prepared Route or Instance, or `analytics_tracking: [{instance_id, domain}]` for the tracking Route and site binding a finished `analytics.enable` leaves (with an active `analytics` role through `roles`), such as a failed Route whose sites stay published), `expect`, `phases` (native job, step and budget), `budget_seconds` and `parity`, a script path or `[script, args...]` that checks the legacy contract on the real target. `expect` is `{status}` for a run, or `{http_status, error_code}` for an admission refusal: the receipt then proves the code, that no Operation was created, and the parity check. Each API call goes through the Gateway's HTTP kernel with the operator's address, or with the address of the Node its `caller` key names, such as `target` for `instance.register`. So peer identity, Node access and admission run as in production. [`gateway.php`](../../tools/swamp-proof-guest/gateway.php) then drives the production `SwampRunSubscriber` and fires its `operations` jobs until the Operation is terminal.

Parity reads the execution envelope from `PROOF_OPERATION_FILE`: Operation ID, kind, target ID, status, error code, execution input, result and Swamp run ID. It omits internal `state`. Check public diagnostics through the Operation API. The runner passes paths for large data, so recipe intents do not exceed the operating system environment size limit.

A `before_gateway` or `after_prepare` hook may also end with `{"bindings": {"operation": 73}}`. These public scalar values bind only under `${fixture.operation}`; they cannot replace Node or secret bindings. An internal kind such as `project.observe` uses its normal Schedule admission action in a hook and follows the returned Operation through the API. Private values still use the separate `secrets` channel.

A scheduled producer with no Operation uses `scheduled_run` instead of `request`: its object is the public workflow input. The runner starts the registered root workflow on the isolated serve, collects native history and runs `after_run` hooks with `${fixture.native_run}`. A hook can drive the production subscriber and operations queue until the family records that exact run. Parity receives `null` in `PROOF_OPERATION_FILE`. Such a receipt proves the scheduled producer and its projection; it makes no Operation admission claim.

## Receipts

`run` writes `~/swamp-execution/evidence/proof/<kind>/<UTC>-minimal.json`. A receipt names the topology and version, the commit, the VM, the Operation and native run, per-step and phase timings, parity, `up` to receipt time and time since first provision. `proof_pass` is true only when the Gateway and native status match `expect.status`, parity passes and every budget holds.

## Limits

- No WireGuard, Router, ingress, Reverb, Horizon or Caddy. Reverb drives the subscriber and Horizon works the queue in production; here `gateway.php` does both, paced below serve's per-IP WebSocket burst limit.
- The Gateway runs from source with `composer install --no-dev --no-scripts`; the release runner is not exercised.

Use `bin/swamp-proof up --fresh` to restage changed workflow code and replace the nested Nodes in one pass on the held VM.

A fixture can name a shared JSON map with `"defaults": "node-role-add-defaults.json"`. Its own fields override that map, including complete arrays such as `phases`. Both the host and guest use the same loader.

### Stock Node enrollment

`node.add.fresh` launches a separate VM from `images:ubuntu/26.04/cloud` inside the owned proof VM. Its hook installs only `openssh-server` and authorizes the Gateway bootstrap public key for root. It records the real DHCP address, approved host fingerprint, package inventory and absent managed account before enrollment. The fixture runs the same enrollment parity checks as `node.add`. Run `node.role_add.fresh` next to add `app-dev` to that enrolled machine. Neither fixture changes the shared topology. `down` destroys the outer VM and its nested stock VM.
