## Findings

### DEFECT 1 — release manifest websocket ref no longer matches the published archive tag (release-breaking)

- Evidence: `.agents/skills/release/SKILL.md:418` now emits
  `--role-image="orbit-websocket=ghcr.io/hardimpactdev/orbit-reverb:${version}@${reverb_digest}"`,
  while `bin/orbit-release-candidate:597` still produces the published archive
  with `docker save "$candidate_reverb_image"`, whose `RepoTags` are
  `["ghcr.io/hardimpactdev/orbit-reverb:<version>-candidate-<build_id>"]`.
  `.agents/skills/release/SKILL.md:405` copies that exact tar into the release.
- Impact: `LocalWebSocketRuntimeAction::validateImageArchive`
  (`apps/cli/app/Services/WebSockets/LocalWebSocketRuntimeAction.php:225`)
  requires `$tags === [$sourceImage]`, where `$sourceImage` is the manifest ref
  before `@`. `["...:<version>-candidate-<id>"] !== ["...:<version>"]`, so every
  credential-free websocket node acquiring the release image from the published
  archive fails with `websocket_runtime_image_artifact_invalid`. The
  pre-change ref (`${candidate_reverb_image}@${reverb_digest}`) matched the
  archive exactly; the new workflow prefix check
  (`.github/workflows/orbit-release.yml:200-207`) now *enforces* the broken
  form, so the release cannot be published any other way. The pairing is
  contract-tested on the CLI side
  (`apps/cli/tests/Feature/InternalWebSocketRuntimeCommandTest.php:121`
  `image_archive_tags => [$sourceImage]`) but nothing in this diff binds the
  release-side archive tag to the manifest ref, which is why the focused suites
  stayed green.
- Note the candidate manifest (`bin/orbit-release-candidate:614`) still uses
  the candidate tag and therefore still matches the archive, so only the
  GitHub-release path is broken.
- Smallest correction: make the archive `RepoTags` and the
  `role_images.orbit-websocket` ref identical again. Either (a) revert
  `SKILL.md:418` to `${candidate_reverb_image}@${reverb_digest}` and relax the
  workflow reverb check accordingly, taking version identity solely from the
  GHCR `:<VERSION>` alias the workflow already creates — the same treatment
  FrankenPHP receives; or (b) in `cmd_build`, `docker tag` the reverb image to
  `ghcr.io/hardimpactdev/orbit-reverb:${version}` and `docker save` that single
  tag, then use that ref in both the candidate and the final manifest. Add a
  focused test asserting the saved archive's single `RepoTags` entry equals the
  manifest `orbit-websocket` ref before `@`.

### DEFECT 2 — reuse has no acceptance provenance (named invariant 1)

- Evidence: `bin/orbit-release-candidate:299-304` selects the reuse source
  purely from `.orbit/release-candidates/latest`; `previous_image_reusable`
  (lines 111-131) validates only fingerprint and digest shape. No acceptance
  record is consulted anywhere.
- Impact: this contradicts the Goal ("may reuse only a previously accepted
  exact digest"), the new documentation that ships in this same diff
  (`SKILL.md:52` "keep their previously accepted digest",
  `apps/docs/content/tech-stack.md` "keeps its previously accepted digest",
  `PRODUCT_DECISIONS.md` "reuse a previously accepted digest"), and the
  script's own rule at `bin/orbit-release-candidate:790` — "the latest pointer
  is not an acceptance identity". A candidate rejected during live acceptance
  because its Reverb/FrankenPHP bytes were bad (bad floating base image, bad
  Composer/apt fetch — none of which move the owned-input fingerprint) is
  silently re-aliased into the next candidate and, once published, into the
  public `<VERSION>` tag. The implementer reported this risk explicitly; per
  the brief, missing acceptance provenance is a DEFECT.
- Smallest correction: record acceptance in candidate state at the existing
  acceptance point (`promote-runtime --build-id=<id> --accepted`, which already
  writes `frankenphp-promotion.log`) — extend it to record Reverb as well, or
  write a single `accepted=<timestamp>` line — and make
  `previous_image_reusable` require that marker on the source candidate,
  falling back to a build when it is absent. Add a focused test proving an
  unaccepted latest candidate is not reused.

### DEFECT 3 — FrankenPHP manifest validation is fail-open on the tag (named invariants 2 and 6)

- Evidence: `.github/workflows/orbit-release.yml:216` accepts
  `ghcr.io/hardimpactdev/orbit-frankenphp:[^@[:space:]]+@sha256:<64hex>` — any
  tag. The reverb check on the adjacent lines is strictly pinned to
  `:{$version}`.
- Impact: a final `github-release` manifest carrying
  `orbit-frankenphp:2-php8.5-bookworm-candidate-<build_id>@sha256:...` passes
  the fail-closed publication gate. Candidate-tag aliasing in
  `WorkloadNodeUpdater::requiredRoleImageAliases`
  (`apps/gateway/app/Services/Operations/WorkloadNodeUpdater.php:467`) is gated
  on `manifest_source === 'topology-candidate'`, so a released manifest would
  hand app nodes a private candidate tag with no alias and no archive. Nothing
  in the diff enforces the documented value (the stable runtime-family tag,
  `SKILL.md` step 13 and `apps/docs/content/domains/14_php/README.md`), so the
  identity claim in invariant 2 rests on convention only. The regex also leaves
  `.` unescaped in the host segment.
- Smallest correction: pin the pattern to the stable runtime-family tag
  (`ghcr\.io/hardimpactdev/orbit-frankenphp:2-php8\.5-bookworm@sha256:...`,
  matching `PhpRuntimeCatalog::imageFor(PhpRuntimeCatalog::DEFAULT)`), and add
  a workflow test asserting a candidate-tagged FrankenPHP ref is rejected.

### DEFECT 4 — the fingerprint derivation, the entire basis of reuse safety, has no coverage (named invariant 3)

- Evidence: `fingerprint_owned_inputs`
  (`bin/orbit-release-candidate:100-122`) resolves inputs from `$source_root`
  (the script's own repo, line 6) rather than `$repo_root`, and forces
  `PATH="/usr/bin:/bin:/usr/local/bin"` for its `git` calls. That deliberately
  bypasses the test harness's `git` stub
  (`apps/gateway/tests/Feature/E2ESupport/ReleaseCandidateHelperTest.php:1044`),
  so every test computes the fingerprint from the real checkout. The
  "rebuilds Reverb when owned-input fingerprints change" test mutates the
  stored `reverb_fingerprint=` line in the *previous* `candidate.env`, which
  proves the comparison and nothing about the derivation.
- Impact: no automated proof that an owned-input change (for example
  `apps/reverb/composer.lock`) moves the fingerprint, nor that unrelated
  changes leave it stable. A silent regression here ships stale Reverb or
  FrankenPHP bytes under a new release version — the exact failure the reuse
  gate exists to prevent.
- Smallest correction: make the fingerprint root injectable (use `$repo_root`,
  or an explicit override the harness can set) and add a focused test over a
  small fixture git repo asserting both sensitivity to an owned-input change
  and stability across an unrelated change.
