# JSON Renderer: `orbit node:new [name]`

[Back to `node:new` technical contract.](1_node-new.md)

This page describes the JSON-rendered output for `node:new`.

**Renderer:** JSON renderer.

## Primitive

None. JSON renderer emits the standard envelope only.

## Selection

Use this renderer when `--json` is present.

`--json` also disables interactive prompts and forces the
[`non-interactive input mode`](5.2_node-new_input-mode_non-interactive.md), even
when the process has a TTY.

Use `--stream-json` instead of `--json` only when callers need newline-delimited
progress frames during gateway-mediated provisioning. That renderer follows the
shared [Stream JSON Frames](../../../README.md#stream-json-frames) contract.

## Envelope

This renderer uses the shared [JSON Envelope](../../../README.md#json-envelope).

Input mode failures, domain validation failures, authorization failures,
network failures, SSH failures, platform failures, and provisioning failures
must all use this envelope. Every successful `node:new` response includes
`success.meta`; empty metadata currently serializes as `[]`, and non-empty
metadata is an object.

If an initial role is created but its first convergence fails, the
command returns an error envelope rather than success. The persisted role
assignment remains in `error`, and failure metadata may include the role,
status, settings, and `last_error` for the failed assignment.

## Node Fields

Node fields and address fields must be explicit and role-specific. Do not
expose an ambiguous top-level `host` field in the JSON node object. Keep the
SSH/bootstrap endpoint under `provisioning.host`; keep canonical node addresses
under `node.addresses`.

Fields that are structural members of the node object, such as `node.tld`
and `node.platform`, are serialized from the durable node identity. `node.tld`
is mandatory for active nodes and is always supplied explicitly;
`node.platform` uses `unknown` when the command cannot detect the value yet. Purely optional metadata fields,
such as `node.addresses.public_ipv4` and `node.addresses.public_ipv6`, are
omitted when absent and never serialized as `null`.

| JSON field | Registry source | Meaning |
| --- | --- | --- |
| `provisioning.host` | `nodes.host` | SSH/bootstrap endpoint used during bootstrap. May be a DNS name, private IP, public IP, or `null` when no SSH provisioning happens. |
| `node.tld` | `nodes.tld` | Mandatory unique node TLD other than reserved `orbit`. The node DNS projection publishes `orbit.<node-tld>` to the node's WireGuard address; development role payloads may also use it for wildcard DNS. |
| `node.platform` | `nodes.platform` and platform probes | Structural platform-version identifier (see format below). Use `unknown` only when platform detection is not yet possible. |
| `node.addresses.wireguard` | `nodes.wg_ip` | Orbit network address assigned to the node identity. CLI callers use the gateway address for API access; the gateway uses non-gateway node addresses for Agent-push reachability. Present for every role. |
| `node.addresses.gateway_endpoint` | Gateway endpoint config | WireGuard endpoint written into generated peer configs for gateway nodes. For first-gateway bootstrap, this starts as the resolved `node_new.host`. Present only for gateway nodes. |
| `node.addresses.public_ipv4` | `nodes.public_ipv4_address` | Operator-supplied public IPv4 metadata recorded through `node:update`. Omitted when not stored; never serialized as `null`. |
| `node.addresses.public_ipv6` | `nodes.public_ipv6_address` | Operator-supplied public IPv6 metadata recorded through `node:update`. Omitted when not stored; never serialized as `null`. |

`node.platform` uses the format `<platform>_<version>` with version dots
normalized to hyphens, for example `ubuntu_24-04` or `macos_15-4`.

The bootstrap `--user` value is intentionally absent from successful JSON
payloads. After provisioning, Orbit stores the Orbit owner/runtime user in
gateway node configuration as `nodes.user` (normally `orbit`) and uses that
stored value when the Agent executes work on that node.

Public IPv4/IPv6 fields are operator-supplied metadata only. `node:new` does
not detect, infer, or store them. They are not required for any node role, are
not inferred from `provisioning.host`, are not drift-checked by node doctor, and
do not decide the gateway endpoint after bootstrap.

When public address metadata is stored through `node:update`, it is
included in `node.addresses`:

```json
{
  "addresses": {
    "wireguard": "10.6.0.7",
    "public_ipv4": "203.0.113.20"
  }
}
```

## Enum and identifier values

JSON enum values and structured identifiers are part of the renderer contract:

| Field | Values |
| --- | --- |
| `node.platform` | Platform-version identifier such as `ubuntu_24-04` or `macos_15-4`; `unknown` when not detectable yet. |
| `node.status` | `provisioning`, `active` |
| `result.action` | `created`, `enrolled`, `provisioned`, `adopted`, `converged` |
| `provisioning.transport` | `client-ssh`, `ssh` (first-gateway bootstrap only), `wireguard`, `none` |
| `provisioning.status` | `complete`, `already_provisioned`, `enrolled`, `adopted` |
| `development_tld.gateway_dns.status` | `configured`, `already_configured` |
| `local_onboarding.wireguard` | `installed`, `already_installed` |
| `local_onboarding.gateway_trust` | `trusted`, `already_trusted` |
| `local_onboarding.gateway_config` | `stored`, `already_stored` |
| `local_onboarding.gateway_api` | `verified` |
| `gateway_trust.status` | `trusted`, `already_trusted` |
| `gateway_trust.trusted` | `true` |
| `error.meta.missing_permission` | `node:new` when gateway grant authorization fails. |
| `error.meta.serving_node` | The gateway node name when gateway grant authorization fails. |
| `error.code` | `validation_failed`, `gateway_unavailable`, `gateway_unreachable_wireguard`, `authorization_failed`, `node.incompatible`, `node.bootstrap_required`, `node.bootstrap_ssh_failed`, `node.host_key_mismatch`, `node.unsupported_platform`, `node.provisioning_incomplete`, `node.gateway_api_error`, `node.not_found`, `node.tld_in_use` |

The `error.code` values listed here are exhaustive for `node:new`. Add a new
value to this renderer contract before implementing another JSON failure code.

## Result action and node status

`node.status` is durable registry lifecycle, not the outcome of this command
run. Command outcomes are returned as `result.action`. Bootstrap and enrollment
details are returned under `provisioning.status`.

| Human action | JSON `result.action` | JSON `provisioning.status` | JSON `node.status` after success |
| --- | --- | --- | --- |
| `created` | `created` | `complete` | `active` |
| `enrolled` | `enrolled` | `enrolled` | `active` |
| `provisioned` | `provisioned` | `complete` | `active` |
| `adopted` | `adopted` | `adopted` | `active` |
| `converged` | `converged` | `already_provisioned` | `active` |

When gateway configuration has been written but node bootstrap/readiness has not
completed yet, persisted node lifecycle is `provisioning`. Once `node:new`
returns success, the returned node lifecycle is `active`.

## Next Steps

`success.data.next_steps` is a human onboarding checklist for successful
`node:new` paths. It may be an empty array. Items are prose instructions and may
include commands inside the text, but they are not machine-runnable recovery
handoffs.

Use `next_command` only in warning or error metadata when Orbit can name one
specific recovery command.

## Workload-Node Success

```json
{
  "success": {
    "data": {
      "result": {
        "action": "provisioned"
      },
      "node": {
        "name": "app-1",
        "tld": "test",
        "platform": "ubuntu_24-04",
        "addresses": {
          "wireguard": "10.6.0.7"
        },
        "status": "active"
      },
      "provisioning": {
        "transport": "client-ssh",
        "host": "app-1.ssh.example.com",
        "status": "complete"
      },
      "development_tld": {
        "tld": "test",
        "gateway_dns": {
          "domain": "*.test",
          "target": "10.6.0.7",
          "status": "configured"
        }
      },
      "next_steps": []
    },
    "meta": []
  }
}
```

Production app-role JSON includes the node-level `node.tld` and omits
`development_tld`. `development_tld` is a path-specific payload for
development app-role provisioning, not a structural member of every successful
`node:new` response.

## Gateway Already Provisioned

Gateway convergence returns success when the gateway is already provisioned,
active, and compatible.

```json
{
  "success": {
    "data": {
      "result": {
        "action": "converged"
      },
      "node": {
        "name": "gateway-1",
        "tld": "gateway",
        "platform": "ubuntu_24-04",
        "addresses": {
          "wireguard": "10.6.0.2",
          "gateway_endpoint": "203.0.113.2"
        },
        "status": "active"
      },
      "provisioning": {
        "transport": "none",
        "host": "203.0.113.2",
        "status": "already_provisioned"
      },
      "next_steps": []
    },
    "meta": []
  }
}
```

## First-Gateway Bootstrap Success

First-gateway bootstrap from an unconfigured client returns the gateway
node, local onboarding status, gateway trust metadata when installed, and no
manual `gateway:add` next step. It does not emit a separate
`local_operator_node` object.

```json
{
  "success": {
    "data": {
      "result": {
        "action": "created"
      },
      "node": {
        "name": "gateway-1",
        "tld": "gateway",
        "platform": "ubuntu_24-04",
        "addresses": {
          "wireguard": "10.6.0.2",
          "gateway_endpoint": "203.0.113.2"
        },
        "status": "active"
      },
      "provisioning": {
        "transport": "ssh",
        "host": "203.0.113.2",
        "status": "complete"
      },
      "local_onboarding": {
        "wireguard": "installed",
        "gateway_trust": "trusted",
        "gateway_config": "stored",
        "gateway_api": "verified"
      },
      "gateway_trust": {
        "gateway_url": "https://203.0.113.2",
        "trusted": true,
        "status": "trusted",
        "ca_sha256": "f3ab...",
        "ca_pem_path": "/var/app/storage/app/orbit/gateway-ca/orbit.crt"
      },
      "next_steps": []
    },
    "meta": []
  }
}
```

## Validation Error

WebSocket input is accepted by the stable command surface but is not
implemented. It fails before side effects. The explicit-role form is:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Node role 'websocket' is not implemented yet.",
    "meta": {
      "field": "roles",
      "reason": "not_implemented",
      "role": "websocket"
    }
  }
}
```

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Node roles must be one or more of app-dev, app-prod, database, agent, ingress, metrics, websocket, s3, or analytics.",
    "meta": {
      "field": "roles"
    }
  }
}
```

An invalid client name resolved during first-gateway bootstrap returns a validation failure
owned by the input mode and rendered with `field=operator_name`:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Client name must be a valid node name.",
    "meta": {
      "field": "operator_name"
    }
  }
}
```

Private `app-prod` placement without an active ingress node
returns:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Private app-prod nodes require an active ingress node.",
    "meta": {
      "field": "ingress_node",
      "required_role": "ingress"
    }
  }
}
```

## Authorization Error

Caller authorization failures identify the missing gateway grant:

```json
{
  "error": {
    "code": "authorization_failed",
    "message": "This node is not authorized for 'node:new' on 'gateway-1'.",
    "meta": {
      "reason": "missing_permission",
      "missing_permission": "node:new",
      "serving_node": "gateway-1"
    }
  }
}
```

## Client Bootstrap SSH Error

Client-local preflight failures use `step=client_ssh_preflight`. Failures after
the gateway returns the bootstrap bundle use `step=client_ssh_bootstrap` and
include the SSH exit status when one exists:

```json
{
  "error": {
    "code": "node.bootstrap_ssh_failed",
    "message": "Client-local SSH bootstrap failed for root@app-1.ssh.example.com.",
    "meta": {
      "host": "app-1.ssh.example.com",
      "user": "root",
      "step": "client_ssh_bootstrap",
      "exit_code": 255,
      "error": "Permission denied (publickey)."
    }
  }
}
```
