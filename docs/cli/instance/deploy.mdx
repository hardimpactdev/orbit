Use `--commit=SHA` to pin a full 40 or 64 character lowercase commit SHA. The selected commit must be on the deployment branch's first-parent chain. This is still a manual deploy and pauses automatic deployment. See [pinned commits](/reference/deployments#pinned-commits-and-automatic-callers).

Deploy a production Instance or an app-dev `default` Instance. For production, the Gateway creates a fresh release, fetches the configured branch, synchronizes stored environment values, runs the `before_activation` steps, atomically replaces `current`, refreshes the PHP runtime cache, and runs the `after_activation` steps. For a development default, it fetches the Project's default branch, checks out its newest commit in the default's checkout, and runs the Project's development deploy steps there. It refuses a checkout with uncommitted changes to tracked files. A failed required step leaves the new commit checked out, and the next scheduled tick retries. A best-effort failure reports a warning and the deployment continues. See [Instance releases](/reference/deployments#development-defaults).

```bash
orbit instance:deploy <instance> [--commit=SHA] [--idempotency-key=KEY] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `instance` | yes | Numeric Instance ID. |

| Option | Meaning |
| --- | --- |
| `--commit=SHA` | Deploy exactly this full commit SHA as a manual action. |
| `--idempotency-key=KEY` | Retry the same operation start with a permanent key. See [Start keys](/reference/operations#retry-a-start-with-a-key) for its form and conflict rules. |

The command starts an `instance.deploy` [operation](/reference/operations) and follows it until it ends. It subscribes to the operation's channel over Reverb and reads the operation again at each event. Without an active `websocket` role, or when the socket fails, it reads the operation every `poll_after_seconds` instead.

Production deploys include a `Restart Processes` step after PHP refresh and before after-activation commands. See [Deploy](/reference/deployments#deploy) for eligible Processes, the opt-out, and restart failures.

Human output shows a progress tree of the operation's steps, which the Gateway plans when a worker starts the operation. Glyphs and color show pending, running, succeeded, failed, and cancelled steps. New output of the running step prints above the tree, labeled and escaped. The output is the step's tail, so a fast step can show only its last 8 KiB; [`instance:deployment:show`](/cli/instance/deployment-show) prints the full log afterwards.

On failure the tree marks the failed step and shows its error code under it. The final lines add the failed step, the error code, the selected release when available, the operation ID, and the request ID. `--json` prints nothing while it follows, then the final operation document with every step.

Pressing Ctrl-C stops following, not the deploy. The CLI prints the command that shows the operation, such as `orbit operation:show 42`, and exits nonzero. It sends no cancel request; [`operation:cancel`](/cli/operation/cancel) stops a deploy.

| Outcome | Exit status |
| --- | --- |
| The operation succeeded. | `0` |
| The operation failed or was cancelled. | Nonzero. The command names the failed step and the selected release when the result includes one. |
| The Gateway refused the request, such as `operation.target_busy` for an Instance that another operation holds. | Nonzero, with the one-line error envelope. |
| You pressed Ctrl-C. | `130`. The operation keeps running. |

```bash
orbit instance:deploy 15
orbit instance:deploy 15 --json > deploy.json
```

A failure during release fetch, environment synchronization, or a `before_activation` step leaves the prior `current` selected. A failure during PHP cache refresh, Process restart, or an `after_activation` step leaves the fresh release selected. Deployment, rollback, deploy-step changes, environment changes, and removal share one operation owner per Instance, so a competing request waits or returns a busy refusal. A second deploy while the first one is queued or running returns `operation.target_busy`. A rollback cancels a deploy that no worker has started; see [`instance:rollback`](/cli/instance/rollback).

<Note>
Only `default` can be deployed on an app-dev Node. Other development Instances still return `deployment_config.unavailable`. Releases, rollback, and per-Instance deploy-step operations remain production-only; `instance:release:list` shows none for a development default.
</Note>
