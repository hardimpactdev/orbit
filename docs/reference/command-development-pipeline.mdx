# Command development pipeline

The command development pipeline is the stages every command goes through during development, from prep to a per-host refresh after release. A command goes through them one at a time. Stages 1 to 4 happen in one PR per command change: the spec, the code and the runnable proof cases land together. Each stage below shows its status on `main`, its flow chart, and links to its pages, skill and key files. The stage charts are drafts of the target design; they live in `docs/reference/pipeline/`. The [feature flow](/reference/feature-flow) holds the proof CI job and the case selection list.

## When each flow runs

Each flow has its own trigger. The first three run for a task. The others keep a host ready.

- **Claim.** `tasks:provision` runs for every task group. It claims a free slot, a stopped task VM that Orbit enrolled from the host's promoted image with its fixed identity, and starts it. The containers start from their `base` snapshot.
- **`base` restore.** It runs for each proof batch, and when the author wants a clean fleet.
- **Release.** The end of a group stops its slot and rolls it back to `clean`.
- **Refresh (stage 6).** It runs after a release whose commit changed playbooks, pins or lock files, and daily. A code-only release needs none. It bakes the next image from the current one; idle slots then re-enrol from it.
- **Image build from the recipe.** It runs only for a new host or a new base OS.

## 1. Prep

**Partly built.** A command has one PR, and prep starts it. The chart, docs page and verification cases (the spec) are the first commit of a draft PR. A merged docs PR does not make a command ready. The spec is approved in the draft, and the PR stays one PR through code, proof and merge. Prep changes no code. Swamp owns the flow and its state and the Gateway only authorizes it: an author agent drafts the spec in a task VM, a separate review agent checks it, and Swamp opens the draft PR as the Orbit App. One of two modes, set per flow, decides what happens next. In manual mode there is an optional spec checkpoint: Nick reviews the chart, docs and cases in the draft before code is written, and may check out a development Instance on the PR branch and review there with an agent. In automatic mode there is no checkpoint. The code and the runnable proof cases then follow in the same PR ([stage 4](#4-pr-and-ci)). Built: [`tasks:prep`](/cli/tasks/prep) admits one run for a task group and Swamp runs it as one workflow. Its children provision the task VM, run the author turn, up to three review rounds, and open the draft PR as the Orbit App. Built: [`tasks:prep-fix`](/cli/tasks/prep-fix) resumes the parked group, applies the review of the owner as a new commit, checks it, pushes it to the same draft PR and parks the group again. Not built: the automatic mode, and the detection of the owner's review by the gate check.

About 74 commands have a chart and a page from earlier docs-only PRs. Their old case tables are deleted. When a command's turn comes, its PR reviews and updates the chart and page, and writes the cases file from them.

## 2. Development environment

**Being rebuilt to the target (Nick, 2026-11-07).** A task VM is a fixed slot, `<node>-tvm-<n>`: a permanent Node whose identity is written once, at enrol. `tasks:provision` claims a free slot and only starts it. The host's image holds everything installed and ready: orbit-agent, the Pi server, the tools, Swamp, a warm checkout of main with its dependencies, and a nested topology of three Incus system containers (a Gateway with Swamp, an `app-dev` Node and an `app-prod` Node), migrated and running, with a `base` snapshot each. A claim starts the slot, fetches the task branch, starts the containers from `base` and checks that they are ready, in under 30 seconds. The end of the group stops the slot and rolls it back to its `clean` snapshot. An agent, or Nick, develops a command here, and the proof cases run here too.

The Gateway and app-dev see the outer VM's checkout as an Incus disk device, so the author's changes reach them at once. A restore of `base` is a reboot of the containers.

## 3. Proof

**Partly built, with one case so far.** The cases of a command run on that topology. The target: Orbit's own Swamp runs the proof directly and reaches into the task VM over SSH, like every other step. A run restores `base`, syncs the author's code and takes `base` again when something changed. Each batch then restores `base` once, and its cases run one after another without undo, each on its own resources. A case that does not pass triggers a restore. Each case calls the real CLI, checks the real effect and prints a verdict. The first case is the `firewall:allow` traffic case. Built: [`orbit proof COMMAND`](/cli/proof/proof) runs the cases of one command on the author's own task VM, restores `base` first and leaves a clean fleet on the latest code after the last batch. Not built: the converge of the nested Nodes.

## 4. PR and CI

**Partly built.** This stage continues the same PR that stage 1 opened as a draft. The author pushes the command code and the runnable proof cases to its branch, so a reviewer can check that the chart, docs, cases, code and proof cases match. There is one CI: the fast checks (about 2 minutes) plus, for command code, the proof CI (`proof:run` for the affected commands). It runs on every push. The proof CI starts only when a changed path selects a command in `swamp/proof/selection.txt`. Docs, charts and case descriptions never start it. A new push cancels the proof run of the previous push on that PR. When everything is green, the PR leaves draft. In manual mode, Swamp also requests Nick's review, so GitHub notifies him. Then comes the gate: in manual mode, Nick's approving review on the exact head; in automatic mode, a final self-review by a fresh review agent, with at most 3 rounds before the PR switches to manual mode. After the gate, Swamp merges the PR straight into `main` with a squash merge, using a Gateway-minted App token. There is no merge queue and no GitHub auto-merge. CI then runs on `main`. A red `main` is fixed forward and never released. The proof runs only on the PR head, never again before or after the merge. Two PRs for the same command normally conflict, because each edits the command's chart, page and cases file. The second PR rebases, which reruns CI and the proof. Built for manual mode: the ready step ([`tasks:pr-ready`](/cli/tasks/pr-ready)), the merge step with the manual gate ([`tasks:pr-merge`](/cli/tasks/pr-merge)), and the gate check that calls them. The gate check is the Gateway command `tasks:pr-gate`. Every minute, like the release check of stage 5, it reads with read-only App tokens the open external Task groups of review-and-merge Projects that have a published PR. A draft PR with a green CI result on its head and a passed handoff check on that commit gets the ready step; a spec-only draft stays a draft. A PR out of draft whose head Nick approved gets the merge step. In automatic mode, a PR out of draft gets a review round, and the merge step once the round on the exact head passed. Each admission is keyed by group and head, so a repeat tick is a no-op, and each starts its own Swamp run. In automatic mode, the Gateway also posts the verdict of each round as a PR comment of the App. In automatic mode, findings start the fix: the author turn, the handoff check and a push, then the next round on the new head. Not built: the proof CI job. A PR that is not in a Task group is outside this flow: the author opens it as `nckrtl` and squash-merges it with `gh pr merge <n> -R hardimpactdev/orbit --squash` when CI is green on the head (the interim).

## 5. Automatic Swamp release

**Built.** The Gateway looks for the newest green commit on `main` and starts one Swamp run: build, snapshot and migrate, switch, load the new workflows and check health. A green commit has `Required checks` and `Gateway release inputs` green in its CI run on `main`. There is no merge queue, so a red `main` commit is never released; `main` is fixed forward. A failed check switches back.

## 6. Per-host task image and seed refresh

**Being rebuilt to the target (Nick, 2026-11-07).** There is no image build per release. Each task VM host (Linux only: beast and shark) bakes its next image from its current one, and the hosts work in parallel. Nothing is copied between hosts. The trigger is a release that changed playbooks, pins or lock files, plus a daily run. Per host, Swamp starts one VM from the current image, and one Ansible run converges everything: the outer VM, the warm checkout, and each container, which then gets a new `base` snapshot. The VM is published as the candidate image, with its container disk as the candidate's seed. One idle slot re-enrols from the candidate and passes the claim's ready check; then the candidate is promoted, and the other idle slots re-enrol one at a time. The target is about 3 minutes. A recipe build runs only for a new host or a new base OS.

## Change the development pipeline

Change a stage in the place that owns it, and update this page in the same PR.

- **This page:** the stages, their order, their status and their links. Edit `docs/reference/command-development-pipeline.mdx`. A stage that gets built changes its status here.
- **The charts:** edit the `.mmd` file next to the command page, chart first. The stage charts are `docs/reference/pipeline/<n>-<stage>.mmd`, placed on this page with a `flow-at` placement, as the CLI pages rules describe. Run `bin/check-flows`. The rules are in [CLI pages and flow charts](https://github.com/hardimpactdev/orbit/blob/main/docs/cli/README.md).
- **The skills:** `preparing-commands` for stage 1, `verifying-commands` for stages 2 and 3, and `developing-commands` for stage 4 and the code. They link here and to the charts and keep only what an agent must do at its own step.
- **The proof CI job and the selection list:** [Feature flow](/reference/feature-flow).
