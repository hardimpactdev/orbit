Show the detail Orbit has recorded for one Node, including its assigned roles and access grants.

## Usage

```bash
orbit node:show <node> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Positive numeric Node ID. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--json` | off | Follow the [CLI standard's machine-output contract](/reference/cli-ux#input-and-output-modes). |

```bash
orbit node:show 7
orbit node:show 7 --json
```

Input selection and output presentation follow the [CLI standard](/reference/cli-ux).

## How it works

<div className="flow-at" data-chart="node/show"></div>

Orbit answers only from recorded Gateway state: Node records and agent facts. It contacts no Node, Grafana or other external system at request time, so the read stays fast even when the Node is unreachable. A repeat reads the current recorded detail again; it changes no records, creates no Operation and is not a skipped action.

Access follows the node family's [shared authority rule](/cli/node#authority).

| Field | Meaning |
| --- | --- |
| `ID`, `Status` | The Node's ID and recorded lifecycle status. |
| `Agent` | The recorded agent liveness, described below. |
| `Roles` | Every assigned role, with its state and any recorded failure. |
| `SSH` | The managed user, public address and port. |
| `Cluster` | The name of the Cluster the Node belongs to. |
| `WireGuard`, `LAN` | The Node's addresses. |
| `WireGuard public key`, `DNS server override` | The Node's network settings. |
| `TLD` | The Node's development TLD. |
| `Platform` | The platform and architecture. |
| `Apps folder` | The [apps folder](/reference/node-settings#set-the-apps-root) where Instances live. |
| `Access to`, `Accessible by` | The Nodes this Node has an access grant to, and the Nodes that have one to it, each as name and ID. |
| `Failure` | The Node's failed step and error code, only when either is recorded. |

Roles use the same shared projection as [`node:list`](/cli/node/list) and [`node:role:list`](/cli/node/role-list): identical `role`, `status`, `failed_step` and `error_code` values for each assignment. All assignment states appear: `active`, `provisioning`, `failed` and `removing`; human output may compact them. JSON also includes the Node's stored `settings`.

### Agent state

The `agent` field contains `state` and `since`:

| `state` | Meaning |
| --- | --- |
| `online` | An agent event arrived in the last 15 seconds. |
| `offline` | No event arrived within that window; `since` is the time of the last one. |
| `not_seen` | Orbit has never received an event from this agent. |
| `unknown` | The Gateway's recorded [agent view](/reference/node-agent#gateway-view) is unavailable, so liveness cannot be determined. |

Human output shows an offline agent as `offline since <time>`. A Node that runs no observing agent, such as an unmanaged Node, has `agent: null`. Missing or stale data does not refuse the read or trigger a live lookup; the available detail is returned.

## Errors

| Code | Meaning |
| --- | --- |
| `node.id_invalid` | The supplied Node ID is not a positive integer. The CLI sends no detail request. |
| `http.404` | No Node has this ID. |
| `node_access.required` | The caller is not authorized for this Node under the shared authority rule above. |
