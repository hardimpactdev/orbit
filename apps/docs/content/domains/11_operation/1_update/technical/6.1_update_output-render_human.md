# Human Renderer: `orbit update`

[Back to `update` technical contract.](1_update.md)

This page describes the human-rendered terminal output for `update`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

`update` always begins by checking for a newer release, so the tree renders
immediately with a single idle `Checking for updates` step before any side
effect. The remaining steps are only revealed once a newer version is confirmed
and the gateway is already on that version; until then the tree stays
single-step. This keeps the common already-current case to one fast, honest
step instead of animating a download that does not happen.

### Checking for updates

```text
┌  Updating Orbit
│
○  Checking for updates
│
└  Working...
```

The `Checking for updates` row animates (cyan `○`/`◉`) while the check runs with
the message `Checking`, then settles. The settle status and footer depend on the
outcome:

| Outcome | Step status | Footer |
| --- | --- | --- |
| Already on the latest release | `Skipped: <version> is already installed` | `Skipped: <version> is already installed` |
| Newer release exists but the gateway is still behind | `Done: new version available, <latest_version>` | `Skipped: please update your gateway first` |
| Newer release exists and the gateway is already on it | `Done: new version available, <latest_version>` | proceeds to the update steps below |

The gateway-first gate is a hard rule: the local CLI is never updated past the
version its gateway runs (see [`1_update.md`](1_update.md#gateway-first-version-gate)).
When the gateway is behind, `update` stops after the check step — it does not
download or replace anything — and the footer directs the operator to update the
gateway first (via `orbit update:all`).

### Applying an update

When a newer version is confirmed and the gateway is already on it, the tree
reveals the remaining steps and runs them in order:

```text
┌  Updating Orbit
│
●  Checking for updates  Done: new version available, 0.1.131
│
◉  Downloading binary    Downloading 0.1.131
│
○  Replacing binary
│
○  Running doctor
│
└  Working...
```

Step status vocabulary:

| Step | Active | Settled |
| --- | --- | --- |
| `Downloading binary` | `Downloading <latest_version>` | `Downloaded <latest_version>` (or `Skipped` when the versioned binary is already staged locally) |
| `Replacing binary` | `Replacing <old_version> with <latest_version>` | `Done` (or `Skipped` when no relink was needed) |
| `Running doctor` | `Running` | `Done` when healthy, or `<n> issue(s) found` when `orbit doctor` reports drift |

`Running doctor` runs `orbit doctor` in verify mode for the local node after the
binary is relinked. A non-zero issue count is reported in the step status but
does **not** fail the update — the binary swap already succeeded; the count is
operator guidance to run `orbit doctor --fix`.

## Success Output

On a completed update the footer becomes a full-strength success line naming the
version transition:

```text
Success: Updated from 0.1.129 to 0.1.131
```

The footer is rendered by the progress tree itself. It must not suggest that
fleet drift or runtime readiness has been verified beyond the local
`Running doctor` step.

## Skip Output

Skips are successful (exit 0) outcomes that performed no binary swap. The footer
states the reason:

```text
Skipped: 0.1.131 is already installed
```

```text
Skipped: please update your gateway first
```

The gateway-first skip renders the resolved `Checking for updates` step
(`Done: new version available, <latest_version>`) so the operator can see which
version is waiting, then the skip footer.

## Failure Output

Human-rendered failures must show:

- the failed step settled to a red `●` in the tree;
- a clear prose error in the footer (`Failed to update local Orbit checkout.`);
- the captured command output beneath the tree when available;
- no JSON envelope.

When the local checkout directory cannot be updated, or the release check cannot
reach the release source, the responsible step settles red and the footer
reports the failure. The version check failing is a failure, not a skip.

```text
┌  Updating Orbit
│
●  Checking for updates  Could not reach the release source
│
└  Failed to update local Orbit checkout.
<captured output>
```

When the local checkout directory is unavailable the renderer keeps the idle
`Checking for updates` row and prints the reason beneath the failed footer:

```text
Local Orbit checkout cannot be updated.
```
