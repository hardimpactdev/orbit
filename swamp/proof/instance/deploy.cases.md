# instance:deploy verification cases

The proof runs the built CLI against a fresh nested topology with a Gateway, an `app-prod` Node with a production Instance of a Laravel Project whose repository the proof controls, an `app-dev` Node with a `default` and another development Instance, and a Vite+ Project. It checks the Gateway records, the release folders, `current`, the PHP runtime, the Processes, the `.env`, the deploy steps' effects and real HTTPS responses. See [verifying-commands](../../../.agents/skills/verifying-commands/SKILL.md).

| Case | Setup and action | Required observations |
| --- | --- | --- |
| Production deploy | Deploy a production Instance with `before_activation` and `after_activation` steps. | The task succeeds. A new release holds the branch head, `current` selects it, and the steps ran in order, the before steps first. The `.env` holds the stored values with mode 0640 in group `orbit-env`. The PHP runtime serves the new code, opted-in Processes were restarted, and the deployment row is `succeeded` with the release and commit. |
| First deploy | Deploy an Instance with no earlier release. | The dedicated PHP-FPM service is created and verified, and the Instance serves. |
| Retention | Deploy four times. | Three releases remain, a release a running process uses stays, and a cleanup failure is a warning. |
| Pinned commit | Deploy with `--commit` set to a commit on the branch, then to one not on its first-parent chain. | The first deploys exactly that commit. The second fails with `deployment.commit_not_on_branch` and `current` is unchanged. |
| Commit format | `--commit=` empty, a short SHA, and an upper-case SHA. | `deployment.commit_required` before any request, then `validation.failed` for the others. No task. |
| Automatic pause | Deploy manually a production Instance with automatic deployment on. | The running row pauses automatic deployment at once, and it stays paused after the deploy ends. |
| Development default | Deploy the `default` Instance on an `app-dev` Node. | The default branch's newest commit is checked out, the development deploy steps ran there, and the deployment row shows the default branch. |
| Dirty checkout | A `default` checkout with an uncommitted change to a tracked file, and one with untracked files only. | `deployment.checkout_dirty` for the first, with the checkout unchanged. The second deploys. |
| Diverged branch | A local default branch with a commit the fetched commit lacks. | `deployment.branch_diverged`, nothing changed. |
| Unavailable | Another development Instance, and an Instance that is not active. | `deployment_config.unavailable`. No task. |
| Projection pending | Deploy a `default` whose Route projection has not finished. | `deployment.projection_pending`. No task. |
| Failure before activation | Make the fetch, the environment sync, or a `before_activation` step fail. | The task fails with the failed step and its code (`deployment.source_failed`, `env.sync_unconfirmed` or `deployment.step_failed`). The prior `current` is selected, the new release folder stays, and the deployment row is `failed`. Later required steps did not run. |
| Failure after activation | Make the Caddy access, the swap, the PHP refresh, a Process install, a Schedule install, a Process restart or an `after_activation` step fail. | A failure before the swap leaves the prior `current` selected, with `deployment.selection_invalid` for the swap itself. A failure after it leaves the fresh release selected, with `deployment.php_runtime_unconfirmed`, `process.install_failed`, `schedule.install_failed`, `process.restart_failed` or `deployment.step_failed`. The task names the failed step. |
| Best effort | Make a best-effort development deploy step fail. | The task succeeds with a warning and the deployment continues. |
| Development steps | Make the credential removal, the local branch read, the untracked-entry list or the stale-directory cleanup fail on a `default`, and let the steps change the branch. | The task fails with `deployment.source_failed` and the failed step, or `deployment.branch_changed`. Fails today: the first four fall through to `operation.native_failed`. |
| Source access | A Project whose source access cannot be used for a development deploy. | `deployment.source_access_unsupported`. No task. |
| Release layout | A deploy with shared paths, a served web root, Schedules, a Process that is stopped, one with `restart_on_deploy` off, a non-PHP Instance and existing local PHP tuning. | The empty persistent directories are seeded and the admitted paths linked, Caddy gains access to each web root, the Schedule timers are installed, stopped Processes stay stopped, the Process with the opt-out is left running, the non-PHP Instance has no PHP runtime, and the local PHP tuning is left intact. |
| Fetch credential | Make the fetch fail. | The fetch credential is removed anyway. |
| Queue | Make the Gateway unable to queue the task. | `operation.queue_unavailable`. Nothing starts. |
| Foreign keys | A `.env` that holds keys Orbit does not manage. | `env.sync_would_drop_keys`. Nothing is overwritten. |
| Vite+ | A Project whose steps need Vite+, with a missing store and with invalid requirements. | The shared steps run once and the build succeeds, or the task fails with `deployment.vp_store_failed` or `deployment.vp_requirements_invalid` and `current` is unchanged. |
| Missing configuration | A production Instance with no stored environment configuration. | `env.configuration_missing`. Nothing is recorded. |
| Busy | Start a second production deploy while one runs, and a deploy while a rollback or an environment change runs. Then start a second deploy of a development `default` while one runs. | `operation.target_busy` for the production cases; the first run is unaffected. Fails today: a development `default` takes no hold, so the second deploy runs too. |
| Lifecycle busy | Deploy a `default` while a setup step holds its checkout. | The task fails with `instance.lifecycle_busy`. |
| Repository identity | A Project whose repository identity does not match its origin, with `--commit`. | `deployment.repository_mismatch`. No task. |
| Deadline and cancel | Make a step outlast its timeout and the whole budget (step timeouts plus 900 seconds), and cancel with `operation:cancel`. | The first stops that step and every later one; the second fails with `operation.timed_out`; the third ends with `deployment.cancelled`. Each leaves the selection as the failure rows say. |
| Interrupt | Stop the run's executor mid-run. | The task ends like a failed step and a new deploy succeeds. |
| Ctrl-C | Press Ctrl-C while following, in human output and with `--json`. | The human CLI prints the `operation:show` command and exits 130; `--json` prints no line and exits 130. The deploy keeps running and finishes. |
| Progress and output | Follow a deploy in a terminal, a narrow terminal and a pipe. | A tree of the task's steps with glyphs and color. No step output appears, and on failure the failed step shows its error code and the final lines add the release, the task ID and the request ID. The piped output has no animation or escape codes. Fails today: one `native` row replaces the tree, and the summary prints only the failed step and the error code. |
| JSON | Run with `--json`. | Nothing prints while it follows; then stdout holds only the final task document with every step. |
| Exit status | A success, a failure, a cancelled task and a refusal. | `0`, nonzero naming the failed step, nonzero, and nonzero with the one-line error. |
| Missing input | In a terminal, run the command with no argument and cancel the list. Then run it noninteractively and with `--json`. | The terminal lists Instances by name. Cancel ends with `input.cancelled` and no request. The noninteractive calls are refused with `instance.id_invalid`, with no request. Fails today: the Instance is a required argument, so every call without it is refused by the parser. |
| IDs only | An Instance by name, the ID `0`, the ID `-1` passed after `--`, and `abc`. | `instance.id_invalid`, with no request. Fails today: `-1` without `--` is read as an option and gives a parser error. |
| Idempotency option | Run with `--idempotency-key`. | The option is refused as unknown. Fails today: the CLI offers it. |
| Lost response | Lose the response to the start, and repeat the command while the first task runs. | Exactly one task exists: the repeat is refused with `operation.target_busy`. A repeat after the first finished starts a second deploy with a new release. Fails today: a development `default` starts a second task. |
| Unknown and access | An ID that does not exist, and a caller without a grant to the Instance's Node. | `http.404` and `node_access.required`. Nothing starts. |
