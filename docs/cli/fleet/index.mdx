After each verified Gateway release, Swamp brings the managed workload Nodes to the same release, one Node at a time. The `fleet` family has no CLI commands. Each rollout pass is one `fleet.rollout` Operation: follow it with [`operation:list --kind=fleet.rollout`](/cli/operation/list) and [`operation:show`](/cli/operation/show). [Fleet rollout](/reference/gateway-recovery#fleet-rollout) explains the rollout set, the order, the steps on each Node, and a failed Node.

## How it works

The rollout publishes the CLI and the Node agent on each Node in turn. Each Node runs the `fleet-release-node` child, which runs the shared `node-cli-install` child from Node 209. A rollout then publishes the pinned Node agent from Node 209 with official resources.

<div className="flow-at" data-chart="fleet/rollout"></div>

`POST /api/v1/fleet/cli/converge` publishes only the CLI, through the same children. It names why it leaves a Node out as that Node's skip reason.

<div className="flow-at" data-chart="fleet/cli-converge"></div>

The fleet reboot reboots the managed Linux Nodes that need a reboot for their security fixes, one at a time, each night, after it drained their work. Each pass is one `fleet.reboot` Operation. [Fleet reboot](/reference/gateway-recovery#fleet-reboot) explains the order, the drain, the checks and the alerts.

After a CI host reboots, Orbit asks GitHub to rerun jobs lost during the drain. It does not repeat that request if execution is lost while the request is in flight.
