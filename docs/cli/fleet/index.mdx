After each verified Gateway release, Swamp brings the managed workload Nodes to the same release, one Node at a time. The `fleet` family has no CLI commands. Each rollout pass is one `fleet.rollout` Operation: follow it with [`operation:list --kind=fleet.rollout`](/cli/operation/list) and [`operation:show`](/cli/operation/show). [Fleet rollout](/reference/gateway-recovery#fleet-rollout) explains the rollout set, the order, the steps on each Node, and a failed Node.

## How it works

The rollout publishes the Node agent on each Node in turn. Each Node runs the `fleet-release-node` child. Only [CLI-eligible Nodes](/reference/node-provisioning#orbit-cli) first run the shared `node-cli-install` child. Other Nodes publish the pinned Node agent without a CLI release or install gate.

The Gateway supplies each run's full Node intent and records its terminal result through the shared run reader. Steps do not fetch intent or report progress to the Gateway. The rollout commit stays on the Gateway for visit history and alerts; the run accepts only the Node list.

`POST /api/v1/fleet/cli/converge` publishes only the CLI, through the same children. It names why it leaves a Node out as that Node's skip reason.

<div className="flow-at" data-chart="fleet/cli-converge"></div>

The fleet reboot reboots the managed Linux Nodes that need a reboot for their security fixes, one at a time, each night, after it drained their work. Each pass is one `fleet.reboot` Operation. [Fleet reboot](/reference/gateway-recovery#fleet-reboot) explains the order, the drain, the checks, safe read retries, interrupted runs and the alerts. A Node that stays unreachable halts the pass, including when it has a reboot hold. The nightly pass is [off in the live fleet](/reference/old-paths#off-in-the-live-fleet); an operator pass still runs.

After a CI host reboots, Orbit asks GitHub to rerun jobs lost during the drain. It does not repeat that request if execution is lost while the request is in flight.

`POST /api/v1/fleet/conn-server/rollout` rolls the pinned Conn Server out to the Nodes that run one, canary first. Each run is one `fleet.conn_server_rollout` Operation. [Conn Server rollout](/reference/development-containers#conn-server-rollout) explains the Node records, the checks, the hold, the swap and the rollback.
