Detailed phases

Proof venues, environments, and sequence

Proof venue Where proof runs (derived from changed files)
  • automated — docs, tests, bin/, repo-only tooling
  • retained-incus — core/SDK/CLI/server runtime
  • browser — gateway or docs web UI
  • host-macos — native macOS Agent
Proof environment What kind of target is exercised (orthogonal axis)
  • dev-fixture — ordinary retained topology / local surfaces
  • live — real managed environment when Goal claims live reachability/convergence

Live is an environment, not a fifth venue.

PROVE sequence

  1. Focused checks, then diff-routed broader gate
  2. Commit exact candidate; clean worktree
  3. Pre-live proof on the derived venue (Incus + terminal when routed; browser/host-macos on those surfaces; automated skips runtime)
  4. General reviewer PASS on that exact HEAD
  5. If Goal requires live reachability/convergence: live-environment proof with the same reviewed candidate
  6. Record candidate-bound evidence → ACCEPT

Same-candidate retry keeps Review and the reviewed tip. Any code change returns to BUILD, invalidates review, and requires all affected proof plus re-review.

Three different ideas (do not collapse them)

  • Live proof — in PROVE: exercise the exact reviewed feature candidate against the live environment when the Goal claims live reachability/convergence.
  • Fleet rollout — after LAND: install a landed Orbit candidate across managed nodes (update:all today is fleet-wide, not canary).
  • Public release — after LAND: publish already-tested artifacts; release candidates build from the pushed origin/main commit per current policy.

Protection ladder (after actionable failure / feedback)

  1. Diagnose and repair the immediate problem
  2. Cheapest reusable protection: test / linter / schema / state check
  3. Then tool, safe default, generated contract, or template
  4. Then cheap UX check, reviewer context, or concise instruction
  5. Integrated Incus safeguard only when the failure genuinely needs integrated topology to reproduce
  6. Unknown cause → improve evidence; do not add speculative protection
  7. Every chosen protection later validates with one rejected and one accepted example

Responsibilities

This is the current local execution policy (from local agent instructions). It is distinct from the generic HARNESS roles. HARNESS calls the coordinating role feature owner; the mapping below is the current local policy for who plays that role and who implements.

  • User Supplies the goal and human judgment when required.
  • Codex Frames, coordinates, reviews worker results, and verifies.
  • Grok via local Solo Owns implementation edits under the current local role split.
  • General reviewer Issues PASS, FIX, or ESCALATE (and human-judgment decision).
  • Orbit harness Records state and evidence; gates transitions (.orbit/loop.md, acceptance, finalization).

HARNESS still allows any capable surface to own FRAME→LAND and implement directly. In this environment, the local policy above governs the loop.

LLM reading guide

  1. Parse #orbit-feature-graph-data for version, enforcement markers, states, PROVE sequence, proof axes (venue vs environment), protection ladder, release lifecycle, guards, loops, actors, and evidence.
  2. Main machine is only FRAME → BUILD ↔ PROVE → ACCEPT → LAND → Done. There is no mandatory “final deployment gate.” Conditional live-environment proof lives inside PROVE when the Goal requires it. Fleet rollout and public release are a separate post-LAND path.
  3. Do not treat live as a venue. Do not invent canary or rollback as present capabilities; they are marked future_prerequisite.
  4. If this page conflicts with instructions, prefer HARNESS.md.
