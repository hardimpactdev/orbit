---
title: "orbit ai-router:setup"
sidebarTitle: "ai-router:setup"
description: "Deploy the collector Process on one Node and publish `https://collector.ai-router.orbit`."
---

```bash
orbit ai-router:setup --node=<node> --cache-connection=<slug> --cliproxy-url=<url> --cliproxy-management-key-file=<path> [--json]
```

| Option | Required | Meaning |
| --- | --- | --- |
| `--node` | yes | Node ID or name that runs CLIProxyAPI. |
| `--cache-connection` | yes | Redis Database connection slug for shared Valkey. |
| `--cliproxy-url` | yes | CLIProxyAPI Management API origin. A collector-local origin such as `http://127.0.0.1:8317`. It needs a port: the task VM guard reaches the router there. |
| `--cliproxy-management-key-file` | yes | File that contains only the management key. The CLI never accepts the key as an argument. |

The output shows `enabled`, `hostname`, `node_id`, `cache_connection`, and `collected_at`. It never includes a token or the management key. Setup can run again with the same options. That run rewrites the collector script when needed and reconverges the same Process in place, keeping its ID. An unchanged, completed collector stays running without a restart. The management key is the only CLIProxyAPI credential. The script uses it for `/v0/management`, including auth-file models. A collector set up before that read stores no models until setup runs again and the next poll finishes.
