# Relocate the gateway role

## Problem

Bootstrap puts `gateway` and `vpn` on one Node. Later you may want the Gateway on a new machine while the WireGuard hub and private DNS stay put. [`node:role:relocate`](/cli/node/role-relocate) does the move, and [native role relocation](/reference/node-provisioning#native-role-relocation) lists its steps. The move leaves several things for you to do by hand.

## Cause

`vpn` never moves. `gateway` is a singleton, so removing it and adding it again would drop the only active Gateway assignment: the next request would lose its Gateway authority and `gateway.orbit` would leave private DNS. Relocate keeps one active assignment for the whole move. It moves no files, so the new machine must already hold a copy of the Gateway.

## Solution

**Rename first.** A Node name is a unique identifier, not the WireGuard key or address. When the old Node is named `gateway` and the new machine must use that name, free it first. `node:add` finds an existing record by name.

```bash
orbit node:update gateway --name=vpn
orbit node:add gateway <new-host>
```

**Prepare the target.** It must not hold `app-dev`, `app-prod`, `database`, `analytics`, or `ingress`, which conflict with `gateway`. Install PHP-FPM and Caddy. Copy the Gateway checkout, `ORBIT_HOME` with the Orbit CA and Gateway SSH keys, and the Gateway `.env`. Both Nodes need recorded SSH management.

**Move the assignment.**

```bash
orbit node:role:relocate gateway gateway --force
```

A failed private DNS route on the target does not stop the move, and `follow_up` names the retry command. A failed removal on the source leaves the move incomplete; rerun the command with `--from`. Caddy and PHP-FPM keep serving on the source, so the old address works during the cutover. Adding or converging a role holds the Node until its Operation ends, and a competing admission fails with `operation.target_busy`. Explicit role convergence requires an active assignment, a failure at a `converge:` step, or provisioning at least 11 minutes old; it cannot repair an assignment being removed. Use numeric Node IDs with `node:role:add`.

**After the move:**

1. Relocate wrote the new assignment to the SQLite database on the machine that ran it. Copy that database to the target, then start Caddy and PHP-FPM there.
2. `gateway.serving_node_id` still names the old Node, so that Node keeps Gateway authority. Only a Gateway bootstrap records a new serving Node.
3. Run `orbit node:converge <node>` on each Node, so its [Node agent](/reference/node-agent#how-it-connects) learns the new Gateway address. Role convergence leaves the observer configuration alone.
4. Point CLI profiles that name the old WireGuard address at the new one.
5. Stop Caddy and PHP-FPM on the old Node once the new `/up` answers.

Private DNS publication runs on the `vpn` Node. Inspect its dnsmasq files and answers there, not on the Gateway. The `vpn` Node needs no Orbit checkout, and the WireGuard hub keys stay in `/etc/wireguard/orbit.conf` there.

## Limits

Relocate does not install Laravel on the target and does not copy the SQLite database or the Orbit CA. It refuses `swamp` with `node.role_relocate_swamp_held`, because serve on that Node runs the relocation. This page does not cover pointing public clients at a new machine.

## Verification

```bash
orbit node:role:list <old-node>
orbit node:role:list <new-node>
orbit doctor --node=<new-node-id>
curl --fail https://gateway.orbit/up
```

`node:role:list` shows `gateway` on the new Node and `vpn` still on the old one. `orbit node:show` on the new Gateway lists access to the `vpn` Node and, when Metrics exists, the Metrics Node. Run `curl https://<new-wireguard-ip>/up` from a peer that trusts the Orbit CA. To prove the split DNS path, converge a Route or Metrics from the new Gateway and confirm that `/var/lib/orbit/dnsmasq/orbit.revision` changes on the `vpn` Node, not on the Gateway.
