---
title: "orbit node:role:relocate"
sidebarTitle: "node:role:relocate"
description: "Move `gateway`, `websocket`, `metrics`, or a Cluster's `ingress` from its current Node to another Node. One assignment stays active for the whole request."
---

```bash
orbit node:role:relocate <node> <role> [--from=NODE] [--force] [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `node` | yes | Numeric ID of the target Node. It must be active and hold no conflicting role. For `ingress`, it must be a member of the Cluster whose Ingress moves. |
| `role` | yes | `gateway`, `websocket`, `metrics`, or `ingress`. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--from=NODE` | the current holder | Numeric ID of the source Node. After an earlier relocation of this role from that Node, the target already holds the role and `--from` names the Node whose leftovers to remove. |
| `--force` | prompt | Confirm the move without prompting. Required without a terminal and with `--json`. |
| `--idempotency-key=KEY` | generated | Reuse a key to retry the same [Operation start](/reference/operations#start-an-operation). |
| `--json` | off | Print the final Operation as JSON. |

```bash
orbit node:role:relocate 7 gateway --force
orbit node:role:relocate 9 websocket --from=7 --force
orbit node:role:relocate 1841 ingress --force
```

In a terminal, an omitted Node is chosen from an interactive list and an omitted role from the roles that can move. The CLI asks to confirm the move with the Node names and the role, with No selected. Declining, Ctrl-C or end of input exits 1 with `input.cancelled`. The prompt appears only after the checks that can refuse the move have passed. A noninteractive or `--json` call without `--force` or without the role is refused with `validation.failed`, and one without the Node with `node.id_invalid`; neither starts an Operation.

For `gateway`, the Gateway opens the `orbit:gateway-https` firewall rule on the target and moves the assignment. It grants the new Gateway Node access to the `vpn` and `metrics` Nodes, publishes private DNS on the `vpn` Node, and adds the [private DNS route](/reference/private-dns#the-gateway-machine) on the target. It then removes that route and the firewall rule from the source. A failed route on the target reports `follow_up` and does not stop the move.

Relocating `gateway` does not move `vpn`, the Gateway checkout, its SQLite database, the Orbit CA, or the SSH keys. It does not stop Caddy or PHP-FPM on the source, so clients that still use the old address keep working. [Relocate the gateway role](/solutions/relocate-gateway-role) gives the full order.

For `websocket`, Orbit copies the Reverb server's Laravel `APP_KEY` only when the target lacks one. The [Reverb apps](/reference/websocket-apps) stay in the Gateway database, so every app keeps its credentials. Orbit builds a new Reverb release on the target as the Node's user, so the target needs Git, PHP and Composer, as an `app-dev` or `app-prod` Node has them. For `metrics`, Orbit copies role credentials that the target lacks, without overwriting any, and applies the same role setup as `metrics:enable` on the target. It then removes the runtime and publication from the source as `node:role:remove` does, but keeps the fleet exporters and the `metrics.orbit` name and certificate, which the moved role uses.

For `ingress`, the source is the active Ingress of the target's Cluster. Add the target to that Cluster first with [`cluster:node:add`](/cli/cluster/node-add); the move never changes Cluster membership. The target can't hold `gateway`, `app-dev` or `database`. It also can't be the Router or run a target of a public Route: its public site would replace that Route's private hop before Let's Encrypt issues its certificate. Move the Ingress to a dedicated Node. When the source runs a target of a public Route, the Router must be the source too (reason `source_serves_public_route`): a Router on another Node would switch its hop to the Orbit certificate while the source still answers with Let's Encrypt. Each public Process Node's firewall must admit the target, as at Route activation, or the move is refused with `route.upstream_firewall_mismatch` before anything is recorded. The listener the target selects must be the one the Route recorded, or the move is refused with `route.upstream_listener_changed`. The move holds every Node of the Cluster against Route writes for the whole run; a Route write that holds one already refuses it with `route.publication_held`, and a Route write started during the run waits. The target first sends an HTTP HEAD request to each public Process listener. Orbit then applies the Ingress role to the target as `node:role:add --converge` does: it installs Caddy and the Orbit root, builds the target's Caddyfile with every public site of the Cluster (Let's Encrypt, `tls force_automate`), and opens `orbit:ingress-http` and `orbit:ingress-https` when the Cluster has a live public Route. The target must then reach the Router address its sites use over HTTPS for every public app Route, and serve a valid public certificate for every public name, within 300 seconds. An answer of 500 or more after the last try fails the check. Only then does private DNS switch, so names that only the Ingress serves, such as public Process hostnames, answer with the target. After the [withdrawal grace period](/reference/routes#withdrawal-grace-period), Orbit rebuilds the source's Caddyfile without the public sites and closes the source's two Ingress rules. Public Routes stay public for the whole move, and no Route changes. [Ingress relocation](/reference/routes#ingress-relocation) gives the order and what you do with public DNS.

Orbit calls no public DNS provider. Lower the TTL of each public record beforehand, or use a proxy that switches its origin at once, and point the records at the target when the run starts. The target gets its Let's Encrypt certificates only once public DNS names it, so the certificate check fails when the records still name the source after 300 seconds. Every public name counts, so a public Route whose name points elsewhere on purpose blocks the move until it is private or removed. Both Nodes serve the public sites until the source removal; a client that still holds the source's answer after it fails until the answer expires.

Both Nodes need recorded SSH management. [Native role relocation](/reference/node-provisioning#native-role-relocation) lists every step.

`swamp` can't be relocated: it stays on its Node. The command answers `node.role_relocate_swamp_held` before it records anything.

Only one add, converge, remove or relocate runs on the target Node at a time; a second call is refused with `operation.target_busy`. The CLI follows the Operation and prints the final result with the request ID.

When a step on the target or the source fails, the role already belongs to the target and stays `active`, so a role such as `gateway` is never taken out of service by a failed move. For `ingress`, a failed probe, role or certificate step before private DNS switches gives the role back to the source instead: the assignment names the source again, stays `active`, and the result has `source_kept: true`. The source never stopped serving; run the same command again after you fix the cause. A `--from` retry never gives the role back, because an earlier run may already have switched private DNS to the target. When only the source removal fails, the target stays the `active` Ingress and keeps serving; the result has `source_cleanup_failed: true`. Run the same command with `--from` to finish the cleanup. The Operation fails with the step's own code. Unless the role went back to the source, the failed step stays on the role: `converge:STEP`, or, for a role other than `ingress`, `remove:Remove from the source` when the source removal failed. After a target step failure the source still serves; after a source removal failure the target serves. Finished steps stay and nothing is rolled back. Run the same command with `--from` after you fix the cause. A cancelled or interrupted run leaves the claim `provisioning`, and the same retry takes it over.

Repeating a completed move without `--from` is refused with `validation.failed`, because the target now holds the role and the source does not. A `--from` is accepted for a target that already holds the role only after an earlier relocation of this role from that Node.

Relocation does not reconcile Metrics. When a Metrics role exists and `websocket`, `gateway` or `ingress` moved, `follow_up` names the `orbit node:role:add <metrics-node> metrics --converge` command.

## Errors

| Code | When |
| --- | --- |
| `node.id_invalid` | The Node is missing or is not a positive integer, and the CLI cannot prompt. |
| `node.role_relocate_swamp_held` | The role is `swamp`. |
| `validation.failed` | The role is not relocatable or not assigned, it cannot be relocated from its status, the role or `--force` is missing without a terminal, `--from` is unknown, `--from` does not own the move, or, for `ingress`, the target is in no Cluster, its Cluster has no Ingress, the target is the Router or runs a target of a public Route (reason `target_is_router` or `target_serves_public_route`), or the source runs a target of a public Route and the Router is another Node (reason `source_serves_public_route`). |
| `node.role_conflict` | The target holds a role that conflicts with the moved role. |
| `route.upstream_firewall_mismatch` | For `ingress`, a public Process Node's firewall does not admit the target. |
| `route.upstream_listener_changed` | For `ingress`, the target would select another listener than the one a public Process Route recorded. |
| `route.publication_held` | For `ingress`, a Route write holds a Node of the Cluster. Run the move again once it ends. |
| `route.upstream_unresolved` | For `ingress`, a public Process publishes no single listener on the address the target selects. |
| `operation.kind_unavailable` | The target or the source is not an active Linux Node with recorded SSH management. |
| `operation.target_busy` | Another add, converge, remove or relocate holds a Node. |
| `node_access.required` | The caller has no access grant to the Gateway Node. |
