---
title: "orbit node:role:relocate"
sidebarTitle: "node:role:relocate"
description: "Move `gateway`, `websocket`, or `metrics` from its current Node to another Node. One assignment stays active for the whole request."
---

```bash
orbit node:role:relocate <node> <role> [--from=NODE] [--force] [--json]
```

| Argument or option | Meaning |
| --- | --- |
| `node` | Target Node ID or name. It must be active and hold no conflicting role. |
| `role` | `gateway`, `websocket`, or `metrics`. |
| `--from=NODE` | Source Node. Omit it to use the current holder. When the target already holds the role, `--from` names the Node whose leftovers to remove. |
| `--force` | Confirm the move. Required without a terminal and with `--json`. |

```bash
orbit node:role:relocate beast gateway --force
orbit node:role:relocate services websocket --from=beast --force
```

For `gateway`, the Gateway opens the `orbit:gateway-https` firewall rule on the target and moves the assignment. It grants the new Gateway Node access to the `vpn` and `metrics` Nodes, publishes private DNS on the `vpn` Node, and adds the [private DNS route](/reference/private-dns#the-gateway-machine) on the target. It then removes that route and the firewall rule from the source. A failed route on the target reports `follow_up` and does not stop the move.

Relocating `gateway` does not move `vpn`, the Gateway checkout, its SQLite database, the Orbit CA, or the SSH keys. It does not stop Caddy or PHP-FPM on the source, so clients that still use the old address keep working. [Relocate the gateway role](/solutions/relocate-gateway-role) gives the full order.

For `websocket`, the Gateway copies the Reverb server's Laravel `APP_KEY` only when the target lacks one. The [Reverb apps](/reference/websocket-apps) stay in the Gateway database, so every app keeps its credentials. Swamp builds a new Reverb release on the target as the Node's user, so the target needs Git, PHP and Composer, as an `app-dev` or `app-prod` Node has them. For `metrics`, the Gateway copies role credentials that the target lacks, without overwriting any, and runs the same workflow as `metrics:enable` against the target. Then the run removes the runtime and publication from the source with the `node:role:remove` workflow.

Both Nodes need recorded SSH management; Swamp reaches them from Node 209 with their recorded host keys. [Native role relocation](/reference/node-provisioning#native-role-relocation) lists every step.

`swamp` can't be relocated: serve on its Node runs every Swamp run, so a run can't move it. The command answers `node.role_relocate_swamp_held` before it records anything. Live relocation of the role is still open.

When a step on the target or the source fails, the role already belongs to the target. The task fails with the step's own code. The role is marked failed with `converge:STEP`, or `remove:Remove from the source` when the source removal failed. Run the same command with `--from` after you fix the cause.

Relocation does not reconcile Metrics. When a Metrics role exists and `websocket` or `gateway` moved, `follow_up` names the `orbit node:role:add <metrics-node> metrics --converge` command.

Use `--idempotency-key=KEY` to retry the same native role admission.

## Errors

| Code | When |
| --- | --- |
| `node.role_relocate_swamp_held` | The role is `swamp`. Serve on its Node runs every Swamp run, so a run can't move it. |
| `validation.failed` | The role is not relocatable or not assigned, `--force` is missing, or `--from` does not own the move. |
| `node.role_conflict` | The target holds a role that conflicts with the moved role. |
| `operation.kind_unavailable` | The target or the source is not an active Linux Node with recorded SSH management. |
