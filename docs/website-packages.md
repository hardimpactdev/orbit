# One project batch per update group

Each project gets one package group with one child and one PR containing every
eligible major and advisory fix from its latest successful detection. Shared
ecosystem extensions select exact stable targets and solve them together against
the project manifests, lockfiles, platform and peer constraints. Major updates
change only the selected direct ranges. No package gets its own task group.

Detection keeps candidate evidence, eligible exact targets and blocked reasons
in Swamp data. It runs resolution and audits in a disposable copy of the tracked
checkout, without dependency installation or changes to the source checkout.
The copy preserves tracked file and directory symlinks. Each link and its chain
must stay inside the checkout; links are never followed to copy untracked
content. Absolute links inside the checkout become equivalent relative links
inside the disposable tree. Untracked files and the Git directory are excluded,
and tracked entries other than regular files or safe symlinks are refused.

Targets must satisfy the configured release age, including security targets;
a finding never authorizes an age exception. Missing release dates, unsupported
sources, unsatisfied constraints and unverified advisory fixes remain recorded.
The native resolver chooses versions jointly from all eligible releases. If
the whole set cannot resolve, keep current versions as optional choices and
require each upgrade in security order while allowing the resolver to adjust
other versions. Coupled updates remain together; unresolved requests keep their
solver reason.
All selected updates are applied together per ecosystem/path, not through a
sequence of individual package installations. Expo SDK alignment remains the JS
extension's responsibility. Post-update audit verifies selected advisory fixes. The fresh checkout also
refuses stale advisory identities and downgrades before changing files; exact
target retries remain valid after repair. Release-age validation covers changed
transitive packages as well as selected targets.

Admission uses the existing orbit-gateway behavior lock. Findings remain data
until capacity is reserved. Only then does the shared scheduler create one
immutable batch group and start the official dependency-package factory.
Security batches go first; within each priority class, the least recently
admitted project goes next, with Project ID as a stable tie breaker. Routine and
detect intents share admission and the same global budget.

At most four maintenance executions may hold or reserve a running VM across
routine, detect and package work. Published groups move to `waiting_for_review`
and use Orbit's keyed `tasks.park` operation. Only its scoped successful result,
plus a fresh eligible group read, releases an execution slot. A parked row alone
proves no completed stop. The group keeps its project ownership and checkout,
so routine, detect and package admission cannot create another group for that
project. Before a worker, check, turn, publish or merge cleanup wakes the VM,
Swamp durably reserves its slot again under the shared admission lock. When all
four slots are held, the VM stays stopped. Assistance and unconfirmed parking retain capacity. A failed or cancelled park retains its next-read deadline and retries with a fresh key after 30, 60 and then 120 seconds. It keeps the factory stage running and the slot held. After three terminal failures, Swamp records an owned group assistance request. Posting a resolution resets the failure count; another request is preserved. Diverged live evidence voids an old release proof and restores normal reservation accounting so the owning group can finish cleanup. Completed cleanup replays need no slot. Existing receipts without parking evidence keep their slots. Existing
work above the limit is left intact; no new work is admitted until room exists.
Orbit remains the only VM allocator: its provision operation waits for actual
free host capacity. The Swamp budget never bypasses that allocator or promises
four free Orbit slots. One project cannot admit another package batch until its
previous batch has merged and completed, or was cancelled, cleaned and acknowledged.
Routine/detect work for the same project also finishes before its batch starts.

Creation records intent before POST. An uncertain response is reconciled by the
saved brief; it is never blindly retried. A reservation is durable before a
create or factory start, so retries and lost replies consume the same place.
An unbound reservation expires after 15 minutes. Before releasing it, admission
reconciles the exact saved brief against Orbit. A matching group is adopted;
confirmed absence retires the intent and releases its reservation. The saved
request is never posted again. Missing or ambiguous Orbit evidence retains the
reservation and records assistance. A released, unconfirmed intent remains
retired, so its findings cannot recreate that batch on the next tick.

The minute tick reconciles reservations even when no new work is queued. A
completed group with a closed, unmerged PR retains its place and raises a Swamp
scheduler issue naming the group and PR. Orbit refuses assistance writes on
terminal groups; the issue is therefore visible in Swamp's `scheduler-issue-*`
and `project-work` resources. The same resources retain expired-create assistance.
Reopening or merging the PR resolves the closed-PR issue on reconciliation;
only merged completion or acknowledged cancellation releases project ownership.
Confirmed review parking releases its execution slot while keeping that ownership.
Unknown, failed or mismatched parking evidence retains the slot and records an
issue. Lost start replies replay the same key. Closed PRs retain their existing
gates. Orbit's host allocation still counts the stopped disk; this policy does
not promise extra physical host capacity.

An immutable batch is identified by its detection receipt and targets. Repeated
ticks cannot create duplicate groups or change targets of an admitted run.
Blocked findings are visible alongside the eligible targets in Swamp resources;
no placeholder backlog groups are created for them.

The unchanged package factory drives provision → worker batch → handoff →
publish → wait for merge → completion and cleanup. A red worker command or
check gets one normal Orbit repair turn in the same VM, then the same full batch
is checked again. A second failure or operator/safety assistance parks. Publish
requires a passed check. Detection uses provision → script → finish and has no
handoff, repair, agent turn or PR.

Production resumes only after the orchestrator merges, deploys and explicitly
unpauses maintenance-projects and the project detect schedules. Deploying code
does not remove Swamp schedule pauses. Existing handoff-era detect groups need
operator reconciliation; deployment never rewrites their jobs or deliverables.


## PR text for apps and packages

The summary uses the authoritative Orbit Project type. App and website Projects (`laravel-app`, `symfony-app`, `monorepo`) list major updates plainly in the package table. Only `laravel-package` and `node-package` include the downstream warning to check upgrade notes. Standalone summaries default to app text unless passed an explicit package Project type.

The execution gate stays update → project checks → agent only on failure. There is no mandatory upgrade-notes step, migration record or extra verification stage for majors. When an update later causes a regression, fix the repository and improve its tests, including browser coverage where needed.

## Pull request text

The table lists each package's old and new version and marks majors and security
fixes. Advisory links follow the table. Related updates with the same effect
share one bold label. `What changes on the site` names each
update and its visible effect, or says `No code changes needed.` Package Projects
use `What changes in the package`; only `laravel-package` and `node-package`
Projects ask readers to check upgrade notes for downstream breaking changes.
Leave test results, check IDs, group numbers and execution history in internal
artifacts. Never rewrite an existing hand-written PR body.

Before repair, the worker returns the exact update inventory using the same
Composer and JS row calculation as publication. The repair prompt lists those
`manager`, `path` and `package` rows; the agent must not reinterpret advisory
ownership. The repair receipt retains that inventory. Updates first reached by a dependency-only rerun need no code explanation when all source changes are already covered. Missing original rows still stop publication. Missing inventory stops the repair before an agent starts.

Inventory failures are separate retryable infrastructure failures, not command failures. They retain the workflow run ID and never produce a failed-script artifact or start a repair turn. The operator can retry the failed inventory step with Swamp workflow resume; it does not capture an audit outage as a dependency command exit code. After the resumed inventory succeeds, the operator must still resolve the group's assistance. Swamp resume does not clear it.

The single repair turn returns JSON in its receipt summary: `updates` contains
`manager`, `path`, `package`, `codeChanged`, optional `label`, `effect` and `files`
per changed package. Code changes need a short plain-text effect and
repository-relative changed files. Labels and effects allow only Unicode letters, digits, spaces and the punctuation `. , ; ( ) ' - /`. They also reject hexadecimal words of seven or more characters containing both letters and digits, `www.`, and `GH-` issue references. Dotted names such as `Next.js` and `e.g.` and digit-only numbers remain plain text. This keeps GitHub from rendering commit links, emoji images, math, mentions or links from agent prose. The full
JSON is limited to 16,384 characters. Unchanged updates use an empty file list;
their effect text is ignored. The worker compares the
report with the immutable base and checked tree, covers all changed source,
configuration, documentation and test files, and refuses unknown or duplicate
updates. Manifest edits between the pre-repair script tree and repair tree also
need coverage while they still differ from base, including exports, autoload
and scripts. Diffs disable rename
detection so both old and new paths need coverage. Dependency-only reruns may
change locks after repair; source changes
invalidate the report. Missing or invalid repair data stops publication through
the existing assistance route, without another turn. The saved body is reused
only for the same check and repair report. Existing repaired groups without a report or retained pre-repair inventory need corrected data bound to the checked source before publication.
A pre-deploy publish identity that did not bind a repair report refuses a resume
with that report. It preserves the saved request and PR; a new publish cycle
needs a valid report bound to the checked source.

## Manifest range styles

Batch targets choose exact locked versions while preserving each direct
requirement's operator and precision: `~7.4` becomes `~8.0`, `^1` becomes `^2`,
and a pin stays a pin. A major target already admitted by the declaration keeps
it unchanged, including unions, lower bounds and wildcards. Routine updates also
keep the declaration. Security updates raise the floor to the fixed version;
if the existing precision cannot express that floor, the target stays blocked.
Prerelease/build metadata, uppercase `V`, and compound ranges that do not admit
the target also stay blocked. A bare Composer partial pin must admit the exact
target: `1.2` can become `2.3` for `2.3.0`, but blocks `2.3.4`. The same npm
partial accepts `2.3.4`.

Planning filters every eligible version for a writable declaration before the
joint solve. Age and major eligibility apply first. Unsupported Expo-aligned
ranges block that SDK candidate before resolution; unrelated updates remain
eligible. A typed range, alignment or registry-miss rejection permits an older
release. Invalid target data and deterministic registry misses block only their
candidate. Transient registry failures during candidate metadata lookup stop
planning instead of selecting an older SDK; aborts always propagate. Errors
during the joint resolver or audit remain solver exclusions.
Each JavaScript plan reads a package's release metadata and each Expo version's
catalog once per configured path, reusing them through solving. A new plan or
batch reads fresh metadata. Blocked records retain distinct reasons from the
newest rejected options.

JavaScript refreshes lock metadata through the package manager; any resolved
version movement fails the batch.
