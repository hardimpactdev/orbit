`instance:restore` keeps an intact Instance whose removal failed. It restores serving, then returns the Instance to active. It does not undelete source, data or runtime. See [Instance removal](/reference/instance-removal#restore-a-failed-removal).

```bash
orbit instance:restore <instance> [--json]
```

| Argument | Required | Meaning |
| --- | --- | --- |
| `instance` | yes | Numeric development Instance ID. An omitted ID uses the [finite record selector](/reference/cli-ux#prompt-selection) in a terminal. |

| Option | Default | Meaning |
| --- | --- | --- |
| `--idempotency-key=KEY` | generated | Reuse an [Operation start](/reference/operations#start-an-operation). |
| `--json` | off | Print the final Operation as [JSON](/reference/cli-ux#input-and-output-modes). |

There is no force flag or recovery option. Orbit admits only a failed removal whose complete source, runtime and database inventory survives. It refuses removal that already deleted a container, member, Route target, source, Process, Schedule trigger or SQLite file, or ran teardown. It also refuses unfinished work, incomplete evidence and identity, ownership or database admission drift.

Orbit first restores the admission values saved by the failed database fence. It accepts a database still closed by that fence or already reopened, and removes only the matching journal rows. The same Route, targets and domain serve again. Only the awake marker is restored; the cold marker stays absent and serving creates the access log. Orbit reports the Instance and Route active only after publication and its check pass.

A failure, including cancellation at a native step boundary, keeps the Instance removing and the removal failed. Orbit withdraws partial publication before releasing its publication holds. A failed withdrawal is reported as incomplete recovery. A timed-out Operation retains its holds until its work ends or cancellation is acknowledged. After the shared 60-minute settlement window, Orbit records an unproven end and frees the holds.

Run `instance:restore` again to retry. A repeat after success checks the restoration receipt and current records, then succeeds with `instance.already_restored`. A later `instance:destroy` captures a new removal identity and inventory.

## Errors

| Code | Meaning |
| --- | --- |
| `instance.id_invalid` | The ID is missing or is not a positive integer, and the CLI cannot prompt. |
| `instance.restore_state_invalid` | The Instance is not in a failed removal, a run is unsettled, or source identity changed. |
| `instance.restore_already_removed` | A required resource is gone or teardown ran. The message and `details.reason` name the item. |
| `instance.restore_database_changed` | The planned database set, users, ownership, identity, admission or required evidence changed. |
| `instance.restore_busy` | Lifecycle, Process, Schedule or publication work still holds a required resource. |
| `instance.restore_publication_failed` | Publication or its check failed; the Instance stays removing. |
| `instance.restore_compensation_failed` | Withdrawing the partial publication failed; recovery remains incomplete. |
| `http.404` | The Instance is unknown. |
| `node_access.required` | The caller has no access grant to its Node. |
