# Human Renderer: `orbit update:all`

[Back to `update:all` technical contract.](1_update-all.md)

This page describes the human-rendered terminal output for `update:all`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update:all` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

`update:all` updates the whole fleet to the latest release. It always begins
with two check steps before any side effect, so the tree renders immediately
with both steps idle:

```text
┌  Updating Orbit
│
○  Checking for updates
│
○  Checking fleet versions
│
└  Working...
```

### Check steps

| Step | Active | Settled |
| --- | --- | --- |
| `Checking for updates` | `Checking` | `Done: latest version is <latest_version>` |
| `Checking fleet versions` | `Checking` | `Done: all nodes running on <latest_version>` when current, or `Done: <outdated_node_number> outdated nodes found` |

When every node already runs the latest release, the tree stops after the two
check steps and the footer settles to `Done`:

```text
┌  Updating Orbit
│
●  Checking for updates      Done: latest version is 0.1.131
│
●  Checking fleet versions   Done: all nodes running on 0.1.131
│
└  All nodes are running on version 0.1.131
```

### Per-node update rows

When outdated nodes are found, the tree is extended with one row per node, in
update order. The **gateway updates first** (the fleet's version ceiling), then
the local node and the remaining workload nodes update in parallel. Each row
keeps the node name in the first column and advances its stage in the second:

```text
┌  Updating Orbit
│
●  Checking for updates      Done
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
◉  gateway                   Updating gateway app
│
○  beast                     Waiting
│
○  main1                     Waiting
│
└  Working...
```

Per-node stage vocabulary:

| Node kind | In-progress stages | Settled |
| --- | --- | --- |
| gateway | `Downloading <new_version> assets` → `Updating gateway app` → `Replacing cli binary` → `Running doctor` | `Done` |
| local / workload node | `Downloading <new_version>` → `Replacing cli binary` → `Running doctor` | `Done`, or `Skipped: already up to date` |

A node already on the latest release settles immediately to
`Skipped: already up to date` (orange `●`) and runs no download. Workload-node
rows stay `Waiting` (dim, not animated) until the gateway row succeeds; the
gateway is the version ceiling, so no node is updated ahead of it. After the
gateway row succeeds, up to four workload nodes advance simultaneously. The
renderer preserves one row per node and must not reorder rows by which parallel
worker finishes first.

Gateway-owned work is streamed back over the typed Gateway API as durable
operation events; the CLI renders those events locally. If the gateway service
is replaced mid-stream the CLI reconnects with `Last-Event-ID` and resumes from
the event journal without duplicating rendered events.

## Success Output

On full success the footer names the fleet-wide version:

```text
┌  Updating Orbit
│
●  Checking for updates      Done
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
●  gateway                   Done
│
●  beast                     Done
│
●  main1                     Done
│
└  Success: All nodes are running on version 0.1.131
```

When nothing needed updating, the footer is
`Skipped: 0.1.131 is already installed on all nodes`. The success output must
not claim that app deployments, state-family drift, or runtime readiness have
been verified beyond each node's `Running doctor` stage.

## Failure Output

Human-rendered failures must show:

- every node that succeeded, was skipped, or failed;
- the failed update output when available;
- no JSON envelope.

The gateway is the ceiling: if the gateway row fails, workload nodes are not
updated (they would exceed the gateway version), and the footer reports the
gateway failure. If a workload node fails after the gateway succeeded, later
nodes continue and the failed node's output is printed below the tree:

```text
┌  Updating Orbit
│
●  Checking for updates      Done
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
●  gateway                   Done
│
●  beast                     Failed
│
●  main1                     Done
│
└  Failed
Failed to update node beast.
Permission denied (publickey).
```

If the gateway update fails, the footer is the gateway failure and no workload
row advances past `Waiting`.
