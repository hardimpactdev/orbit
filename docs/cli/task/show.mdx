---
title: "orbit task:show"
sidebarTitle: "task:show"
description: "Show one task as a detail tree, followed by its brief and a table of its subtasks in position order."
---

```bash
orbit task:show [task] [--json]
```

Token totals use the thread observations already recorded by task operations. Showing a task does not contact its agent sessions. A slow or unavailable session does not delay the task detail.

The tree shows the ID, title, Project, status, whether the task is asking for assistance, the assistance kind, the question, the reason, Instance, pull request, the implementer and reviewer agents, tokens, line diff, and duration. Each agent row shows the role's resolved [copy turn agent](/reference/tasks#copy-turn-agents) as `claude / claude-opus-5-5 / high`, then where its values come from: `(gateway)` when all three agree, or one source per value, such as `(gateway / group / project)`. JSON holds the values the task names in `implementer_provider`, `implementer_model`, `implementer_effort` and the same three for the reviewer, null where it names none, and the resolved values with their sources in `resolved_agents`. The subtask table shows the position, ID, title, status, deliverables, tokens, line diff, duration, assistance kind, and the question or reason of each subtask. A direction request shows its question in that last column. A failure shows its reason. A subtask or task that is not asking shows an em dash in the kind, question, and reason columns, even when an old value is still stored. JSON includes `assistance_requested`, `assistance_kind`, `assistance_question`, and `assistance_reason` on the task and each subtask, and `fails_on_base` on every command deliverable. When that value is true, the detail names the deliverable under Fails on the start commit. Showing an active task refreshes its metrics, as the [tasks reference](/reference/tasks#tokens-and-line-diff) describes.

The tree shows **VM power** when the task's `vm_power` is not `null`. JSON includes `vm_power` when power is known: `running`, `stopped`, or `destroyed`; it omits the field when the API reports `null`. [VM power](/reference/compute-drivers#vm-power) describes how those values map to the task VM's state, separately from task status.

JSON includes `last_activity_at` on the task: when an Operation on it was last created, started or ended, or null. `preview_url` is the `https://` URL of the task workspace's active Route, or null while the workspace has no active Route. The tree shows them as **Last activity** and **Preview URL**. While the task waits for a task place, JSON includes `capacity_wait` with `operation_id`, `position`, and `holders`, and the tree shows **Queue position** and **Places held by**. [Task places](/reference/tasks#task-places) defines these fields.

On the task, `watched_pr_url`, `watched_pr_number`, and `watched_pr_state` report the pull request found on `task-{id}` while subtasks are open. Those fields do not change `pr_url`, which remains the reviewed pull request Orbit opened.

A task of a review-and-merge Project, or one that reviews an incoming pull request, also has `review_and_merge` in JSON: `enabled`, `pr_branch`, `merge_status`, `merge_reason`, `merged_sha`, and `reviewed_commits`. Each reviewed commit has `sha`, `source`, `review_task_id`, `pushed_at`, `github_review_id`, and `recorded_at`. Other tasks return `null`. The tree adds `Review and merge`, `Pull request branch`, `Merge`, and `Merged commit`, and a table lists the reviewed commits. A final review subtask has `type` `final_review`. [Review and merge](/reference/tasks#review-and-merge) defines these fields.
