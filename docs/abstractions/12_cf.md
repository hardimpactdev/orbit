# Cloudflare Implementation Patterns

Read this with `docs/abstractions/cross-cutting.md` before implementing
Cloudflare command ports.

Product behavior remains owned by `docs/commands/12_cf/**` and the top-level
product docs.

## Domain Constraints

- Cloudflare is a provider utility command domain, not a state family.
- The gateway is the only Orbit node that talks directly to the Cloudflare API.
- Cloudflare API tokens are external secrets stored on the gateway.
- Control callers use typed gateway API requests and must be authorized for
  provider administration.
- App callers are denied before prompts or side effects.
- Cloudflare commands operate on real Cloudflare-backed domains only.
  Development TLDs and caller-local DNS overrides are out of scope.
- Provider DNS/cache/SSL state supports app and proxy behavior but does not
  replace gateway-owned app, proxy, TLS, or DNS intent.
- There is no `doctor --family=cf`; provider health belongs to the app and
  proxy family checks that depend on it.

## Service Pattern

- Keep Cloudflare API access behind a gateway-local client/factory service.
- Validate zone resolution before provider writes.
- Never expose provider tokens in human output, JSON output, logs, activity
  metadata, or exception metadata.
- Provider write commands should return provider identifiers and status, not
  persist Cloudflare records as Orbit intent.

## Command Pattern

- `cf-zone:list` and `cf-dns:list` are provider reads through the gateway.
- `cf-dns:add` and `cf-dns:remove` are limited to documented address-record
  behavior.
- `cf-cache:flush` and `cf-cache-rule:*` mutate provider cache state for
  resolved real domains.
- `cf-ssl:enable` and `cf-ssl:disable` mutate provider SSL mode. `strict` is
  the default target; `flexible` stays outside the product boundary.
- Control callers forward to typed gateway API endpoints; gateway callers use
  the local Cloudflare client.

## E2E Pattern

- Use Docker feature E2E with HTTP-faked provider calls when validating command
  contracts and gateway forwarding.
- Use real-provider tests only as opt-in external-provider checks, not as the
  required E2E lane for command ports.
