## Item 2 — empty/failed `git ls-files` fails closed: CONFIRMED

`firewall_proof_list_synced_paths()` gains two guards, and they cover both halves of the
gap I raised as P2:

- `shell_exec(... 2>/dev/null)` is replaced by
  `firewall_proof_run_command(['git','-C',$root,'ls-files','-z','--full-name','--cached'], $root, 30)`
  with `if ($listed['exit'] !== 0) throw`. Git failure is now observed instead of
  swallowed, and it carries a real timeout and separated streams like every other
  command in the rig.
- `if ($paths === []) throw` sits **after** normalization, exclusion filtering, and the
  `is_file()` check, so it also catches the case where git succeeds but nothing survives
  filtering — not only the empty-stdout case.

Both throw `InvalidArgumentException('checkout digest mismatch')`, consistent with the
surrounding identity failures, and both fire before `firewall_proof_hash_paths()`, so the
degenerate `hash('sha256', '')` digest that would have satisfied `require_digest()` can no
longer be produced.

**The regression is focused and exercises the intended branches.** The new test drives
the two cases through the real function against real directories rather than mocking:
a directory with no repo, and a `git init`-ed repo with nothing committed. I verified the
first case hits the branch it claims — `sys_get_temp_dir()` on this host is
`/var/folders/…`, outside any repository, and `git ls-files` there exits **128** — so it
asserts the exit-code guard, not the empty-list guard by accident. The second asserts
`git init` exits 0 first, so an empty result there can only come from an empty index.
Cleanup uses `File::deleteDirectory` in `finally`; the gateway's `pest()->extend(TestCase::class)`
is unscoped, so the container is booted and the facade resolves.

No other caller is affected: `--dry-run` exits before listing, `--cleanup` never lists,
and the two existing tests that call the function pass a real repo root.

## POLISH

### P1. The sibling git calls were not hardened the same way

`local_firewall_proof_candidate()` still uses bare `shell_exec` for `rev-parse HEAD` and
`status --porcelain --untracked-files=all` with no exit check
(`bin/orbit-firewall-retained-proof:124,131`). The HEAD call still fails closed by
accident rather than by design — a failed call yields `''`, which reaches
`firewall_proof_require_sha('')` and throws. The dirty check does not: if `status` fails
while `rev-parse` succeeds, `$dirty` is `''` and the tree is treated as clean. The tree
digest still binds the real bytes, so this cannot produce a wrong digest, only a
candidate accepted from a dirty worktree. Converting both to
`firewall_proof_run_command()` with an exit check would make the whole entry gate
consistent with what this delta just fixed one function below it.

### P2. "complete tracked tree" is precise only with its qualifier

The sentence is accurate because "on the synced transport checkout" scopes it, and I
verified that scoping numerically. Read without the qualifier it could suggest all 10,544
tracked files rather than the 5,111 that are synced. If the paragraph is ever trimmed,
that qualifier is the part that must survive.
