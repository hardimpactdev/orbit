Wake one sleeping development container Instance. A visit to its Route does the same, so you rarely need this command. [Sleep and wake](/reference/development-containers#sleep-and-wake) explains the lifecycle.

## Usage

```sh
orbit instance:wake 42
orbit instance:wake 42 --json
```

| Argument or option | Meaning |
| --- | --- |
| `instance-id` | Numeric Instance ID. |
| `--idempotency-key=KEY` | Reuse a key to retry this operation start. |
| `--json` | [Machine output](/reference/cli-ux#input-and-output-modes). |

Orbit resumes a frozen container: its processes continue where they stopped, and nothing boots. When FrankenPHP does not answer after 10 tries one second apart (about 20 seconds at most), Orbit stops the container and starts it. A container found stopped (after a host reboot, or a sleep that fell back to a stop) is started: T3, FrankenPHP and each Process that ran before the sleep start with it; a stopped Process stays stopped. Orbit waits until each of them runs and the app answers. An answer of 500 or above gets up to 5 more seconds to clear; after that the app is served as it is. Then it removes the asleep marker, and the Route serves the app again. In a clone, the wake then waits until T3 answers; a visitor does not wait for it. The result names the path: `wake` is `resumed`, `restarted_after_resume`, `started` or `already_running`; `marker_found` says whether the marker was there; a resume adds `resume_seconds` and `web_probe_seconds`. A successful wake also renews the Gateway's T3 session at once when it ends within 7 days or ended during the sleep.

There is one wake per Instance at a time. A second caller joins the open wake and gets the same Operation.

Waking an Instance that is awake changes nothing and also succeeds. A failed wake keeps the asleep marker: the Route shows a failure page with Try again. Try again, or this command, starts a new wake.

The API is `POST /api/v1/instances/{instance}/wake`; it starts an `instance.wake` Operation, or an `instance.start` Operation for a clone of a nested-fleet default. The MCP tool is `instance-wake`.

## A stopped nested-fleet clone

A clone of a nested-fleet default never sleeps. A host reboot, an out-of-memory kill or a stop by hand can still leave it stopped, and its container does not start at boot. For such a clone, this command starts an `instance.start` Operation instead of a wake. Orbit starts the container through the same checks as a deployment's start, puts the nested Gateway's Club key into the container's `/run`, and then starts the inner fleet as the clone's create does: the nested containers, the operator tunnel `wg-nested`, and a wait for Doctor and the three agents. The result gives `power_state`, `nested_fleet_club_key` (what the start did with the key) and `fleet_seconds` (the time of the fleet start). A start of a copy that runs changes nothing that already runs. [A stopped nested-fleet clone starts](/reference/development-containers#a-stopped-nested-fleet-clone-starts) has the details.

A nested-fleet default does not take this path: it starts only through its deployment.

## Errors

| Code | Meaning |
| --- | --- |
| `instance.id_invalid` | The Instance ID is not a positive number. |
| `operation.kind_unavailable` | The Instance has no container. |
| `instance.sleep_unsupported` | The Instance is not a development Instance, or it is a nested-fleet default, which starts only through its deployment. |
| `instance.start_unsupported` | The start of a nested-fleet clone was called for another Instance. |
| `instance.nested_club_key_missing` | The start of a nested-fleet clone found no Club key on the Gateway. Its inner fleet cannot become ready, so the run did not start. |
| `instance.container_fleet_check_failed`, `instance.container_fleet_resume_failed` | The inner fleet of a nested-fleet clone did not start or did not become ready. The failure's detail says why. |
| `instance.lifecycle_busy`, `operation.target_busy` | Other lifecycle work runs on the Instance. |
| `instance.container_start_failed` | The container or one of its units did not start, or the asleep marker could not be removed. |
| `instance.web_unready` | FrankenPHP gave no answer within about 30 seconds. The marker stays. |
| `instance.t3_unready` | T3 did not answer within about 30 seconds. The app already serves: the marker is gone, and the Instance is recorded as running. |
