# Human Renderer: `orbit update:all`

[Back to `update:all` technical contract.](1_update-all.md)

This page describes the human-rendered terminal output for `update:all`.

**Renderer:** Human renderer.

## Primitive

- Progress: [Progress tree](../../../../ux/commands/progress/progress-tree.md)

## Selection

Use this renderer when `--json` is not present.

The human renderer does not own input prompting. `update:all` takes no required
arguments and does not prompt in any input mode.

## Progress Tree

The header is `Updating Orbit`. `update:all` always begins with two check steps
before any side effect, so the tree renders immediately with both steps idle:

```text
┌  Updating Orbit
│
○  Checking for updates
│
○  Checking fleet versions
│
└  Working...
```

### Check steps

| Step | Active | Settled |
| --- | --- | --- |
| `Checking for updates` | `Checking` | `Done: latest version is <latest_version>` |
| `Checking fleet versions` | `Checking` | `Done: all nodes running on <latest_version>` when current, or `Done: <outdated_node_number> outdated nodes found` |

### All-current short-circuit

When the fleet-version probe finds 0 outdated nodes, the gateway and workload
phases are skipped entirely. Only the two check rows appear; no gateway or node
rows are added. The footer settles to `Skipped: <version> is already installed
on all nodes`:

```text
┌  Updating Orbit
│
●  Checking for updates      Done: latest version is 0.1.131
│
●  Checking fleet versions   Done: all nodes running on 0.1.131
│
└  Skipped: 0.1.131 is already installed on all nodes
```

### Per-node update rows

When outdated nodes are found, the tree is extended with one row per node, in
update order. The **gateway updates first** (the fleet's version ceiling), then
the local node and the remaining workload nodes update in parallel. Each row
keeps the node name in the first column and advances its sub-stage in the
second:

```text
┌  Updating Orbit
│
●  Checking for updates      Done: latest version is 0.1.131
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
◉  gateway                   Updating gateway service
│
○  local                     Waiting
│
○  beast                     Waiting
│
└  Working...
```

#### Per-node sub-stage vocabulary

Each node row advances through sub-stages as the gateway emits ordered journal
sub-steps. The active sub-stage is shown in the row; when the node settles the
row shows `Done`, `Done (<n> issues)`, or `Skipped: already up to date`.

| Node kind | Sub-stages (in order) | Settled |
| --- | --- | --- |
| gateway | `Updating gateway service` → `Stopping scheduler` → `Running gateway migrations` → `Starting scheduler` | `Done` |
| local / workload node | `Downloading <v>` → `Replacing cli binary` → `Running doctor` | `Done`, `Done (<n> issues)`, or `Skipped: already up to date` |

The gateway is a Docker service replaced from the digest-pinned image, not a
CLI-binary swap, so its row advances through the service-update lifecycle rather
than the `Replacing cli binary` sub-stage. Each updated CLI node (local and
workload) runs a post-update `orbit doctor` verify; a non-zero issue count is
folded into the node's `Done (<n> issues)` settle text and never fails the node.

A node already on the latest release settles immediately to
`Skipped: already up to date` (orange `●`) and runs no download. Workload-node
rows and the local row stay `Waiting` (dim, not animated) until the gateway row
succeeds; the gateway is the version ceiling, so no node is updated ahead of it.
After the gateway row succeeds, the local node and up to four workload nodes
advance simultaneously. The renderer preserves one row per node and must not
reorder rows by which parallel worker finishes first.

Gateway-owned work is streamed back over the typed Gateway API as durable
operation events; the CLI renders those events locally. If the gateway service
is replaced mid-stream the CLI reconnects with `Last-Event-ID` and resumes from
the event journal without duplicating rendered events.

## Success Output

On full success the footer names the fleet-wide version:

```text
┌  Updating Orbit
│
●  Checking for updates      Done: latest version is 0.1.131
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
●  gateway                   Done
│
●  local                     Done
│
●  beast                     Done
│
└  Success: All nodes are running on version 0.1.131
```

When nothing needed updating, the footer is
`Skipped: 0.1.131 is already installed on all nodes` (no gateway or node rows
appear). The success output must not claim that app deployments, state-family
drift, or runtime readiness have been verified beyond each node's `Running
doctor` stage.

## Failure Output

Human-rendered failures must show:

- every node that succeeded, was skipped, or failed;
- the failed update output when available;
- no JSON envelope.

The gateway is the ceiling: if the gateway row fails, the local and workload
nodes are not updated (they would exceed the gateway version), and the footer
reports the gateway failure. If a workload node fails after the gateway
succeeded, later nodes continue and the failed node's output is printed below
the tree:

```text
┌  Updating Orbit
│
●  Checking for updates      Done
│
●  Checking fleet versions   Done: 3 outdated nodes found
│
●  gateway                   Done
│
●  beast                     Failed
│
●  local                     Done
│
└  Failed
Failed to update node beast.
Permission denied (publickey).
```

If the gateway update fails, the footer is the gateway failure and no local or
workload row advances past `Waiting`.
