# Conn revocation data

Swamp core runs each bounded T3 request through `command/shell` on the Swamp role worker. The official SSH, cfgmgmt and vault behaviors have no T3 session API. The official HTTP behavior has no streaming WebSocket RPC method. The shipped Deno reader uses the runtime’s WebSocket client for upstream Effect RPC: one subscribeAuthAccess request, one initial snapshot, then close. The workflow bounds it to 15 seconds. There is no retry or polling. The behavior locates this asset, creates the private reply directory, selects public request bodies and reads private JSON replies; it starts no process.

The reader and curl receive the admin session through its step environment and expands the authorization header internally. It writes replies below a private `mktemp` directory. Data methods retain only selected session IDs, public request bodies, completion indices and counts. Cleanup removes the directory after failure too. A native assert checks the end state, and the Gateway projects public captures from the same terminal history read.

Fan-out commands use stable indexed slots (`conn-revocation-session-0`, `conn-revocation-link-0`, and so on). Their input schema bounds the slots at 4,096. The name does not depend on a run or task, and each slot has one behavior type. Per-item names let independent requests run in parallel without sharing Swamp's 60-second behavior lock. Fixed data and scratch-step names serve one target.

After terminal cleanup, repeat the command to reconcile remaining pairings. A direct native resume at a failed HTTP step cannot reuse the removed private directory. There is no custom retry, ownership recheck, result-reporting step or Gateway callback.

Pairing selection follows [the Conn contract](../../../../../docs/reference/conn.md#native-pairing-revocation) and the upstream evidence in `fixtures/README.md`. Exact labels identify Conn token-exchange sessions; the approved source-IP and issue-window rule identifies MCP OAuth sessions. Admission rejects overlapping windows, including historical revoked pairings. Selection rejects an unmatched delivered pairing before publishing any request. Session reply shaping requires at least one actual revocation per delivered pairing; an unmatched receipt blocks link revocation and preserves all pairing rows. Cleanup-label selection remains exclusive to Gateway session cleanup.

Pairing revocation rejects an empty session selection before publishing requests. A zero-session receipt fails even for an undelivered pairing. Label-based Gateway cleanup keeps its separate empty-inventory behavior.
